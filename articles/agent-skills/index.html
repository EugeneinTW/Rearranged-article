Equipping Agents with Agent Skills · 圖卡＋教材整合版

Agent Skills：把程序知識 裝進一個資料夾通用 agent 於是變成懂你規矩的專用 agent

模型再強，也不知道你們公司的報價單怎麼填、交付前要跑哪幾個檢查。Anthropic 工程團隊給的答案不是再訓練一個模型，也不是再寫一個客製 agent，而是一個資料夾：裡面放指令、附檔和可執行的腳本，agent 需要時自己找出來讀。這篇把它的設計原理拆成三層漸進式揭露、一次觸發的四拍載入、以及「什麼該交給程式」的分工。每章開頭先放一張圖解卡講重點，往下是詳細說明；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

模型變強，補不上你們公司的流程

通用 agent 已經能操作完整的電腦環境，但它缺的往往不是能力，而是「這件事在這裡是怎麼做的」。

2025-12 起，這個格式已發佈為開放標準。
共同前提：agent 要有檔案系統與執行程式的能力，skill 才載得進來。

今天的 agent 已經不只是回答問題。它有檔案系統，有終端機，能寫程式也能執行程式，因此可以跨領域完成一整串任務。但真實工作要的不只是聰明：要的是程序知識（一件事按什麼順序做、做到什麼程度算完成）和組織脈絡（你們內部的命名、格式、禁忌、誰會看這份輸出）。這兩樣東西不在模型的訓練資料裡，它只存在你的團隊裡。

以前補這個缺口的做法，是為每一個用途各做一個客製 agent：一個做財報摘要、一個做設計稿審查、一個做客服回覆。做得出來，但代價很清楚：每個 agent 都要重寫一次同樣的流程知識，寫好的東西鎖在那個 agent 裡，換一個場景就要重來，也很難分享給別人。

Anthropic 的做法是把這件事反過來：不要為每個用途做一個 agent，而是讓同一個通用 agent 去載入一包包可組合的專業。這包東西就是 Agent Skill：一個有組織的資料夾，裡面有指令、腳本與資源，agent 可以自己發現它、在需要時動態載入它。

給初學者

先把四個名詞對齊

  • Agent：能自己決定下一步、而且能真的動手（讀寫檔案、執行指令）的 AI 系統。Claude Code 是一個例子。
  • Agent Skill：一個資料夾，核心是 SKILL.md，告訴 agent「什麼時候該用我、用我時該怎麼做」。
  • Context window：模型一次能看見的文字總量。所有系統提示、對話、讀進來的檔案都擠在這裡面，是有限資源。
  • Progressive disclosure（漸進式揭露）：不要一次攤開全部資訊，只在需要時載入下一層。這是整套設計的核心原則。

原文給了一個很好懂的比喻：替 agent 寫一個 skill，像是替新人寫一份入職手冊。你不會在新人報到第一天就把公司二十年的文件全部倒給他，你會給他一份目錄，讓他遇到什麼查什麼。差別只在於，這位新人讀得很快，而且你寫一次，之後每個人都能用。

不要為每個用途做一個 agent。把你的流程寫成資料夾，讓同一個 agent 需要時自己去拿。 序章核心觀念

Chapter 01 · The anatomy of a skill

一個 skill 就是一個資料夾，加一個 SKILL.md

格式刻意簡單：一個目錄、一個 Markdown 檔、開頭兩個必填欄位。複雜度留給內容，不留給格式。

原文用一個真實例子來講：Claude 本來就很懂怎麼「看」PDF，但要它直接動手操作 PDF，例如把一份表單填好，能力是不足的。支撐 Claude 文件編輯功能的那個 PDF skill，補的就是這一段。

最小的 skill 長這樣：一個目錄，裡面有一個 SKILL.md。這個檔案必須以 YAML frontmatter 開頭，而 frontmatter 裡有兩個必填欄位：name 與 description。

pdf/SKILL.md · 教學用精簡版 
--- 檔案開頭的 YAML frontmatter，必要 ---
name: pdf
description: 處理 PDF：讀取欄位、填寫表單、合併與拆分。
             使用者提到 PDF、表單、填表時使用。
---

# 以下是正文，只有在 Claude 判斷這個 skill 相關時才整份讀進來
要填表單時，先讀 forms.md。
需要完整欄位對照時，再讀 reference.md。

關鍵在於這兩個欄位什麼時候被讀。agent 啟動時，會把每一個已安裝 skill 的 name 與 description 預先載入系統提示。不是全部內容，只有這兩行。這就是漸進式揭露的第一層：資訊剛好夠 Claude 判斷「這個 skill 什麼時候該用」，而不必把整包東西攤進 context。

第二層是這個檔案的正文。如果 Claude 認為這個 skill 和當下任務有關，它才會把整份 SKILL.md 讀進 context。換句話說，你裝了二十個 skill，平常付的成本只有二十組 name 與 description。

機制背景

為什麼 description 值得你多花時間寫

Claude 決定要不要用你的 skill 時，手上只有 name 與 description 這兩樣東西。正文寫得再好，描述沒寫到讀者會用的說法，它就不會被觸發，而不被觸發的 skill，效果等於不存在。原文在後面的開發準則裡特別把這點單獨提出來講一次。

Chapter 02 · The anatomy of a skill (continued)

第三層以後，內容再多也幾乎不再是成本

當 SKILL.md 撐不下，或某些內容只在特定情境才用得到，就把它們移到附檔，由 SKILL.md 點名引用。

skill 變複雜之後會遇到兩種狀況：內容多到一個 SKILL.md 裝不下；或者某些內容只有在特定情境才用得到（填表單才需要的規則，對其他 PDF 任務是雜訊）。這時候的做法是把它們放進同一個資料夾的其他檔案，然後在 SKILL.md 裡用檔名點名它們。

原文的 PDF skill 就有兩個附檔：reference.md 與 forms.md。作者刻意把「怎麼填表單」的指令搬到 forms.md，讓核心的 SKILL.md 保持精瘦，並且相信一件事：Claude 只有在真的要填表單時，才會去讀 forms.md。

1
Frontmatter（name、description）啟動時就進系統提示，每個已安裝的 skill 都有一份。這層是常駐成本，所以只放判斷用得上與否所需的資訊。
2
SKILL.md 正文Claude 判斷這個 skill 和當下任務相關時，才整份讀進 context。放核心流程與「什麼時候該去讀哪個附檔」。
3
資料夾裡的附檔被點名、而且當下真的用得到時才讀。第三層之後還可以再往下長：附檔可以再引用附檔。
關鍵觀念 · 一

像一本編排良好的手冊

原文的比喻是：先有目錄，再有各章，最後才是詳盡的附錄。你查一件事時不會從第一頁讀到最後一頁，你看目錄、翻到那一章、必要時才去翻附錄。skill 讓 Claude 用同樣的方式讀你的知識。

這個比喻還有一層意思常被略過：手冊的價值不只在「寫了什麼」，也在「編排讓人找得到」。附檔取什麼名字、在 SKILL.md 裡怎麼描述它，決定了 Claude 會不會在對的時候翻到它。

把這件事推到底，會得到一個相當反直覺的結論：只要 agent 有檔案系統和執行程式的能力，它就不需要把整包 skill 讀進 context 才能工作。因此一個 skill 能夠附帶的內容量，實際上是沒有上限的。你可以放一份三百頁的規格對照表，只要它平常不被讀，它就幾乎不花 context。

為什麼這樣設計

「沒有上限」的前提是「平常不讀」

無上限講的是可以放多少，不是可以載入多少。context window 沒有變大，變的是載入時機。所以拆檔的價值來自於你拆得夠準：如果每個任務都得把三個附檔全讀一遍，那你只是把一個大檔拆成三個小檔，成本一毛都沒省。

漸進式揭露聽起來抽象，看一次實際的觸發過程就清楚了。原文用一張圖解釋一個 skill 被使用者訊息觸發時，context window 裡發生了什麼事。順序是這樣的：

1
起點context window 裡有核心系統提示、每一個已安裝 skill 的 metadata（就是那兩行 name 與 description），以及使用者的第一則訊息。
2
觸發Claude 判斷這件事該用 PDF skill，於是呼叫 Bash 工具去讀 pdf/SKILL.md 的內容。注意它是用「讀檔」這個一般動作載入的，不是什麼特殊機制。
3
往下一層正文告訴它填表單要看 forms.md，於是它選擇再讀這個附檔。到這裡，context 裡才有填表單的細節。
4
開工需要的指令都在手上了，Claude 接著執行使用者真正交代的任務。

這四拍裡最值得記住的是第二拍：載入 skill 用的是 Bash 讀檔。這也是為什麼 skill 需要一個有檔案系統與程式執行能力的執行環境：它不是某個 API 端點的新參數，而是「agent 自己去把文件翻出來讀」。

實作提示

這個順序對你寫 skill 的三個影響

  • 沒被觸發的 skill，成本只有那兩行 metadata。所以裝很多 skill 本身不貴，貴的是描述寫得含糊、讓 Claude 在不該用的時候用了。
  • SKILL.md 正文的任務之一是當路標：明確寫出「遇到 X 就去讀 Y 檔」，否則附檔可能永遠不會被翻開。
  • 第三拍是 Claude 自己選的。它會不會選對，取決於你在正文裡怎麼描述那個附檔，這件事只能靠實際觀察它的行為來調。

Chapter 04 · Skills and code execution

能交給程式做的事，不要用 token 去算

skill 裡可以放程式，讓 Claude 自行決定何時執行。省錢之外，還拿到程式才有的確定性。

適用範圍：判斷、歸納、取捨、寫作留給模型；排序、抽取、轉換、驗證交給程式。extract_fields.py 是示意檔名，原文只說附了一支預先寫好的 Python 腳本。

語言模型很多事情做得很好，但有些操作本來就更適合交給傳統程式。原文舉的例子非常直白：把一串清單排序這件事，用生成 token 的方式做，比直接跑一個排序演算法昂貴得多。

"sorting a list via token generation is far more expensive" 「用生成 token 的方式排序一份清單，成本高得多。」原文用這個例子說明什麼工作該交給程式。

但成本只是第一個理由。更重要的是第二個：很多應用需要的是決定性的可靠度，而那是只有程式給得起的。同一份輸入跑一百次得到一百次相同結果，這件事模型不保證，程式保證。

回到 PDF 的例子。那個 skill 裡附了一支預先寫好的 Python 腳本，功能是讀取一份 PDF、把所有表單欄位抽出來。重點在於：Claude 執行這支腳本時，腳本本身和那份 PDF 都不需要進入 context。它只要下指令、拿結果。而因為程式是決定性的，這段流程每次都一樣，可以重複、可以信任。

面向用 token 生成結果執行 skill 附的腳本
成本隨資料量增加而增加幾乎與資料量無關
一致性同樣輸入可能得到不同輸出決定性：同樣輸入、同樣輸出
context 佔用資料與中間結果都得進 context資料與腳本都不必進 context
適合的工作判斷、歸納、取捨、寫作排序、抽取、轉換、驗證

所以一個成熟的 skill 通常是混血的：指令的部分交給 Markdown，把判斷留給模型；重複而且要求精確的部分寫成腳本，由模型在適當時機呼叫。哪些該寫成腳本？一個好用的判準是問自己：這一步如果做錯，我看得出來嗎？ 看不出來的（欄位抽漏一個、格式差一個字元），就寫成程式。

    extract_fields.py   # 由 Claude 直接執行，不進 context

Chapter 05 · Developing and evaluating skills

Skill 不是先想好的，是從失敗裡長出來的

原文給了四條開發準則。它們指向同一件事：先觀察 agent 實際在哪裡卡住，再補那一塊。

注意：四條準則出自原文；把它畫成一個五步迴圈，是本文為了好記所做的整理。
Evaluation

先量，再寫

拿代表性任務去跑你的 agent，看它在哪裡表現不好、哪裡需要額外脈絡。那些地方就是要寫的 skill，而且一次補一塊。

Structure

為規模拆檔

SKILL.md 大到難用時就拆成附檔並引用。互斥或很少一起出現的路徑分開放，token 用量會降下來。

Perspective

站在 Claude 的角度看

觀察它在真實情境怎麼用你的 skill：有沒有走出你沒預期的路徑、有沒有過度依賴某段脈絡，然後照觀察修。

Iteration

讓 Claude 一起寫

做完一件事，請它把成功的做法與常犯的錯寫進 skill；走偏時請它自省哪裡出錯。你會發現它真正需要的脈絡，和你以為的不一樣。

第一條「先量再寫」之所以排在最前面，是因為它決定了後面三條有沒有意義。沒有先跑過代表性任務，你寫的是你以為它不會的東西；跑過之後，你寫的是它確實卡住的地方。差別通常很大。

第二條牽涉到一個實務判斷：什麼時候該拆？原文給的訊號是「SKILL.md 變得笨重（unwieldy）」，以及「某些脈絡彼此互斥或很少一起用到」。後者是更精準的判準：填表單的規則和合併 PDF 的規則不會同時需要，分開放，兩種任務各自只載一半。

實作提示

程式在 skill 裡有兩種身分，要講清楚是哪一種

原文特別提醒：程式碼既可以是「可執行的工具」，也可以是「當成參考資料被閱讀的文件」。你要在 SKILL.md 裡寫清楚，Claude 面對某支腳本時該直接執行它，還是讀進來當範例。沒寫清楚，兩種情況都可能發生，而且都不是你要的。

第三條的重點在 name 與 description。原文要你特別留意這兩個欄位，因為 Claude 就是靠它們決定要不要在當下觸發這個 skill。寫 skill 的人容易把全部注意力放在正文，但正文只有在被觸發之後才有機會發揮。

第四條是這四條裡最容易被跳過、卻最省力的一條：把寫 skill 這件事變成你和 Claude 的共同工作。一起做完一個任務之後，請它把「這次哪裡順利、哪裡撞牆」整理成可重複使用的脈絡與程式。這比你坐在空白檔案前面憑空預想它需要什麼，準確得多。

思考題 · 01

你手上有哪件事，是每次都要重講一遍前提的？

想一個你這個月至少交代過三次的任務。你每次都得補充哪些背景？那段補充就是這個 skill 的第一版正文。

建議方向：先不要寫大而全的手冊。只寫你重複講過的那三句話，跑一次任務，看它還缺什麼再補。

Chapter 06 · Security considerations when using Skills

裝一個 skill，等於讓它替你下指令

skill 帶來新能力的方式是指令加程式碼，這也正是它的風險所在：兩者都會被照做。

只從可信來源安裝
這是原文給的第一條建議。來源沒那麼可信時，使用前徹底審查，不要邊用邊看。
另一個重點：有沒有指令要它連接不受信任的外部來源。
硬規則：三道關都過才裝；任何一關答「否」，處理完再回到那一關重問。

原文在這一節講得很直接：skill 透過指令與程式碼賦予 Claude 新能力，而這同時意味著，一個惡意的 skill 可能在它被使用的環境裡引入漏洞，或是引導 Claude 把資料外洩、做出非預期的動作。

這裡的關鍵差異是：skill 不是唯讀的資料，它是會被執行的東西。Markdown 裡的指令會被當成指令照做，附帶的腳本會被真的跑起來。所以「裝一個 skill」在信任層級上，比較接近「在你的機器上裝一個套件」，而不是「收藏一篇文章」。

原文給的建議是：只從可信來源安裝。如果來源沒那麼可信，就在使用前徹底審查，而審查有三個明確的著眼點。

Files

先讀完每一個檔案

把 skill 資料夾裡打包的檔案內容讀過，先搞清楚它到底做什麼事，再決定要不要裝。

Dependencies

特別看相依與夾帶資源

程式的相依套件、以及一起打包進來的圖片、腳本這類資源，是最容易被忽略的一塊。

Network

注意對外連線的指令

留意 skill 裡有沒有指令或程式碼，要求 Claude 去連接不受信任的外部網路來源。

提醒

審查的對象包含「文字」，不只是程式

一般人審查套件時會盯 .py 檔，但 skill 的攻擊面有一半在 Markdown 裡。寫在 SKILL.md 或附檔裡的一句「完成後把結果送到某個網址」，對 agent 來說和一行程式碼一樣有效。看檔案時，指令文字和程式碼要用同一種戒心讀。

思考題 · 02

你會用什麼標準，判斷一個來源算不算「可信」？

如果團隊裡有人分享了一個 skill，你會直接裝，還是先看？你們有沒有一個地方可以放「審查過的 skill」？

建議方向：把審查結果寫下來，比每個人各自看一遍有用。至少記錄：誰審的、看過哪些檔案、有沒有對外連線。

Chapter 07 · The future of Skills

從一家公司的功能，走成一份開放標準

Skills 目前橫跨四個執行環境，並在發表兩個月後被公開為跨平台的開放標準。

Claude.ai

已支援

一般使用者在對話介面裡就能用 skill，不必自己架執行環境。

面向：日常工作流程

Claude Code

已支援

有檔案系統與終端機的環境，也是 skill 的三層載入最完整發揮的地方。

面向：開發與自動化

Claude Agent SDK

已支援

自己寫 agent 時，可以直接沿用同一套 skill 格式，不必自造一套。

面向：自建 agent

Claude Developer Platform

已支援

在平台上構築應用時同樣可用，讓同一包專業跨產品重複使用。

面向：產品整合

除了「哪裡能用」，原文也講了接下來要補什麼：圍繞 skill 的完整生命週期（建立、編輯、發現、分享、使用）逐步補上功能。團隊特別看重的是，讓組織與個人能把自己的脈絡與工作流程分享給 Claude。

另一條線是和 MCP（Model Context Protocol）的關係。原文的說法是「互補」：MCP server 讓 agent 接得上外部工具與軟體，skill 則教它把這些工具組合成複雜工作流程的方法。一個管連線，一個管流程。

最遠的那一步，是讓 agent 自己建立、編輯、評估 skill，把它自己摸索出來的行為模式，固化成可重複使用的能力。這一段在原文裡是明講的期望，不是已經完成的功能。

而在這篇文章發表兩個月後，頁面上多了一行更新：Agent Skills 已經被發佈為開放標準，目標是跨平台的可攜性。這讓前面那句「可組合、可分享、可攜」的第三個詞，從設計意圖變成了具體進度。

補充說明

MCP 與 skill 不是二選一

一個常見的誤解是把兩者當成競爭關係。用原文的分工來看比較清楚：MCP 解決「agent 能碰到什麼」，skill 解決「碰到之後該怎麼做」。你可以有 MCP 而沒有 skill（工具在，但每次都要重講流程），也可以有 skill 而沒有 MCP（流程在，但只能操作本機既有的東西）。

Conclusion · A simple concept, a simple format

格式簡單，是為了讓更多人寫得出來

Skills 是一個簡單的概念，配上一個同樣簡單的格式。這個簡單是刻意的，它決定了誰有能力貢獻。

圖卡 08 / 08三條收尾規則
把 skill 當成新人的入職手冊來寫

把整篇收攏起來，Agent Skills 的主張只有一句：專業知識應該是資料夾，不是程式碼分支。因為是資料夾，所以可組合、可分享、可攜；因為有三層漸進式揭露，所以裝很多也不會拖垮 context；因為可以附腳本，所以該精確的部分交給程式而不是交給運氣。

格式簡單這件事，帶來的不只是好寫。原文的收尾指出，正因為簡單，組織、開發者、一般使用者才都做得出客製化的 agent。一個需要寫程式才能擴充的系統，能擴充它的只有工程師；一個用 Markdown 就能擴充的系統，最懂那件事的人自己就能動手，而那個人往往不是工程師。

能寫下入職手冊的人，就能替 agent 寫一個 skill。這才是「格式簡單」真正換到的東西。 整理自結論一節

如果你只帶走三件事：先量再寫，不要憑空設計；把不常用的內容移到附檔，讓常駐層保持精瘦；該確定的部分寫成腳本，不要交給 token。剩下的，交給下一次真實任務告訴你還缺什麼。

思考題 · 03

你們團隊最該被寫成 skill 的，是哪一份「口耳相傳」的規矩？

那種新人一定會做錯一次、老手懶得每次解釋、但寫下來其實只有十行的東西。

建議方向：從「新人最常犯的錯」清單反推。每一條錯誤，背後都是一段沒被寫下來的程序知識。

Workshop · Apply it yourself

動手做：把一段重複交代的流程變成 skill

這一章不在原文裡。它把前面的原則壓成一份今天就能跑完一輪的清單。

  1. 先跑一次沒有 skill 的版本挑一個你重複交代過的任務，原封不動丟給 agent 做一次，把它做錯或問你的地方記下來。這份清單就是你的缺口。
  2. 只寫缺口，不寫教科書建一個資料夾放 SKILL.md，frontmatter 填 name 與 description，正文只寫上一步記下來的那幾條。第一版短到有點心虛才是對的。
  3. 把描述寫成「使用者會怎麼說」description 不要寫成功能名稱，寫成觸發情境：使用者提到哪些字、遇到什麼狀況時該用它。
  4. 把只在特定情境用的內容搬出去正文開始變長時，拆成附檔，並在正文裡寫明「遇到 X 就去讀 Y」。互斥的路徑分開放，效果最好。
  5. 把不能出錯的那一步寫成腳本抽欄位、改格式、對帳、驗證，這類做錯了你不一定看得出來的步驟，寫成程式讓 agent 執行，並在正文註明「直接執行，不要讀進來」。
  6. 再跑一次，讓它自己回頭改同一個任務重跑，觀察它有沒有觸發、有沒有讀對附檔。走偏就請它自省哪裡出錯，把答案補回 skill。一輪一輪疊，不要一次寫完。

Reference · 名詞速查

關鍵名詞與檔案

讀原文或動手寫 skill 時會反覆遇到的 14 個詞，依「概念、檔案結構、執行環境」三群排列。

Agent Skill
技能
一個有組織的資料夾，裝著指令、腳本與資源，agent 可以自己發現並動態載入，用來在特定任務上表現更好。
SKILL.md
技能主檔
skill 的核心檔案，也是最小組成。必須以 YAML frontmatter 開頭，正文寫核心流程與「什麼時候該讀哪個附檔」。
YAML frontmatter
前言區塊
檔案開頭的中繼資料區塊，必填 name 與 description。這是啟動時唯一會被預載進系統提示的部分。
name
技能名稱
frontmatter 必填欄位之一。和 description 一起決定 Claude 會不會在當下觸發這個 skill。
description
技能描述
frontmatter 必填欄位之一，寫「什麼時候該用我」。寫得含糊，skill 就不會在該用的時候被用到。
Progressive disclosure
漸進式揭露
本文的核心設計原則：資訊分層，只在需要時載入下一層。第一層 metadata、第二層 SKILL.md 正文、第三層以後是附檔。
Bundled files
附檔
和 SKILL.md 放在同一個資料夾、由它以檔名點名引用的其他檔案，例如 forms.md、reference.md。用得到才會被讀。
Context window
脈絡視窗
模型一次能看見的文字總量。skill 的整套設計就是在管理這個有限資源的使用時機。
Metadata
中繼資料
本文特指每個已安裝 skill 的 name 與 description。它們在 agent 啟動時就常駐於系統提示中。
Code execution
程式執行
skill 可以附上腳本讓 Claude 直接執行。腳本與被處理的檔案都不必進入 context，且結果具決定性。
Deterministic
決定性
同樣輸入必得同樣輸出。這是把步驟交給程式而非交給模型生成的主要理由，僅次於成本。
MCP
模型脈絡協定
Model Context Protocol。讓 agent 接上外部工具與軟體的協定。原文定位它與 skill 互補：MCP 管連線，skill 管流程。
Open standard
開放標準
原文頁面於 2025-12-18 補充：Agent Skills 已發佈為開放標準，目的是跨平台可攜。
Prompt injection
提示注入
原文未使用這個詞，整理者補充：指外部內容裡的文字被 agent 當成指令執行。這正是安全一節要你連 Markdown 也一起審查的原因。
