02 / 08為什麼需要 skill
Agent 缺的不是能力，是你的流程
一個用途做一個客製 agent —— 同一份流程知識要重寫三次，而且鎖在那三個 agent 裡，誰都拿不走
✗ 一個用途，一個客製 agent
✓ 一個通用 agent ＋ 可組合的 skill
財報摘要 agent
設計審查 agent
客服回覆 agent

第 1 次重寫
同一份流程知識
第 2 次重寫
同一份流程知識
第 3 次重寫
三份幾乎一樣的知識，分別鎖在三個 agent 裡 —— 規矩改一次，要改三個地方，而且沒有一份給得出去。
通用 agent
pdf/
SKILL.md ＋ forms.md
quote/
SKILL.md ＋ 報價範本
review/
SKILL.md ＋ 檢查表
同一個 agent，任務需要哪一包就載哪一包 —— 寫一次，換場景還能用，也能整包分享出去。
知識不可組合
流程被寫死在各自的 agent 裡，換一個用途就要從頭再做一個。
每多一個用途，維護面積就多一份。
可組合、可分享、可攜
專業被打包成資料夾，agent 需要時自己載入；同一包換個人也能用。
2025-12 起，這個格式已發佈為開放標準。
共同前提：agent 要有檔案系統與執行程式的能力，skill 才載得進來。
03 / 08SKILL.md 的三層
Skill 像手冊：目錄先進來，章節用到才翻
一個 skill ＝ 一個資料夾 ＋ 一個 SKILL.md；frontmatter 只有 name 與 description 兩個必填欄位。原文把三層比作手冊的目錄、章節與附錄

第二層　SKILL.md 正文

一個檔案的量，會變笨重
第三層　資料夾裡的附檔
forms.md、reference.md、腳本
被點名、當下真用得到才讀
不讀就不花
實際上沒有上限
常駐成本只有那兩行
agent 啟動時，只把每個已安裝 skill 的 name 與 description 放進系統提示。
所以裝得多不貴，描述寫得含糊才貴。
附檔再多，不讀就不花
agent 有檔案系統與執行能力，不必把整包 skill 讀進 context 才能工作。
因此一個 skill 能附帶的內容量，實際上沒有上限。
正文的工作是當路標
「遇到 X 就去讀 Y 檔」要寫明，否則附檔可能永遠不會被翻開。
拆檔的省，來自拆得準，不是來自拆得多。
硬規則：name 與 description 是 Claude 判斷要不要用這個 skill 的唯一依據 —— 不被觸發的 skill 等於不存在。
04 / 08觸發的四拍
Context 不是一次裝滿，是分四拍載入
使用者丟出一個 PDF 表單任務 —— 把這一刻放慢看，context window 依序長出四段內容，每一段都是被需要才進來的

05 / 08程式與 token 的分工
該執行的事，不要用 token 生成
同一個任務：讓模型逐 token 產出答案，或讓它去跑 skill 裡附的腳本 —— 差的不只是成本，還有「每次都一樣」

✓ 讓它執行 skill 附帶的程式

一份欄位清單，如此而已
成本幾乎與文件長度無關；程式是決定性的，明天再跑還是同一份結果。
又貴，又不保證一致
原文的例子：用生成 token 的方式排序一份清單，比直接跑一個排序演算法昂貴得多。
而且它錯得很安靜 —— 少一個欄位不會有錯誤訊息。
同樣輸入，同樣輸出
執行腳本時，腳本與 PDF 都不必進 context；Claude 只下指令、拿結果。
因為程式是決定性的，這段流程可重複、可信任。
適用範圍：判斷、歸納、取捨、寫作留給模型；排序、抽取、轉換、驗證交給程式。extract_fields.py 是示意檔名，原文只說附了一支預先寫好的 Python 腳本。
06 / 08寫 skill 的迴圈
Skill 不是先想好的，是跑出來的
原文的四條準則指向同一件事：先觀察 agent 實際在哪裡卡住，再補那一塊 —— 而不是先寫一本手冊給它

③ 只寫那個缺口
最小可用的 SKILL.md
最小
④ 觀察真實軌跡
有沒有走出預期外的路
每輪
⑤ 請它自省補回
成功做法與常犯的錯
回寫
下一輪：帶著補過的 skill 再跑一次同一個任務
四條準則裡的三個具體動作
① 先量，再寫
沒有先跑過代表性任務，你寫的是「你以為它不會的東西」；跑過之後，你寫的是它確實卡住的地方。
那份缺口清單，就是第一版 skill 的大綱。
② 特別盯 name 與 description
Claude 就是靠這兩行決定要不要在當下用你的 skill。寫 skill 的人卻常把全部力氣花在正文。
正文只有在被觸發之後，才有機會發揮。
③ 腳本是拿來跑的，還是讀的
程式在 skill 裡有兩種身分：可執行的工具，或當成參考文件被讀進來。你要在正文裡講清楚是哪一種。
沒寫清楚，兩種情況都可能發生。

裝一個 skill，等於讓它替你下指令

先確認外連
有沒有叫它連不受信任的來源
三道關各自在擋什麼
skill 不是唯讀資料
它帶的是指令與程式碼，兩者都會被照做：可能在你的環境引入漏洞，或做出非預期的動作。
信任層級接近「裝一個套件」，不是「收藏一篇文章」。
最容易略過的是「資源」
審查時特別看：程式的相依套件，以及一起打包進來的圖片、腳本這類夾帶資源。
看起來越無害的檔案，越少人打開來看。
只從可信來源安裝
這是原文給的第一條建議。來源沒那麼可信時，使用前徹底審查，不要邊用邊看。
另一個重點：有沒有指令要它連接不受信任的外部來源。
硬規則：三道關都過才裝；任何一關答「否」，處理完再回到那一關重問。
08 / 08三條收尾規則
把 skill 當成新人的入職手冊來寫
簡單的概念，配一個同樣簡單的格式 —— 這個「簡單」決定的不只是好不好寫，而是誰有能力替 agent 加上新能力
01　起手
不要一次寫一本大全
從你重複交代過的那幾句開始，跑一次任務，缺什麼再補。第一版短到有點心虛，通常才是對的。
✗ 先寫完整手冊再驗證
✓ 先寫缺口，跑一次再說
02　迭代
讓它一起寫自己的手冊
做完一個任務，請 Claude 把成功的做法與常犯的錯寫回 skill；走偏時請它自省哪裡出錯。
它實際需要的脈絡，和你坐著猜的通常不一樣。
03　為什麼是資料夾
格式簡單，能寫的人才多
要寫程式才能擴充的系統，只有工程師擴充得了；用 Markdown 就能擴充的系統，最懂那件事的人自己就能動手。
而最懂那件事的人，往往不是工程師。

順序也是重要性：第一步沒做，後面四步都是在猜 —— 你會寫出一份沒人需要的漂亮手冊。
