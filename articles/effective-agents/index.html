Building Effective Agents · 圖卡＋教材整合版

Building Effective Agents先找最簡單的解 需要時才把它做成 agent

Anthropic 工程團隊和幾十個團隊一起做了一年的 LLM agent，看到的規律是：最成功的實作沒有用複雜的框架或特殊的函式庫，而是用簡單、可組合的模式。這篇文章把那些模式一個一個攤開：一個積木（擴增型 LLM）、五種工作流、一種 agent，加上什麼時候該用哪一種、工具要怎麼寫、以及三條原則。本頁分十二章重述，每章開頭一張圖解卡講機制，往下是詳細說明；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

最成功的 agent 用的是簡單、可組合的模式

這篇文章的第一句觀察就是它的主張：一年下來，做得最好的團隊不是框架用得最深的，而是把幾個簡單模式組合得最準的。

作者是 Anthropic 的工程師，過去一年和跨產業的幾十個團隊一起做 LLM agent，也自己做。他們看到的一致規律是，最成功的實作沒有用複雜的框架或特殊的函式庫，而是用簡單、可組合的模式在搭。文章要做的事有三件：把「agent」這個詞定義清楚、把生產環境裡常見的模式一個一個講、給開發者實際可用的建議。

閱讀順序跟著原文走：先分清楚工作流和 agent 的差別，決定什麼時候該用哪一種；再從最基本的積木「擴增型 LLM」開始，一層一層加複雜度，經過五種工作流，最後到真正自主的 agent。兩篇附錄分別講兩個值得做的應用領域，以及工具該怎麼做提示工程。

給初學者

先把五個名詞對齊

  • Agentic 系統：作者用來統稱所有這類系統的傘狀詞，底下再分兩種。
  • 工作流（workflow）：模型與工具的呼叫順序由預先寫好的程式碼決定。
  • Agent：模型自己動態決定流程與工具用法，掌握怎麼完成任務。
  • 擴增型 LLM（augmented LLM）：一個模型加上檢索、工具、記憶三種能力，是所有模式的積木。
  • ACI：agent 與電腦之間的介面，也就是工具的定義與文件；作者說要像做人機介面一樣用心。
閱讀時間座標

原文發表於 2024 年 12 月。頁面頂端現在有一行註記：文中描述的工具生態自那時起已經改變很多，目前的做法請看 Claude Managed Agents。本頁重述的是文章本身的方法與模式，這些模式不依賴特定工具；文中提到的框架與模型名稱照頁面現在的版本保留，不另外更新。

「Agent」有很多種定義。有的客戶指的是完全自主、長時間獨立運作、用各種工具完成複雜任務的系統；有的指的是照預定流程走、比較規範的實作。作者把這些統稱為 agentic 系統，但在架構上畫一條清楚的線：工作流是模型與工具透過預先定義的程式路徑被安排的系統；agent 是模型動態指揮自己的流程與工具使用、自己掌握怎麼完成任務的系統。

建議從最簡單的解開始，只在需要時才增加複雜度，這可能代表根本不做 agentic 系統。理由是它們常常用延遲與成本去換任務表現，你得先判斷這個交換划不划算。真的需要更多複雜度時，工作流給的是定義明確任務上的可預測與一致；agent 適合需要彈性、需要由模型做決定、而且要規模化的情況。作者補了一句很多人會略過的話：對很多應用來說，把單一次模型呼叫配上檢索與情境內範例做好，通常就夠了。

不做 agentic 系統也是一個正確答案。單一次呼叫加檢索與範例，是很多應用的終點，不是起點。 整理自第一節與第二節

框架的問題也在這一節談。市面上有不少讓 agentic 系統更容易實作的框架，頁面目前列的是 Claude Agent SDK、AWS 的 Strands Agents SDK、拖拉式介面的 Rivet 與 Vellum。它們把呼叫模型、定義與解析工具、串接呼叫這些底層工作簡化了，起步很快；代價是多出來的抽象層會遮住底下的 prompt 與回應，除錯變難，也讓人在簡單設定就夠的時候忍不住加複雜度。

agentic 系統最基本的積木，是一個被檢索、工具、記憶這類能力擴增過的模型。重點是「主動」兩個字：現在的模型可以自己產生搜尋查詢、選擇合適的工具、判斷哪些資訊值得保留，不需要程式替它一步步安排。

Chapter 03 · Workflow: Prompt chaining

提示鏈用延遲換準確：把任務拆成一串更容易的呼叫

每一次呼叫處理上一次的輸出；中間任何一步都可以加程式檢查，也就是「閘」，確保流程還在軌道上。

延遲。多一次呼叫就多一段等待；換到的是每一步的任務更簡單、更不容易錯。閘是程式不是模型，所以便宜、確定，放在最貴的一步前面，擋掉的就是最貴的浪費。
什麼時候用、原文的兩個例子
① 任務能乾淨地拆成固定子任務
這是唯一的適用條件。拆不乾淨的任務硬拆，每一步都得猜前一步沒講清楚的事，延遲付了、準確沒換到。
子任務事先不知道有幾個，就不是提示鏈，見第 6 卡。
② 例子一：先寫文案，再翻譯
先讓模型寫行銷文案，再另一次呼叫把它翻成另一種語言。寫與譯分開，每一次呼叫只顧一件事。
兩步之間可以加閘：文案長度、必含的關鍵字。
③ 例子二：大綱、檢查、全文
先寫文件大綱，用程式檢查大綱符不符合某些條件，通過才依大綱寫全文。這是原文圖裡那個閘的用法。
閘的數量原文沒規定，「任何中間步驟」都可以放。
注意：五格裡的「寫大綱、寫全文」是原文的第二個例子；閘用程式檢查而不是另一個模型，是原文圖示的畫法。

提示鏈把一個任務拆成固定順序的幾步，每一步是一次模型呼叫，處理前一步的輸出。原文在圖裡標了一個「閘」：在中間步驟加上程式化的檢查，中間結果不對就不往下走。這種檢查是程式，不是另一個模型，所以便宜、確定。

什麼時候用：任務可以乾淨地拆成固定的子任務時。主要目的是用延遲換更高的準確度，因為每一次呼叫都變成一個更容易的任務。原文的兩個例子：先寫行銷文案，再翻成另一種語言；先寫文件大綱，檢查大綱符不符合某些條件，再依大綱寫全文。

示意 · 一條帶閘的提示鏈（教學用假想程式碼，非原文程式） 
outline = llm("替這個主題寫大綱", topic)
if not outline_ok(outline):        # 閘：程式檢查，例如節數、必含段落
    return ask_for_fix(outline)        # 不對就停在這裡，不往下寫
draft = llm("依這份大綱寫全文", outline)

閘的位置決定了鏈的價值。放在最貴的一步前面，擋掉的就是最貴的浪費；原文沒有規定要放幾個，只說「任何中間步驟」都可以放。拆不乾淨的任務不適合這個模式，硬拆會讓每一步都要猜前一步沒講清楚的事。

什麼時候用：任務複雜、而且有明顯不同的類別更適合分開處理，同時分類本身能做得準。分類可以交給模型，也可以交給更傳統的分類模型或演算法，作者兩種都接受。

補充說明

分類器可以不是 LLM

原文明說分類可以由「更傳統的分類模型或演算法」處理。實務上這常常是路由能不能便宜又穩定的關鍵：分類器越便宜，路由省下的就越多；分類器越準，下游專門化的好處才收得到。這一段是整理者的引申。

Chapter 05 · Workflow: Parallelization · Workflow: Orchestrator-workers

子任務是預先定好的，還是跑的時候才決定的

平行化和協調者-工作者的圖長得很像，差別只有一個：平行化的子任務是預先定義、由程式彙整；協調者-工作者的子任務由一個中央模型依輸入即時決定。

什麼時候用：開放式的問題，難以或不可能預測需要幾步，也沒辦法寫死一條固定路徑。模型可能要跑很多輪，你得對它的決策有一定程度的信任；agent 的自主性讓它適合在可信任的環境裡把任務規模化。

代價

自主代表更高的成本，以及錯誤會累積

原文的建議是在沙箱環境裡大量測試，配上合適的護欄。錯誤累積是 agent 特有的風險：第三步的小錯會變成第十步的大錯，而中間沒有人看。

原文的兩個例子都來自 Anthropic 自己的實作：解 SWE-bench 任務的程式 agent，依任務描述修改多個檔案；以及「電腦操作」的參考實作，讓 Claude 操作一台電腦完成任務。文章附了一張程式 agent 的高層流程圖，讀法是：人給任務，模型在環境裡改程式、跑測試、看結果，直到測試通過，再交回人審。

最後一段講組合。這些積木不是規定，而是開發者可以塑形、組合的常見模式；成功的關鍵和任何 LLM 功能一樣，是量測表現並迭代實作。作者重複了一次：只有在複雜度能明顯改善結果時才加上去。

Appendix 1 · Agents in practice

Agent 最有價值的任務，同時需要對話和行動

作者從客戶身上看到兩個特別有前景的領域。它們共同的特徵有四個：對話加行動、清楚的成功標準、有回饋迴圈、有意義的人工監督。

客服把熟悉的聊天介面和工具整合後的能力結合起來，很自然地適合開放式的 agent：支援互動本來就照對話流走，同時需要外部資訊與動作；工具可以拉客戶資料、訂單歷史、知識庫文章；退款、更新工單這類動作可以用程式處理；成功可以用使用者定義的「已解決」清楚量測。作者提到有幾家公司用「只對成功解決收費」的計價模式證明了可行性，這種收費方式本身就是對 agent 效果的信心。

寫程式這個領域的潛力更明顯，能力已經從補全程式碼演進到自主解決問題。agent 特別有效的原因：程式的解可以用自動化測試驗證；agent 可以拿測試結果當回饋迭代；問題空間定義明確、有結構；輸出品質可以客觀量測。作者自己的實作已經能只憑 pull request 的描述解決 SWE-bench Verified 裡的真實 GitHub issue。但他們也提醒，自動化測試驗證的是功能，解法是否符合更廣的系統需求，仍然要人來審。

不管做哪一種 agentic 系統，工具都會是重要的一部分。工具讓 Claude 能和外部服務與 API 互動，方式是在 API 裡指定它們精確的結構與定義；模型打算呼叫工具時，回應裡會帶一個 tool use 區塊。作者的主張是：工具的定義與規格應該得到和整體 prompt 一樣多的提示工程注意力。

同一個動作常有好幾種指定方式。改檔案可以寫 diff，也可以整個檔案重寫；結構化輸出可以把程式碼放在 markdown 裡，也可以放在 JSON 裡。在軟體工程裡這些差異只是表面的，可以無損互轉；但對模型來說，有些格式難寫得多。寫 diff 要在寫新程式碼之前，先在區塊標頭裡算對要改幾行；把程式碼放進 JSON，要額外跳脫換行與引號。

01

給模型足夠的 token 先想

在它把自己寫進死角之前，留出思考的空間。

02

格式貼近網路上自然出現的文字

模型看過最多的樣子，就是它最不容易寫錯的樣子。

03

不要有格式上的「額外負擔」

不要要求它精確數幾千行程式碼，也不要要求它跳脫自己寫的程式碼。

作者給了一個經驗法則：想想人機介面（HCI）花了多少心力，就替 agent 與電腦的介面（ACI）投入同樣多的心力。具體怎麼做，原文列了四點。

1
站在模型的角度光看描述和參數，用法明顯嗎？你需要仔細想才懂的，模型多半也是。好的工具定義常包含用法範例、邊界情況、輸入格式要求，以及和其他工具的清楚分界。
2
改參數名稱與描述把它當成替團隊裡的初級工程師寫一份好的 docstring。有很多相似工具時尤其重要。
3
測試模型怎麼用你的工具在 workbench 跑很多範例輸入，看它犯什麼錯，然後迭代。
4
把工具防呆作者用日文的 poka-yoke 一詞：改參數的設計，讓錯誤更難發生。
原文的例子

做 SWE-bench 的 agent 時，花在工具上的時間比花在 prompt 上的多

他們發現，agent 離開根目錄之後，用相對路徑的工具就會出錯。修法不是在 prompt 裡提醒，而是把工具改成一律要求絕對路徑；改完之後，模型用這個方法完全沒再錯。

這個例子把附錄二的主張講完了：模型的錯常常是介面的錯，修介面比修提醒有效。

作者的總結是：在 LLM 這個領域成功，靠的不是做出最精巧的系統，而是做出符合你需求的那個系統。做法是從簡單的 prompt 開始，用全面的評估最佳化它，只在更簡單的解法不夠時才加上多步驟的 agentic 系統。

"building the right system for your needs" 「替你的需求做對的系統。」這是整篇文章的一句話版本；前面十一章都是在回答「對的系統」怎麼找。

實作 agent 時，他們遵守三條核心原則：讓 agent 的設計保持簡單；把 agent 的規劃步驟明確地顯示出來，優先做到透明；透過周到的工具文件與測試，細心打造 agent 與電腦之間的介面（ACI）。框架能幫你快速起步，但走向生產環境時，不要猶豫減少抽象層、用基本元件來建。照這些原則做，agent 才會既強大又可靠、可維護、被使用者信任。

複雜度是要付利息的：每加一層，都要能用評測證明它換到了更好的結果。 整理自「組合與客製化」與總結兩節

下面這份清單不在原文裡，是整理者把全文的建議壓成的順序，讓你今天就能跑一輪。

  1. 先用一次呼叫加檢索與範例做出第一版直接用 API，不用框架；量它在你的評測上的表現，這是後面所有複雜度的基準線。
  2. 把工具的定義寫到像 docstring用法範例、邊界情況、輸入格式、和其他工具的分界；在 workbench 跑一批輸入，看它犯什麼錯就改參數。
  3. 哪一步失敗，就挑對應的工作流能固定拆步就提示鏈；輸入類別不同就路由；可以同時做就平行化；子任務事先不知道就協調者；有明確標準可迭代就評估者。
  4. 每加一層都重跑評測複雜度只有在明顯改善結果時才留下來；沒有改善就拿掉。
  5. 真的需要開放式路徑，才做 agent先在沙箱裡大量測試，設停止條件與檢查點，工具全部用絕對、防呆的參數。
  6. 上線前減少抽象層把還在用的框架功能換成你看得懂的基本元件，prompt 與回應要能直接看到。
整理者的思考題 · 02

你現在的系統，哪一層複雜度是評測證明過的？

把每一層列出來：路由、平行、迴圈、agent。旁邊寫上它換到了什麼結果。

寫不出來的那一層，就是原文說的「簡單設定就夠卻加了複雜度」。

整理者的思考題 · 03

你的 agent 最近一次出錯，是 prompt 的錯還是工具介面的錯？

回想它用錯工具、傳錯參數的那一次。你是加了一句提醒，還是改了工具？

原文的絕對路徑例子給了判準：改介面之後模型不再錯，代表錯在介面。

Reference · 名詞速查

用十六個名詞辨認你正在做哪一種系統

依「分類、模式、agent、工具」四群排列，都是整理者依原文的用法寫的解釋。

Agentic system
Agentic 系統
作者用來統稱工作流與 agent 的傘狀詞；兩者的差別在誰決定流程。
Workflow
工作流
模型與工具透過預先定義的程式路徑被安排的系統；給定義明確的任務可預測與一致。
Agent
代理
模型動態指揮自己的流程與工具使用的系統；適合開放式、無法預測步數的任務。
Augmented LLM
擴增型 LLM
接上檢索、工具、記憶的模型，能自己產生查詢、選工具、決定保留什麼；所有模式的積木。
MCP
Model Context Protocol
原文提到的一種接法：用簡單的客戶端實作接上第三方工具的生態。
Prompt chaining
提示鏈
任務拆成固定順序的呼叫，每一步處理前一步的輸出；用延遲換準確。
Gate
閘
提示鏈中間步驟上的程式化檢查，確保流程還在軌道上。
Routing
路由
先分類輸入，再導向專門的 prompt、流程或模型；分類器可以是 LLM 或傳統分類器。
Sectioning / Voting
分段 / 投票
平行化的兩種：把任務拆成獨立子任務同時跑；或同一任務跑多次取多樣輸出。
Orchestrator-workers
協調者-工作者
中央模型依輸入動態拆解任務、派給工作者、再合成；適合子任務無法預測的任務。
Evaluator-optimizer
評估者-優化者
一個呼叫生成、另一個評估並回饋的迴圈；需要清楚的評估標準與可量化的迭代價值。
Ground truth
環境的真實回饋
agent 每一步從環境拿到的事實，例如工具結果或程式執行輸出；用來判斷進度。
Stopping condition
停止條件
例如最大迭代次數；讓 agent 的迴圈不會無限跑下去，把控制權留在手上。
ACI
Agent-computer interface
agent 與電腦之間的介面，也就是工具的定義、文件與參數設計；作者要求和 HCI 一樣用心。
Poka-yoke
防呆
改參數設計讓錯誤更難發生；原文例子是把相對路徑改成一律要求絕對路徑。
SWE-bench Verified
程式 agent 基準
由真實 GitHub issue 組成的基準；原文說他們的 agent 能只憑 PR 描述解題，但人審仍然必要。
