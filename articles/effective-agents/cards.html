複雜度是用延遲和成本買的
agentic 系統常常用更慢、更貴換更好的任務表現。作者要你先判斷這個交換划不划算，可能的結論是根本不做。
只有在複雜度能明顯改善結果時才加上去。
工作流給可預測，agent 給彈性
定義明確的任務用工作流，拿到一致與可預測；需要彈性、要由模型做決定、而且要規模化的情況，才輪到 agent。
兩者都是「agentic 系統」，差別在誰決定流程。
框架幫你起步，也會遮住 prompt
多出來的抽象層讓 prompt 與回應看不見、除錯變難，也讓人忍不住加複雜度。作者建議先直接用 API，很多模式幾行就寫得出來。
要用框架就看懂它底下的程式碼。

03 / 10擴增型 LLM：檢索、工具、記憶
積木是一個接上檢索、工具、記憶的模型
現在的模型能主動使用這三種擴增；文章後面的每一個「模型呼叫」都預設帶著它們，所以積木好不好用，決定了上面每一種模式
擴增
模型主動做什麼
介面長什麼樣
你要做什麼
檢索
retrieval
自己產生搜尋查詢，不用程式替它決定要查什麼
查詢進去、結果回來；模型看到的是找回來的內容
貼合你的用途：接的是你的資料，不是通用的檢索
工具
tools
自己挑合適的工具來呼叫
呼叫出去、回應回來；工具的定義與參數就是它的說明書
介面簡單、有清楚的文件；MCP 是一種接上第三方工具生態的方法
記憶
memory
自己決定哪些資訊值得保留
讀與寫；跨呼叫留下來的東西才叫記憶
決定什麼該留、留在哪；原文沒有指定實作，只要求介面清楚
接上通用能力不算完成
作者要你盯的第一件事是「貼合你的用途」：檢索接你的資料、工具做你的動作、記憶留你需要的東西。
通用的三件套是起點，不是成品。
介面要簡單、要有文件
第二件事：給模型一個容易用、文件清楚的介面。怎麼寫工具定義才不會被用錯，是第 9 卡的主題。
MCP 讓一個簡單的客戶端接上成長中的工具生態。
後面每個節點裡都藏著這三樣
從第 4 卡開始，圖上每一個「模型呼叫」都預設能檢索、能用工具、有記憶；工作流安排的是這些積木的順序。

04 / 10提示鏈：每一步變簡單，中間加閘
提示鏈用延遲換準確：每一步都變得更容易
任務拆成固定順序的幾步，每一次呼叫處理上一次的輸出；中間任何一步都可以加程式檢查，原文叫它「閘」
輸入
例如一個主題，
要寫成一份文件
模型呼叫 1
只做第一步：寫大綱
閘（程式檢查）
大綱符合條件嗎？
不符合就停，不往下
模型呼叫 2
只做第二步：
依大綱寫全文
輸出
每一步都比一次做完容易
準確度換到了
付出的是
延遲。多一次呼叫就多一段等待；換到的是每一步的任務更簡單、更不容易錯。閘是程式不是模型，所以便宜、確定，放在最貴的一步前面，擋掉的就是最貴的浪費。
什麼時候用、原文的兩個例子
① 任務能乾淨地拆成固定子任務
這是唯一的適用條件。拆不乾淨的任務硬拆，每一步都得猜前一步沒講清楚的事，延遲付了、準確沒換到。
子任務事先不知道有幾個，就不是提示鏈，見第 6 卡。
② 例子一：先寫文案，再翻譯
先讓模型寫行銷文案，再另一次呼叫把它翻成另一種語言。寫與譯分開，每一次呼叫只顧一件事。
兩步之間可以加閘：文案長度、必含的關鍵字。
③ 例子二：大綱、檢查、全文
先寫文件大綱，用程式檢查大綱符不符合某些條件，通過才依大綱寫全文。這是原文圖裡那個閘的用法。
閘的數量原文沒規定，「任何中間步驟」都可以放。
注意：五格裡的「寫大綱、寫全文」是原文的第二個例子；閘用程式檢查而不是另一個模型，是原文圖示的畫法。
05 / 10路由：先分類，再交給專門的流程
路由先分類，再把輸入交給專門的流程
針對一種輸入把 prompt 調到最好，常會傷到別種輸入；分開之後各自用專門的 prompt、流程與工具，這就是關注點分離
一則客服訊息
分類器：這是哪一種？
LLM，或傳統的分類模型
一般問題
退款請求
技術支援
專門的 prompt：回答常見問題
簡單常見的問題可以交給較小、較省的模型（頁面舉 Claude Haiku 4.5）
專門的流程與工具：查訂單、走退款流程
這一類需要的工具和另外兩類不同，分開才不用把所有工具塞進同一個 prompt
專門的 prompt：技術排錯
困難罕見的問題交給較強的模型（頁面舉 Claude Sonnet 4.5），成本花在需要的地方
前提
類別要明顯不同、分開處理確實比較好，而且分類本身做得準；分類器不準，路由只是把錯誤換個地方發生
路由換到的三件事
不分開的代價：顧此失彼
所有輸入走同一條路，替某一類最佳化 prompt 就可能損害另一類的表現。
原文把這句當成路由存在的理由。
每一類都能用更專門的 prompt
關注點分離之後，prompt、後續流程與工具都可以針對那一類寫，而不是一份 prompt 兼顧所有情況。
難易分流時，分出去的還有模型大小。
分類器可以不是 LLM
原文明說分類可以由更傳統的分類模型或演算法處理；分類器越便宜越準，路由省下的越多。
後半句是整理者的引申。
注意：三個出口是原文的客服例子（一般問題、退款、技術支援）；把難易分流的模型例子寫在出口裡，是整理者把原文兩個例子合在一張圖上。
06 / 10平行化 vs 協調者-工作者：子任務由誰決定
子任務是預先定好的，還是跑的時候才決定的
平行化和協調者-工作者的圖長得很像，原文說關鍵差別只有一個：子任務由誰決定。左邊寫程式時就定了，右邊由協調者依這次的輸入決定
PARALLELIZATION
平行化：子任務預先定義，程式彙整
ORCHESTRATOR-WORKERS
協調者-工作者：子任務由協調者即時決定

呼叫 A
分段：處理查詢
呼叫 B
分段：篩查不當內容
呼叫 C…
投票：同一題再跑一次
程式彙整
合併各段，或數票、設門檻
分段（sectioning）：拆成獨立子任務同時跑。投票（voting）：同一任務跑多次拿多樣輸出。彙整都是程式做的。
任務：要改幾個檔案，事先不知道
協調者模型
看這次輸入，決定拆成什麼、派給誰

改檔案 a

改檔案 b

虛線框代表寫程式時還不存在的東西：子任務的數量與內容，協調者跑的時候才決定。
分段換速度，投票換信心
每個考量各自一次呼叫、注意力集中在一個面向，通常比一次呼叫全包表現更好。原文的例子：護欄與回答分開、自動化評測各評一面、多個 prompt 審程式碼、內容審核設投票門檻。
適合：子任務可以獨立平行以換速度，或需要多個視角、多次嘗試提高信心。
子任務無法預測時才值得
寫程式時不必先知道要拆成什麼；協調者看到輸入才決定要拆、派誰、怎麼合成。原文的例子：每次都要改多個檔案的程式產品、從多個來源蒐集並分析資訊的搜尋任務。
彈性有代價：多一個模型在做決定，就多一個要量測的地方。
注意：兩種在原文裡各是一節，「拓樸相似、差在彈性」是原文自己的比較；左右都是可用的做法，所以這張不用 ✗／✓。
07 / 10評估者與優化者：生成與評估的迴圈
人會給的回饋，讓另一個模型呼叫來給
一次呼叫生成、另一次呼叫評估並回饋，在迴圈裡來回直到通過；原文的類比是作家寫一份精緻文件時的反覆修改
① 任務與評估標準
例如：譯文要保留原文的
語氣與細微之處
② 優化者生成一版
第一次通常抓不到全部細節
③ 評估者對照標準
通過就輸出；沒通過就
寫出具體的批評
④ 回饋交回優化者
像人把意見講清楚那樣
每一輪都要花一次呼叫
⑤ 帶著回饋改一版
回到第 ③ 步再評
通過才輸出
下一輪：改過的版本回到評估者，直到通過或用完輪數
兩個適用訊號
一、人把回饋說清楚時，模型的回應能明顯變好；二、模型自己也給得出那種回饋。兩個都成立，這個迴圈才有可量測的價值
條件、與原文的兩個例子
① 沒有清楚的標準，迴圈就空轉
原文說它在兩種情況特別有效：評估標準清楚，而且反覆修正帶來可量測的價值。缺了標準，評估者只能憑感覺，每一輪都在花錢。
回饋要具體到優化者能據以修改。
② 例子一：文學翻譯
譯者模型第一次可能抓不到的細微之處，評估者模型能給出有用的批評；譯者帶著批評再譯一版。
評估者不是打分機器，它要說得出「哪裡不對」。
③ 例子二：多輪搜尋
需要多輪搜尋與分析才蒐集得完整的任務，由評估者判斷還要不要再搜。這裡的評估者決定的是迴圈要不要繼續。
停止條件交給評估者，而不是固定輪數。
注意：原文的圖只有生成與評估兩個節點來回；拆成五步是整理者為了標出誰在哪一步做什麼。

09 / 10工具的格式決定模型會不會寫錯
工具的格式決定模型會不會寫錯
同一個動作有好幾種寫法，對軟體只是表面差異、可以無損互轉；對模型來說，有的格式難寫得多。工具定義值得和整體 prompt 一樣多的提示工程
✗ 讓模型難寫的格式
✓ 貼近模型自然看過的文字
用 diff 改檔案
寫新程式碼之前，得先在區塊標頭算對要改幾行；算錯整段作廢
程式碼放進 JSON
每個換行與引號都要額外跳脫；模型一邊寫程式一邊跳脫，錯了也不會報錯
用相對路徑的檔案工具
agent 離開根目錄之後就會出錯；原文做 SWE-bench 時真的踩到
共同點：格式上的「額外負擔」，例如精確數幾千行、跳脫自己寫的程式碼。負擔越多，模型越容易把自己寫進死角。
整個檔案重寫
不用算行數；多花一點輸出，換掉一整類錯誤
程式碼放 markdown 區塊
這是模型在網路上看過最多的樣子，不需要跳脫
一律要求絕對路徑
原文把工具改成只收絕對路徑之後，模型用得毫無差錯
原文的三條建議：給模型足夠的 token 先想；格式貼近網路上自然出現的文字；不要有格式上的額外負擔。
每多一個格式負擔，就多一種錯法
模型的錯常常是介面的錯。修法不是在 prompt 裡多一句提醒，而是把工具改成不容易寫錯的樣子；原文叫它 poka-yoke，防呆。
工具的定義與規格，要得到和 prompt 一樣多的注意力。
ACI 要像 HCI 一樣用心
站在模型的角度看工具說明是否明顯；參數名稱與描述寫成給初級工程師的 docstring；在 workbench 跑很多輸入看它怎麼錯；然後把工具防呆。
做 SWE-bench 的 agent 時，他們花在工具上的時間比花在 prompt 上的多。
注意：三組對照都出自附錄二；「相對路徑改絕對路徑」是原文的實例，diff 與 JSON 是原文用來說明格式難易的例子。
10 / 10對的系統，不是最複雜的系統
對的系統，不是最複雜的系統
原文的總結：從簡單的 prompt 開始，用完整的評估調好它，只有在簡單解法不夠時才加多步驟的 agentic 系統；實作 agent 時守三條原則
01　簡單
讓 agent 的設計保持簡單
複雜度是用延遲和成本買的，而且會遮住錯在哪裡。每一層都要能用評測證明它換到了更好的結果；證明不了的那一層就拿掉。
✗ 一開始就用框架把所有模式接上
✓ 先直接用 API，幾行程式寫出需要的那一種
02　透明
把 agent 的規劃步驟明確顯示出來
看得見它打算怎麼做，人才能在檢查點介入，出錯時也才追得到是哪一步偏掉。原文把透明列為優先事項。
✗ 只回傳最後結果
✓ 規劃、行動、回饋每一步都留下痕跡
03　ACI
用周到的工具文件與測試，
打造 agent 與電腦的介面
工具定義要像給初級工程師的 docstring：用法範例、邊界情況、輸入格式、和其他工具的分界；再用很多輸入測它怎麼錯，然後防呆。
原文做 SWE-bench 時，花在工具上的時間比 prompt 多。

03
不夠時才加多步驟系統
04
