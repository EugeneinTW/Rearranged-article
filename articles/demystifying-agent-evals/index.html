Prologue · 整理者的引言

判官之外，還要題庫、harness 與路線圖

這一講談 LLM 當判官，也談評估的基礎建設。判官只是評分的一環；題目怎麼出、環境怎麼搭、分數怎麼讀、從哪裡開始，這篇一路講到底。

這篇是 Stanford CS 329Z 第 8 週的必讀，屬於 Evaluation for Agentic Systems 分區的〈LLM-as-Judge & Evaluation Infrastructure〉那一講。那一講的題目有：三種 grader、judge 的 prompt 怎麼設計、判官已知的偏誤、pairwise 與 pointwise 兩種比法、非確定性的指標（pass@k 對 pass^k）、harness 的設計，以及 Anthropic 的八步路線圖，也就是這一篇。同一講的另兩篇必讀是 MT-Bench 論文（Zheng 等人）與 AutoMetrics（Ryan 等人），選讀是 AutoLibra。

整理者對照講題與原文，這篇負責的是工程上的整套做法：三種 grader 各自的長短、pass@k 與 pass^k、harness 怎麼搭、路線圖怎麼走。判官已知的偏誤，這篇沒有展開；pairwise 比較只在模型 grader 的做法清單裡出現一次。這兩題要看同一講的其他讀物，本頁不替原文補寫。另外，講題說「八步」，原文的編號是從第 0 步到第 8 步，本頁照原文寫成九步。

原文是 Anthropic 工程部落格 2026 年 1 月 9 日的文章，由 Mikaela Grace、Jeremy Hadfield、Rodrigo Olivares、Jiri De Jonghe 執筆。作者說，這些做法來自 Anthropic 內部的工作，以及和走在 agent 開發前沿的客戶合作的經驗。因為是公司部落格，文中關於自家產品與模型的說法（Claude Code、Claude.ai、Claude for Chrome、Opus 4.5），以及它轉述的客戶案例，本頁都寫成「作者說」。

整理者的補充：本站整理過的〈Building effective agents〉是這篇開頭引用的前作，〈Effective context engineering for AI agents〉出自同一個部落格，OpenAI 的〈Testing Agent Skills Systematically with Evals〉則是用 eval 測 agent skill 的相近題目；本頁不用它們的內容擴寫。

給初學者

先把六個名詞對齊

  • eval（評估）：給 AI 一個輸入，再用一段評分邏輯判斷它的輸出算不算成功；本篇談的是開發時自動跑、不需要真實使用者的那一種。
  • agent：會跑很多輪、自己呼叫工具、改變環境狀態、依中間結果調整做法的模型系統。
  • grader（評分器）：替 agent 表現的某個面向打分的邏輯，可以是程式、另一個模型，或人。
  • transcript：一次執行的完整紀錄，含輸出、工具呼叫、推理與中間結果；也叫 trace 或 trajectory。
  • harness：把東西跑起來的那一層系統。原文分兩種：跑 eval 的 evaluation harness，和讓模型能當 agent 的 agent harness。
  • regression（退步）：以前做得到的事，改了東西之後做不到了。

作者開頭先講評估帶來什麼。好的評估讓團隊比較有把握地出貨；沒有評估，團隊很容易陷進被動的循環：問題要到上線後才發現，修好一個又冒出另一個。評估讓問題與行為上的變化在影響使用者之前就被看見，它的價值也會在 agent 的整個生命週期裡累積。

難處在 agent 本身。原文引用自家的〈Building effective agents〉：agent 跑很多輪，一路呼叫工具、改變狀態、依中間結果調整做法。讓 agent 有用的自主、聰明與彈性，正是讓它難評估的地方。

eval 的定義很單純：它是替 AI 系統做的測試，給一個輸入，再對輸出套用評分邏輯，量它成不成功。這篇只談開發期間就能自動跑、不需要真實使用者的評估。單輪的評估最直接：一個 prompt、一個回應、一段評分邏輯，早期的 LLM 主要就是這樣評；能力變強之後，多輪的評估越來越常見。原文的第一張圖把兩者並排：

面向單輪評估agent 評估
給什麼一個 prompt 加資料：「{動物}有幾根腳趾？」，動物＝貓工具、環境、task：替我的 app 寫一個 MCP server

agent 的評估又更複雜。它在很多輪裡使用工具、改動環境的狀態、邊做邊調整，所以一個錯誤可能一路傳下去、越滾越大。前沿模型也可能找出靜態 eval 沒想到的解法。

團隊剛開始做 agent 時，靠手動測試、自己內部先用（dogfooding）和直覺，可以走得出乎意料地遠。更嚴謹的評估甚至像是拖慢出貨的額外負擔。作者說，問題出在原型期之後：agent 上線、開始擴大規模，沒有 eval 的開發方式就開始撐不住。

斷點常常是這樣來的：使用者回報改版後 agent 變差了，團隊卻像在盲飛，除了猜一猜、試一試，沒有辦法確認。沒有 eval，除錯只能被動地跟在問題後面：

1
等抱怨使用者先碰到問題，回報進來。
2
手動重現從描述裡猜出條件，自己再跑一次。
3
修 bug改 prompt、改工具或改流程。
4
希望別的沒壞沒有辦法確認這次的修改，有沒有在別處造成退步。

作者列了三件團隊因此做不到的事：分不出真正的退步和雜訊；沒辦法在出貨前自動拿改動去跑幾百個情境；也量不出改善了多少。

作者說他們看過這個過程很多次，Claude Code 就是一例。它一開始靠 Anthropic 員工與外部使用者的回饋快速迭代；之後才加上 eval，先針對簡潔、檔案編輯這類範圍窄的地方，再擴到過度設計（over-engineering）這類比較複雜的行為。這些 eval 幫忙找出問題、引導改進、讓研究與產品的合作有焦點；再加上生產監控、A/B 測試、使用者研究等方法，Claude Code 在規模變大時還有訊號可以繼續改進。

寫 eval 在 agent 生命週期的任何階段都有用。早期，它逼產品團隊講清楚這個 agent 怎樣算成功；後期，它幫忙守住一致的品質門檻。作者轉述了兩個客戶的做法：

regression 評估問的是：以前處理得了的 task，它現在還處理得了嗎？這一組的通過率應該接近 100%。它防的是退步：分數一掉，就表示有東西壞了、要修。團隊在 capability 評估上往上爬的時候，也要一起跑 regression 評估，確認這些改動沒有在別的地方造成問題。

寫程式的 agent。它們寫程式、測試、除錯，在程式碼庫裡找路、執行指令，做的事很像一位開發者。作者說，好用的評估通常靠三樣東西：規格清楚的 task、穩定的測試環境、完整的測試。

確定性的 grader 很適合寫程式的 agent，因為軟體通常好評：程式能不能跑、測試有沒有過。兩個廣泛使用的基準都這樣做。SWE-bench Verified 拿熱門 Python 專案的 GitHub issue 當題目，用跑測試的方式評分：一個解法要修好原本失敗的測試，又不能弄壞既有的測試，才算通過；原文說 LLM 在這個 eval 上一年內從 40% 進步到超過 80%。Terminal-Bench 走另一條路，測端到端的技術任務，例如從原始碼編譯 Linux 核心、訓練一個機器學習模型。

有了一組驗證關鍵結果的通過或失敗測試之後，通常也值得評 transcript。啟發式的程式品質規則，可以評測試以外的程式品質；帶著清楚 rubric 的模型 grader，可以評 agent 怎麼呼叫工具、怎麼和使用者互動。原文用一個修補登入漏洞的 task 示範，下面是精簡改寫的版本：

task:

    - type: static_analysis      # 以下三種是示範，需要時才加

作者特別說明，這個例子把能用的 grader 全部掛上去，是為了示範。實務上，寫程式的評估通常靠單元測試驗正確性，再用一份 LLM rubric 評整體的程式品質，其他 grader 與指標只在需要時才加。

對話的 agent。它們在客服、銷售、教練這類領域和使用者互動。和傳統聊天機器人不同，它們會記住狀態、使用工具、在對話中途採取行動。寫程式與研究的 agent 也可能和使用者來回很多輪，但對話 agent 有一個獨特的難處：互動本身的品質就是評估的一部分。好的評估通常靠兩樣東西：可以驗證的最終狀態，以及同時涵蓋任務完成與互動品質的 rubric。和大部分 eval 不同，它們常需要第二個 LLM 來扮演使用者；作者說 Anthropic 的對齊稽核 agent（alignment auditing agents）也用這個方法，透過長時間、對抗性的對話對模型做壓力測試。

對話 agent 的成功可能有好幾個面向：工單解決了嗎（狀態檢查）、10 輪之內結束了嗎（transcript 的限制）、語氣恰當嗎（LLM rubric）。τ-Bench 與後繼的 τ2-Bench 兩個基準都納入了這種多面向：它們在零售客服、訂機票這類領域模擬多輪互動，由一個模型照設定好的人設扮演使用者，agent 在擬真的情境裡應對。原文的第二個例子是處理一位不滿客戶的退款：

示意 · 對話 agent 的 grader（依原文 YAML 精簡改寫，assertion 譯成中文） 
graders:
  - type: llm_rubric         # 互動本身的品質
    rubric: prompts/support_quality.md
    assertions:
      - "對客戶的不滿表現出同理心"
      - "把解決方式講清楚"
      - "回答根據 fetch_policy 工具的結果"
  - type: state_check        # 環境裡的最終狀態
    expect: {tickets: resolved, refunds: processed}
  - type: tool_calls
    required: [verify_identity, process_refund(amount <= 100), send_confirmation]
  - type: transcript
    max_turns: 10

和寫程式的例子一樣，這個 task 掛上多種 grader 是為了示範。實務上，對話 agent 的評估通常用模型 grader 同時評溝通品質與目標達成，因為很多 task（例如回答一個問題）可能有好幾個「對」的解。

實作提示

先寫出成功的面向，再替每個面向挑 grader

兩份例子的共同做法是：把「成功」拆成幾個可以各自檢查的面向，再替每個面向找最便宜、夠可靠的 grader。結果在環境裡的，用狀態檢查；過程有硬規則的，用工具呼叫或輪數；互動品質這種主觀的，才交給 rubric。這段是整理者對兩個例子的歸納。

pass@k 量的是 agent 在 k 次嘗試裡，至少拿出一個正確解的可能性。k 越大，pass@k 越高：射門的次數越多，至少進一球的機會就越大。寫程式時，通常最在意的是 agent 第一次就找到解，也就是 pass@1；在其他情境裡，提出很多個解是可以接受的，只要其中一個能用就好。

pass^k 量的是 k 次 trial 全部成功的機率。k 越大，pass^k 越低，因為要在更多次 trial 裡都保持一致，門檻更難跨過。面對客戶的 agent 特別要看這個指標，因為使用者期待它每一次都表現可靠。

示意 · 兩個指標的算法（整理者的補充，假設每次 trial 獨立、成功率都是 p） 
# pass^k：k 次全部成功
pass^k = p^k                 # 原文的例子：0.75^3 ≈ 0.42
# pass@k：至少一次成功 = 1 減掉「k 次全部失敗」
pass@k = 1 - (1 - p)^k      # k = 1 時兩者都等於 p

原文的第三張圖把兩條線畫在一起：隨著 trial 次數增加，兩者越分越開。k＝1 時它們完全相同，都等於每次 trial 的成功率；到了 k＝10，它們講的是相反的故事：pass@k 逼近 100%，pass^k 掉到 0%。圖上那個例子標的是：跑 3 次，pass@3 到 97%，pass^3 掉到 39%。

兩個指標都有用，選哪一個看產品需求：只要成功一次就夠的工具，看 pass@k；一致性是必要條件的 agent，看 pass^k。

作者建議替每個 task 準備一份參考解：一份已知能用、通過所有 grader 的輸出。它證明這道題解得出來，也驗證 grader 的設定是對的。

第 3 步：建立平衡的題組。某個行為該出現的情況要測，不該出現的情況也要測。單邊的 eval 會帶來單邊的最佳化：如果只測 agent 在該搜尋時有沒有搜尋，最後可能得到一個幾乎什麼都要搜尋的 agent。所以要避免類別不平衡的題組。

作者說，他們替 Claude.ai 的網頁搜尋建 eval 時，親身學到這一課。難處在於，要讓模型在不該搜尋時不搜，同時保住它在適當時候做大量研究的能力。團隊建的 eval 兩個方向都涵蓋：

方向例子錯了叫什麼
應該搜尋查天氣觸發不足（undertriggering）：該搜卻沒搜
應該直接用既有知識回答「誰創立了 Apple？」過度觸發（overtriggering）：不該搜卻搜了

在觸發不足與過度觸發之間取得平衡很難，作者說花了好幾輪，同時修改 prompt 與 eval；之後遇到新的問題例子，就繼續加進 eval，擴大涵蓋的範圍。

拿你的一個 task，請一位同事不看你的答案各判一次，你們判得一樣嗎？

挑一個你覺得很清楚的 task，只給同事 task 描述與一份 agent 的輸出，請他判通過或失敗。

第 5 步：用心設計 grader。好的 eval 設計要替 agent 與 task 挑最合適的 grader。作者的建議有先後：

1

2

3
人工 grader 審慎地用拿來做額外的驗證。

關鍵觀念 · 二

同一個模型，修掉 eval 的毛病後從 42% 到 95%

作者說，Opus 4.5 起初在 CORE-Bench 上只拿到 42%，直到一位 Anthropic 的研究員找出好幾個問題：評分太死，預期 96.124991… 時把 96.12 判成錯；task 的規格含糊；有些帶隨機性的 task 根本無法精確重現。修掉這些 bug、改用限制比較少的 scaffold 之後，Opus 4.5 的分數跳到 95%。

METR 也在他們的時間跨度（time horizon）基準裡發現幾個設定錯誤的 task：題目要 agent 最佳化到一個指定的分數門檻，評分卻要求超過那個門檻。結果照指示做的模型（例如 Claude）反而被扣分，忽略指定目標的模型分數更高。仔細地再檢查一次 task 與 grader，可以避開這些問題。

最後，grader 要能抵抗繞過與作弊。agent 不應該能輕易騙過 eval；task 與 grader 的設計要讓通過真的需要解決問題，而不是鑽到沒預料到的漏洞。

不需要真實使用者		迭代快、完全可重現、不影響使用者；每次 commit 都能跑；不必部署就能大規模測情境前期要投入更多來建；產品與模型演進時要持續維護，避免漂移；和真實用法不符時，會帶來假的信心
生產監控
追蹤線上系統的
指標與錯誤		看得到大規模的真實使用者行為；抓得到合成 eval 漏掉的問題；知道 agent 實際表現如何被動：問題先碰到使用者才知道；訊號可能很吵；要投資埋點；缺少評分用的標準答案
A/B 測試
用真實流量
比較不同版本		量得到留存、任務完成這類真實結果；控制了干擾因素；可擴展、有系統慢：要幾天到幾週才達到顯著，還要有足夠的流量；只測得到你部署的改動；不徹底讀 transcript 的話，很難知道指標變化背後的原因
使用者回饋
倒讚、bug 回報
這類明確的訊號		冒出你沒預料到的問題；附有真實使用者的例子；常和產品目標相關稀少、自我選擇、偏向嚴重的問題；使用者很少說明失敗的原因；無法自動化；主要靠使用者抓問題，會傷到使用者
人工讀 transcript
人一段段讀
agent 的對話		培養對失敗模式的直覺；抓到自動檢查漏掉的細微品質問題；幫忙校準「好」長什麼樣費時、無法擴展、覆蓋不一致；評閱者疲勞或換人會影響訊號品質；通常只給質性的訊號，給不出清楚的量化評分
系統化的人工研究
受訓評分者有結構地
評 agent 的輸出		多位評分者給出的黃金標準判斷；處理得了主觀或含糊的任務；提供改進模型 grader 的訊號相對貴、週期長；很難常常做；評分者之間的分歧要調解；法律、金融、醫療這類複雜領域，要請專家來做

這些方法對應 agent 開發的不同階段。自動化 eval 在上線前與 CI/CD 裡特別有用：每次改 agent、每次升級模型都跑，是對抗品質問題的第一道防線。生產監控在上線後接手，偵測分布的漂移與沒料到的真實世界失敗。A/B 測試等流量足夠了，再拿來驗證重大的改動。使用者回饋與讀 transcript 是持續的習慣，用來補漏：隨時分流處理回饋、每週抽樣讀 transcript、需要時再深入。系統化的人工研究則留給兩件事：校準 LLM grader，或評估那些要以人類共識當參考標準的主觀輸出。

原文用安全工程裡的瑞士起司模型來比喻：沒有任何一層評估能接住每一個問題。好幾種方法疊在一起，從一層的洞漏過去的失敗，會被另一層接住。原文的圖畫了三層：

1
自動化 eval一致地量測、建立效能的基準線，在部署前抓到退步。
2
人工讀 transcript、搶先體驗計畫抓到細微的失敗，以及沒料到的使用者或 agent 行為。
3
生產監控、A/B 測試、使用者回饋冒出罕見的邊界情況，以及大規模的真實使用模式。

作者的結論是，最有效的團隊會把這些方法組合起來：自動化 eval 負責快速迭代，生產監控提供真實情況，定期的人工審閱負責校準。

eval 的價值會累積，前提是當成核心

沒有 eval 的團隊修一個壞一個；早投入的團隊，失敗變成 task、task 擋住退步、指標取代猜測。做法依 agent 的類型而不同，基本功不變。

作者在結論裡再比一次兩種團隊。沒有 eval 的團隊陷在被動的循環裡：修好一個失敗、又造成另一個，分不出真正的退步與雜訊。早早投入的團隊看到的是相反的情況：失敗變成測試案例，測試案例防止退步，指標取代了猜測，開發跟著加速。eval 給整個團隊一座清楚的山可以爬，把「agent 感覺變差了」變成可以處理的事。這份價值會累積，但前提是把 eval 當成核心元件，而不是事後才補的東西。

  1. 從 bug 追蹤與客服佇列挑 20 到 50 個真實失敗，寫成 task加上發版前的手動檢查；依對使用者的影響排順序。
  2. 每個 task 請一位同事獨立判一次，再附一份參考解判得不一樣就改規格；參考解要能通過所有 grader。
  3. 補上反面的題目該做與不該做的情況都要有，例如該搜尋與不該搜尋。
  4. 每次 trial 從乾淨的環境開始，結果到環境裡查不共用檔案、快取與資源；outcome 用環境的狀態判，不用 agent 的話判。
  5. grader 先用程式，需要彈性才加 LLM 判官一個面向一個判官，允許回答 Unknown；先和人工判斷對齊。
  6. 同一個 task 跑多次，依產品需求看 pass@k 或 pass^k一次成功就夠的看 pass@k，每次都要可靠的看 pass^k。
  7. 每週讀一批 transcript，接近滿分的題組移進 regression再替 capability 題組補更難的 task。

Reference · 名詞速查

二十四個名詞，看懂 agent 的評估

依「組成、grader、題組、非確定性、路線圖、其他方法」的順序排，解釋是整理者依原文的用法寫的。

Eval (evaluation)
評估
給 AI 一個輸入，再用評分邏輯判斷輸出算不算成功；本篇談開發時自動跑、不需要真實使用者的那一種。
Task
題目
一道有定義好的輸入與成功標準的測試，也叫 problem 或 test case。
Trial
試跑
對一個 task 的一次嘗試；模型每次輸出不同，所以同一題跑好幾次。
Grader
評分器
替 agent 表現的某個面向打分的邏輯；一個 task 可以掛好幾個，每個含多條 assertion。
Assertion
斷言
grader 裡的一條檢查，也叫 check；例如「回答根據 fetch_policy 工具的結果」。
Transcript
執行紀錄
一次 trial 的完整紀錄：輸出、工具呼叫、推理、中間結果；也叫 trace 或 trajectory。
Outcome
最終狀態
trial 結束時環境裡的狀態，例如資料庫裡有沒有那筆訂位；它和 agent 說了什麼是兩回事。
Evaluation harness
評估框架
端到端跑 eval 的基礎設施：給指示與工具、同時跑 task、記錄每一步、打分、彙整。
Agent harness
agent 框架
讓模型能當 agent 的系統，也叫 scaffold；評一個 agent，評的是它和模型一起。
Evaluation suite
題組
為了量某些能力或行為而設計、共享一個大目標的一組 task，例如客服的退款、取消、升級處理。
Code-based grader
程式 grader
字串比對、測試、靜態分析這一類；快、便宜、可重現，但對有效的變化很脆弱。
Model-based grader
模型 grader
也就是 LLM 當判官：依 rubric、assertion 或兩兩比較打分；有彈性，但不確定，要和人工校準。
Human grader
人工 grader
專家審閱、抽樣檢查、群眾判斷；是黃金標準，也用來校準模型 grader，但又貴又慢。
Rubric
評分準則
寫給 grader 的評分標準；原文建議每個面向一份、交給獨立的判官，含糊的 rubric 會判得不一致。
Partial credit
部分分數
由好幾個部分組成的 task，依完成的程度給分，不只記通過或失敗。
Capability eval
能力評估
問「它能把什麼做好」，從低通過率開始，給團隊一座可以往上爬的山；也叫品質評估。
Regression eval
回歸評估
問「以前會的還會嗎」，通過率應接近 100%；分數一掉，就是有東西壞了。
Saturation
飽和
agent 通過了所有解得出來的 task，eval 只剩抓退步的作用，看不出進步。
pass@k
至少一次成功
k 次嘗試裡至少一次成功的機率；k 越大越高，適合一次成功就夠的工具。
pass^k
每次都成功
k 次 trial 全部成功的機率；k 越大越低，適合要求每次都可靠的 agent。
Reference solution
參考解
一份已知能通過所有 grader 的輸出，證明題目解得出來、grader 設定正確。
Class-imbalanced eval
不平衡的題組
只測行為該出現的情況、不測不該出現的；單邊的 eval 會帶來單邊的最佳化。
Eval-driven development
eval 驅動開發
在 agent 做得到之前，先寫 eval 定義規劃中的能力，再迭代到它表現良好。
Swiss cheese model
瑞士起司模型
借自安全工程的比喻：每一層都有洞，好幾層疊起來，漏過一層的問題會被另一層接住。
