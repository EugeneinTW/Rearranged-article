Data Flywheels · 圖卡＋教材整合版

Data Flywheels讓每一筆生產資料 回頭改進 LLM 應用

LLM 應用上線之後，生產資料就一直進來：使用者的查詢、模型的輸出、人工的判斷。Shreya Shankar 在這篇 2024 年的文章裡提出一個三步框架：評估、監控、持續改進，讓這些資料回頭把指標、LLM 判官和應用本身一起變好；最後一節是她還在想的三個研究問題。本頁分十一章重述。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

同一批生產資料，既拿來評估也拿來改進

作者把它叫資料飛輪：每一筆輸出都被打分、記錄，標註過的例子再回到判官與應用的 prompt 裡，應用就一圈一圈變好。

這篇是 Stanford CS 329Z 第 6 週的必讀，屬於 Data for Agentic Systems 分區的〈What Data Do Agents Need?〉那一講。那一講談 agent 需要哪些資料：執行軌跡、示範與回饋，最佳化用的資料和評估用的資料有什麼不同，資料飛輪，合成資料，以及怎麼從人與 agent 的互動收集資料。同一講的選讀是 Tan 等人整理 LLM 資料標註與合成的綜述。

這篇負責其中的資料飛輪。整理者讀下來的重點是：同一批生產資料，在這個框架裡有兩種用途。標註過的輸入與輸出，一方面放進 LLM 判官的 prompt 當範例，讓評估跟上人的判斷；另一方面，人工修正過的低分輸出，會在執行時被找出來、放進應用的 prompt，讓應用本身變好。前者是評估用的資料，後者是改進用的資料，正好對上這一講的另一個題目。這是整理者的讀法，原文沒有用這兩個詞來分。

作者 Shreya Shankar 是研究者。她說這些想法來自她和合作者驗證 LLM 管線資料品質的研究，而那些研究已經開始被垂直領域的 AI 應用與 LLMOps 公司採用。整理者補一句：下一講（第 7 週 Data Selection & Quality）的必讀〈Who Validates the Validators?〉，第一作者也是 Shankar；原文圖 1 的說明寫著改編自一篇論文的圖 1，連結指向的就是那一篇。本頁不用那篇論文的內容擴寫。

原文的順序是：先講四個觀察與整條管線的全貌，再依序講評估、監控、持續改進三步，最後是三個還在想的研究問題。本頁照這個順序走，評估一節的前兩小段併成一章。

給初學者

先把六個名詞對齊

  • 資料飛輪（data flywheel）：應用產生資料，資料回頭讓應用變好，變好的應用再產生更多資料的循環。
  • 生產資料、生產軌跡：應用上線後真實跑出來的輸入、輸出與中間步驟；一次完整的執行紀錄叫一條軌跡（trace）。
  • 驗證器（validator）：檢查一筆輸入或輸出合不合格的東西，可以是一段程式，也可以是一次 LLM 呼叫。
  • LLM 判官（LLM-as-a-judge）：請一個 LLM 依你定義的指標，判斷一筆輸出好不好。
  • Few-shot 範例：放在 prompt 裡、示範「什麼算對、什麼算錯」的少數幾個例子。
  • 二元指標（binary metric）：答案只有 True 或 False 的指標，也就是一個是非題。

作者說，過去幾個月她一直在想，怎麼用生產資料自動、動態地改進 LLM 應用。她把資料飛輪的想法建立在四個觀察上：

01

人要定期回到評估裡

人對 LLM 輸出的偏好會隨時間改變，所以評估不能只做一次，要定期有人參與。

02

輸出需要驗證器

微調的負擔大，很多團隊寧可用 LLM API，迭代快、部署也簡單。但 API 不一定照 prompt 的指示做，一次處理大批輸入時更明顯，所以輸出要有驗證器把關。

03

LLM 判官越來越普及

用 LLM 當判官的做法越來越流行，模型本身也越來越便宜、越來越好、越來越快。

04

範例能讓判官對齊人

作者引用的實證研究指出，few-shot 範例是改善 prompt 表現最有效的方法。所以只要給對範例，LLM 判官就能對齊人的偏好。

關鍵觀念 · 一

為什麼叫飛輪

作者在致謝裡說，資料飛輪這個敘事的靈感來自同事 Parth Asawa。飛輪的意思是每一圈的產出，成為下一圈的動力。

放在這篇裡，一圈就是一批生產資料被打分、標註、修正，再回到判官與應用的 prompt；下一批資料因此被判得更準，也答得更好。這段解釋是整理者寫的。

談評估的好資源很多，作者推薦朋友 Hamel 的一篇文章，裡面有具體該評哪些指標、用哪些工具。她自己只談比較高層的流程：先建立清楚的成功標準，再找對的實作方式。她說這件事比看起來細緻。

標準要從資料裡讀出來。以客服聊天機器人為例，你可能在意「回應是否簡潔」或「同理心分數」。但作者提醒，只靠推想任務可能出哪些錯，定不出有效的標準；要實際看資料，看很多筆 LLM 的輸出，才知道這個任務該驗哪些東西。

理由是有些指標對應的是 LLM 本身的怪癖，甚至是你這個任務特有的毛病。原文的例子：你可能發現 delve、crucial 這類字常帶著一股「GPT 味」，想避開它們，那就可以做一個檢查這些字有沒有出現的指標。作者說，這種洞見只會在仔細讀過真實輸出之後才冒出來。

實作分兩種。圖 1 的二元指標區塊畫了兩種：用程式算的指標，以及用 prompt 交給 LLM 判的指標。程式適合啟發式的規則，例如數字元數來判斷夠不夠簡潔；LLM 判官是請一個 LLM 依你定義的某個指標做評估，適合比較主觀或複雜的標準。

用 LLM 判官時，難處在讓它的判斷對上你自己的判斷，客製的任務尤其難。作者說，在判官的 prompt 裡放幾個你認為好與不好的輸出（針對這個指標），就能明顯改善對齊。

示意 · 兩種二元指標（教學用骨架，非原文） 
# 程式指標：啟發式規則，直接算
def no_gpt_smell(output) -> bool:
    banned = ["delve", "crucial"]   # 讀真實輸出時發現的字
    return not any(w in output.lower() for w in banned)

# LLM 判官：一個指標、一個是非題、一好一壞兩個範例
JUDGE_PROMPT = """指標：這則回應夠簡潔嗎？只回答 True 或 False。
通過的範例：{passing_example}
不通過的範例：{failing_example}
要判的回應：{output}"""

先用二元。作者特別提到，二元指標（True／False）比較容易對齊，從使用者體驗來看也比較好推理。很多人反射性地替 LLM 判官選 Likert 量表或更細的分級，但通常從簡單的開始比較好：二元指標只要大家對「什麼算 True、什麼算 False」有共識就能對齊，人也比較容易判得一致；判得一致，評估資料的品質才守得住。

實作提示

一個指標只問一件事

作者在第三步又回到這一點：把「好」拆成幾個各自只問一件事的指標，人標得比較一致，判官也比較好對齊（第 7 章）。所以寫判官的 prompt 時，一個指標就只問一個是非題。這個對照是整理者把兩處原文接起來的。

複雜的 LLM 應用常是好幾個 LLM 呼叫接成的圖。作者把驗證器比作軟體可觀測性（observability）裡的探針：探針放在策略性的位置監看軟體的行為，驗證器也該放在 LLM 圖的節點上，評估中間與最終輸出的品質和正確性。圖上每一種節點，探的方式都不一樣。

節點的分類來自作者的朋友 Han Lee。他提了三種節點類型，作者說和自己的經驗很合，再加上她在實務上的觀察。原文的圖 2 是一個客服聊天機器人：使用者的訊息先進「分類意圖」，再依意圖走到「產生 SQL」或「產生查文件用的鍵」，最後由「產生自由文字回覆」寫出機器人的回答。圖裡省略了工具使用，例如拿產生的 SQL 去資料庫執行、拿鍵去知識庫找文件。

節點類型在圖 2 裡做什麼要看什麼怎麼驗
分類器（狀態轉移節點，圖 2 的菱形）分類使用者的意圖，例如帳務問題、技術支援、一般詢問，再把對話導到對應的子圖決策對不對：準確率、precision、recall、F1規則比對：使用者提到 bill 或 payment，預期的意圖就是帳務問題；LLM 預測的不一樣，就標給人看，也可能要更新 few-shot 範例與訓練資料
寫手（生成節點，長方形）產生查文件用的鍵、產生最後的回覆最客製的一類，依使用者與任務而定：品質、連貫、恰當；也可以看 perplexity、多樣性、任務限制，看它們對業務有沒有用例如寫一個 LLM 驗證器，依公司品牌的範例，檢查回覆有沒有守住品牌的語氣
程式產生器（codegen 節點，六角形）依意圖與上下文產生 SQL，從知識庫取資料產生的程式對不對、跑不跑得起來靜態分析、linter、測試；能動態分析就實際執行，例如把 SQL 丟到資料庫跑、檢查結果；也可能再用 LLM 驗證器看輸出有沒有合理回答使用者的問題

每個節點都放驗證器，很快就會有一大堆，而且不一定看得出哪幾個最關鍵。作者的建議是把驗證器的輸出標註起來、算出每一步的準確率，這樣就能追出錯誤怎麼在管線裡一路累積，改進時也更有針對性。她也說，要完整驗證多步驟的 LLM 管線，目前仍是開放的研究問題，文章最後一節會再回來談（本頁第 8 章）。

補充說明

探針這個比喻在說什麼

可觀測性的探針不改變程式的行為，只負責在關鍵位置回報發生了什麼。把驗證器當成探針，重點就落在「放在哪裡」與「每個位置量什麼」：放在分類之後，量的是路由有沒有走對；放在產生 SQL 之後，量的是程式能不能跑。這段是整理者對比喻的解釋。

挑法怎麼做原文說的現況
依相似度挑和這次要判的那一筆相關的範例；圖 1 的動態 few-shot 範例就是依輸入相似度取回圖 1 畫的做法
分歧優先借主動學習的想法，優先挑人工標註和 LLM 預測不一樣的例子，集中在邊界情況與可能沒對齊的地方作者知道有 2 個人這樣做；比隨機均勻抽樣好多少，還不知道
越新越重相似度分數依標註的新舊加權，最近的生產資料比較容易被選中作者說不知道有誰在做，但覺得重要，要讀者保留地看；另有 1 個人資料量少，乾脆只取最新的範例、不看相似度
示意 · 替判官挑範例（教學用示意，非原文；數字是示意） 
def pick_examples(store, item, k=4):
    cands = store.most_similar(item.input, n=50)   # 依輸入相似度取候選
    def rank(e):
        disagree = e.human_label != e.llm_label          # 人與 LLM 判得不一樣
        return (disagree, e.similarity * recency_weight(e.labeled_at))
    return sorted(cands, key=rank, reverse=True)[:k]   # 分歧優先，再看依新舊加權的相似度

這套流程最大的挑戰，是每個指標都要有人定期標註。這很重要，也很累人。作者提到 LangChain 在試一種做法：預設由 LLM 先標，人可以隨時修改。這確實減輕了標註負擔，但 LLM 標註者能不能長期對齊人的判斷，還不清楚，工程師或團隊成員懶得檢查時更是如此。作者的看法是，就算不完美，這種做法至少保證有一股穩定的、最近的相關範例可以當 few-shot 示範，這本身就有價值。

提醒 · 原文註腳 2

動態範例的兩個風險

替作者審稿的 Han Lee 提了兩個疑慮。一是有些產業不一定能接受這種做法，例如法務團隊想在 prompt 上線前先簽核，範例一直在變就很難簽。二是 prompt 下毒（prompt poisoning）的風險：有人可能刻意寫出對抗性的查詢，讓它們被選進 prompt 當 few-shot 範例。

評估與監控到位之後，焦點轉到有系統地改進應用，這裡同時要靠人的洞察與自動化的技巧。作者說前提是圖 1 的「日誌」：完整記錄每一筆輸出與它的指標分數，LangSmith 這類 LLMOps 工具可以幫忙。

手動迭代。關鍵是用上評估與監控得到的洞察。指標定義清楚、實作又持續更新，你就能看出哪些生產軌跡表現好、哪些不好，從錯誤裡學著改 prompt 或其他元件。作者建議的做法有三個：定期看指標分數在生產資料上的分布，找低分實例的模式或群聚；分析輸入或查詢的分布，觀察使用者行為的模式與變化；對不同的 prompt 結構或管線設定做 A/B 測試，實際看哪個在你的指標上表現比較好。

自動改進。作者說人工分析有價值，但把改進流程的一部分自動化，可能更有效率。她想像中的基本策略有兩層。第一層是定期檢查並「修正」低分的輸出，依應用的規模與資源，每天或每週一次。修正包含三件事：找出原本的輸出錯在哪、把它改寫成對的、記下改了什麼與理由，讓其他團隊成員學得到。

第二層借用主動學習的想法：用一個資料庫存生產軌跡，連同它們的指標分數與人工修正；低分的軌跡優先送人工檢查與修正；應用在執行時，取回和這次查詢最像的「已修正」軌跡，放進 prompt 當 few-shot 示範。取回的方式可以實驗，作者列了三種：同時放最像的一筆（不管分數、有沒有修正）與最像的一筆已修正軌跡；依時間加權，偏好比較新的例子；加上多樣性的衡量，讓範例涵蓋不同類型。

補充說明 · 原文註腳 3

prompt 工程變成檢索問題

作者在註腳推薦前同事 Devin Stein 的一篇文章，主張在執行時動態抓範例放進 prompt，並說她認識的人裡至少有 5 個在做類似的事。她點出這種架構把 prompt 工程的問題變成了檢索的問題：要找的範例得同時是對 LLM 最有資訊量的，也是和終端使用者想要的最相關的。

作者最後補充一點：與其讓人對整條軌跡下一個整體的好壞判斷，不如把「好」拆成幾個維度。她列了三個好處：

01

人標得更準、更一致

標註者不必下一個高層的整體判斷，只要專心看簡潔、禮貌這類定義清楚的面向；顆粒度細，比較容易對齊，主觀也比較少。

02

判官比較好對齊

LLM 驗證器一次只檢查一個指標時比較容易對齊；一口氣抓住「好」的全部意思很難，逐個維度驗證就可行得多。

03

看得出問題在哪

每個指標都有分數，表現就看得更細；多數輸出都卡在某一個指標上，要改的地方就很明確。

作者的結論是，不管怎樣都還是要有人標註，但用多個指標，能讓持續改進的過程更嚴謹、更一致，也更知道下一步該做什麼。

你的應用最近的低分輸出，有人修過嗎？修好的去了哪裡？

這一節的語氣和前面不同：前面三步是作者建議的做法，這裡是她在 LLMOps 生命週期裡一直在想的問題，而且是偏研究的角度。本頁照原文寫成問題與提案。

一、用不確定性估計來對齊驗證器。作者說一個關鍵挑戰是 LLM API 的不確定性量化，客製任務尤其難。主動學習是改進機器學習模型的有力工具，但用 LLM API 時很難做，因為拿不到有意義的機率估計：指令微調過的模型，下一個 token 的機率沒有校準，大量分析輸出時派不上用場；有些研究讓 LLM 在輸出後自己報一個信心分數，作者說效果也不太好。改成自己微調模型當然是直接的解法，但那就違背了前提，也就是 LLM API 的簡單。

她認為，穩健的不確定性估計能大幅提升三件事：對齊指標的實作、挑有資訊量的 few-shot 範例、決定哪些資料優先送人工標註。這還是開放的研究問題，但有進展的話，能直接強化框架裡的評估與持續改進兩步。

二、替 LLM 呼叫的圖做資料飛輪。應用越複雜，越常是好幾個 LLM 呼叫接成的網路或圖，代表多步驟的推理；有些應用甚至把 LLM 放進迴圈。作者說替這種系統做飛輪有三個特別的難處：一個節點的錯誤會在後面的節點被放大，所以要早點發現、早點修正；中間與最終的輸出都要評，人工評分的量很大；圖是動態的，結構可能隨輸入或中間結果改變，評估與改進都更複雜。

她列的研究方向都是問句。第一，怎麼實作看得懂圖的評估指標：要不要做階層式的驗證，先驗單一呼叫或節點，再驗路徑或子圖，最後驗整張圖；不同類型的節點該用不同的探針，但類型有哪些、差在哪裡。第二，能不能設計出在圖的關鍵位置動態插入驗證探針的系統，依歷史表現、不確定性或因果分析找出高風險的節點或轉換，在錯誤傳開之前抓到並修正。第三，能不能把動態 few-shot 延伸到圖，依目前的圖結構與任務取回相關的子圖軌跡，例如用懂圖的 embedding 或子圖比對演算法。

三、由資料庫驅動的管線驗證。作者說她好奇能不能把驗證器直接整合進資料庫系統。現在應用開發者要自己做大量工作：記錄並驗證所有軌跡、實作 few-shot 檢索、確保每個驗證器（尤其是用 LLM 的）都順利跑完、把結果寫回資料庫，不管是即時還是在背景跑，都可能很耗運算、很花時間。理想上，資料庫可以替我們做這些事。

她想的問題也有三個。把驗證器做成資料庫的觸發器（trigger）或預存程序（stored procedure），新資料寫入或更新時自動跑程式與 LLM 驗證器，但要怎麼設計才不拖慢資料庫。用資料庫的 view 來算指標，不必把所有指標都算一遍（指標由 LLM 評估時尤其貴），那即時計算和實體化 view（materialized view）各有什麼取捨。替日誌維護語意索引，讓 few-shot 範例檢索得有效率，有沒有簡單的增量更新策略，不必每次整個重建。

Chapter 09 · Wrapping Up

把每一筆生產軌跡，都變成改進的機會

作者說這個框架刻意簡單，不靠複雜的工具或企業級監控系統；重點在挑對指標、持續監控、用資料改進。LLM 判官還不完美，研究也還有得做。

作者的總結是：打造會自我改進的 LLM 應用，靠的是有系統的做法，專注在你的使用情境真正在意的事，並依真實世界的表現迭代。她說這個框架刻意保持簡單，不依賴精密的工具、機器學習平台或企業級的監控系統，強調的是用心挑選指標、持續監控、用資料驅動改進。

"turning every production trace into an opportunity for refinement" 「把每一筆生產軌跡，都變成一次改進的機會。」出自原文的結語。作者說，在所有生產資料都被充分用在之後的執行之前，大家（包括她自己）都不會滿意，而這個希望夠簡單的做法，是往那裡跨出的一大步。

她也說清楚還有工作要做：LLM 當判官並不完美，LLM 應用也可能複雜到需要不同的驗證技巧。拉遠一點看，她覺得現在是打造智慧軟體很令人興奮的時候：會自我改進的應用現在就做得出來，也還有很多問題待答；她最期待的是這條路會由業界實務者、研究者與電腦科學各個子領域的專家一起走。

文末作者感謝 Han Lee 對草稿的回饋、指導教授 Aditya Parameswaran 建議她把最近的 LLMOps 研究寫成一篇詳細的部落格文章，以及同事 Parth Asawa 啟發了資料飛輪這個敘事；她也邀請對這些研究題目有興趣的人和她聯絡合作。

指標從資料裡讀出來，判官靠範例跟上人，應用靠修好的例子變好：三件事轉的是同一個飛輪。 整理自全文

下面這份清單不在原文裡，是整理者把全文的建議壓成的順序，讓你從一個已經上線的 LLM 應用開始轉第一圈。

  1. 讀一批真實輸出，寫下幾個最在意的指標每個指標都是一個是非題；讀到的怪癖（例如一再出現的字眼）也可以寫成指標。
  2. 能用程式算的寫成程式，其餘交給 LLM 判官判官的 prompt 放一個通過、一個不通過的範例；先用 True／False，不急著用 Likert。
  3. 在輸入端加幾道檢查從語言、長度、主題相關這類容易做的開始；不符合的拒絕，或標給人看。
  4. 每筆輸出和各指標的判定都寫進日誌留一欄給人工判定；定期抽樣標註，附上時間戳。
  5. 判官的範例改成從日誌裡挑先依輸入相似度挑；人與 LLM 判得不一樣的例子，優先放進來。
  6. 定期修一批低分輸出，執行時取回記下錯在哪、怎麼改、為什麼；取回最像的修正軌跡，放進應用的 prompt 當範例。
整理者的思考題 · 03

把指標集交給一個 agent 定期檢查，它會先建議拿掉哪一個？

看看你現在追蹤的指標，有沒有哪個和你真正在意的結果（準確率、點擊率、客訴）沒什麼關係。

原文列的三種提案裡，「移除」最容易被忽略。整理者的建議：和關鍵績效指標沒有相關的指標，只會增加標註與維護的負擔，先拿掉它。

Binary metric
二元指標
只答 True 或 False 的指標；作者說它比較容易對齊，人也比較容易判得一致。
Likert scale
李克特量表
1 到 5 這類分級量表；作者說很多人反射性地替判官選它，但通常先從二元開始比較好。
Few-shot example
少樣本範例
放在 prompt 裡示範好與壞的少數例子；作者引用研究說它是改善 prompt 最有效的方法。
Dynamic few-shot retrieval
動態範例檢索
每次呼叫前，從日誌或標註庫挑最相關的範例放進 prompt；判官與應用都可以這樣做。
Judge alignment
判官對齊
讓 LLM 判官的判定對上人的判斷；生產資料會漂移，所以要持續重新評估。
Probe
探針
借自軟體可觀測性的比喻：驗證器放在 LLM 圖的節點上，監看中間與最終輸出。
Classifier node
分類器節點
狀態轉移節點，例如分類意圖再導向子圖；用準確率、precision、recall、F1 與規則比對來驗。
Writer node
寫手節點
生成文字的節點；指標最客製，例如用 LLM 驗證器檢查品牌語氣。
Codegen node
程式產生器節點
產生 SQL 這類程式的節點；用靜態分析、linter、測試，能執行就實際執行來驗。
Per-step accuracy
每一步的準確率
把各節點驗證器的輸出標註後算出的準確率，用來追錯誤怎麼在管線裡累積。
Input validation
輸入驗證
查詢送進 LLM 前先過的檢查，例如身分、主題、語言、敏感資訊；不符合的拒絕或標記。
Postel's Law
Postel 定律
作者借用的原則：送進 LLM 的要嚴格，接受什麼算有效的回應要寬鬆。
Out-of-distribution input
分布外輸入
管線沒被設計來處理的輸入；輸入驗證要把它拒絕或標記。
Active learning
主動學習
優先把最有資訊量的資料送去標註或當範例，例如人和 LLM 判得不一樣的例子。
Uncertainty quantification
不確定性量化
估計模型對一個輸出有多不確定；作者說用 LLM API 時拿不到可靠的機率，是研究問題。
Prompt poisoning
prompt 下毒
有人刻意寫出對抗性的查詢，讓它被選進 prompt 當範例；動態範例的風險之一。
