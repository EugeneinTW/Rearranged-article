DSPY · COMPILING DECLARATIVE LM CALLS · 圖卡＋教材整合版

prompt 不再手寫， 改由編譯器替管線產生DSPy：signature 宣告做什麼，模組包住技巧，teleprompter 依 metric 產生示範

2023 年的語言模型管線，多半靠一段段手寫、試錯出來的 prompt 模板串起來；換一個模型或多接一步，模板就得重調。這篇論文提出 DSPy：每個 LM 呼叫只宣告輸入與輸出欄位，Chain of Thought、ReAct 這類技巧變成可以互換的模組，再由稱為 teleprompter 的最佳化器拿少量訓練資料與一個 metric，自動跑出示範、挑出組合，把整個程式「編譯」成 prompt 或微調。作者在 GSM8K 數學題與 HotPotQA 多跳問答上，用幾行程式、幾分鐘的編譯，讓 GPT-3.5 與 llama2-13b-chat 勝過標準 few-shot 與專家寫的示範。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

框架各自抽象掉一層，DSPy 抽掉的是 prompt 本身

Stanford CS 329Z 第 3 週「Frameworks & Orchestration」那一講，講 DSPy 的 signature、module、optimizer，也講 LangChain／LangGraph 與 LlamaIndex，問框架替你抽象掉了什麼、抽象層級該怎麼選。這篇 2023 年的論文就是 DSPy 的出處，排在這一講的必讀。

做一條 LLM 管線或一個 agent，每一步幾乎都是一次 LM 呼叫，每次呼叫背後都有一段 prompt。各種框架的差別，在於它們替你包起來的是哪一層。依這篇論文附錄 B 的說法，LangChain 與 LlamaIndex 主要包的是現成的鏈、代理、檢索流程與各種工具連線，給需要現成元件的應用開發者用；這些元件裡的 prompt 多半是手寫的模板。DSPy 包的是 prompt 本身：你只宣告每一步吃什麼、吐什麼，prompt 的文字與範例交給一個最佳化器，依你給的 metric 去找。這正是這一講要比較的「框架抽象掉什麼」。

這篇論文的第一作者是 Stanford 的 Omar Khattab，作者群還有 Matei Zaharia、Christopher Potts 等人，2023 年 10 月貼上 arXiv（只有 v1，PDF 頁首標 Preprint），後來發表於 ICLR 2024。DSPy 念作 dee-ess-pie，是同一群人 2022 年 Demonstrate–Search–Predict（DSP）框架的第二代。論文用的模型是 GPT-3.5、llama2-13b-chat 與 T5-Large 這些 2023 年的模型，數字只對它們成立；這一頁更在意的是抽象怎麼設計、編譯怎麼運作。

讀論文和讀部落格不同，這一頁的處理方式也要先說清楚。章節跟著論文的論證走，不跟著節號走：第 1 到 3 章是問題與定位，第 4 到 7 章是程式模型與編譯器，第 8 到 12 章是評估與兩個案例，第 13 章是結論與代價。有兩處合併：第 3.3 節（teleprompter 的用法）和第 4 節第 1 階段（bootstrap 的內部）講的是同一個機制，併成第 6 章；第 4 節第 2、3 階段和第 6 節實際用到的編譯設定，併成第 7 章。數字只用正文、表 1、表 2、附錄 B 的文字與附錄 C 的表；摘要與引言的百分比照原文寫，不自己重算，整理者算的差距會標出來。程式片段都是教學用的精簡版，保留 API 名稱，結構與註解是整理者寫的。論文寫於 2023 年 10 月，沒有提到 LangGraph；這一頁提到它的地方都是整理者的補充。

先把幾個名詞對齊

  • prompt 模板（prompt template）：一段固定的文字，留幾個空格填使用者的輸入；常常夾著幾個手寫的範例。管線裡每一步各有一段。
  • few-shot／in-context learning：不改模型權重，只在 prompt 裡放幾個「輸入與正確輸出」的範例，讓模型照著做。
  • 管線（pipeline）：把一個任務拆成幾次 LM 呼叫，前一步的輸出接到後一步，中間可以穿插檢索、程式執行這類工具。
  • metric：判斷一次輸出好不好的函式，例如答案是否完全相符（exact match）。DSPy 用它決定哪些示範留下來。
  • 微調（finetune）：用資料更新模型的權重。DSPy 把「挑 prompt 裡的示範」和「拿示範去微調」放在同一個框架裡。

論文從當時的熱潮講起。語言模型讓研究者能在更高的抽象層級、用更少的資料做出 NLP 系統，於是出現大量的 prompting 技巧與輕量微調方法：讓模型適應新任務、引導它一步步推理（例如 Chain of Thought），或讓它接上檢索來源與工具。這些技巧多半各自被研究，但越來越多人開始把任務拆成幾次比較好處理的 LM 呼叫，組成多階段的管線或 agent，希望整體表現更好。

問題出在接縫。LM 對每個任務的 prompt 寫法很敏感；在管線裡，好幾次呼叫還得彼此配合，敏感度被放大。結果是現有的管線與熱門的開發框架，都把每一次 LM 呼叫寫成寫死的 prompt 模板：一長串指令加示範，靠人工反覆試錯調出來。作者承認這種做法到處都是，但認為它脆弱、無法擴展，並用了一個類比：

"conceptually akin to hand-tuning the weights for a classifier" 「概念上就像手動調整分類器的權重」：第 1 節對手寫 prompt 模板的評語。

類比的意思可以這樣理解（這段是整理者的展開）：訓練分類器時，沒有人會自己一個一個設定權重，而是定好模型架構、給資料與損失函數，交給最佳化器去找。一段手寫的 prompt 模板，等於一組人工設定的權重：指令怎麼措辭、放哪幾個範例、範例的順序。原文點出它會在四種變動下失效：換到另一條管線、換一個 LM、換一個資料領域，甚至只是換一批輸入。

作者的方向是把建管線這件事，從「操作自由格式的字串」推向「寫程式」：用可組合的模組拼出一張文字轉換圖（text transformation graph），再由編譯器從程式自動產生最佳化過的 LM 呼叫策略與 prompt。後面幾章依序說明要寫的程式長什麼樣、編譯器又做了什麼。

作者說 DSPy 的靈感來自深度學習框架後來形成的共識，有兩點：第一，許多通用的層可以模組化地組成任意複雜的架構；第二，模型的權重用最佳化器訓練，而不是手調。第 2 節也把 Torch、Theano、Chainer 列為榜樣：它們提供的抽象推動了深度學習的發展，作者想為所謂的「基礎模型程式設計」（foundation model programming）提供同樣的概念框架。做法上借用了可微分程式設計的想法，只是對象換成 LM 呼叫而不是神經網路；語法則直接借自 PyTorch。

在 DSPy 裡，LM 被當成一個抽象的文字產生裝置：吃進 prompt 字串、吐出補全的文字。它可以是能做 in-context learning 的大模型（例如 GPT-3.5、Llama2-7b），也可以是可以微調的小模型（例如 T5-base），並可以設一個預設的 LM。一個 DSPy 程式就是一段 Python：拿任務的輸入（要回答的問題、要摘要的論文），經過幾個步驟，回傳輸出。DSPy 提出三個抽象來讓這件事能自動最佳化：

signature

抽象輸入輸出

宣告一個模組吃什麼、吐什麼，例如「問題進、答案出」，不寫要怎麼問 LM。

module

取代手寫的技巧

把 Chain of Thought、ReAct 這類 prompting 技巧做成模組，可以接成任意的管線。

teleprompter

最佳化整條管線

對管線裡所有模組一起最佳化，讓 metric 最高；課程與後來的 DSPy 文件叫它 optimizer。

模組的角色就像神經網路的層，每一個都是能適應任務的元件，負責一種文字轉換，例如回答問題或摘要論文。每個模組都被參數化，能在管線裡反覆 bootstrap 出有用的示範，藉此學到該有的行為。管線的寫法分兩步：先宣告需要哪些模組，再用任何控制流程（if、for 迴圈、例外處理）把它們接起來。這是 define-by-run 的計算圖，圖長什麼樣，取決於程式實際跑了哪些程式碼。

編譯器吃三樣東西：程式、幾筆訓練輸入（標籤可有可無）、一個驗證用的 metric。它在這些輸入上模擬程式的各種版本，替每個模組 bootstrap 出範例的執行軌跡，再用這些軌跡組出有效的 few-shot prompt，或替管線的某幾步微調小型 LM。實際的最佳化由 teleprompter 負責，它們是通用的最佳化策略，決定模組怎麼從資料裡學。名字的由來是「遠距的 prompting」：prompting 這件事被抽象化、自動化，不需要人在旁邊手動介入。

作者把貢獻定位在經驗與演算法兩方面：這是第一個把 prompting 技巧轉成參數化宣告式模組的程式模型，加上一個能最佳化任意管線的編譯器。他們發現很短的程式就能 bootstrap 出會自我改進的多階段系統，用的 LM 小到 llama2-13b-chat 與 7.7 億參數的 T5-Large。不用手寫 prompt、編譯幾分鐘到幾十分鐘，引言報告的提升如下：

第 2 節把 DSPy 放進四條研究脈絡。第一條是 in-context learning，作者稱它為基礎模型程式設計的關鍵機制：尤其在指令微調之後，光靠 prompting 就能引出複雜的行為；以前需要任務專用或人工規則的弱監督，現在也交給 LM 來做。第二條是工具：in-context learning 的方法開始例行呼叫檢索模型、多模態模型、API 與計算機，於是出現 LangChain、Semantic Kernel、LlamaIndex 等工具包，提供把 LM 接上大量工具的現成鏈與代理。作者的評語是，這些工具包同樣有 DSPy 要處理的 prompt 工程問題：它們用手寫的 prompt 模板表達任務專屬的行為。

第三條是 prompt 最佳化。已經有研究用離散最佳化或強化學習找有效的 prompt，但通常只針對單一次邏輯上的 LM 呼叫。DSPy 想把這件事推廣到任意管線：從高層的宣告式 signature 出發，在約束下 bootstrap 出高品質的多階段示範。teleprompter 可以用交叉驗證這類模型選擇技巧，原則上也可以用強化學習、LM 回饋，或學習式、貝氏的超參數最佳化方法。第四條是寫法上的傳承：作者效法 Theano、PyTorch、HuggingFace 的論文，用基準數字加上一些質性說明來支持一個程式模型。

附錄 B 專門比較 LangChain 與 LlamaIndex。作者先說焦點不同：DSPy 要處理的是為新的 LM 計算圖做 prompt 工程這個根本問題；LangChain 與 LlamaIndex 通常幫的是需要現成元件的應用開發者，提供熱門、可重用的管線實作（特定的代理、特定的檢索流程），以及工具（接各種資料庫、替代理實作長期與短期記憶）。DSPy 提供的則是可以組合的核心運算子：signature 抽象 prompt，module 抽象 prompting 技巧，teleprompter 最佳化把模組串起來的任意命令式程式碼。它的目標是讓研究者與實務工作者快速做出新的管線，並用自動編譯（自我改進）而不是手動 prompt 工程達到高品質。

接著是那份非正式統計。2023 年 9 月底，作者發現 LangChain 的程式碼裡有 50 個超過 1,000 字元的字串，大多是 prompt；DSPy 裡一個都沒有。LangChain 還有相當多的 Python 檔專門放任務模板與 prompt 工程：12 個 prompts.py 與 42 個 prompt.py。反過來，DSPy 函式庫在當時沒有任何一個任務的手寫 prompt 示範。幾個具體例子：LangChain 的 Program-Aided Language Model（PAL）鏈用一個 3,982 字元的模板，裡面有 8 道數學應用題與對應的程式；SQL 查詢的 prompt 為 Oracle、GoogleSQL、DuckDB、Crate、MySQL 各寫一份，平均 1,058 字元；「附來源的問答」與 Graph_QA 的模板平均 1,337 與 722 字元。作者的看法是，專家寫的 prompt 有它的用處，但自動 bootstrap、能隨 LM 與任務調整的 prompt 更有力，也比在程式庫裡替每個資料庫供應商各寫死一段 prompt 更模組化。

DSPy 程式不寫自由格式的 prompt，而是用自然語言的 signature 把工作交給 LM。signature 是一個帶自然語言型別的函式宣告：一段簡短的宣告式規格，說明一次文字轉換要做什麼（例如「吃進問題、回傳答案」），而不是某個 LM 該被怎麼 prompt。形式上，它是一組輸入欄位、一組輸出欄位，再加一個選填的指令；每個欄位有名字，也可以附上前綴與描述，但描述通常省略。欄位預設裝的是自由文字；作者正在試驗讓欄位宣告型別（例如 bool、int），在寫論文的當時還不是核心功能。

欄位的名字就是語意。DSPy 會從欄位名推斷每個欄位的角色，例如編譯器會用 in-context learning 把 question 和 answer 當成不同的東西，並在反覆編譯中調整用法。實務上可以用簡寫：

signature 的簡寫 · 教學用精簡版 
# 宣告欄位，不寫 prompt：這一行就是一個完整的問答程式
qa = dspy.Predict("question -> answer")
pred = qa(question="台灣最高的山是哪一座？")
pred.answer            # 輸出欄位的名字，就是取值的名字

# 欄位名換掉，任務就跟著換
translate = dspy.Predict("english_document -> french_translation")

DSPy 會解析這種寫法，把欄位名展開成給 LM 的有意義指令；english_document -> french_translation 就會變成英翻法的 prompt。作者說 signature 比 prompt 多兩個好處：第一，它可以被編譯成會自我改進、能配合所在管線的 prompt 或微調，做法主要是替每個 signature bootstrap 有用的示範（第 6 章）；第二，它處理結構化的格式與解析，減少、最好是免除使用者程式裡脆弱的字串操作。

需要更多控制時，signature 可以寫成 Python 類別（附錄 A）：類別的 docstring 就是指令，每個欄位用 InputField、OutputField 宣告並可附描述。下面是附錄 A 那個「依脈絡產生搜尋查詢」例子的精簡版；附錄 A 也提到，輸出欄位可以選擇宣告成 bool、int、float、list、dict，這在當時是開發中的功能。

signature 只是介面。要用它，得宣告一個帶著它的模組；最核心的就是 Predict。Predict 內部存三樣東西：傳入的 signature、一個選填的 LM（預設是空的，代表用全域的預設 LM），以及一串示範（一開始是空的）。它和 PyTorch 的層一樣是可以呼叫的函式：收下對應輸入欄位的關鍵字參數，組出實作這個 signature 的 prompt 並放進適當的示範，呼叫 LM，再把輸出解析回各個輸出欄位。當 Predict 發現自己處在編譯模式，還會記下每次的輸入與輸出，也就是 trace，交給 teleprompter 做 bootstrap。附錄 D.1 的簡化虛擬碼就是這幾步，外加一個判斷「現在是不是在編譯」的 if。

一般做法是把任務的細節直接寫進 prompt，例如手寫幾個 few-shot 範例。DSPy 的模組反過來，把 prompting 技巧翻成支援任何 signature 的模組化函式。內建的有 ChainOfThought、ProgramOfThought、MultiChainComparison、ReAct，分別推廣自 Wei 等人、Chen 等人、Yoran 等人與 Yao 等人的技巧，也把零樣本 prompting、讓模型自己產生推理這些想法，推廣成能 bootstrap 任意多階段管線的參數化模組。它們可以互相替換來實作同一個 signature：把上一章那一行程式的 Predict 換成 ChainOfThought，系統就會在填輸出欄位之前先一步步推理。

這些模組都只有幾行：把使用者的 signature 展開成新的 signature，再呼叫一次或幾次 Predict。以 ChainOfThought 為例，它把「輸入 → 輸出」改成「輸入 → rationale（推理）、輸出」，推理欄位的前綴是一句「Reasoning: Let's think step by step.」，然後用改過的 signature 宣告一個 Predict，呼叫時把輸入原封不動轉交給它。作者說這已經是一個完整的模組，能替任何 LM 或任務學會有效的 few-shot prompting，並拿附錄 C 那些又長又手寫的推理 prompt 來對照。

ChainOfThought 的內部 · 依附錄 D.2 的精簡版 
class ChainOfThought(dspy.Module):
    def __init__(self, signature):
        # 在所有輸出欄位前面，多插一個推理欄位
        rationale = dspy.OutputField(prefix="Reasoning: Let's think step by step.")
        signature = dspy.Signature(signature).prepend_output_field(rationale)
        self.predict = dspy.Predict(signature)     # 裡面還是一個 Predict

    def forward(self, **kwargs):
        return self.predict(**kwargs)              # 輸入原樣轉交

模組之外還有工具，也就是會執行計算的模組。檢索模型透過 dspy.Retrieve 接入，當時內建支援 ColBERTv2、Pyserini 與 Pinecone；作者也在試驗 dspy.SQL（執行 SQL 查詢）與 dspy.PythonInterpreter（在沙箱裡執行 Python）。

模組可以組成任意的管線，介面是 define-by-run，直接取法 PyTorch 與 Chainer：先在初始化時宣告需要的模組，讓 DSPy 能追蹤它們、之後拿來最佳化；再在 forward 方法裡用任意程式碼呼叫這些模組。論文用一個簡單但完整的 RAG 系統示範：

一個完整的 RAG 程式 · 教學用精簡版 
class RAG(dspy.Module):
    def __init__(self, num_passages=3):
        self.retrieve = dspy.Retrieve(k=num_passages)          # 工具：用預設的檢索設定
        self.generate_answer = dspy.ChainOfThought("context, question -> answer")

    def forward(self, question):
        context = self.retrieve(question).passages             # 先檢索三段
        return self.generate_answer(context=context, question=question)

編譯一個 DSPy 程式，通常就是呼叫一個 teleprompter：一個最佳化器，收下程式、訓練集與 metric，回傳一個新的、最佳化過的程式。不同的 teleprompter 用不同的策略（第 7 章）。

DSPy 對訓練集的要求很低。它可以很小，小到只有幾筆，資料多當然能做更強的最佳化；它可以不完整，只有輸入值是必要的。管線中間步驟的標籤不需要，除非 metric 要用到；實務上作者通常最多只假設程式的最終輸出有標籤。作者認為這種標籤效率是模組化的關鍵：做一條新管線，只要重新編譯新程式的程式碼，不必為新管線的每一步另外標註資料。

BootstrapFewShot 內部做的事，寫在第 4 節的第 1 階段「產生候選」與附錄 E.1 的簡化虛擬碼。編譯器先遞迴地找出程式裡所有獨一無二的 Predict 模組（稱為 predictor），包括包在其他模組裡的。對每個 predictor，teleprompter 可以替它的參數產生候選值：指令、欄位描述，以及最重要的示範（輸入與輸出的配對）。這一版的 DSPy 專注在示範，作者發現類似拒絕取樣（rejection sampling）的簡單做法，就能 bootstrap 出很有效的多階段系統。BootstrapFewShot 是其中最簡單、但不陽春的一個：

1
決定誰來跑teleprompter 模擬一個 teacher 程式；沒有指定 teacher 時，就用正在編譯的程式本身的零樣本版本。學生與老師的 Predict 模組依名稱一一對上。
2
在訓練輸入上跑逐筆拿訓練例的輸入去跑 teacher，可以跑一次以上，也可以用較高的溫度取樣。
3
記下多階段的 trace在編譯模式下，整個執行過程裡每一次 Predict 呼叫的輸入與輸出都被透明地記下來，而且是執行緒安全的。
4
用 metric 篩拿程式的 metric 檢查這一次的最終預測（metric 也看得到 trace），只留下整條管線一起通過的那幾次。
5
存成示範留下的 trace 裡每一步，都變成對應 predictor 的一個候選示範；不好的例子丟掉。收集夠了就停。

作者說，丟掉壞例子、留下好例子當示範，這些設計決定都讓使用者控制。至於為什麼行得通，他們的解釋是：LM 本身很不可靠，但在多階段設計的解空間裡搜尋，效率反而不錯；一個拆得好的程式，通常找得到至少幾筆訓練例，讓 LM 能通過 signature 與 metric 的約束。需要的話，還可以反覆 bootstrap。

Chapter 08 · Goals of Evaluation

比較的單位是「程式加編譯策略」，不是單獨一個 LM

框架可以比運算效率、開發效率、好不好懂；這篇只量一件事：手寫、任務專用的 prompt 對做出好系統到底有多必要。三個假設分別講品質、適應不同 LM、以及探索複雜管線。

第 5 節先承認，一個程式設計框架可以從很多面向評估：運算效率、開發者的效率、程式與概念是否直觀等等。這篇論文只挑作者認為當下 LM 管線最迫切的問題：要做出高效能的系統，手寫、任務專用的 prompt 到底有多必要。評估要檢驗三個假設：

H1
可以取代用 DSPy 簡潔、定義清楚的模組取代手寫的 prompt 字串，品質與表達力都不會下降。
H2
更能適應把模組參數化、把 prompting 當成最佳化問題，讓 DSPy 更能適應不同的 LM，而且可能勝過專家寫的 prompt。
H3
更好探索模組化讓人能更徹底地探索複雜的管線，找出有用的效能特性，或配合細緻的 metric。

作者希望這組評估能讓問題的問法轉個方向。「不同的 LM 在 GSM8K 上比起來如何」是一個沒有講清楚的問題；「用程式 P、以策略 S 編譯之後，它們在 GSM8K 上比起來如何」才是一次定義清楚、可以重現的執行。長遠的目標，是降低現代 AI 裡「精巧的 prompt 手藝」的份量，讓位給新的、模組化、可組合的程式與最佳化器。

vanilla = dspy.Predict("question -> answer")          # 一步：直接答
cot     = dspy.ChainOfThought("question -> answer")   # 兩步：先推理再答

class ThoughtReflection(dspy.Module):
    def __init__(self, num_attempts=5):
        self.predict = dspy.ChainOfThought("question -> answer", n=num_attempts)
        self.compare = dspy.MultiChainComparison("question -> answer", M=num_attempts)

    def forward(self, question):
        attempts = self.predict(question=question).completions    # 五條推理鏈，各帶一個答案
        return self.compare(question=question, completions=attempts)

reflection = ThoughtReflection(num_attempts=5)

reflection 的做法是：從 LM 取樣五條推理鏈（連同各自的答案），交給內建的 MultiChainComparison 模組平行比較，它推廣自 Yoran 等人 2023 年的做法。這個模組看過五次嘗試裡的模式，再產生一個新的答案。作者特別強調，這裡用到的模組全是通用的，沒有任何一個是為數學題或為某個特定 LM 寫的。

背景

MultiChainComparison 和多數決不一樣

第 7 章的 ensemble 用一個函式（dspy.majority）數票，選出現最多次的答案。MultiChainComparison 則是一個 LM 模組：它讀過五條推理與答案，再寫出新的答案，所以有機會發現「五條裡有兩條算錯同一步」這類模式。這個對照是整理者加的，原文只說它「考量五次嘗試的模式」產生新答案。

編譯設定用的是第 7 章那一組：none、fewshot、bootstrap、bootstrap×2、+ensemble。GSM8K 本身附有人寫的推理鏈，但預設的訓練集不含它們；作者另外做了一份把人寫推理加進去的 trainset_human_CoT，兩份訓練集可以互換傳給同一個 teleprompter。這給了一個很直接的對照組：自動 bootstrap 的示範，比不比得上人寫的推理鏈？

關鍵觀念 · 二

vanilla 把推理寫進了答案欄

附錄 F 的圖 9 是 Llama2-13b-chat 的 vanilla 程式經過 bootstrap×2 之後的 prompt。signature 仍是 question -> answer，格式也只有 Question 與 Answer 兩欄；但被選中的示範，Answer 欄先寫出單價乘數量、折扣、相減的算式，最後才給數字。沒有人叫模型推理，是 bootstrap 留下了「答對的那幾次」，而答對的那幾次剛好把算式寫在答案欄裡。

整理者的讀法：編譯最佳化的是 metric 量到的東西。metric 只抽最後的數字，所以「在答案欄裡推理」完全合法；如果 metric 要求答案欄只能有數字，同樣的編譯就會挑出不一樣的示範。

作者也拿其他論文的數字做了非正式比較，條件各不相同，只能當參考。Zhang 等人（2022）報告 text-davinci-002 為 48%，和這裡 Llama2-13b-chat 的結果相近；codex 用人工 CoT 是 59.4%，用自動 CoT 是 62.8%。Wang 等人（2022b）用 PaLM 540B 做 CoT 是 57%，加上 self-consistency 變成 74%。Llama 2 的作者報告 llama2-13b 為 28.7%、34b 為 42.2%、70b 為 56.8%；作者指出，他們用 13b 的程式可以和 34b 的結果相比，而且沒有用人寫的推理鏈。Zhao 等人（2023b）報告 2023 年 4 月的 gpt-3.5-turbo 用 CoT 是 80.8%。GPT-4 的技術報告說 GPT-3.5 為 57.1%、GPT-4 為 92%，但也註明 GPT-4 的預訓練資料包含 GSM8K 訓練集的一部分。

提醒

摘要裡的百分比怎麼來的，論文沒有寫

摘要說，編譯後的管線通常勝過標準 few-shot prompting 超過 25%（GPT-3.5）與 65%（llama2-13b-chat），勝過專家示範的管線最多 5–46% 與 16–40%。論文沒有給這些數字的算法（例如是相對還是絕對的差距），這一頁照抄，不自己從表裡重算。

class BasicMultiHop(dspy.Module):
    def __init__(self, passages_per_hop=3):
        self.retrieve = dspy.Retrieve(k=passages_per_hop)
        self.generate_query = dspy.ChainOfThought("context, question -> search_query")
        self.generate_answer = dspy.ChainOfThought("context, question -> answer")

    def forward(self, question):
        context = []
        for hop in range(2):                               # 兩跳：每跳依目前的脈絡寫新查詢
            query = self.generate_query(context=context, question=question).search_query
            context += self.retrieve(query).passages        # 脈絡越疊越多
        return self.generate_answer(context=context, question=question)

multihop = BasicMultiHop(passages_per_hop=3)

編譯器沿用 GSM8K 那一組，另外加兩個 teleprompter 的組合。ReAct 從先前的一次 bootstrap 出發，再用 BootstrapFewShotWithRandomSearch 編一次（表中的 bootstrap×2）。multihop 則從先前那次 bootstrap 出發，用 T5-Large 微調：把 bootstrap 編好的程式當 teacher，用 BootstrapFinetune、以答案完全相符為 metric，目標模型是 t5-large。

關鍵觀念 · 三

編譯改得了模型寫的查詢，改不了原題

整理者的讀法：CoT_RAG 的 Psg 不管怎麼編譯都是 36.0，因為它檢索用的是使用者的原始問題，這一步沒有 LM 參與，編譯只能改善「拿著同樣三段文字怎麼回答」。multihop 的查詢是 generate_query 模組寫出來的，是 LM 的輸出，也就是編譯碰得到的地方；bootstrap 之後，它的段落準確率從 fewshot 的 38.3 與 32.0 升到 47.0 與 48.3。

作者對 CoT_RAG 的診斷是「完全依賴檢索器直接用原題找段落」；把查詢交給一個模組，是他們的解法。

作者也列了幾篇近期論文在 HotPotQA 上的數字，同時提醒評估方法與測試樣本差異很大：Si 等人（2022）用 CoT prompting 是 25.2% EM；Sun 等人（2022）用 PaLM-62B 先「背誦」證據段落再回答，是 26.5%；Wang 等人（2022a）用 PaLM-540B 加 self-consistency，是 33.8% EM 與 44.6% F1；Yao 等人（2022）的 ReAct 用 PaLM-540B 是 27.4% EM，用 text-davinci-002 搭配維基百科 API 搜尋是 30.8，再加一步帶 self-consistency 的 CoT 推到 35.1%，作者說這有點像他們的 ensemble；Trivedi 等人（2022）用 code-davinci-002 的管線在 500 題樣本上報告 49%。

思考題 · 03

你的 RAG 管線裡，哪幾步是 LM 產生、編譯得到的？

把管線畫出來，標出每一步的輸入是誰寫的：使用者、程式，還是 LM。

只有 LM 產生的那幾步（改寫查詢、挑段落、寫答案）有示範可以 bootstrap。如果召回卡住，先看檢索的查詢是不是還直接用原題；表 2 的 CoT_RAG 就是這種情況，換成讓模組寫查詢之後段落準確率才動。

整理者的讀法

放回這一講：框架抽象掉哪一層

下面是整理者的連結，論文沒有這樣講。附錄 B 其實區分了兩種抽象：LangChain 與 LlamaIndex 抽象的是現成的流程與整合（鏈、代理、資料庫連線、記憶），DSPy 抽象的是 prompt、prompting 技巧與 prompt 工程這個過程本身。兩者不互斥，DSPy 自己也有接 ColBERTv2、Pyserini、Pinecone 的檢索模組。選抽象層級時，可以先問最常變動的是什麼：常換模型、常改管線步驟，把 prompt 交給編譯器的好處最大；主要工作是接資料源與工具，現成元件省的時間最多。LangGraph 這類管控流程與狀態的工具，論文沒有討論。

一定要準備大量標註資料嗎？
不用。第 3.3 節說訓練集可以只有幾筆，而且可以不完整，通常最多只需要最終輸出的標籤。HotPotQA 的 T5-Large 只用了 200 筆標註的輸入加 800 筆沒有標籤的問題；沒有答案時，可以改用 answer_passage_match 這類不需要標籤的 metric。
編譯一次要多久？
第 6 節說通常幾分鐘，最多幾十分鐘：即使比較貴的設定，也只要把程式跑幾千次（例如 10 到 20 次試驗、每次 150 到 300 筆驗證例），而且可以平行。
DSPy 只會產生 prompt 嗎？
不只。第 4 節說 prompting 與微調在 teleprompter 裡是統一的；BootstrapFinetune 用 bootstrap 出的示範更新每個 predictor 的 LM 權重，第 12 章的 T5-Large 就是這樣編出來的。
prompt 是編譯的產物：人寫的是程式與 metric，示範與措辭由最佳化器去找。 整理自第 1、4、8 節

Reference · 名詞速查

關鍵名詞與它們在論文裡的位置

先列程式模型的三個抽象與它們的零件，再列編譯器與 teleprompter，最後是兩個案例的資料集與指標。

signature
簽章
用自然語言寫的函式型別：輸入欄位、輸出欄位、選填的指令；只說做什麼，不說怎麼 prompt（第 3.1 節）。
module
模組
帶著 signature、可以呼叫的元件；內建模組把 prompting 技巧包成支援任何 signature 的函式（第 3.2 節）。
teleprompter
最佳化器
拿程式、訓練集與 metric，回傳最佳化過的新程式；課程與後來的 DSPy 文件稱為 optimizer（第 3.3、4 節）。
compile
編譯
對一個 DSPy 程式呼叫 teleprompter，產生示範、挑選組合或微調權重的整個過程。
program
程式
繼承 dspy.Module 的類別：在 __init__ 宣告模組，在 forward 用任意 Python 控制流程呼叫它們。
define-by-run
邊跑邊定義
計算圖由實際執行的程式碼決定，借自 PyTorch 與 Chainer；所以可以用 if、for 與例外處理接模組。
text transformation graph
文字轉換圖
論文對 LM 管線的抽象：LM 透過宣告式模組被呼叫的命令式計算圖。
demonstration
示範
一筆輸入與輸出的配對；對凍結的 LM 是 few-shot prompt，對要微調的 LM 是訓練資料，是模組最重要的參數。
bootstrap
自舉產生示範
讓程式在訓練輸入上自己跑，把通過 metric 的那幾次執行裡每一步的輸入輸出留下來當示範。
trace
執行軌跡
編譯模式下記下的每一次 Predict 呼叫的輸入與輸出；metric 看得到它。
metric
評分函式
判斷一次預測好不好的函式，可以是 EM、F1，也可以是一整個 DSPy 程式。
teacher
老師程式
bootstrap 時實際拿來跑、產生示範的程式；沒指定時是被編譯程式的零樣本版本，也可以是已編譯的程式或大模型的 ensemble。
Predict
核心模組
存 signature、LM 與示範；組 prompt、呼叫 LM、解析欄位，編譯時記 trace。
ChainOfThought
先推理再答
在輸出欄位前插一個 rationale 欄位的模組，裡面是一個 Predict（附錄 D.2）。
MultiChainComparison
多鏈比較
讀過 M 條推理與答案，再產生新答案的模組；GSM8K 的 reflection 程式用 M＝5。
ReAct
推理加行動的代理
會使用工具的多步代理，DSPy 內建；HotPotQA 用檢索當工具、最多 5 輪。
dspy.Retrieve
檢索工具
接檢索模型的模組；當時內建 ColBERTv2、Pyserini、Pinecone。
LabeledFewShot
隨機示範
從有標籤的訓練集隨機抽 k 筆當示範；實驗裡的 fewshot 設定用 k＝8。
BootstrapFewShot
基本的 bootstrap

BootstrapFewShotWithRandomSearch
bootstrap 加隨機搜尋
洗牌訓練集、多次 bootstrap 出候選程式，在驗證集上挑最高分（附錄 E.2）；實驗裡的 bootstrap 設定。
BootstrapFinetune
bootstrap 後微調
把 bootstrap 出的示範拿去更新 LM 權重；HotPotQA 用它編出 T5-Large 版本。
ensemble
整合
第 3 階段的最佳化：平行跑多個編好的程式，用多數決等函式合成；實驗取前 7 名。
GSM8K
