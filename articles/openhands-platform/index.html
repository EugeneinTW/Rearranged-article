給 agent 一套 開發者的工具OpenHands：用一條事件流串起 agent 與沙箱， 再用 15 個基準量它

coding agent 要能寫程式、跑指令、上網查資料，還不能弄壞使用者的電腦。這篇 ICLR 2025 的論文介紹開源平台 OpenHands（早期叫 OpenDevin）：agent 只讀一條事件流、送出動作，動作在 Docker 沙箱裡的 bash、IPython 與瀏覽器執行，結果寫回成觀察；工具寫成 Python 函式給每個 agent 共用，agent 之間可以委派；最後用 15 個基準與整合測試量它。這一頁交代每個元件怎麼運作，以及每張表的數字怎麼讀。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

coding agent 的骨架，從一個開源平台看起

Stanford CS 329Z 第 9 週「Coding & Software Agents」那一講（Coding Agents & Proactive Agents 分區），談 coding agent 從頭到尾怎麼運作、幾個代表系統的架構，以及怎麼評估它們。這篇 OpenHands 論文是那一講的兩篇必讀之一：它把一個 coding agent 需要的零件做成開源平台，一件一件攤開。

Chapter 01 · Introduction

讓 agent 像開發者一樣，透過軟體做事

agent 框架通常有三塊：介面、環境、互動機制。作者主張軟體是人類做事最有力的方式，所以也是 agent 最好的介面，並點出三個難題：怎麼改複雜的程式、怎麼邊做邊查資料、怎麼不弄壞使用者的系統。

引言從 LLM agent 講起：能感知並作用於外部環境的 AI 系統，正往開發軟體、瀏覽真實網站、做家事，甚至做科學研究這些複雜任務前進。任務越難，開發與評估 agent 也越難，所以出現了許多開源框架。作者歸納，這些框架通常包含三樣東西：agent 和世界互動的介面（例如 JSON 格式的函式呼叫，或直接執行程式）、agent 運作的環境，以及人與 agent、agent 與 agent 之間的互動機制。各框架怎麼替開發者省事，作者整理在表 1 與附錄 C（第 12 章）。

接著作者換個角度，從人怎麼和世界互動來想 agent 該怎麼設計。引言寫：

"The most powerful way in which humans currently interact with the world is through software" 「人類目前和世界互動最有力的方式，是透過軟體」：第 1 節的說法，後面接著說軟體支撐了從民生物流到科學、科技與 AI 本身的一切。

軟體這麼有力，又已經有一整套開發、使用、部署它的工具，作者因此認為軟體是讓 agent 以複雜方式作用於世界的理想介面。可是要做出能有效開發軟體的 agent，有三個它自己的難題：

難題 1

在複雜的系統裡寫程式、改程式

程式庫很大、檔案很多的時候，agent 要怎麼有效地建立與修改程式碼。

難題 2

邊做邊蒐集需要的資訊

除錯或做任務時，agent 手上要有工具，能隨時查到完成任務需要的資訊。

難題 3

安全，不傷到使用者的系統

開發的過程不能對使用者的電腦造成負面的副作用。

OpenHands 是作者的回答：一個由社群推動的平台，用來開發透過軟體和世界互動的通用與專門 agent。註腳說，它一開始受到 Cognition.ai 的 AI 軟體工程師 Devin 啟發，之後靠各方的社群貢獻，很快擴展到軟體工程以外的用途。引言列了五個功能，本頁各有對應的章：

第 2.1 節先定義 agent：它感知環境的狀態（例如先前的動作與觀察），在解使用者交代的任務時產生要執行的動作。在 OpenHands 裡，狀態（state）是一個資料結構，裝著 agent 執行時需要的所有資訊。它的核心就是事件流：依時間排列的過去動作與觀察，既有 agent 自己的動作，也有使用者的互動，例如指示與回饋。事件流之外，state 還記著一些輔助資訊：LLM 呼叫累積的成本、追蹤多 agent 委派用的中繼資料（第 6 章），以及其他執行參數。

動作的設計受 CodeAct（Wang 等 2024a）啟發：agent 透過一組核心的通用動作和環境連接。IPythonRunCellAction 與 CmdRunAction 讓 agent 在沙箱裡執行任意的 Python 程式與 bash 指令；瀏覽器的互動則用 BrowserGym 引入的一種瀏覽專用語言。作者說選這幾個動作，是因為它們涵蓋了人類軟體工程師與分析師大部分的工作，又保有彈性。瀏覽器動作的名字有兩種拼法：第 2.1 節正文寫 BrowserInteractiveAction，圖 2 與圖 3 寫 BrowseInteractiveAction；本頁的程式照圖 3。

作者說，以程式語言為基礎的動作空間夠強也夠有彈性，各種形式的工具（Python 函式、REST API）都能用，而且可靠、好維護。它也相容需要預先定義工具清單的 tool-calling agent：工具就用 Python 寫成函式，再透過 JSON 格式的函式呼叫提供給 agent。遇到沒有現成 API 的任務，agent 甚至能自己寫 Python 函式，替自己造工具。觀察則是 agent 看到的環境變化，例如先前動作的執行結果，或使用者傳來的文字訊息。

要實作一個新的 agent，核心是 step 函式：輸入目前的 state，依 agent 自己的邏輯產生一個合適的動作。圖 3 是一個最小的例子，下面是教學用的精簡版：

class MinimalAgent:
    def reset(self):
        self.system_message = "你是一個有幫助的助理……"

    def step(self, state):
        messages = [{"role": "system", "content": self.system_message}]
        for prev_action, obs in state.history:       # 事件歷史：一個動作配一個觀察
            messages.append(get_action_message(prev_action))
            messages.append(get_observation_message(obs))
        response = self.llm.do_completion(messages)  # 讓 LLM 想下一步
        action = self.parse_response(response)
        if 是結束指令: return AgentFinishAction()
        if 是 bash:    return CmdRunAction(command=...)
        if 是 Python:  return IPythonRunCellAction(code=...)

第 2.3 節從 SWE-Agent（Yang 等 2024）講起：它強調，精心設計的 agent-computer interface（ACI，為特定任務做的專門工具）對解複雜任務很重要。作者說麻煩在後頭：要建立、維護、散佈一大批工具，工程上很吃力，尤其想讓不同的 agent 實作都能用的時候（第 6 章）。所以他們做了 AgentSkills 函式庫，一個增強 agent 能力的工具箱，提供基本的 bash 指令或 Python 程式不容易直接做到的功能。

設計上它是一個 Python 套件，裡面是一個個工具函式，會自動匯入 Jupyter IPython 環境（第 3 章）。定義一個 Python 函式就是一個工具，作者說這降低了社群成員貢獻新工具的門檻；Python 套件的通用性，也讓不同的 agent 實作都能透過核心動作 IPythonRunCellAction 使用這些工具。

收錄的原則寫得很明確。AgentSkills 不打算把每個可能的 Python 套件都包一層、再教 agent 怎麼用：LLM 本來就知道 pandas 能讀 CSV 檔，就不需要另做一個工具，教它讀同一種格式。只有兩種情況才加一個新技能，原文用「and/or」連接，符合一條就收：

01

LLM 不容易直接寫程式做到

例如編輯程式碼、取代檔案裡特定的幾行。

02

需要呼叫外部模型

例如語音轉文字的模型，或專門編輯程式的模型。

當時的技能包括改編自 SWE-Agent 與 Aider 的檔案編輯工具，例如從指定的行開始修改現有檔案的 edit_file，以及切到檔案其他段落的 scroll_up、scroll_down；還有讀多模態文件的工具，例如用視覺語言模型（如 GPT-4V）從圖片擷取資訊的 parse_image，以及讀 PDF 文字的 parse_pdf。附錄 I 列了 OpenHands v0.6 時的完整清單，下表的分類是整理者加的：

附錄 E 從軟體工程的老做法講起：整合測試（Leung 與 White 1990）長期被用來確保軟體的品質。作者說 agent 和輸入輸出單純的 LLM 不同，是一大套複雜的軟體，開發過程中很容易混進小錯誤，傷到最後的任務表現。跑完整的評估（第 7 到 10 章）是衡量退步的最終標準，但每改一次程式就跑一次，慢得也貴得跑不起：註腳說，用 gpt-4o 跑一次 SWE-Bench Lite 大約 600 美元。

所以他們做了一個端到端的 agent 測試框架，測 prompt 的回歸、動作與沙箱環境，作者說這是他們首創的。它結合兩件事：軟體工程的整合測試，以及把基礎模型換成假的（mock），讓行為變成確定的。

1
定義測試開發者定義任務與預期結果，例如「修正 bad.txt 這份文件裡的錯字」；任務經 OpenHands 執行完，輸出和事先準備的 gold file 比對。
2
攔下 LLM 呼叫框架攔截所有 LLM 呼叫，依 prompt 完全相符，回傳事先存好的回應；結果一致，也少用真的 LLM，省下成本。
3
回應從哪裡來新增測試或改了 prompt 時，由一支腳本產生並存下成對的 prompt 與回應。一般的測試會稍微調整 prompt 來沿用舊的回應；改動大到影響任務的處理時，就用真的 LLM 重新產生。
4
自動跑每個 pull request 與 main 分支上的每次 commit 都自動排程測試，跑在 Linux 與 Mac、local、SSH 與 exec 三種沙箱，以及多個 agent 上。

作者列了三個好處：

回歸

prompt 的回歸測試

存下的 prompt 與回應，方便追蹤每次改動，也讓新加入的成員看懂 LLM 實際上怎麼互動。

多平台

每次改動都在多種環境跑

自動排程到每個 pull request 與 main 的 commit，涵蓋不同作業系統、沙箱與 agent。

抓錯

抓得到三種錯

prompt 生成、訊息傳遞、沙箱執行裡的錯誤都抓得到，作者說維持了高的測試覆蓋率。

表 1 的最後一欄 Agent QC（品質控制）指的就是這件事：判斷標準是框架有沒有整合測試來確保整體的軟體品質。12 個框架裡打勾的只有 AutoGPT、MetaGPT 與 OpenHands（第 12 章）。

提醒

錄好的回應測的是程式，不是模型

整理者的提醒：模型換成錄好的回應之後，測試抓的是 prompt 組裝、訊息傳遞、沙箱執行這些程式的錯；模型本身的能力有沒有退步，還是要靠第 7 到 10 章那種完整的評估。附錄 E 自己也說，完整的評估才是衡量退步的最終標準。

思考題 · 03

你改 prompt 的時候，怎麼知道沒改壞？

回想你的 agent 最近一次改 system prompt 或工具說明，之後是怎麼確認沒有退步的。

附錄 E 的做法可以縮小來做（整理者的建議）：挑三五個代表任務，第一次用真的模型跑、存下每一次呼叫的 prompt 與回應，之後改程式就用存下的回應重播；prompt 改了對不上的地方，就是該重錄、也該看一眼差在哪裡的地方。

自動產生工作流程

倫理聲明說，今天的 AI agent 多半還是研究成品，還不能在真實世界可靠地完成複雜、長時程的任務；隨著表現進步、越來越多部署到真實世界，它們可能大幅提升生產力，也可能對社會帶來重大的安全風險。作者說 OpenHands 從三方面幫忙降低風險：

1
系統性的評估在大規模部署之前，找出並處理這些 agent 的風險。
2
促成人與 agent 的互動不讓 agent 在沒有監督的情況下自主運作。
3
開放給研究者讓各地的研究者用得到最好的一套 agent，做打造安全又有用的 agent 所需要的前沿安全研究。
