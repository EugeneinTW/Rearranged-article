11 / 12錄好 LLM 回應的整合測試
LLM 換成錄好的回應，測試就能常常跑
附錄 E：完整跑一次基準太慢太貴（SWE-Bench Lite 用 gpt-4o 約 600 美元），所以每次改程式跑的是端到端的整合測試，LLM 呼叫全部被攔下來
Step 1　定義任務
例如修正 bad.txt 的錯字；
事先備好一份 gold file
Step 2　攔下 LLM 呼叫
測試時每一次 LLM 呼叫，
都不送給真的模型
Step 3　比對 prompt
完全相符，就回傳存好的回應
結果變成確定的
Step 4　比對 gold file
執行完的輸出要和它一樣
驗證輸出
Step 5　每次改動都跑
每個 PR 與 main 的 commit；
Linux、Mac 與三種沙箱
留下來的
成對存下的 prompt 與回應：它就是 prompt 的回歸測試，每次改動都對得出差在哪裡，新加入的成員也能從它看懂 LLM 實際上怎麼互動。
三件要知道的事
確定又便宜
同樣的 prompt 永遠拿到同樣的回應，
測試結果一致；少打真的 LLM，
也省下成本。
作者點名的兩個問題：不確定性與高成本。
prompt 大改，就要重錄
一般的測試會稍微調整 prompt 沿用舊回應；
影響任務處理的大改動，
要用真的 LLM 重新產生、存下。
由一支腳本負責產生與儲存。
抓得到三種錯
prompt 生成、訊息傳遞、沙箱執行裡的錯，
每次開 PR 就會被抓出來；
作者說維持了高的測試覆蓋率。
表 1 的 Agent QC 欄指的就是它。

12 / 12平台之後的五個方向
平台把骨架搭好，agent 本身還得更強
第 5 節、附錄 A、B：作者把 OpenHands 的貢獻收成五樣，也點名目前 agent 的弱點；上面三條原則是整理者歸納的，下面五格照附錄 A
01　給 agent 開發者的介面
程式、終端機、瀏覽器，
就是 agent 的動作空間
三種核心動作都用程式表達，
工具寫成 Python 函式就能共用；
瀏覽可以交給專門的 agent，
用的都是開發者熟悉的工具。
第 1 節：軟體是 agent 最好的介面，
這是作者的主張。
02　動作與執行分開
agent 只寫 step()，
執行交給沙箱
事件流是共同的介面：agent 讀歷史、
送動作，runtime 在 Docker 裡執行，
使用者隨時可以插話；
任何 base image 都能當執行環境。
換 agent、換 image、換介面，
其他兩塊不必跟著改。
03　量進步，也擋退步
15 個基準量能力，
整合測試擋回歸
完整跑基準很貴，每次改動就用
錄好 LLM 回應的整合測試守住程式；
倫理聲明也把系統性評估，
列為降低風險的第一步。
