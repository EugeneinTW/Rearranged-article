GENERAL USER MODELS · 圖卡＋教材整合版

讓電腦從觀察中 認識使用者GUM： 從截圖與通知推出帶信心的命題， 再讓主動助理 Gumbo 決定何時開口

今天的使用者模型大多只懂一個應用裡的事。這篇 2025 年的 UIST 論文提出通用使用者模型 GUM：觀察使用者在電腦上的各種互動（例如螢幕截圖），推出一句句關於使用者的命題，每條附一個信心分數，並持續檢索與修正。任何應用都能查詢它；作者也用它做出會主動找事做的助理 Gumbo，再用兩個使用者研究檢驗準不準、用起來如何。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

讓電腦先看懂你，助理才能主動

Stanford CS 329Z 第 11 週「Proactive Agents」那一講（Coding Agents & Proactive Agents 分區），談 agent 怎麼從等指令走到主動幫忙，以及主動之後的隱私、信任與時機。這篇 2025 年的論文是這一講的必讀，它處理主動之前的那一步：系統得先知道使用者是誰、正在做什麼。

這一講的講題有六個：從被動到主動；General User Models（GUM）；Next Action Prediction；開源的主動個人 agent；隱私與信任的影響；agent 何時該主動、何時該等（mixed initiative）。同一講的選讀是 Shaikh 等人的〈Learning Next Action Predictors from Human-Computer Interaction〉與 Steinberger 的〈OpenClaw: Open-source proactive AI agent〉。

這篇論文的出發點很直接。我們想像中的好系統，會在對的時候做對的事，前提是它夠了解使用者；今天的使用者模型卻大多只看得到一個應用裡的行為。作者提出的通用使用者模型（general user model，GUM）改從使用者在電腦上的所有互動學習：把螢幕截圖這類沒有結構的觀察，推成一句句自然語言的「命題」，每條附一個信心分數，新證據進來就修正。任何應用都能查詢它；作者也拿它做出主動助理 Gumbo，會自己找出值得做的事，先評估該不該打擾使用者，做得到的就先做。

先把幾個名詞對齊

  • 使用者模型（user model）：系統對某位使用者的偏好、習慣與目標的內部表示；推薦系統、個人化功能都靠它。
  • 共同基礎（common ground）：對話雙方共享的知識、信念與假設；有了它，說話才不必每次從頭解釋。
  • 校準（calibration）：信心和實際的正確率對得上；說有八成把握的命題，大約八成是對的。
  • 消融（ablation）：拿掉系統的某個部件，看表現怎麼變，用來確認每個部件的貢獻。

引言從兩個經典場景講起。Mark Weiser 在〈The Computer for the 21st Century〉裡描述一個鬧鐘，知道主人快醒了，主動問要不要煮咖啡；Apple 1987 年的 Knowledge Navigator 影片裡，助理在使用者苦思一個問題時找來相關資料，又在使用者專心時擋掉一通電話。作者說，這種「夠了解使用者，才能在對的時間做對的事」的想法，貫穿了兩條研究線：會隨使用者情境調整的 context-aware 系統，以及代替使用者主動行動的 interface agent。

作者的判斷是，這些願景大多還做不到。使用者模型、推薦系統與 context-aware 系統都有進展，電腦卻仍然不知道我們是誰、在做什麼、什麼對我們有幫助。問題出在模型太窄：它懂我們的音樂偏好、我們在某一個應用裡怎麼用工具、我們下一部可能看的劇。就算有模型整合了好幾個應用的資料，整合也停在表面，換到新情境就沒辦法推論。作者要的使用者模型要夠廣，從一般的偏好到眼前的資訊需求都能推想，也要能跨情境套用，從工作到休閒。他用「針孔視野」形容今天的應用：Weiser 的願景需要能推想家人、朋友與工作的模型，不是一個應用，也不是一種一維的訊號。

論文提出的是一個通用使用者模型的架構：一個跨領域、跨時間尺度，實際存下使用者資訊與推論的計算模型。GUM 讓使用者把沒有結構的觀察（例如電腦畫面的截圖）送進一個以大型多模態模型（例如視覺語言模型，VLM）為核心的推論架構，建出一份私有的表示，描述自己的行為、知識、信念與偏好。架構有三個主要元件，另外加一個稽核：

Propose

提出

把沒有結構的觀察，轉成關於使用者偏好、情境與意圖的命題，每條附信心。

Retrieve

檢索

替命題建索引，依查詢找出和情境最相關的一小組。

Revise

修正

用檢索的結果，在新觀察進來時重新評估、改寫既有的命題。

Audit

稽核

依情境完整性，用 GUM 自己估計哪些資訊使用者不會預期被記錄，事先濾掉。

作者說所有資料都安全地留在使用者的裝置上，硬體夠強就能在本機推論。作業系統、應用程式或使用者自己都能即時查詢 GUM；不論是哪一種互動，使用者都直接在本機掌控底下的命題，可以編輯、刪除、新增。

引言也預告了幾種用法。最簡單的是替應用與使用者建立共同基礎，例如向 ChatGPT 這類語言模型提問時自動補上相關脈絡：問起剛才讀的那篇論文的方法，不必再自己引用或摘要。其他應用也能查 GUM 來調整體驗：接上 GUM 的作業系統，可以在開會時只放行真正相關的通知，例如即將截止的研討會報名，同時壓下食譜信；信件程式可以依觀察到的優先順序排信，不用另外替這個應用訓練。

GUM 也能撐起一類新的主動系統。作者做的助理 Gumbo 持續私下擷取使用者電腦的畫面來學 GUM，隨時依使用者的脈絡找出值得提出的建議，並用 GUM 判斷要不要、什麼時候介入，以及要不要自己動手執行。引言舉的例子是：第一作者收到朋友的婚禮邀請後，Gumbo 主動找了可以租西裝的地方，還顧到他的預算（圖 1）；開發期間它也找出並提出系統本身 bug 的修法，並依他和合作者的互動建議論文怎麼改。對研究的參與者，它替一個新的理論框架整理出融入研究的方式、做了一份高度個人化的搬家計畫、幫忙整理散落各處的信件，全都是主動做的，只靠觀察。

評估的預告：信件研究有 18 位參與者，信心最高的命題（信心 10）全部被評為正確，所有命題平均 76.15% 正確；消融顯示每個元件都不可少。接著 Gumbo 在 5 位參與者的電腦上跑了 5 天，結果重現了 GUM 的準確與校準，參與者也找到不少有用、執行得不錯的建議，其中兩位在研究結束後想繼續用。評估也暴露了限制與邊界，包括隱私，以及過於直白的命題。作者列的貢獻是：GUM 這種表示、它的一個實作、讓應用查詢它的介面、示範應用 Gumbo、信件的技術評估、截圖的長期評估，以及對這類應用的規範與影響的反思。

整理者的讀法

GUM 和聊天助理的「記憶」差在哪裡

聊天助理的記憶，記的是你和它說過的話；GUM 記的是它在你電腦上看到的一切，而且每條推論都附信心、會被新證據修正，任何應用都能來查。第 2 章會看到，作者正是把「只從和模型的對話建立脈絡」當成現有做法的限制。這一段是整理者的讀法，論文沒有這樣並列。

Chapter 02 · Related Work

共同基礎，不該只在對話裡建立

作者從兩個問題定位 GUM：AI 系統和使用者缺少共同基礎，現有的補法只看得到使用者和模型之間的互動；把脈絡寫進 prompt 又很難，負擔全在使用者身上。GUM 改用觀察，主動建立共同基礎。

第一個問題是共同基礎（common ground）：人與人溝通時共享的知識、信念與假設（作者引 Clark 與 Schaefer）。人透過對話、手勢、表情與其他多模態的線索，不斷更新對彼此的理解，一點一點建立共同基礎；有了它，說話才不必多解釋。

AI 系統和使用者之間卻很少有共同的脈絡，只好對使用者的背景做假設，給出一體適用的答案：資訊給太多、過度自信、處理不了歧義。作者說無法建立共同基礎的後果不只出現在問答：設計與原型化 AI 系統需要協作式的 grounding；少了它，系統可能採取不利、甚至不可逆的行動。

補這個缺口有兩種常見做法。一是問澄清問題，模擬人來回對話建立理解，可以靠 prompting、微調或兩者並用。二是記住使用者和聊天助理互動的長期記憶。長脈絡模型也讓使用者能丟進很長的輸入當 grounding，但脈絡越長，模型越會忘記內容；另一條路是檢索增強生成（RAG），從資料庫取回脈絡，例如 OmniQuery 從處理過的相簿記憶裡取脈絡，替 LLM 的查詢補上背景。作者指出，不論哪一種，脈絡都只來自使用者和模型之前的互動，或少數預先定義好的應用與來源；其他的電腦互動，模型都看不到。

整理者的補充：這一類被引用的長期記憶研究包括本站整理過的〈MemGPT〉（Packer 等人，2023），Letta 談 agent 怎麼管記憶的〈Agent Memory〉也可以對照著讀。

作者的主張是：只在使用者和模型互動時才建立共同基礎，是一種受限的互動方式；替特定領域拼湊客製的 grounding 互動，又把它綁在對話上，會限制使用者能和 AI 建立多少共同基礎。GUM 則透過觀察主動建立。

第二個問題是有效地 prompt LLM 很難。使用者常給出不夠具體的 prompt，要反覆迭代才能講清楚某個情境的限制。ChainForge、EvalGen（本站整理過介紹它的〈Who Validates the Validators?〉，整理者的補充）讓使用者互動地驗證、迭代特定任務的 prompt；Graphologue、Sensescape 讓使用者探索一個 prompt 可能的各種輸出。這些互動裡，提供明確輸入、建立共同脈絡的負擔都在使用者身上。

另一方面，HCI 一直想做不打擾使用者的主動系統。早期的 mixed-initiative 介面在自主與使用者掌控之間取平衡，用脈絡找出最適合互動的時機（Horvitz 1999）。也有系統用傳統的 AI 模型理解使用者的多模態脈絡：Memory Landmarks 與 LifeBrowser 分析行事曆與信箱，推想使用者覺得哪些事件重要。少數系統開始用 LLM 有選擇地處理脈絡：PICAN 在 VR 上手的情境裡，聚焦使用者在虛擬世界的對話與動作；GPTCoach 用外部的健康資料與質性脈絡，幫助行為改變。作者說，以 LLM 為基礎的系統都在限制模型處理的輸入、輸出與任務類型；這篇反過來利用 LLM 擅長的事，也就是不受限的輸入，從觀察建立對使用者與情境的假設，作者稱之為「多模態的 grounding 引擎」。

最後是 context-aware computing。這個領域很早就想像過這樣的工具組（作者引 Schilit、Dey 等人），但這些框架通常綁在輸入資料或感測器的某種固定結構上（Dourish 2004），一開始就限制了脈絡的定義與能支援的應用。GUM 只給很少的限制，用彈性的結構建立脈絡。

這個抽象借自人與人溝通的共同基礎。共同基礎的一部分可以定義成雙方共享的假設；人和 AI 之間的難題，在於 AI 能對使用者做出哪些站得住的假設。第 3.1 節的例子是：使用者一再搜尋「科羅拉多最好的健行步道」、逛戶外用品網站，模型可能以高信心推出「使用者喜歡戶外活動，對在科羅拉多健行有興趣」。作者再借用貝氏的 grounding 模型：共享的知識是機率分布，不是一組確定的命題，對話雙方在溝通中不斷修正。要實作這種機率式的共同基礎，作者利用大型語言模型的 in-context learning，這種能力可以粗略看成貝氏更新。落到實作，是三個抽象：

Observation

觀察

GUM 處理的原始輸入，只要能切成 token、送進大型模型就行：截圖、檔案系統、通知。每筆附來源、時間戳與唯一 ID；觀察是事實紀錄，不是推論。

Proposition

命題

GUM 從觀察建出的文字假設。看到朋友的婚禮邀請，可以推出「受邀參加朋友的婚禮」這種表面推論，也可能推出「需要為婚禮買或租一套西裝」這種要推測的。

Confidence

信心

命題為真的把握，取決於支持它的證據有多少、多好。邀請就在畫面上，信心 1.0；西裝的事從沒明說，信心 0.4。應用可以靠它在不確定下做決定。

命題另外帶著給下游應用用的 metadata。作者受認知 agent 架構啟發（引 Anderson 1993 與 Park 等人 2023），讓模型產生 0 到 1 的衰減分數，表示命題多快過時：「作者是博士生」衰減得慢，分數 1.0；「作者在除錯記憶體洩漏」是短暫的，分數 0.6。每條命題也帶著 grounding，也就是支持它的觀察，外加一段生成的推理，說明它怎麼被推出來。第 3.1 節的推理例子描述截圖裡的人在用記憶體分析工具、看著記憶體用量一路上升、在建立物件的地方加除錯訊息，結論是正在排查記憶體洩漏。

整理者的補充：這裡引用的 Park 等人 2023，就是本站整理過的〈Generative Agents〉。

第 3.2 節交代介面。GUM 用 Python 實作，可以用 pip 安裝。實例化需要一個會照指令做事的語言模型或視覺語言模型；作者用在安全伺服器上跑的 Llama 3.3 70B，但任何支援 OpenAI ChatCompletions API 的模型都行。所有命題與 metadata 都放在私有的 GUM._propositions 變數裡，只有使用者能存取；應用程式不能直接改它，除非使用者明確授權。

經使用者允許，GUM 可以訂閱各種資訊來源。它預設提供幾個 hook，叫作 Observers，監聽螢幕內容、通知與手動輸入的新觀察：例如使用者存檔或移動滑鼠時，檔案系統與螢幕的 Observer 就把新觀察交給 GUM，由 GUM 轉成命題。

使用者與應用都能用自然語言查詢命題與底下的觀察，例如查「HCI conference」會回傳和使用者的 HCI 活動相關的命題。查詢有三個參數：相關性與多樣性的平衡（0 是最相關、1 是最多樣）、從哪個時間點往回找，以及要不要依命題的時間套用衰減。實際的函式與參數名稱，請看論文與作者公開的程式；本頁不另外寫示意程式，免得和真正的介面混淆。

第 5 節的工程原則是主要用開源模型。作者承認閉源模型比較強，但預期 GUM 屬於個別使用者，最後會被蒸餾到使用者自己的裝置上跑；用開源模型，就能示範並主張核心的 GUM 不必把私人資料送到第三方的 AI 平台。開源與閉源的差距縮小、推論變便宜之後，GUM 會更好用，也能在一般硬體上跑。這篇的 GUM 由兩個模型撐起：看螢幕用視覺語言模型 Qwen 2.5 VL，提出與修正命題用只吃文字的 Llama 3.3 70B。

觀察。GUM 的基礎材料是使用者的行為。過去的使用者模型多半建在狹窄、人工記錄的觀察上；現代 VLM 的推論能力，讓截圖、檔案、開放式的文字流這類不設結構、不打擾使用者的輸入，都能當原始觀察。Observers 刻意設計得很泛用：例如一個音訊 Observer 可以接上麥克風，把使用者的話轉寫成文字交給 GUM，只做這件事。作者在 macOS 上實作了兩個。Screen Observer 監聽鍵盤與滑鼠，一有輸入就截圖，用 Qwen 2.5 VL 72B 把畫面的變化轉寫成文字；除了內容，它也描述使用者在最多 10 個不同畫面裡做了什麼。Notification Observer 監看作業系統底層的通知資料庫，回傳新通知的文字與內容。作者說這兩個只是例子，任何模態都能寫新的 Observer，例如音訊、健康感測器、影片。

附錄 E 給了 Screen Observer 的輸出，分兩段。第一段是畫面的文字轉寫：正在跑哪個程式、開了哪些分頁、正在編輯哪個檔案與函式。第二段是最近 10 個不同畫面裡使用者做了什麼的描述，例如在設計工具裡調整一張介面草圖、在 LaTeX 編輯器裡改論文、在開發工具裡除錯一個回傳錯誤的函式。第 9.4 節說，GUM 每天存下約 1GB 的截圖，轉寫成文字的觀察只有 5 MB。

稽核。轉寫之後、進入命題之前，Audit 模組先過濾，用 GUM 自己推測這筆資訊使用者會不會預期被記錄；細節與評估在第 8 章。

提出。Propose 把觀察轉成命題，順序是先推理、再命題、再信心、再衰減。先要求模型解釋觀察和使用者的關係，作者說這段理由有兩個用處：讓使用者看得到推論的依據，也通常能提升模型表現。第 5.3 節的例子：觀察是使用者在 Overleaf 與 YouTube 之間切換的截圖；推理是「使用者看起來分心了，在冰淇淋食譜影片與 Overleaf 視窗裡斷斷續續的打字之間切換」；命題是「使用者寫作時會定期去看冰淇淋食譜」。作者在論文裡自承，這條是真的。

信心的做法是直接請模型說出一個分數。理論上可以看模型對輸出的 log probability，但作者說現成模型的預測常常過度自信；他們和 Tian 等人（2023）一樣，觀察到直接請模型產生信心分數，比看底層的 logit 更校準。作者的設定略有不同：這裡估的是對使用者信念的信心，不是模型對自己回答的信心，但他們認為 Tian 等人的結論可以推廣。模型在 1 到 10 分之間給分，再正規化到 0 到 1。衰減不用一套全域的規則，而是把命題的所有資訊（推理、信心）放進脈絡，請模型替這一條命題產生 1 到 10 的衰減分數：「使用者正在吃冰淇淋」比「使用者是博士生」過時得快。

第 4 節從最樸素的用法開始：prompting。作者說 prompting 的根本問題，是和模型缺少共同的 grounding：除非明說，LLM 不知道你在做什麼專案、和誰一起做、這件事為什麼重要，所以常常猜錯你的處境。prompt 本來就不夠具體，我們被迫把豐富的脈絡壓成一句去掉脈絡的自然語言查詢。

例子是論文寫到這裡時，第一作者對 LLM 說「幫我處理這一節」。作者說今天的前沿模型會迷路，反問「可以給我你說的那一節嗎？」，雖然從觀察能建構出大量脈絡：GUM 看得到作者之間的互動、最近讀的論文、論文目前的狀態、作者喜歡的 HCI 研究。沒有 GUM 時，使用者最糟要一輪一輪重建脈絡、糾正模型的錯誤假設；最好也只是靠過去的聊天紀錄，用上真實脈絡的一小片，或被問澄清問題。有了 GUM，系統查詢相關命題與底下的觀察，取回作者稍早讀的論文、共同作者的意見、正在改的那一節，例如「正在專注改應用一節」0.8、「最近讀了 Weiser 的 Calm Computing」0.6、「指導教授提到可以看看 interface agents」0.5。以這些命題為條件，LLM 的回答就具體了：既然你在改應用一節、又想著 Calm Computing 與 interface agents，可以強調系統怎麼靠脈絡延伸 calm computing 的原則，也可以拿 Gumbo 的通用協助對比傳統 interface agent 的固定做法，後面附上一段草稿。圖 2 的示範畫面印出的四條命題信心是 1.0、1.0、0.8、0.8。

第 4.2 節主張，除了 prompting，任何應用都能接上 GUM，用上其他所有應用與使用者的脈絡；作者說在許多 HCI 系統裡，取得並處理脈絡是讓應用成立的那一層。作者重訪三個經典願景：

Calm technology。Weiser 的普適運算願景催生了一批在使用者注意力的中心與邊緣之間移動的系統。過去這類系統靠攝影機、麥克風這種客製感測器，每個應用都要自己做一條機器學習管線來判斷；GUM 不需要這些儀器或訓練資料，而且會依使用者的任務調整。calm technology 的一個設計重點，是認清邊緣的東西時時在變。例子：第一作者忙著寫論文，錯過了一個研討會的早鳥報名截止。作業系統預設替主要收件匣的每封信都跳通知，他平常就一概忽略，因為同一段時間還有帳單通知、新創公司的徵才信這類信件。只問 Llama 3.3「幫我濾出對我重要的通知」，它建議全部放行，讓注意力超載；同一個 prompt 加上 GUM 的命題與信心，提供了「很滿意當博士生」「有一個重大的截止日逼近」「常忽略帳單通知」這些脈絡，LLM 就只放行研討會報名那一則。

Interface agents。interface agent 把主動與個人化的協助帶進人機互動：與其讓使用者自己起頭，不如預判需求、自動完成任務。它需要領域知識與個人化的使用者模型；作者說，少了一個持續學習的個人偏好模型，實作一直很難，每個新 agent 都要專門的資料集與手工設計的學習目標。以 Maes 的電影推薦 agent Firefly 為例：第一作者正趕著完成論文，這時看電影再糟不過。問一般的 LLM（Llama 3.3 70B）現在適不適合看電影，它同意，還推薦了一串和作者興趣毫不相干的片；同一個 prompt 加上 GUM，模型看到作者「草稿上還有很多沒處理的意見」「離論文截止只剩幾個小時」，判斷現在不適合。作者還做了一個對照：把 GUM 裡所有和截止日有關的命題拿掉，加上 GUM 的 LLM 就正確地同意，並推薦了相關的片。作者說有了 GUM，只要很少的領域工程與幾句簡單的 prompt（例如「我該看電影嗎？」），就能做出各種主動、個人化的 interface agent。

Context-aware computing。統一跨應用的脈絡是 context-aware computing 的老願景，但有效的脈絡協定一直做不出來；如果做得到，任何應用都能查同一個 API。過去用 context toolkit 做的應用，從提醒系統到研討會參加者的助理，都倚賴專用感測器的基礎設施，每加一種感測器就要手工做一條新的資料處理管線。作者說 GUM 正好解決這件事：截圖、感測器資料、影片，任何輸入原則上都能放進 GUM。例子是第一作者把手機上健身 app 的自填訓練紀錄、健康 app 的步數匯出成文字檔，除了轉成 .txt 之外沒有前處理，直接餵進自己的 GUM，得到一條命題：把論文截止日排在日常運動前面，信心 0.6。

評估怎麼做。第 7 節沿用第 7 章的信件設定與同一批 18 位參與者，假設是：推論使用者的隱私偏好時，GUM 自己有幫助。作者請參與者標註時跳過任何違反自己隱私偏好的命題，等於把它們標記出來，再統計被標記的數量。參與者也看到 GUM 對情境完整性問題的回答，就是驅動稽核模組的那組問題；他們從三個條件的回答裡選出最好的一份，再用 7 點量表評它有多準。作者附了自己的匿名範例：回答列出使用者的信箱分享給了哪些服務、帳號被誰邀請協作、這些資料在什麼情境下分享（例如排行程、收社區的推薦），也指出使用者沒回應某個平台的信，可能代表不想和它分享資料或互動。

多半守得住。參與者替完整 GUM 標註的 180 條命題裡（18 人各 10 條，整理者算的），只有 7 條被標為違反情境完整性。參與者對情境完整性回答的評分平均 6.06（1 到 7），介於同意與非常同意之間。61.1% 的參與者選完整 GUM 的回答最好，原文接著寫「沒有檢索的消融（22.2%）與修正（16.6%）」，沒有明說後一個是哪個條件；三個比例合計 99.9%，大約等於 18 人中的 11、4、3 人（整理者算的）。作者另外檢查過，沒有任何命題逐字寫出信用卡號、電話或地址。

守不住的時候很糟。作者說，還是有七筆觀察繞過了稽核，這個數量不容忽視。一位參與者（兩條違規）很驚訝 GUM 能從信裡叫出特定的名字：提到和別人的訊息或社群互動、又明確點名幾位朋友的命題讓他有點意外，雖然想得到這些資訊是從信裡來的。作者的結論是，GUM 只從 200 封信就能推出多得驚人的東西；對某些使用者，明確推論他和別人的社交關係，是 GUM 的一條界線。原則上使用者可以直接告訴 GUM 自己想要的隱私規範，但這裡有一條微妙的信任平衡。另一位參與者（三條違規）說，某條命題是從他收到的一封釣魚信推出來的，不是他真正的信，信心還不低，卻完全不準：模型把釣魚信的內容當成他本人和他的興趣。

作者由此指出，廣告與垃圾信可能惡意改寫 GUM，讓攻擊者有機可乘。prompt injection 是已知的視覺語言模型弱點，GUM 則暴露出更大的攻擊面；作者認為，就像 prompt injection 可以靠紅隊測試緩解，針對 GUM 的注入攻擊也能被緩解，但不做進一步的研究就無法完全消除。第 12 章的風險會再回到這一點。

關鍵觀念 · 一

理想的自己，和真實的自己

作者說，理想自我與真實自我之間的落差，是有文獻記載的心理現象（引 Higgins 1987、Rogers 1995）。GUM 照實描述的是真實的那一個，所以參與者面對自己的 GUM 時，反應從覺得被評斷到有建設性的自省都有；註腳說，不只一位參與者把 GUM 比成 BuzzFeed 的性格測驗。

整理者的讀法：一條命題可以同時「對」又「不該讓人看到」。準確解決的是下游建議好不好，要不要顯示是另一個設計決定。

作者提出的設計問題是：Gumbo 該給使用者看底下原始的使用者模型、淨化過的版本，還是完全藏起命題？一個方向是依情境調整看得到的內容，只在使用者願意接受時才顯示自省性的內容，就像稽核模組用 GUM 做隱私的過濾決定一樣。

當下的幫忙。一部分有用的建議是低層次的，幫使用者做眼前的事。P5 正把學校的信箱搬到 Gmail，一直搞不懂怎麼開 Gmail 的通知，Gumbo 產生了一份逐步的說明，P5 很高興。P3 正在替即將到來的資格考做簡報，Gumbo 給了投影片轉場的建議，P3 先試了，後來採用。

沒想到要問的事。更讓人興奮的一類，是處理使用者沒有明說的需求。P3 正在考慮在研究裡用一個新的框架，Gumbo 主動用 P3 熟悉的工具，產生了一份腦力激盪的大綱。P3 說，他遇到新想法時習慣開一個空白的 Overleaf 文件，列出這個想法和自己研究的關係；他什麼都沒告訴系統，它卻看出這個習慣，用 LaTeX 寫出一整份大綱，說明論文可以怎麼放進這個新框架，讓他很驚訝。P5 花不少時間看遊戲直播；Gumbo 從他在哪裡暫停、停多久、重播哪些片段，推出他感興趣的角色，找出也玩同一個角色的其他實況主，P5 後來真的去看了那些推薦的頻道。

從通用使用者模型，到通用的 Clippy？所有參與者都覺得 Gumbo 常推薦、並試著執行它做不到的建議；作者說這是今天的模型做 agent 式執行的實際限制。相當一部分建議（20.69%）被標為方向對、但執行失敗。有些參與者倒是很享受看 Gumbo 試了又失敗。P2 的指導教授一直要他聽某集 podcast，這件事一直掛在待辦清單的最上面；系統推了他一把，查了這集 podcast，說它和 P2 的研究有關，大綱還可以，找出的關聯卻完全是垃圾，但這讓他終於去聽了，之後專心做了好幾個小時；他甚至更喜歡這樣，因為它沒有拿走任何思考的負擔。作者說這種失敗反映底層 LLM 的能力或工具使用的限制：Gumbo 並沒有上網取得並讀完那集 podcast。更簡單的建議也會失敗：Gumbo 聲稱替 P5「排好了提醒」，但它根本沒有通知的 API，執行完全失敗。

急著幫忙的大型語言模型。較差的建議常常出在太急著幫忙：使用者正要完成某件事，Gumbo 就搶先建議；或建議一件參與者早就做完的事。作者說，當下有用的建議和太晚的建議之間，界線很細。

敏感主題的推論。P1 對 Gumbo 推論並存下敏感主題感到不自在。稽核模組誤以為既然 P1 看過、也和別人談過這些主題，它存下這些資訊也沒關係。P1 說，GUM 的完整性標準應該比情境暗示的更嚴，稽核模組本身也應該能被稽核。

螢幕以外的事。所有參與者都談到，GUM 只從電腦使用學，電腦以外的事 Gumbo 抓不到。P2 說，有時在手機上做事，會希望這些也能被收進來。P3 也提到類似的事，並明確想到替 Gumbo 這類系統加更多脈絡時，隱私與能力之間的取捨：有些很棒的東西是他自己想不到的，要怎麼放大這些、又少看到評斷式的命題；他覺得要用超過五天，也會想放進更多個人的工作。第 12 章接著談這個悖論。

第 9.2 節用隱私悖論解讀這些反應：人常說自己非常在乎線上隱私，實際上卻願意為了好處交出隱私（作者引 Norberg 等人 2007）。對多數應用，這代表透過社群帳號，把位置、瀏覽習慣這類敏感資訊交給定向廣告商。作者認為 GUM 是更通用、也強得多的使用者模型，所以隱私行為成了核心問題。

GUM 看得越多就越精準，下游的建議也越好；模型能解析的任何東西，使用者都能拿來改進它。作者觀察到，幾位參與者一開始聚焦在隱私風險上，後來自然得出同樣的結論，開始主動提供更多資料給 GUM。端到端研究裡，五位參與者中有兩位想在研究後繼續用某個版本的 Gumbo，儘管一開始有隱私疑慮，仍在想辦法給 GUM 更多資料。作者的推論分兩邊：如果相信和私有、本機的 GUM 分享資料是安全且值得的，揭露就會自我強化，因為使用者看到模型的表現隨自己貢獻的資料具體變好，可能分享得更多；如果考慮 GUM 的意外揭露風險或安全風險，這個迴圈可能反噬。

Persuasion

說服、廣告與監控

用 GUM 鎖定使用者。作者強烈建議所有 GUM 都在使用者自己的電腦或個人基礎設施上訓練與託管，這也是整篇的指導原則；外部系統若被授權存取，存取要受控、可稽核。第三方也可能未經同意，用使用者在自家應用裡的活動訓練 GUM，這時可以用混淆系統產生假的互動資料，掩蓋真實行為。

Manipulation

操弄 GUM

信件研究裡已經看到非蓄意的操弄：GUM 吃進的垃圾信，惡意地改寫了底下的命題。攻擊者可以不直接針對使用者，而是設計訊息去操弄使用者的 GUM，倚賴它的應用都會受影響。緩解的方向：遇到和目前理解不相符的輸入先請使用者確認；做出類似廣告封鎖或垃圾信過濾的技術，在 GUM 處理之前攔截；或讓模型反思是不是有人在騙它。

Bias

偏誤

參與者沒有提到有偏誤的推論，但 GUM 建立在有偏誤的模型上；推薦系統長期以來會把有偏誤的推薦推給使用者，GUM 等於擴大了推薦系統的影響面。作者說部署之前，要在更多刻意設計的對抗情境裡仔細做紅隊測試，了解 GUM 會做出哪些推論。

抽樣偏誤。端到端研究招募參與者的難處在信任，所以招募主要在作者的機構，並透過口耳相傳與滾雪球；機構的 IRB 只准最多 5 人，以降低 Gumbo 可能出的問題帶來的影響。作者建議，目前把結果看成最可能推廣到熟悉 AI 的技術使用者。

幻覺與錯誤歸因。現在的大型模型仍有幻覺。錯的命題大致被適當地校準了，但仍有少數信心高卻錯。GUM 偶爾也會幻想出使用者電腦上不存在的應用程式，或把兩條無關的命題連起來。

螢幕仍是狹窄的脈絡代理。接上信箱或螢幕的 GUM 看得到使用者的很大一部分，但不是全貌，離 Dourish 說的「透過日常行動建立脈絡」還很遠；使用者做了 GUM 範圍以外的事，它就推廣不了。

更好的模型。作者說 GUM 管線的很多元件，是在補今天 LLM 的限制，因為把所有東西都塞進脈絡並不夠：模型會忘記部分脈絡，或產生籠統的命題。檢索一步是因為模型無法可靠地處理極長的脈絡；明確說出信心是因為模型的 logit 沒有校準。作者預期未來針對 GUM 的建模（例如端到端學習管線的一部分）會取代特定步驟，模型也會變小、完全在裝置上跑，進一步降低隱私風險、減少儲存；目前 GUM 每天存約 1GB 的截圖，轉寫後的觀察只有 5 MB，部署越久累積越多。另一個方向是研究有效的使用者模型最少需要多少觀察資料。最後，目前的實作倚賴視覺與語言模型，限制了輸入空間；能吃更多模態、會用更多工具的大模型能擴充 GUM，例如語音模型聽得出語氣、醫療模型讀得懂各種感測訊號，原則上都能整合進 GUM。附錄 B.1.1 另外提到，GUM 的校準也許能靠微調或更好的 prompt 改進。

第 10 節的結論：GUM 是從日常行為學到使用者脈絡豐富表示的計算模型，把非結構的互動轉成帶信心的命題，隨證據累積持續修正推論。它打開一系列可能，從讓語言模型立足於觀察到的使用者行為，到做出能代替使用者行動的主動系統。作者用 Gumbo 示範：一個從個人脈絡直接找出有用建議、並試著完成它們的互動助理。評估中，GUM 對使用者做出快速、校準且準確的推論。作者主張 GUM 提供了一個框架，讓使用者模型從各自為政的應用專屬模型，走向一個通用的使用者模型：了解你在生活各種情境裡是誰。

放回這一講：主動之前的兩塊基礎

下面是整理者的連結。這一講談 agent 從被動走向主動。這篇給了主動之前的兩塊基礎：一份夠廣、帶信心、會修正的使用者模型，讓 agent 知道使用者在做什麼；以及一條用期望效用決定何時開口的規則，外加每分鐘一則的上限。它也把代價攤開來：命題太直白、執行常失敗、隱私悖論會讓人越給越多。同一講的兩篇選讀，分別從預測使用者的下一個動作與開源的主動 agent 接續這些問題。

GUM 的資料會離開使用者的電腦嗎？
作者的原則是模型與基礎設施都由自己掌握：GUM 只用開源模型，作者建議在使用者電腦或個人基礎設施上訓練與託管。研究中的模型跑在研究團隊自己配置、只有團隊能存取的 GPU 上，命題與 metadata 存在參與者的電腦；Gumbo 的外部工具預設關閉，只有搜尋或執行程式時才呼叫 Gemini 2.0 Flash。
GUM 的命題有多準？
信件研究的完整版平均 76.15% 正確，信心 1.0 的全對、高於 0.8 的 88.2% 正確；五天的部署是 0.79。誤差多半來自信心偏低，但作者也說少數命題信心高卻錯，稽核也有漏網（第 6、7、8 節）。
Gumbo 怎麼決定要不要打擾？
用 GUM 估出建議有用的機率、好處、誤報與漏報的成本，打擾的期望效用大於不打擾才顯示，再加上每分鐘最多一則的限制；做得到而且沒有不可逆副作用的，就先做完（第 4.3 節）。

Reference · 名詞速查

關鍵名詞，和它們在論文裡的位置

先列系統與它的抽象，再列管線的模組與檢索用到的方法，接著是 Gumbo 的決策，最後是兩個使用者研究與討論裡的名詞。

general user model（GUM）
通用使用者模型
從使用者在電腦上的非結構觀察學出的一組帶信心的自然語言命題，任何應用都能查詢（第 3 節）。
Gumbo
主動助理
建在 GUM 上的桌面助理：發現建議、依期望效用決定是否顯示、做得到就先做（第 4.3 節）。
common ground
共同基礎
溝通雙方共享的知識、信念與假設；GUM 想透過觀察和使用者建立它（第 2、3.1 節）。
observation
觀察
GUM 的原始輸入，例如截圖的轉寫、通知、使用者的回饋；附來源、時間戳與 ID，是事實紀錄（第 3.1 節）。
proposition
命題
關於使用者的一句自然語言推論，不限類型，會被修正（第 3.1 節）。
confidence
信心
命題為真的把握；模型說出 1 到 10 分，再正規化到 0 到 1（第 5.3 節、附錄 B.1.1）。
decay score
衰減分數
命題多快過時；檢索時以 exp（−α × k × 年齡）調整相關分數，k ＝ 2（第 3.1、5.4 節）。
grounding、reasoning
依據與推理
支持命題的觀察，以及說明命題怎麼被推出來的生成文字（第 3.1、5.3 節）。
Observer
觀察來源的 hook
監聽某種來源；Screen Observer 截圖並轉寫，Notification Observer 讀作業系統的通知資料庫（第 5.1 節）。
Propose
提出
先推理、再產生命題、信心與衰減分數的模組（第 5.3 節）。
Retrieve
檢索
BM25 取回、新近度調整、MMR 取多樣、LLM 重排的兩階段檢索（第 5.4 節）。
Revise
修正
依新舊命題與 metadata 改寫命題、重算信心；信心 0 的保留，但預設不回傳（第 5.5 節）。
Audit
稽核
在觀察進入命題前，用 GUM 推測情境規範，擋下使用者不會預期被記錄的資訊（第 5.2 節）。
contextual integrity
情境完整性
Nissenbaum 的隱私理論：資訊的流動符合社會情境的規範，才算保護隱私（第 5.2 節）。
BM25
詞頻檢索
依詞頻、逆文件頻率與文件長度計分的經典檢索方法；GUM 用它做第一階段的取回（第 5.4 節）。
MMR（Maximum Marginal Relevance）
最大邊際相關
在相關與多樣之間取捨的挑選法，每次挑分數最高的一條；λ ＝ 0.5（第 5.4 節）。
mixed-initiative interaction
混合主導互動
Horvitz 的原則：人與系統輪流主導，依成本效益決定何時介入（第 4.3.2 節）。
expected utility
期望效用
以機率加權的好處與成本；打擾的期望效用大於不打擾，才顯示建議（式 1 到 4）。
false positive、false negative cost
誤報與漏報成本
沒必要卻打擾的代價，以及需要卻沒提的代價；由 GUM 依 prompt 打 1 到 10 分（附錄 B.2.1）。
token bucket
權杖桶限流
限制事件速率的演算法；Gumbo 用它限制每分鐘最多一則建議（第 4.3.2 節）。
ablation
消融
拿掉部件來比較：No {Retrieve, Revise}、No {Retrieve}、Full（第 6.1 節）。
Brier score
Brier 分數
預測機率與實際結果之差的平方平均，越低越校準；完整版 0.17（第 6.3 節、表 1）。
win rate
勝率
成對比較裡勝出的比例；完整版 0.618（第 6.4 節）。
burn in、active use
暖機與實際使用
端到端研究的兩段：24 小時只收資料，接著 4 天和建議互動（第 8.1 節）。
privacy paradox
隱私悖論
說在乎隱私，卻為了好處交出隱私；作者認為 GUM 會讓揭露自我強化，也可能反噬（第 9.2 節）。
