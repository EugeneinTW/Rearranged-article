多代理系統把一件工作拆給幾個 LLM 代理分工合作，但在熱門基準上，它們常常沒比單一代理好多少。這篇 UC Berkeley 團隊的論文不看總分，改讀失敗：六位專家先細讀五個開源框架的 150 條執行軌跡，用紮根理論歸納出失敗分類法 MAST，14 種失敗模式分成系統設計、代理間協調、任務驗證三類；再讓 o1 當標註者，把資料擴大到七個框架、1,642 條軌跡。作者的結論是，很多失敗出在系統的組織設計，只換更強的模型不夠，改 prompt、改拓樸這類修補也只推高一點。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

論文先把名詞定下來。一個以 LLM 為基礎的代理有三樣東西：prompt 寫下的規格是它的初始狀態，一路累積的對話軌跡是它的狀態，能使用工具、和環境互動是它的行動。多代理系統就是一組這樣的代理，透過編排彼此互動，合起來完成一件事。作者列出大家採用它的理由：把任務拆開、平行處理、隔離各自的脈絡、組合不同專長的模型，以及讓不同的推理互相討論。軟體開發、藥物發現、科學模擬與通用助理都有人在試。

問題是效果。作者引用的研究顯示，多代理系統比起單一代理的框架，或 best-of-N 取樣這種簡單的基線，效能增益常常很小。他們自己的測試更直接：附錄 B 的圖 5 把六個開源系統跑在各自的基準上，失敗率從 AG2 在 OlympiadBench 的 41.0%，到 AppWorld 在 Test-C 的 86.7%。引言說這是七個系統的結果，圖 5 實際畫出的是六個，沒有 OpenManus。作者也說，怎麼做出穩健、可靠的多代理系統，目前沒有明確的共識。

於是論文要回答的問題很單純：多代理系統為什麼失敗？開頭的題辭先引托爾斯泰「幸福的家庭都相似，不幸的家庭各有各的不幸」，再套成自己的版本：

"Successful systems all work alike; each failing system has its own problems." 「成功的系統都一樣，失敗的系統各有各的問題」：論文開頭仿托爾斯泰的題辭，署名 Berkeley'25。

要回答這個問題，作者先碰到兩個難處。多代理系統的失敗很少有單一、清楚的根源，常常是代理之間的互動、單一模型的行為與整體設計交纏在一起；也沒有一套大家共用的失敗定義，不同系統的失敗很難用同一把尺比較。所以他們做了兩樣東西：一個叫 MAST 的失敗分類法，以及用它標註的資料集 MAST-Data。下兩章講這兩樣東西怎麼做出來。

作者列的貢獻有四項：公開 MAST-Data 與規模小得多、由專家標註的 MAST-Data-human；提出 MAST；做出和 MAST 整合、可以大量標註的 LLM 標註流程；用案例研究說明這些失敗常常出在系統設計，而不只是模型的限制或 prompt 沒寫好，所以需要的是結構上的重新設計，表面的修補不夠。

第 3.1 節的起點是 150 條執行軌跡，來自五個框架：HyperAgent、AppWorld、AG2、ChatDev、MetaGPT，任務分成寫程式與解數學題兩類。挑框架用的是理論抽樣（theoretical sampling）：刻意讓系統的目標與代理互動的方式各不相同，找到的失敗才不會只是某一個系統的怪癖。引言提到，這些軌跡平均每條超過 15,000 行文字。

分析方法是紮根理論。它的特點是不帶預設的假設進場，讓失敗模式從資料裡自然浮現。作者用了它的四個核心技巧，反覆循環：

1
開放編碼（open coding）讀軌跡，把觀察到的失敗行為貼上標籤。
2
持續比較（constant comparative analysis）把新的標籤和舊的、不同系統裡的同類行為反覆對照，修正對每一種失敗的理解，也看它在各系統重複出現的情形。
3
寫備忘（memoing）把分析過程中的想法記下來。
4
理論化（theorizing）把這些發現整理成一組初步的失敗模式與定義。

這個循環一直做到理論飽和（theoretical saturation）：再多分析軌跡，也找不到新的失敗模式為止。代價是人力，每位專家在這 150 條軌跡上花了超過 20 小時標註。

歸納出來的失敗還只是觀察。要拿來給大量軌跡貼標籤，定義必須清楚到換不同的人標，也會標出一樣的結果。第 3.2 節用標註者一致性研究（inter-annotator agreement，IAA）來磨定義：從紮根理論得到的初步版 MAST 開始，每一輪由三位專家各自獨立標註 5 條隨機挑出的軌跡，再一起討論意見不同的地方，依討論結果調整定義、新增模式，或刪除、合併既有的模式。這樣做了三輪，光是解決分歧就花了大約 10 小時，還不算標註本身的時間。最後幾輪的 Cohen's κ 平均是 0.88。引言的說法是三位標註者總共標了 15 條軌跡。一致性研究裡由專家標過的所有軌跡，後來公開成 MAST-Data-human，引言寫它有 21 條；15 與 21 的差別，論文沒有說明。

背景

κ 0.88 在說什麼

兩個人標同一批資料，就算各自亂標，也會有一部分碰巧一樣。Cohen's κ 把這部分扣掉，只看超出碰巧的一致程度：1 是完全一致，0 是和隨機差不多。作者說 0.88 這個高分代表 MAST 對失敗模式的定義清楚，大家的理解一致，所以後面可以拿它來一致地標註整個資料集。這段對 κ 的說明是整理者加的背景。

執行前、執行中、執行後

要解決它，作者推測可能得從結構上改善代理訊息的內容，或加強模型的脈絡推理，以及推斷其他代理資訊需求的能力，例如透過針對性的訓練，因為基礎模型通常沒有為這種細膩的代理互動做過預訓練。他們認為可靠的解法，大概要同時改進多代理系統的架構與模型層次的溝通能力。

給初學者

心智理論（theory of mind）

指推想別人知道什麼、不知道什麼、需要什麼的能力。放到多代理系統裡，就是一個代理在交棒或回報時，能不能想到對方缺的是哪一塊資訊。圖 3 的電話代理讀到了 username 的格式，卻沒想到主管不知道這件事。這段說明是整理者加的背景。

思考題 · 02

你的代理在交棒時，會說出對方需要的東西嗎？

打開你的系統裡一段兩個代理交接的紀錄：主管派工、子代理回報，或 handoff 給下一個角色。

逐句檢查接手的一方缺了什麼：是交出去的一方沒說（2.4）、說了但沒被採用（2.5），還是早先說過、後來從脈絡掉了（1.4）？三種的修法不同，第一種改回報的內容格式，第二種改決策的規則，第三種改脈絡或記憶的管理。修法的分法是整理者的建議。

關鍵觀念 · 二

成功率與失敗次數，量的是兩件事

成功率只看最後的答案對不對；MAST 標的是過程中出了哪些錯。兩者可以往不同的方向走：答案更常答對了，過程裡被標出的失誤卻變多；或是失誤少了很多，答案卻沒有更常答對。第 3 章的表 7 也說過，成功的軌跡裡一樣找得到失敗。

所以作者把 MAST 當成總分之外的第二個儀表：改了一個地方，看它壓下了哪一類失敗、有沒有讓另一類冒出來，再決定下一步改哪裡。這一段是整理者的讀法。

思考題 · 03

你上一次的修改，改到的是哪一類失敗？

想一個你最近對多代理系統做的修改：改 prompt、加一個審查代理，或改了誰能結束對話。當時你用什麼判斷它有效？

如果只看成功率，試著把修改前後各挑幾條軌跡，照 MAST 的三類各數一次失敗。成功率升了但某一類變多，代表修改有取捨；成功率沒動但某一類明顯變少，代表修改可能有用，只是還沒改到決定成敗的那一類。

驗證

全面的驗證機制

弱或不足的驗證是失敗的重要原因。軟體工程可以生成單元測試，但通用的驗證很難做：寫程式要測試覆蓋、問答要查經過認證的資料、推理可以用符號驗證，每個領域各不相同。

溝通

標準化的溝通協定

代理多半用沒有結構的文字溝通，容易含糊。把意圖與參數定清楚，才能在互動中與互動後做一致性檢查；相關研究用圖注意力建模互動，或學習選擇性溝通的協定。

訓練

用強化學習微調代理

用針對角色的演算法訓練代理，獎勵對齊任務的行動、懲罰沒效率的行為；作者舉 MAPPO、SHPPO 與 Optima 為例。

信心

機率式的信心門檻

受 Horvitz 的框架啟發：代理只在信心超過預設門檻時行動，信心低時暫停、蒐集更多資訊；門檻也可以依情況動態調整。

Chapter 12 · Related Work

既有評測看總分，這篇從失敗往上歸納

作者把自己放在三條研究線之間：解決代理系統特定難題的工作與各種基準、以單代理為主的設計原則，以及描述代理失敗的資料集與分類法。他們的定位是由下往上：從失敗的軌跡歸納出細緻的分類。

第一條線處理代理系統的特定難題。Agent Workflow Memory 用工作流程記憶處理長程的網頁導覽，DSPy 處理代理流程的程式化，StateFlow 聚焦在代理工作流程的狀態控制；也有幾篇綜述點出多代理系統的挑戰與風險。作者說這些工作各有貢獻，但都沒有提供一個跨系統、跨任務、細緻又有實證依據的失敗分類。大量的代理基準也屬於這一脈：它們是由上往下的觀點，看整體表現，或可信度、安全這類高層目標；這篇則由下往上，專注辨認具體的失敗模式。

第二條線是設計原則，多半針對單代理。Anthropic 的部落格文章強調模組化的元件、避免過度複雜的框架；Kapoor 等人示範了複雜度如何妨礙實際採用。作者把這些見解延伸到多代理的情境，並用 MAST-Data 提供實證資料，支持更穩健的設計原則的發展與驗證；這也呼應 Stoica 等人對更清楚的規格與設計原則的呼籲。

第三條線是失敗的資料集與分類法。Bansal 等人整理人與代理溝通的挑戰，這篇專注在自主的多代理系統執行時的失敗；另有評估多輪 LLM 對話、評估程式生成能力的分類法，作者說它們和「可以推廣到多代理互動與協調的失敗分類」這個目標差很多。改善多代理系統的其他工作還有：AgentEval 用 LLM 代理定義並量化多面向的評估準則；AGDebugger 讓開發者檢查、編輯訊息歷史，來除錯並引導代理團隊；同期的 Zhang 等人提出 Who&When 資料集與除錯器，把特定任務的失敗歸到某個代理與某個出錯的步驟。

作者推測不夠。圖 8 裡把 MetaGPT 的模型換成 GPT-4o，FC1、FC2 少了一些，FC3 兩個模型都高；圖 9 裡同一個模型換架構，失敗的輪廓變化更大。第 5.3 節主張需要的是組織設計上的改變。

可以。作者公開了 MAST-Data、MAST 與 LLM 標註者，附錄 C 的 agentdash 套件能直接標註一段軌跡；各框架平均每條軌跡的 API 成本約 1.8 美元，依軌跡長度而定。

Reference · 名詞速查

關鍵名詞與它們在論文裡的位置

先列研究的產出與方法，再列三大類與幾個關鍵的失敗模式，最後是系統、基準與修法。

MAST
多代理系統失敗分類法
Multi-Agent System Failure Taxonomy：14 種失敗模式、3 大類，並標出每種通常出現的執行階段（第 4 節、圖 1）。
MAST-Data
失敗資料集
1,642 條標註過的執行軌跡，來自七個框架、四個模型家族（表 1）。
MAST-Data-human
專家標註集
一致性研究裡由三位專家各自標過的軌跡，附文字理由；引言說有 21 條。
trace
執行軌跡
一次執行留下的代理對話與動作紀錄；初期分析的軌跡平均每條超過 15,000 行文字。
failure mode（FM）
失敗模式
有定義、可辨認的失敗樣式，編號 FM-1.1 到 FM-3.3（附錄 A）。
failure category（FC）
失敗類別
FC1 系統設計問題、FC2 代理間協調失誤、FC3 任務驗證問題。
execution stages
執行階段
執行前、執行中、執行後；圖 1 用它標出失敗的根源通常出現在哪裡。
Grounded Theory
紮根理論
不先設假設、讓分類從資料裡長出來的質性研究方法；用了開放編碼、持續比較、寫備忘、理論化（第 3.1 節）。
theoretical saturation
理論飽和
再多分析資料也不再出現新的失敗模式，歸納就停在這裡。
inter-annotator agreement（IAA）
標註者一致性研究
三位專家各自標同一批軌跡、討論分歧、修改定義；做了三輪（第 3.2 節）。
Cohen's κ
一致度係數
扣掉碰巧一致之後的一致程度；專家之間 0.88，LLM 標註者對專家 0.77，領域外那一輪 0.79。
LLM annotator
LLM 標註者
讓 o1 讀軌跡、MAST 的定義與 few-shot 例子，判斷出現哪些失敗並寫出理由（第 3.3 節）。
FM-1.3 Step Repetition
步驟重複
不必要地重做已完成的步驟；佔 15.7%，是 14 種裡最多的。
FM-1.5 Unaware of Termination Conditions
不知道終止條件
沒認出該停的條件；佔 12.4%，附錄 J.1 顯示它幾乎只出現在失敗的軌跡。
FM-2.4 Information Withholding
資訊扣留
握有會影響別人決定的資訊卻沒分享；圖 1 寫 0.80%，正文寫 0.85%，圖 3 是它的例子。
FM-2.6 Reasoning-Action Mismatch
推理與行動不一致
推理的結論和實際的行動對不上；佔 13.2%，是第二常見的失敗。
theory of mind
心智理論
推想別人知道什麼、需要什麼的能力；作者用它的崩潰解釋第二類失敗。
verifier
驗證者
專門檢查產出的代理或階段；有它的系統失敗較少，但常只做能否編譯這類表面檢查。
topology
拓樸
代理之間的連接與交棒方式，例如星狀、組裝線、階層式，以及流程有沒有迴圈。
ProgramDev
程式題基準
作者做的 30 道程式題；ProgramDev-v2 有 100 題，ProgramDev-v0 是 ChatDev 案例用的 32 題。
AG2（formerly AutoGen）
代理框架
前身是 AutoGen 的開源代理框架；MathChat 案例建在它上面（附錄 H.1）。
ChatDev
軟體公司模擬
用 CEO、CTO、工程師、審查者等角色分階段開發軟體；第二個介入案例（附錄 H.2）。
tactical approaches
戰術做法
針對特定失敗的直接修補：改 prompt、改拓樸、管理對話；效果常不一致（附錄 G.1）。
structural strategies
結構性策略
影響整個系統的做法：驗證、溝通協定、強化學習微調、信心量化、記憶與狀態管理（附錄 G.2）。
high-reliability organization
高可靠度組織
組織研究的概念；作者用它說明定義清楚的設計原則可以預防失敗（第 5.3 節）。
