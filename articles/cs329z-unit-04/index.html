這張表是整理者依各篇的章節對出來的，不是原文的分類。從表上看得出幾件事：

  • function-calling API：規格裡沒有這個詞，對應的原語叫 tools。伺服器用 tools/list 列出工具，客戶端用 tools/call 呼叫，要用哪一個由模型決定（MCP 第 5、6 章）。單元 1 的 Ng 在談工具使用的那封信裡，講的是同一件事的機制：模型輸出一段指定格式的字串，程式看到就去呼叫函式，把結果放回脈絡；他也提到 GPT-4 在 2023 年中推出的 function calling（Agentic Design Patterns 第 5 章）。OpenHands 說它以程式為主的動作空間也相容 tool-calling agent：工具寫成 Python 函式，再用 JSON 格式的函式呼叫交給 agent（OpenHands 第 2 章）。
  • REPL：MCP 的讀法頁沒有出現這個詞。最接近的是 OpenHands：沙箱裡跑一個 Jupyter IPython 伺服器，agent 用 IPythonRunCellAction 一段一段執行 Python（OpenHands 第 3 章）。Ng 的例子是讓模型呼叫 Python 直譯器算複利（Agentic Design Patterns 第 5 章）。SWE-agent 的 system 模板反過來寫明，不支援 python、vim 這類互動式指令（SWE-agent 第 6 章）。
  • 設計好工具、程式沙箱：規格給的是欄位與邊界。工具定義有哪些欄位在 MCP 第 6 章，roots 劃出伺服器能操作的目錄在 MCP 第 8 章。工具的描述怎麼寫、工具在哪裡執行，是其他單元的讀物在談，本頁第 2 章與第 4 章整理。
  • 錯誤處理與重試：兩邊都有專章。規格把錯誤分成兩層（MCP 第 6 章），SWE-agent 把編輯的錯誤寫成退回的訊息（SWE-agent 第 5 章），本頁第 3 章把它們並排。讀法頁裡有逾時與取消（MCP 第 4、12 章），沒有「失敗之後重試幾次」的規則。

講題裡的 MCP 就是這份規格本身。其他單元有七篇讀物在原文裡提到 MCP，本頁第 5 章逐條列出它們各拿 MCP 做什麼。

規格：欄位與義務

伺服器回覆 tools/list 時，每個工具是一份定義：唯一的 name、選用的 title、description、用 JSON Schema 寫的 inputSchema，以及選用的 outputSchema 與 annotations（MCP 第 6 章）。這一版加了 title：name 留給程式當識別字，title 是給人看的顯示名（MCP 第 5 章）。讀法頁沿用規格的說法，把 description 寫成給人讀的功能說明。

和信任有關的規則有兩條。客戶端 MUST 把工具的 annotations 當成不可信，除非它來自受信任的伺服器；總覽頁的安全原則把工具行為的描述也算進去（MCP 第 6、11 章）。結構化的結果另有一條：有 outputSchema 的工具，伺服器 MUST 讓結果符合它，客戶端 SHOULD 驗證（MCP 第 6 章）。

讀法頁整理的 2025-06-18 版沒有「描述該怎麼寫」的建議。它的版本表記下，下一版 2025-11-25 的重大變更裡有一項「工具命名指引」，內容不在本站整理的範圍（MCP 第 1 章）。

其他單元：怎麼寫

單元 2 的〈Building Effective Agents〉用整個附錄 2 談這件事。作者說工具的定義與規格值得和整體 prompt 一樣多的提示工程：站在模型的角度讀描述和參數，把定義寫成替團隊新進工程師寫的 docstring，在 workbench 跑很多範例、看模型犯什麼錯，並且防呆（poka-yoke），改參數的設計讓錯誤更難發生。作者說他們替 SWE-bench 做 agent 時，花在工具上的時間比花在整體 prompt 上的多（Building Effective Agents 附錄 2）。同一篇介紹擴增型 LLM 時，把 MCP 列為替模型做介面的一種做法（Building Effective Agents 第 2 章）。

單元 13 的 SWE-agent 把替模型設計的這一層叫做 ACI（agent-computer interface），列了四條原則：動作簡單好懂（選項少、說明短），動作精簡（一步就有實質進展），回饋有料但簡潔，用護欄擋住錯誤。作者說四條是看 agent 的軌跡、跑網格搜尋之後歸納出來的，證據的份量不同：第二、四條有消融的數字，第一條只有設計上的說明（SWE-agent 第 2 章）。消融在 SWE-bench Lite 的 300 題上用 GPT-4 Turbo 跑：預設設定 18.0%，不給 edit 指令 10.3%，搜尋改成一筆一筆看 12.0%（SWE-agent 第 8 章）。

單元 2 的〈Effective Context Engineering〉談工具集的大小。原文要工具之間的功能重疊少，每個工具自成一體、對錯誤有韌性、用途清楚，參數有描述性、不含糊；作者看到最常見的失敗是臃腫的工具集，判準是：人類工程師都說不出某個情況該用哪個工具，就別期待 agent 做得到（Context Engineering 第 4 章）。同一篇把 MCP 列為 context 的一部分，和 system 指示、工具、外部資料、對話歷史並列（Context Engineering 第 1 章）。

單元 13 的 OpenHands 談的是哪些東西值得做成工具。它的 AgentSkills 是一個自動匯入 IPython 的 Python 套件，只收兩種：模型不容易直接寫程式做到的，例如取代檔案裡特定的幾行；或要呼叫外部模型的，例如看圖、轉錄語音。模型本來就會用 pandas 讀 CSV，就不另做一個工具（OpenHands 第 5 章）。

工具回傳什麼，兩邊也各有說法。規格定的是格式：content 可以是文字、圖片、音訊、resource_link 或內嵌的資源，structuredContent 另外放一個 JSON 物件（MCP 第 6 章）。Context Engineering 要工具回傳的資訊省 token（Context Engineering 第 4 章）；SWE-agent 的第三條原則要回饋只報目前的狀態與剛才那個動作的效果，不附多餘的細節（SWE-agent 第 2 章）。

整理者的觀察

同一段描述，讀的人不同

規格把 description 寫成給人讀的說明，並把工具行為的描述列為不可信；Effective Agents 與 SWE-agent 談的是模型讀了之後會不會用錯。兩件事落在同一段文字上：它是模型要讀的 prompt，也可能來自一個不受信任的伺服器。這是整理者把幾篇並排時看到的差別，各篇都沒有這樣比；怎麼取捨留在第 6 章的判斷題。

還沒有答案的地方：四篇的寫法建議都不是在 MCP 的設定下量出來的。SWE-agent 的數字只來自軟體工程的任務，那一頁的思考題也提醒了這一點（SWE-agent 第 2 章）；Effective Agents 與 Context Engineering 寫的是團隊的經驗，沒有附數字。

規格：兩層錯誤

規格把工具出錯分成兩層（MCP 第 6 章）。協定錯誤是標準的 JSON-RPC error，用在不認識的工具、參數不合法、伺服器錯誤；工具執行錯誤放在結果裡，用 isError: true 標記，用在 API 失敗、輸入資料不合、業務邏輯錯誤。讀法頁的解讀是：前一層表示呼叫沒有成立，由客戶端處理；後一層表示呼叫成立但失敗了，錯誤文字回到模型的脈絡，模型可以換個參數或換個工具再試。

同一件事在下一版多了一句。2025-11-25 修訂版的小改動寫明，輸入驗證錯誤該回工具執行錯誤、不回協定錯誤，讓模型能自我修正；這一句不在 2025-06-18 的文字裡（MCP 第 1 章）。

等待有上限。實作 SHOULD 為每個送出的請求設逾時，逾時就送取消通知；收到進度通知 MAY 重設時鐘，但 SHOULD 永遠有一個最大逾時（MCP 第 4 章）。取消是通知，不會有回覆；網路延遲可能讓取消在請求完成之後才到，雙方 MUST 處理這種情況（MCP 第 12 章）。讀法頁整理的規則裡，沒有「失敗之後重試幾次」這類規定。

SWE-agent：錯誤寫成訊息

SWE-agent（單元 13）的 edit 指令套用修改之後，先對檔案跑 flake8。出現語法類的錯誤，修改就不套用，並把三段內容給 agent 看：錯誤類型、這次修改套上去會長怎樣、原本的內容；訊息最後要它修正行號或程式，也提醒不要重跑同一個失敗的指令（SWE-agent 第 5 章）。作者試過拿掉其中一兩段：沒有錯誤類型，agent 可能誤判錯在哪裡；沒有修改後的片段，它更常原封不動重下同一個指令；沒有原本的片段，它得回頭去找好幾輪之前的內容（同一章）。

另外兩處也和錯誤有關。回應的格式不對時，系統套一個格式錯誤的模板請它重來；收到正確的回應之後，格式錯的那次回應與錯誤訊息會從歷史裡刪掉。連續格式錯誤就提早結束：圖 26 寫連續 2 次以上，附錄 C 的正文寫 3 次，本站照錄兩處；所有的執行裡只有兩次因此提早結束（SWE-agent 第 6 章）。每一題的 instance 模板也寫了一條提示：指令沒用就換一個，同一個指令不會第二次突然成功（同一章）。

護欄的效果有消融：在 SWE-bench Lite 用 GPT-4 Turbo，拿掉 linting 從 18.0% 降到 15.0%（SWE-agent 第 8 章）。作者也寫了代價：想刪掉函式的一個參數時，受護欄限制，得在同一個動作裡把所有引用一起刪掉，或先刪引用、再刪函式標頭；要不要加一道護欄，要看它減少了多少常見的錯誤，又妨礙了多少模型偏好的做法（SWE-agent 第 5 章）。

Effective Agents：錯誤發生之前

〈Building Effective Agents〉（單元 2）把防呆放在工具的設計上。作者的例子是：agent 離開根目錄之後，用相對路徑的工具就會出錯；他們把工具改成一律要求絕對路徑，作者說改完之後，模型用這個方法沒有再出錯（Building Effective Agents 附錄 2）。同一篇談 agent 時建議加停止條件，例如最大迭代次數，把控制權留在手上（Building Effective Agents 第 7 章）。

單元 14 的 OpenClaw 把等待的上限寫成預設值：agent.wait 等 30 秒，時間到只停止等待、不停掉 run；整次 run 的預算是 48 小時；模型閒置時，雲端 120 秒、自架 300 秒就中止那一次請求（OpenClaw 第 3 章）。

整理者的讀法

三篇處理的是不同的時點

  • 呼叫之前：Effective Agents 改工具的參數，讓錯誤寫不出來；證據是團隊的經驗，沒有數字。
  • 呼叫的結果：MCP 規定錯誤放在哪一層、誰看得到；規格沒有數字。
  • 錯誤之後：SWE-agent 規定訊息寫什麼、失敗的回應留不留在歷史；數字來自 SWE-bench Lite 與 GPT-4 Turbo。
  • 放在一起：三種做法可以同時用在一個系統上；三篇沒有在同一個工具上並排量過，留在第 6 章的判斷題。

還沒有答案的地方：2025-06-18 版把「參數不合法」列在協定錯誤、「輸入資料不合」列在執行錯誤，下一版補的那一句把輸入驗證錯誤歸到執行錯誤；兩版的界線怎麼對齊，讀法頁沒有再比對。SWE-agent 的作者說加不加護欄要看取捨，沒有給通用的準則（SWE-agent 第 5 章）。

規格：誰同意

工具頁的警告是 SHOULD：永遠有人在迴圈裡，能拒絕工具呼叫；應用 SHOULD 讓人看清楚哪些工具暴露給模型、在工具被呼叫時插入明確的視覺指示、對操作向使用者確認（MCP 第 6 章）。總覽頁的安全原則把它寫成主機的事：工具代表任意的程式執行，主機在呼叫任何工具之前要取得使用者明確的同意；規格也說協定層無法強制這些原則，實作者 SHOULD 把它們做進應用（MCP 第 11 章）。

和「在哪裡」有關的規則有兩條。roots 是客戶端暴露給伺服器的檔案系統邊界，這一版的 URI MUST 是 file://，客戶端 MUST 驗證以防路徑穿越，SHOULD 在暴露之前徵求使用者同意（MCP 第 8 章）。stdio 傳輸是客戶端把伺服器當子程序啟動（MCP 第 9 章）。讀法頁整理的規則裡沒有沙箱。

其他單元：在哪裡跑

OpenHands（單元 13）每個任務 session 開一個隔離的 Docker 容器，事件流裡的動作全部在裡面執行；使用者要 agent 處理的檔案放在一個可以設定的工作目錄，掛載進沙箱（OpenHands 第 3 章）。容器的網路與權限怎麼設定，論文沒有討論，這是那一頁整理者的提醒。批准的那一面，OpenHands 的介面讓使用者隨時打斷 agent，補上回饋或指示（OpenHands 第 2 章）。

SWE-agent（單元 13）的推論與評估都在用完即丟的 Docker 容器裡跑。作者把在自己電腦上執行模型產生的程式列為第一個風險，也說 Docker 的命名空間隔離不如硬體虛擬化安全，但對不是刻意利用容器逃逸漏洞的程式碼已經足夠（SWE-agent 第 3 章）。

OpenClaw（單元 14）的沙箱預設關閉；README 說，除非設定了沙箱，main session 的工具就在主機上跑（OpenClaw 第 10 章）。開了之後 Gateway 仍在主機，只有工具執行搬進沙箱；工具的 allow／deny 政策在沙箱規則之前套用，被 deny 的工具，沙箱不會把它帶回來；tools.elevated 是讓 exec 在沙箱外跑的逃生口（OpenClaw 第 11 章）。每個 agent 的 workspace 是工具唯一的工作目錄；plugin 的 before_tool_call hook 可以擋下一次工具呼叫，而且擋下是終局的（OpenClaw 第 3 章）。

Claude Code 的文件（單元 13）把兩種控制放在同一節。權限模式：v2.1.283 起，互動式 session 預設 auto mode，由分類器模型審查動作；Manual 模式在寫檔、Bash 指令、MCP 工具之前先問。文件說批准到第十次，你已經是在點過去，不是在審；減少打擾的兩個工具是允許清單，以及限制檔案系統與網路存取的作業系統層沙箱（Claude Code 第 5 章）。〈Building Effective Agents〉（單元 2）談 agent 的代價時也建議，在沙箱環境裡大量測試，配上合適的護欄（Building Effective Agents 第 7 章）。

REPL 在哪裡跑

講題裡的 REPL 也落在這條線上。OpenHands 的 Jupyter IPython 伺服器跑在同一個沙箱裡，由容器中的執行 API 管理（OpenHands 第 3 章）。Ng 讓模型呼叫的 Python 直譯器，本站那一頁沒有談在哪裡執行（Agentic Design Patterns 第 5 章）。SWE-agent 的介面不支援 python 這類互動式指令（SWE-agent 第 6 章）。

整理者的讀法

兩條線：誰同意、在哪裡跑

MCP 的規則畫的是「誰同意」這條線：人、主機、客戶端各守什麼。OpenHands 與 SWE-agent 畫的是「在哪裡跑」這條線；Claude Code 與 OpenClaw 兩條都畫。兩條線可以同時存在，Claude Code 的文件把允許清單與沙箱寫成減少批准打擾的工具。這是整理者把幾篇並排時的讀法；哪一條擋下了什麼，本頁用到的讀物都沒有報告數字。

判斷題 · 01

第三方伺服器給的工具描述，該照單全收進 prompt 嗎？

把描述當成 prompt 來寫的一方：Effective Agents 說工具定義值得和 prompt 一樣多的提示工程，SWE-agent 的四條原則也是寫給模型的。把描述當成可能不可信的一方：MCP 規格要客戶端把 annotations 當成不可信，總覽頁的原則把工具行為的描述也算進去（都在第 2 章）。

還缺的證據：本頁用到的讀物都沒有在 MCP 的設定下量過描述的寫法，也沒有報告接上不受信任的伺服器時，描述被照用會發生什麼。

寫一個 MCP 伺服器，同一個工具準備三份描述：一份照 Effective Agents 的建議寫，一份只有一句話，一份多了一句和工具用途無關的要求。記下模型選錯工具、參數寫錯的次數，也看你的客戶端能不能在描述送進模型之前先給人看。

判斷題 · 02

工具出錯時，該交給模型自己修，還是在呼叫前就擋掉？

交給模型的一方：MCP 的工具執行錯誤把錯誤文字放進模型的脈絡，下一版把輸入驗證錯誤也歸到這一層；SWE-agent 的 linter 退回修改並附三段訊息，拿掉 linting 時 Lite 從 18.0% 降到 15.0%。在呼叫前擋掉的一方：Effective Agents 的防呆，作者說改成絕對路徑之後模型沒有再出錯（都在第 3 章）。

還缺的證據：三篇沒有在同一個工具上並排比過；SWE-agent 的數字只來自 SWE-bench Lite 與 GPT-4 Turbo，Effective Agents 的例子沒有數字。

挑一個常被模型用錯的參數，做三個版本：回協定錯誤、回 isError 並寫出原因、改參數讓那種錯寫不出來。各跑二三十次，記成功率、重試次數，以及模型有沒有原封不動重下同一個呼叫。

判斷題 · 03

工具呼叫要逐次批准，還是放進沙箱讓它跑？

逐次批准：MCP 規格要人留在迴圈裡、主機呼叫工具之前取得同意；Claude Code 的 Manual 模式在用 MCP 工具之前先問。放進沙箱：OpenHands 與 SWE-agent 每題一個容器，OpenClaw 可以把工具執行搬進沙箱；Claude Code 的文件說批准到第十次就變成照點，允許清單與沙箱是減少打擾的工具（都在第 4 章）。

可以拿來判斷的問題：你的工具動到的東西，出了容器還在不在？你拒絕的那些呼叫裡，有多少真的該擋？

讓同一個 agent 跑同一組任務兩次：一次每個工具呼叫都要你批准，一次放進容器、只在要動到容器外的東西時才問。記下你批准與拒絕的次數、花的時間，以及事後才發現該擋卻放行的呼叫。

為什麼不附答案

證據在別的系統上量出來

規格沒有數字，其他單元的數字來自各自的任務、模型與年份；放到你的工具與使用者身上會不會成立，要自己量過才知道。這一頁只負責把證據排在一起，判斷留給讀者。

Reference · 用詞對照

同一件事，各篇用不同的名字

規格和其他單元的讀物，對工具、錯誤與邊界各有說法。每一條先寫這件事，再列各篇怎麼稱呼、在本站讀物頁的哪一章；沒有談到的篇就不列。

tool
工具叫什麼
MCP：tools，模型控制的原語（第 5、6 章）。Ng：模型請求呼叫的函式（第 5 章）。SWE-agent：自訂指令，每個有簽名與說明（第 3 章）。OpenHands：動作，加上 AgentSkills 的 Python 函式（第 2、5 章）。
function calling
函式呼叫
課程講題的用語。MCP：tools/call（第 6 章）。Ng：GPT-4 在 2023 年中推出的 function calling（第 5 章）。Effective Agents：回應裡的 tool use 區塊（附錄 2）。OpenHands：JSON 格式的函式呼叫（第 2 章）。
tool definition
工具定義
MCP：name、title、description、inputSchema、outputSchema、annotations（第 6 章）。Effective Agents：工具的定義與規格（附錄 2）。SWE-agent：指令的簽名、說明與參數，編進 system 模板（第 3、6 章）。
ACI
替模型設計的介面
SWE-agent：agent-computer interface，全篇的主題（第 1、2 章）。Effective Agents：替 ACI 投入和 HCI 一樣多的心力（附錄 2）。OpenHands：AgentSkills 是可擴充的 ACI（第 5 章）。MCP 的讀法頁沒有用這個詞。
tool error
工具出錯
MCP：協定錯誤與工具執行錯誤（isError）兩層（第 6 章）。SWE-agent：護欄、linter 退回的訊息、格式錯誤模板（第 5、6 章）。Effective Agents：防呆，poka-yoke（附錄 2）。
timeout
等待的上限
MCP：逾時 SHOULD、最大逾時、取消通知（第 4、12 章）。OpenClaw：agent.wait 30 秒、run 預算 48 小時（第 3 章）。SWE-agent：成本上限、連續格式錯誤就結束（第 6 章）。Effective Agents：停止條件，例如最大迭代次數（第 7 章）。
human in the loop
誰批准
MCP：人在迴圈裡（SHOULD）、主機取得同意（第 6、11 章）。Claude Code：auto 與 Manual 權限模式、允許清單（第 5 章）。OpenClaw：工具政策的 allow／deny、before_tool_call hook（第 3、11 章）。OpenHands：使用者隨時打斷（第 2 章）。
sandbox
在哪裡跑
OpenHands：每個 session 一個 Docker 容器（第 3 章）。SWE-agent：用完即丟的 Docker 容器（第 3 章）。OpenClaw：沙箱的 mode 與後端，預設關閉（第 11 章）。Claude Code：作業系統層的沙箱（第 5 章）。MCP：roots 劃出伺服器能操作的目錄（第 8 章）。
REPL
互動式執行
OpenHands：沙箱裡的 Jupyter IPython 伺服器，IPythonRunCellAction（第 2、3 章）。Ng：Python 直譯器工具（第 5 章）。SWE-agent：不支援 python、vim 這類互動式指令（第 6 章）。
MCP server
MCP 伺服器
MCP：提供脈絡與能力的服務，可以是本機子程序或遠端服務（第 2 章）。Claude Code：用 claude mcp add 接上的外部工具（第 5 章）。Effective Harnesses：Puppeteer MCP（第 5 章）。Demystifying Evals：評估任務要寫出來的東西（第 1 章）。
skill
名字相近的兩種東西
OpenHands：AgentSkills，一個 Python 工具函式庫（第 5 章）。OpenClaw：含 SKILL.md 的資料夾，教 agent 怎麼、何時用工具（第 12 章）。站上的非課程文章〈Agent Skills〉談的也是含 SKILL.md 的資料夾（第 1 章）。
context
脈絡
MCP：伺服器只拿到必要的脈絡，看不到整段對話（第 2 章）。Context Engineering：工具與 MCP 都是 context 的一部分（第 1 章）。Claude Code：和外部服務互動，CLI 是最省 context 的方式（第 5 章）。
resource_link
先給位置，再載入
MCP：工具結果可以回一個 URI，客戶端再抓或訂閱（第 6 章）。Context Engineering：agent 手上留輕量的識別碼，需要時才載入（第 5 章）。兩者放在一起是整理者的對照。
