Effective Context Engineering · 圖卡＋教材整合版

Effective Context Engineeringcontext 是有限的資源 每一步都要重新挑

用模型做事的功夫，正在從「找對 prompt 的措辭」移到「決定這一步要讓模型看到哪些 token」。Anthropic 的 Applied AI 團隊把這件事叫做 context engineering：模型的注意力是一份有限的預算，所以每一步都要找出最小、訊號最強的一組 token。本頁分十二章重述，從 system prompt、工具與範例，到跑的時候怎麼找資料，再到長任務怎麼撐過 context window 的上限。每章開頭先放一張圖解卡講重點，往下是詳細說明；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

問題從「怎麼寫 prompt」變成「給模型看什麼」

單次呼叫的年代，功夫花在措辭上；agent 要跑很多輪，真正要管的是每一輪送進模型的那一整包 token。

這篇是 Stanford CS 329Z 第 2 週的選讀。那一講（LLMs for Builders）談用模型做產品的基本功：API、結構化輸出、context engineering、怎麼選模型、成本與延遲；這篇負責其中 context engineering 的部分。

原文的起點是一個定義：context 就是從模型取樣時放進去的那一組 token。工程上的問題，是在模型本身的限制下讓這組 token 發揮最大用處，穩定地得到你要的結果。作者用「用 context 思考」形容這種習慣：隨時想著模型此刻手上有哪些東西，以及這些東西可能引出什麼行為。

全文的論證順序很清楚，本頁照著走：先分清楚 context engineering 和 prompt engineering，再解釋為什麼 context 是有限的資源；接著看寫的時候怎麼收緊（system prompt、工具、範例），跑的時候怎麼找資料（即時載入），最後是長任務的三種技巧：壓縮、結構化筆記、子 agent。

給初學者

先把五個名詞對齊

  • Token：模型讀寫文字的最小單位；context 的長度用 token 數來算。
  • Context window：模型一次能看到的 token 上限。system prompt、工具定義、對話歷史、工具結果全部擠在裡面。
  • System prompt：放在最前面、告訴模型處境與規則的指示。
  • Agent：原文採用的定義很短，就是模型在迴圈裡自主地使用工具。
  • Context engineering：在推論時挑選、維護「最適合的那一組 token」的策略，範圍包含 prompt 以外所有會進到 context 的東西。
prompt 仍然要寫好，但它只是 context 的一部分；agent 每多跑一輪，要決定的就不只是措辭。 序章核心觀念

注意：原文把 context engineering 看成 prompt engineering 的自然延伸；寫好 prompt 仍是其中一塊，所以這張不用 ✗／✓。

prompt engineering 指的是怎麼寫、怎麼組織給模型的指示，讓結果最好，重心通常在 system prompt。context engineering 指的是在推論期間挑選並維持最適合的那一組 token 的策略；除了 prompt，還包含其他所有可能落進 context 的資訊。

兩者的差別來自用途的變化。早期用模型做事，除了日常聊天，大部分用途是一次性的分類或文字生成，一個調好的 prompt 就是工作的大半。現在要做的是能跑很多輪推論、持續更長時間的 agent，要管理的是整個 context 的狀態：system 指示、工具、MCP、外部資料、對話歷史。

agent 在迴圈裡跑，每一輪都會產生更多可能和下一輪推論有關的資料，這些資料得一輪一輪地篩過。原文借用 Karpathy 的說法（附了他的貼文連結），把 context engineering 形容成一門「藝術與科學」：從一個不斷長大的資訊池裡，挑出要放進那個有限視窗的東西。原文附圖的說明也強調同一點：寫 prompt 是一件離散的任務，context engineering 是反覆的，每一次決定要把什麼傳給模型，挑選就發生一次。

注意：分段條是整理者的示意畫法，原文沒有畫圖也沒有給數字；原文的結論是把 context 當成邊際效益遞減的有限資源。

作者觀察到，模型雖然處理得了越來越大量的資料，卻和人一樣，到某個程度就會失焦或混淆。大海撈針式的基準測試揭露了一個叫 context rot 的現象（原文連結到 Chroma 的研究）：context window 裡的 token 數增加，模型從中準確回想資訊的能力就下降。有些模型退化得比較平緩，但每個模型都有這個特性。

所以 context 要被當成一種邊際效益遞減的有限資源。人的工作記憶容量有限，模型則有一份「注意力預算」，讀大量 context 時就從這份預算裡支出；每多放進一個 token，預算就被用掉一些。這是要仔細挑選 token 的理由。原文接著從架構上解釋這份稀缺從哪裡來，一共三個因素。

01

n² 組兩兩關係

模型建立在 transformer 架構上，每個 token 都能注意整段 context 裡的每一個 token；n 個 token 就有 n² 組兩兩關係。context 越長，模型掌握這些關係的能力被拉得越薄，context 的大小和注意力的集中天生互相拉扯。

02

訓練資料以短序列居多

模型的注意力模式是從訓練資料學來的，而資料裡短序列比長序列常見。結果是模型對跨越整段 context 的依賴關係，經驗比較少，專門處理它的參數也比較少。

03

位置編碼內插

位置編碼內插這類技術，把較長的序列調整到模型原本訓練時的較短長度來處理，讓模型撐得住更長的輸入；代價是對 token 位置的理解會有些退化。

三個因素加起來，造成的是一道漸層，而不是一個懸崖。模型在長 context 下仍然很能幹，只是和短 context 相比，資訊檢索與長距離推理的精準度會降低。作者由此下結論：要做出能幹的 agent，用心的 context engineering 是必要的。

多放一個 token 不是免費的：它會分走一點注意力，你真正需要的那段資訊就分到少一點。 整理自第二節

「最少」是把期望行為完整講清楚所需的最少資訊，不是字數越少越好；prompt 的確切格式（XML 或 Markdown），會隨模型變強越來越不重要。
注意：兩端的失敗與中間的原則出自原文；卡內的 prompt 片段是整理者寫的示意，四步切成四格也是整理者的畫法。

既然注意力是有限的預算，原文替整個 context 定了一條指導原則：找出最小、訊號最強的一組 token，讓想要的結果出現的機率最大。作者也承認這說起來比做起來容易得多，所以接著把它落到 context 的各個組成上，第一個就是 system prompt。

system prompt 要非常清楚，用簡單直接的語言，而且寫在適合 agent 的「高度」。這個高度是兩種常見失敗之間的那一段。一端是工程師把複雜又脆弱的邏輯寫死在 prompt 裡，想逼出精確的 agent 行為；這讓系統越來越脆弱，維護也越來越複雜。另一端是只給模糊、高層的指引，模型拿不到產出該長什麼樣的具體訊號，或者寫的人誤以為模型和自己有共同的背景。剛好的高度同時做到兩件事：具體到能有效引導行為，又有足夠的彈性，給模型強的啟發法去應付各種情況。

結構上，作者建議把 prompt 分成幾個明確的區段，例如背景資訊、指示、工具指引、輸出說明，用 XML 標籤或 Markdown 標題把它們隔開。不過他們也說，隨著模型變強，prompt 的確切格式大概會越來越不重要。

示意 · 一份分段的 system prompt（教學用骨架，非原文） 
<background_information>
你在協助一家線上書店處理客戶問題。      # 背景：模型需要知道的處境
</background_information>

<instructions>
先確認訂單狀態再回答；確認不了時，說明還需要哪些資訊。  # 給啟發法，不寫 if-else
</instructions>

## Tool guidance
查訂單用 lookup_order；它只能查，不能改資料。

## Output description
兩到四句，最後一句寫出下一步。

不管用什麼格式，目標都是用最少的資訊把期望的行為完整描述出來。原文特別提醒，最少不等於最短：agent 一開始仍然需要足夠的資訊，才會照期望行動。建議的做法是先用手上最好的模型，測一份最小的 prompt 在你的任務上表現如何，再根據初步測試找到的失敗模式，補上清楚的指示與範例。

實作提示

讓失敗決定 prompt 要長多長

從最小的版本出發，每一條新加的指示都對應一個觀察到的失敗。這樣寫出來的 prompt 會停在「剛好夠」的地方，不會一開始就把所有想像得到的狀況都寫進去。這段是整理者依原文建議做的延伸。

工具讓 agent 能和環境互動，一邊做事一邊把新的 context 拉進來。因為工具界定了 agent 和它的資訊空間、行動空間之間的契約，原文要求工具促進效率：回傳的資訊要省 token，也要引導 agent 用有效率的方式做事。

這一節先回顧定義。Anthropic 在〈Building effective AI agents〉裡區分過工作流與 agent；之後他們越來越傾向一個簡單的定義（原文連結到 Simon Willison 的整理）：agent 就是模型在迴圈裡自主地使用工具。作者和客戶合作時看到整個領域正往這個簡單的樣子收斂；模型越強，agent 能承擔的自主程度就越高，能自己在細膩的問題空間裡找路，也能從錯誤中恢復。

這也改變了工程師替 agent 設計 context 的方式。今天許多 AI 原生應用會在推論之前用 embedding 做檢索，把重要的 context 找出來給 agent 推理。隨著領域轉向更 agentic 的做法，越來越多團隊在這類檢索系統之外，加上「即時」（just in time）的策略。

即時策略不預先處理所有相關資料，而是讓 agent 手上保留輕量的識別碼，例如檔案路徑、存好的查詢、網址，跑的時候再用工具把資料動態載入 context。Claude Code 用這個方法分析大型資料庫：模型寫出有針對性的查詢、把結果存起來，再用 head、tail 這類 Bash 指令看大量資料，完全不必把整份資料物件載進 context。原文說這很像人的做法：我們不背下整批資料，而是靠檔案系統、收件匣、書籤這類外部的組織與索引，需要時再去找。

識別碼本身也帶著訊號。在檔案系統裡工作的 agent，看到 tests 資料夾裡的 test_utils.py，和看到 src/core_logic/ 底下同名的檔案，會推斷出不同的用途。資料夾層級、命名慣例、時間戳，對人和 agent 都是判斷「怎麼用、什麼時候用」這份資訊的線索。

讓 agent 自己導航、自己取資料，還帶來漸進揭露（progressive disclosure）：agent 透過探索，一步一步發現相關的 context。每一次互動都會帶回下一個決定需要的線索：檔案大小暗示複雜度，命名暗示用途，時間戳可以拿來估計相關性。agent 一層一層建立理解，工作記憶裡只留必要的東西，要長期保存的就寫成筆記。這種自己管理的 context window，讓 agent 專注在相關的子集，不會淹沒在大量卻未必相關的資訊裡。

代價

跑的時候探索，比讀預先算好的資料慢

原文把取捨講得很直接：即時探索比取用預先計算的資料慢，而且要有主見、周到的工程設計，模型才有對的工具與啟發法在資訊之間導航。沒有適當的引導，agent 會用錯工具、追進死路、找不到關鍵資訊，白白浪費 context。

所以在某些情境下，最有效的 agent 可能採用混合策略：先取一部分資料換速度，其餘讓 agent 自己決定要不要再探索。自主要放多少，看任務而定。Claude Code 就是混合的：CLAUDE.md 檔案一開始就直接放進 context，glob 和 grep 這類基本工具則讓它即時在環境裡找檔案，避開索引過時與複雜語法樹的問題。

原文認為，內容變動比較少的情境，例如法律或金融工作，可能更適合混合策略。長期的方向則是隨著模型變強，agentic 的設計會越來越放手讓聰明的模型自己判斷，需要人工預先挑選的越來越少。在這個變化速度下，作者給團隊最好的建議大概仍是：先做最簡單、能用的那一版。

壓縮要把一個視窗的內容高保真地濃縮，讓 agent 在表現幾乎不下降的情況下接著工作；它通常是第一個拉的槓桿。

壓縮的做法是：拿一段快要碰到 context window 上限的對話，把內容摘要，再用這份摘要重新開一個 context window。它通常是 context engineering 裡第一個拉的槓桿，用來換取長期的連貫。核心是用高保真的方式把一個視窗的內容蒸餾出來，讓 agent 在表現幾乎不下降的情況下繼續工作。

以 Claude Code 為例，做法是把訊息歷史交給模型，請它摘要並壓縮最關鍵的細節。模型會保留架構上的決策、還沒解決的 bug、實作細節，丟掉重複的工具輸出或訊息。agent 接著帶著這份壓縮過的 context，加上最近存取過的五個檔案繼續做。使用者得到的是連續的工作，不必操心視窗的上限。

壓縮的難處在取捨。壓得太兇，會丟掉一些細微但關鍵的 context，而它的重要性常常要到後面才看得出來。原文給實作壓縮系統的工程師一個調整順序：拿複雜的 agent trace 來仔細調壓縮用的 prompt，先把召回率拉到最高，讓 trace 裡每一條相關資訊都被抓到；再一輪一輪提高精準度，刪掉多餘的內容。

示意 · 壓縮用 prompt 的第一版（教學用草稿，非原文） 
# 第一輪：先求召回，寧可多留
把以上對話壓縮成一份接手用的摘要。
必須保留：架構決策與理由、還沒解決的 bug、做到一半的實作細節。
可以丟掉：已經處理完的工具輸出、重複的訊息。
# 之後拿真實的 agent trace 比對，確認沒漏，再逐條刪多餘的內容

最容易下手的多餘內容，是工具呼叫與它的結果。一個工具在訊息歷史深處被呼叫過之後，agent 為什麼還需要再看一次原始結果？清掉工具結果是最安全、最輕量的壓縮形式之一，最近也在 Claude Developer Platform 上推出成一項功能。

實作提示

先召回、後精準，順序不能反

先求精準，容易在一開始就把「看起來多餘、其實後面會用到」的東西刪掉，而這種損失在短測試裡看不出來。先確定該留的都留下，再慢慢修剪，犯的錯頂多是多留了一些 token，比較容易察覺，代價也比較小。這段理由是整理者的引申，順序本身出自原文。

Chapter 08 · Structured note-taking

筆記寫在視窗外，重置之後讀回來接著做

結構化筆記也叫 agentic memory：agent 定期寫下筆記，存在 context window 之外的記憶裡，之後需要時再拉回 context。它用很小的額外負擔換到持久的記憶。Claude Code 建立待辦清單，或你自己的 agent 維護一份 NOTES.md，都是這個簡單的模式：agent 可以在複雜任務裡追蹤進度，把原本會在幾十次工具呼叫之間流失的關鍵脈絡與依賴關係留下來。

關鍵觀念 · 整理者的觀察

重置清空的是視窗，檔案還在

壓縮是把視窗裡的東西濃縮了再帶著走；筆記則是 agent 在過程中主動把重要的東西寫到視窗外。重置之後，視窗是空的，但檔案還在，agent 讀回來就能接上。

所以筆記的品質取決於 agent 在當下判斷「什麼之後會用到」的能力。寶可夢的例子有意思的地方，就是這個判斷在沒有人教它記憶結構的情況下自己長出來了。

Anthropic 在推出 Sonnet 4.5 時，也在 Claude Developer Platform 上推出公開測試的 memory tool：一套以檔案為基礎的系統，讓 agent 更容易在視窗外存放與查詢資訊。agent 可以藉此逐步累積知識庫、跨 session 維持專案狀態、參照過去的工作，而不必把所有東西都留在 context 裡。

Chapter 09 · Sub-agent architectures

補充說明

和第 5 章的即時載入是同一個想法的放大

即時載入是一個 agent 只把需要的那一片拉進自己的視窗；子 agent 架構則把整段探索交出去，只把結果拉回來。兩者守的是同一條原則：主要的 context 裡只放高訊號的 token。這段對照是整理者的整理，原文沒有把兩節並列。

整理者的思考題 · 02

你的長任務，比較像連續的對話、有里程碑的開發，還是需要平行探索的研究？

拿一個最近跑到 context 上限的任務，對照第 6 章的三種形狀。

來回很多的先試壓縮；有明確里程碑的讓 agent 維護一份筆記；要同時查很多來源的才考慮子 agent。原文說選擇取決於任務的特性。

Chapter 10 · Conclusion

每一步都找最小、訊號最強的一組 token

不論是做壓縮、設計省 token 的工具，還是讓 agent 即時探索環境，指導原則都是同一條。模型越強，需要的規定越少，但 context 仍是珍貴而有限的資源。

作者把 context engineering 看成用模型做事的方式的一次根本轉變。模型越強，挑戰就越不只是寫出完美的 prompt，而是在每一步用心挑選：哪些資訊可以進入模型那份有限的注意力預算。

"find the smallest set of high-signal tokens" 「找出最小、訊號最強的一組 token。」這是原文結論重申的指導原則，後半句是：讓想要的結果出現的機率最大。第 3 章開頭也是同一句。

文中的技巧會隨著模型進步而演變。作者已經看到，越聰明的模型需要越少規定式的工程，agent 能以更高的自主程度運作。但即使能力持續提升，把 context 當成珍貴、有限的資源來對待，仍會是做出可靠、有效 agent 的核心。原文最後指向 Claude Developer Platform，以及一份記憶與 context 管理的 cookbook。

寫的時候收緊，跑的時候少拿，長任務時懂得放下：三件事都是在替注意力預算記帳。 整理自全文

下面這份清單不在原文裡，是整理者把全文的建議壓成的順序，讓你今天就能對自己的 agent 跑一輪。

  1. 用最好的模型測一份最小的 system prompt分成背景、指示、工具指引、輸出說明幾段；只針對觀察到的失敗模式補指示與範例。
  2. 把工具清單砍到人能一口說出怎麼選功能重疊的合併或刪掉；參數名稱與描述寫到不含糊；回傳只給省 token 的資訊。
  3. 把邊界情況清單換成幾個典型範例挑多樣、能代表期望行為的例子，不要試著窮舉每條規則。
  4. 大資料改成帶識別碼、跑的時候再載入檔案路徑、存好的查詢、網址；需要速度的部分先放進 context，其餘讓 agent 自己找。
  5. 長任務先加最輕的壓縮清掉深埋在歷史裡的工具結果；要做摘要時，先在真實的 trace 上把召回調到最高，再修精準。
  6. 依任務形狀加上筆記或子 agent有里程碑的開發讓 agent 維護一份筆記；需要平行探索的研究交給子 agent，只收摘要。
整理者的思考題 · 03

你的 agent 下一次呼叫模型時，context 裡有多少 token 是這一步真的用得到的？

把某一輪的完整 context 印出來，逐段標記：這一步用得到、之後可能用到、已經用不到。

「已經用不到」的那一堆，就是原文說的污染；可以從清掉工具結果、壓縮，或改成即時載入開始處理。

Reference · 名詞速查

十七個名詞，看懂 context 怎麼被管理

依「定義、為什麼、寫的時候、跑的時候、長任務」的順序排，解釋都是整理者依原文的用法寫的。

Context
情境
從模型取樣時放進去的整組 token：system prompt、工具、範例、對話歷史、工具結果都算。
Context window
情境視窗
模型一次能處理的 token 上限；長任務的 token 總數會超過它。
Prompt engineering
提示工程
寫與組織給模型的指示，重心在 system prompt；原文把 context engineering 看成它的自然延伸。
Context engineering
情境工程
推論時挑選並維持最適合的一組 token 的策略；每次決定要傳什麼給模型時都要做一次。
Context rot
情境腐化
token 越多，從 context 準確召回資訊的能力越差；大海撈針式測試觀察到，每個模型都有。
Attention budget
注意力預算
原文的比喻：模型讀 context 時有一份有限的注意力，每個新 token 都會用掉一些。
Right altitude
剛好的高度
system prompt 介於「寫死的 if-else」與「空泛的指引」之間的那一段：夠具體，又給得出啟發法。
Few-shot prompting
少樣本提示
在 prompt 裡給範例；原文建議給多樣、典型的範例，不要塞邊界情況的長清單。
Just-in-time context
即時載入
agent 只保留檔案路徑、查詢、網址這類識別碼，跑的時候再用工具載入需要的資料。
Progressive disclosure
漸進揭露
agent 透過探索一步步發現相關的 context；每次互動帶回的線索決定下一步看哪裡。
Hybrid strategy
混合策略
先放一部分資料進 context 換速度，其餘讓 agent 自己探索；Claude Code 先放 CLAUDE.md，再用 glob、grep 找檔。
Long-horizon task
長任務
連續數十分鐘到數小時、token 總數超過 context window 的任務，例如大型程式庫遷移。
Context pollution
情境污染
context 裡累積了不相關或多餘的資訊；原文認為任何大小的視窗都躲不掉。
Compaction
壓縮
快到上限時摘要對話，帶著摘要開新視窗；Claude Code 另外附上最近存取的五個檔案。
Tool result clearing
工具結果清除
最輕量的壓縮：把歷史深處已經用過的工具結果清掉，agent 不必再看一次原始輸出。
Structured note-taking
結構化筆記
也叫 agentic memory：agent 定期把筆記存到視窗外，之後讀回；memory tool 是平台提供的檔案式版本。
Sub-agent architecture
子 agent 架構
主 agent 拿高層計畫協調，子 agent 在乾淨的視窗深挖，交回 1,000 到 2,000 token 的摘要。
