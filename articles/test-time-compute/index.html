SCALING LLM TEST-TIME COMPUTE OPTIMALLY · 圖卡＋教材整合版

多想一下有沒有用， 看題目對模型多難依難度分配測試時算力， 有時勝過把模型放大 14 倍

讓語言模型在回答前多花一點算力，有幾種做法：多抽幾個答案挑最好的、對一個驗證器做搜尋，或讓模型一次次修改自己的答案。這篇論文用 MATH 數學題與 PaLM 2 系統地比較這些做法，發現哪一種有效，要看題目對這個模型有多難；依難度分配算力，比 best-of-N 最多省 4 倍。作者再把同樣的 FLOPs 拿去預訓練一個大約 14 倍的模型來比：簡單與中等的題目、或推論量不大的情境，多花測試時算力比較划算；最難的題目或推論量很大時，還是放大模型比較有效。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

調推論算力這一塊，從這篇論文讀起

Stanford CS 329Z 第 5 週「Optimization」那一講，把讓系統變好的方法排成一張全景：調 prompt、調權重、調推論算力。這篇 2024 年的論文回答第三件事：推論時多花的算力要怎麼花，什麼時候它比把模型做大更划算。它和 GEPA 同列這一講的必讀。

這一講的講題從 prompt 一路談到微調。prompt 這一側有 GEPA、MIPROv2、OPRO、TextGrad 這些自動最佳化 prompt 的方法；權重這一側有 LoRA、QLoRA 這類參數高效的微調、蒸餾，以及 RLHF、DPO 這類對齊方法；中間還有一塊是 test-time compute，也就是推論時的算力。講題最後落在一個實務問題：手上的系統不夠好時，該調 prompt、調權重，還是調推論算力。這篇論文是最後一塊的代表讀物。它研究的是：驗證器與修訂模型都微調好之後，回答每一題時多給的生成次數要怎麼用，才能換到最多的準確度。

同一講的另一篇必讀 GEPA 在調 prompt：讓模型讀執行的軌跡、反思之後改寫 prompt。兩篇放在一起讀（這是整理者的讀法）：GEPA 改的是每次呼叫都會帶著的指令，成本在開發時付一次；這篇改的是每一題花多少次生成，成本在每一次推論時都要付。兩篇問的是同一件事的兩面：模型不換，準確度還能從哪裡來。第 13 章的最後會回到這一講的問題，看這篇給了什麼判斷標準。

第一作者 Charlie Snell 當時在 UC Berkeley，這項工作是他在 Google DeepMind 實習期間做的；另外三位作者在 Google DeepMind，其中 Kelvin Xu 與 Aviral Kumar 是共同指導。論文 2024 年 8 月貼上 arXiv，只有 v1；課程書單把它列為 ICLR 2025 的論文，論文本身沒有寫會議名，這一頁的數字都依 arXiv v1。實驗只用了 MATH 一個資料集與 PaLM 2-S* 一個模型，數字只對那個設定成立；這一頁更在意「算力怎麼分配」背後的道理。

讀論文和讀部落格文章不同，處理方式先說清楚。章節跟著論文的論證走：第 1、2 章是問題與兩個旋鈕（論文第 1、2 節），第 3 章是依難度分配的定義與實驗設定（第 3、4 節），第 4 到 6 章是驗證器與搜尋（第 5 節），第 7 到 9 章是修訂模型（第 6 節），第 10、11 章是預訓練與測試時算力的交換（第 7 節），第 12 章是相關工作（附錄 A），第 13 章是討論與限制（第 8 節）。第 6.1 節拆成兩章（怎麼訓練、怎麼用），第 7 節拆成兩章（匯率怎麼算、結果怎麼讀），附錄 B 到 K 併進對應的章。這篇論文沒有任何表格，結果幾乎都畫成圖，圖上的點也多半沒有標數字：這一頁只用正文與圖說寫出的數字，加上圖 1 右邊長條上印出的百分比；其他圖只轉述原文描述的走勢，並附上「怎麼讀這張圖」的說明。整理者自己算的數字會標出來，公式都改用文字講。

多想一下有沒有用，要看題目對模型多難

先前的研究對「多花推論算力」有好有壞的結論。作者在 MATH 上系統地比較兩種做法，發現有效與否取決於題目對這個模型有多難：簡單題適合讓模型修改自己的答案，難題要多試幾種解法，最難的題多花算力幾乎沒用。

引言從人的習慣講起：遇到難題，人會想久一點，做出的決定才可靠。作者問的是，今天的大型語言模型能不能也這樣：面對一個有挑戰性的問題，把額外的推論算力用得最有效，讓答案更準。理論上，推論時多算一點，模型應該能做得比它訓練出來的樣子更好。作者列了兩個動機：如果預訓練的模型大小能用推論算力換，就能在裝置上用小模型取代資料中心規模的大模型；用推論算力自動產生更好的輸出，也是一條比較不需要人工監督的自我改進路線。

先前的結果互相矛盾。有些研究顯示模型能用測試時算力改善輸出；另一些研究則顯示，在數學推理這類較複雜的任務上效果很有限，即使推理題多半只是要從已有的知識推論，不需要新知識。這種矛盾，是作者做這份系統分析的理由。

最簡單、研究最多的做法是 best-of-N：從 base 模型平行抽 N 個答案，用學過的驗證器或 reward model 挑分數最高的。作者認為可以從兩個方向改進：改「提案分布」，也就是答案從哪裡抽，例如讓模型循序修訂原本的答案；或改驗證器的用法，例如訓練一個逐步打分的過程型驗證器，再對它做搜尋。實驗用 MATH 數學題與 PaLM 2 模型，模型事先微調過：一個學會修訂答案，一個學會檢查每一步對不對。作者在註腳說明，連強的專有模型都還沒有這兩種能力，所以要針對能力微調；他們預期未來的模型會直接具備，不再需要這一步。

主要發現是：一種測試時算力的做法有沒有效，同時取決於題目本身與 base 模型。題目簡單、模型本來就寫得出像樣的答案時，讓它一次次修正初始答案（循序修訂 N 次），可能比平行抽 N 個獨立答案更划算；題目較難、需要試很多種高層解法時，平行重抽，或對過程獎勵模型做樹搜尋，比較可能有效。所以作者主張依題目選做法的「compute-optimal」策略，並用「對這個模型來說的題目難度」預測哪種做法會有效。引言的說法是，照這樣分配，修訂與搜尋都只用大約四分之一的算力，就超過 best-of-N；第 5 節對搜尋的說法比較保守，是「幾乎追上」。

引言最後預告第 7 節：在 FLOPs 對等下，拿小模型加上測試時算力，和預訓練一個 14 倍大的模型比。簡單與中等的題目，在某些預訓練與推論負載的條件下甚至包括難題，多花測試時算力常常比較好；最難的題目，多花測試時算力幾乎沒有幫助，把算力花在預訓練比較有效。作者的解讀是，目前的測試時做法還不能和預訓練一比一互換，但即使方法還很天真，擴展測試時算力在某些情境已經比擴展預訓練好；長期來看，預訓練花的 FLOPs 可能變少、推論花的變多。

作者先換一個角度看測試時算力：多用的算力，是在測試時依這一題調整模型預測的分布，讓輸出比直接從模型抽樣更好。能動手的地方有兩個。一個在輸入端：在 prompt 裡加上額外的 token，讓模型以它們為條件，得到新的分布。另一個在輸出端：從原本的模型抽出好幾個候選，再對這些候選動手術，例如打分、挑選、沿著分數搜尋。作者拿它比作 MCMC（馬可夫鏈蒙地卡羅）：用一個簡單的提案分布加上一個評分函數，從複雜的目標分布取樣。

改提案分布有兩類做法。一類是針對推理任務直接微調模型，例如 STaR、ReST-EM 這種受強化學習啟發的方法，它們不加任何輸入 token，而是讓模型本身的分布變好。另一類在測試時叫模型批評並修改自己的輸出，一輪一輪地改，前面的嘗試會放進 prompt。作者指出，直接 prompt 現成的模型去修訂效果不好，所以他們特別微調了一個會迭代修訂答案的模型，做法沿用 Qu 等人：在 on-policy 的資料上，以 best-of-N 引導出來的改進當訓練目標。第 7 章會看到，作者因為算力成本改了其中幾個步驟。

驗證器那一側，最標準的用法是 best-of-N：抽 N 個完整的解，依驗證器挑最好的。更進一步，可以訓練一個過程型驗證器，也就是 PRM（process reward model），它對解裡的每一個中間步驟預測對不對，不只看最後答案。有了逐步的分數，就能在解的空間裡做樹搜尋，比單純的 best-of-N 更有效率地對驗證器搜尋。

兩個旋鈕在論文裡分開研究：第 5 節只動驗證器，提案分布維持 base 模型；第 6 節換成修訂模型當提案分布，再用驗證器或多數決挑答案。第 3 卡把兩條軸畫成四格，四格在論文裡都有對應的做法；唯一沒試的組合是 PRM 樹搜尋加上修訂，作者把它列在第 8 節的未來方向。

第 3 節先把問題講清楚：給一個 prompt 和一份測試時算力預算，怎麼決定最有效的用法？和直接用一個大得多的預訓練模型比，又會如何？同一份預算有很多種花法。以修訂模型當提案分布、ORM 當驗證器為例，可以把預算全部拿去平行抽 N 個再做 best-of-N，也可以讓修訂模型循序改 N 次、再用 ORM 從這條序列裡挑，或是在兩個極端之間取一個比例。對驗證器搜尋時，還可以選 beam search、lookahead search 或 best-of-N，哪一個好要看驗證器與提案分布的品質。

作者的直覺是：簡單題的初始答案多半已經在對的方向，只差修正，應該比較受益於修訂；難題可能要探索不同的高層解法，平行多抽幾次比較好；較複雜的搜尋，可能在難題上比單純的 best-of-N 或多數決有用。

第 3.1 節把「compute-optimal 的擴展策略」寫成式 1。用文字講是：把「用超參數 θ、預算 N 回答題目 q 時，模型輸出的分布」叫做目標分布；對每一題，選一組讓這個分布抽出正確答案的機率最高的 θ。θ 可以是修訂與平行的比例，也可以是搜尋演算法與它的參數。這個定義要知道每一題的正確答案才算得出來，所以實際上只能近似。作者的近似是用題目的某個統計量當條件，這個統計量就是難度；它雖然只是式 1 的近似解，比起隨意或平均地分配推論算力，仍然帶來明顯的改善。

1
估難度每一題抽 2048 個解，算出一個難度分數。
2
分五級依分數的五分位，把測試題分成五個難度等級，等級越高越難。
3

難度的定義照 Lightman 等人：對一個給定的 base 模型，每一題用 2048 個樣本估 pass@1，再依五分位切成五個等級。作者發現，這種依模型而定的等級，比 MATH 資料集本身的人工難度標籤更能預測測試時算力有沒有用。在這個設計裡，難度就是一題的充分統計量：同一個等級的題目，用同一組設定。

問題是 pass@1 要用標準答案檢查，部署時拿不到。作者把它叫做 oracle 難度，另外做一個模型預測的版本：同樣那 2048 個樣本，改用學過的驗證器對最後答案的分數取平均，再用同樣的方法分五級，叫做 predicted 難度。它不需要標準答案，但估難度本身也要花推論算力。作者說這一次性的成本可以併進真正的推論策略裡，例如用驗證器搜尋時，同一批抽樣也能拿來估難度；更一般地說，這像強化學習裡的探索與利用，部署時要在「估難度」和「用最好的策略解題」之間分配算力。實驗為了簡單，沒有把這筆成本算進去，因為目標是先展示有效分配算力能做到什麼；附錄 C 也承認，在實際的上線環境，這筆成本會是問題。

用同一份測試集既分等級、又挑策略，結果會有混淆，所以作者在每個難度等級裡做兩折交叉驗證：一折挑、另一折量，交換之後取平均。

第 4 節的實驗設定只有兩段，一併放在這裡。資料集是 MATH，用 Lightman 等人的切法：12k 題訓練、500 題測試。作者選它的理由是：測試時算力應該在模型已經有需要的知識、難處在於用這些知識做（複雜的）推論時最有用。模型是 PaLM 2-S*（Codey）的 base 模型；作者認為它能代表當時許多 LLM 的能力，在 MATH 上的表現不差又還沒飽和，適合當測試平台。

測試時，PRM 對一組解裡的每一步打分。要用它挑出 best-of-N 的答案，還需要把逐步分數彙整成一個決定，分兩層。第一層是逐步彙整：先前的研究用所有步驟分數的乘積或最小值，作者直接用最後一步的預測當整個解的分數，在他們比過的方法裡最好。第二層是跨答案彙整：照 Li 等人的 best-of-N weighted，把最後答案相同的解的分數加總，選總分最高的答案，而不是只挑單一分數最高的解。

兩層彙整 · 教學用虛擬碼（整理者寫的） 
def score(solution):
    return prm(solution.steps)[-1]            # 只看最後一步的預測

def best_of_n_weighted(solutions):
    total = defaultdict(float)
    for s in solutions:
        total[s.final_answer] += score(s)     # 同一個答案的分數加總
    return max(total, key=total.get)          # 總分最高的答案

附錄 E 比了三種逐步彙整：取所有步驟的最小值（Lightman 等人的做法）、取所有步驟正確機率的乘積、只取最後一步，結果最後一步最好。先前的研究發現最小值最好，作者認為差異來自標籤：他們的 PRM 用軟的 Monte Carlo 回報訓練，和二元的對錯標籤很不一樣，其他彙整方式未必有同樣的效果。附錄 E 還點出一件有意思的事：只取最後一步時，其實是把 PRM 當 ORM 用；但 PRM 仍然勝過 ORM，而且附錄 F 顯示兩者的差距隨樣本數變大。作者因此猜測，逐步訓練在這裡的主要用處可能是一種表徵學習，而不只是推論時的工具。附錄 G 另外說明，這個 4-shot prompt 和 Lewkowycz 等人的 prompt 結果相近；PRM 與修訂模型的訓練資料、測試時對 PRM 的搜尋，都用它。

再展開從每個留下的候選再抽 M 個下一步，又回到 N/M×M 個前綴，重複第 2 到 4 步。

lookahead search 改的是 beam search 評估每一步的方式。它不直接用 PRM 對目前這一步的分數，而是先往前模擬：最多再寫 k 步，遇到解的結尾就提早停，再用 rollout 結尾的 PRM 分數當作目前這一步的分數。為了降低模擬的變異，rollout 用溫度 0。所以 beam search 就是 k＝0 的 lookahead；如果 PRM 夠準，k 越大，每一步的價值估計越準，代價是多花算力。作者也指出，這個版本的 lookahead 是 MCTS（蒙地卡羅樹搜尋）的特例：MCTS 為了探索而加的隨機成分被拿掉了，因為 PRM 已經訓練好、凍結，那些隨機成分主要在學價值函數時有用，測試時要的是利用而不是探索。作者因此認為，lookahead search 大致代表 MCTS 一類方法在測試時會怎麼用。

關鍵觀念 · 一

最強的搜尋，找到的是驗證器的弱點

直覺上，搜得越仔細，答案應該越好。這一節的結果相反：lookahead 每一步都往前試寫，照設計是評估最仔細的方法，表現卻最差；beam search 在簡單題上，預算越多越差。作者的解釋是搜尋在利用 PRM 的預測：搜尋最佳化的是 PRM 的分數，PRM 只要在某些地方給了偏高的分數，例如重複的步驟、太短的解，搜尋越用力，就越容易找到這些地方。

整理者的讀法：驗證器已經判得準的題目，強力搜尋能多得到的很少，放大錯誤的風險卻變大；best-of-N 只在抽出來的完整解裡挑，比較不會被帶偏。搜尋真正有用的，是 base 模型自己很難抽到正確答案、需要被引導的題目，這一點是作者自己的說法。

第 5 節的小結

搜尋設定跟著難度與預算走

作者的小結框：驗證器搜尋方法的效果，同時取決於算力預算與題目。beam search 在較難的題與低預算時比較有效，best-of-N 在簡單題與高預算時比較有效；依題目難度與預算挑最好的搜尋設定，幾乎能用最多四分之一的測試時算力追上 best-of-N。

關鍵觀念 · 二

驗證 loss 變差之後，模型反而比較會改

附錄 H 有一個反直覺的觀察：用同樣方式拼出來的驗證集算 loss，不是好的 early stopping 訊號。驗證 loss 開始上升之後很久的 checkpoint，修訂能力反而強得多。作者最後選的，是驗證集剛出現過擬合之後不久的 checkpoint。

作者的解釋是：微調之後，這份驗證集對修訂模型來說是 off-policy 的資料，它裡面的錯答案是 base 模型寫的，和修訂模型自己會寫出的軌跡分布不同。所以驗證 loss 量到的，不是模型在自己的修訂鏈上表現得好不好。

附錄 K 試過再用簡化的強化學習演算法 ReST-EM 最佳化這個修訂模型：在 MATH 訓練集上，每題產生 64 條最長 5 步的修訂軌跡，遇到第一個正確答案就停，並刻意平衡軌跡的長度，再拿正確答案的資料微調。結果這個新模型的循序修訂越多，表現下降得越多。作者推測，ReST-EM 取得的線上資料放大了修訂資料裡的假相關，讓模型學不會修訂這件事；他們認為像 Qu 等人那樣比較離線的資料收集方式可能比較有效，留待之後研究。

但推論時有分布轉移：訓練時前文只有錯答案，測試時模型可能已經寫出正確答案、放在前文裡，下一次修訂就可能把它改錯。作者發現確實如此：用天真的做法，約 38% 的正確答案會被改回錯的，和 Qu 等人觀察到的相似。所以他們用循序的多數決，或用驗證器從整條修訂序列裡挑出最可能正確的答案（圖 5）。

上一章看到循序勝過平行，但作者認為兩者的性質不同。平行抽樣比較像全域搜尋，原則上能涵蓋很多完全不同的解題方法，例如各個候選走不同的高層路線。循序抽樣比較像局部修正，修改已經大致在對的方向上的答案。兩者互補，所以應該在兩個極端之間取一個平衡：一部分預算給平行（例如 √N 條鏈），其餘給循序修訂（例如每條 √N 次）。

匯率用兩個常見的近似：預訓練 FLOPs X 約等於 6 × 參數量 N × 預訓練 token 數（Hoffmann 等人），推論 FLOPs Y 約等於 2 × N × 推論時產生的 token 總數（Sardana 與 Frankle）。參數乘上 M，預訓練與推論的 FLOPs 都跟著乘上 M，其中推論算的是大模型做 greedy 解碼的成本，總共 M(X+Y)。要讓小模型用測試時算力花掉同樣多的 FLOPs，它的推論算力可以乘上：M ＋ 3 ×（預訓練 token ÷ 推論 token）×（M − 1）。

思考題 · 03

你的用途，R 大概落在哪裡？

估一下你的系統在整個使用期間會產生多少推論 token，再和你用的模型的預訓練 token 量級比一比。

大量對外服務的產品，推論 token 累積起來很容易超過預訓練，這時論文的結果偏向用更大的模型；內部的批次工作、資料產生或自我改進的流程，推論量相對小，花在測試時算力比較划算。再看你的題目多半落在模型能力的哪一段：多數題目都在能力範圍內時，測試時算力最有機會贏。

驗證器與修訂之外，還有其他讓模型在推理時多用算力的做法：做階層式的假設搜尋來做歸納推理；在測試時讓模型使用工具；用非監督的方式學習「思考 token」，例如 Quiet-STaR 與 pause tokens，讓模型更能用上抽樣較長序列時多出來的算力。作者認為，依題目難度分配算力這一類分析方法，原則上也能套用在這些做法上，是值得研究的方向。

整理者的讀法

放回這一講：什麼時候調推論算力

下面是整理者的連結，論文本身沒有談 prompt 或權重的選擇。這一講的最後一個問題是：什麼時候調 prompt、什麼時候調權重、什麼時候調推論算力。這篇只回答最後一項的一部分，但它的判斷標準可以借來用：先看題目對目前的模型難不難。多數題目在模型能力範圍內、只是偶爾答錯時，推論時多抽幾次、讓模型修改或對驗證器搜尋，就能換到準確度；多數題目超出模型能力時，多花推論算力幫不上，該換更大的模型或改權重。推論量很大的服務，每一題多花的算力會一直累積，這時把預算花在更好的模型上比較划算。另外，這篇的修訂模型與驗證器本身都是微調出來的：調推論算力之前，常常要先調過權重。

多花測試時算力一定有用嗎？
不一定。最難的題目上，搜尋幾乎沒有進展；在 FLOPs 對等下，困難題與推論負載高的情境，放大模型比較有效，圖 1 右最低到 −52.9%。簡單題上，beam search 甚至會因為過度最佳化而越搜越差。
需要訓練模型嗎？
需要。作者說直接 prompt 現成的模型去修訂或驗證效果不好，所以 PRM、修訂模型、修訂用的 ORM 都是從 PaLM 2-S* 微調的；他們預期未來的模型會直接具備這些能力。
compute-optimal 怎麼知道題目的難度？
論文每題用 2048 個樣本估：有標準答案時用 pass@1（oracle），沒有時用驗證器分數的平均（predicted），兩者的曲線大致重疊。這筆估難度的成本沒有算進實驗，作者把更便宜的估法列為未來方向。

test-time compute
測試時算力
模型訓練好之後，回答一題時額外花的推論算力；這篇用生成次數當預算單位。
proposal distribution
提案分布
模型產生候選答案的分布；改它是第一個旋鈕（第 2 節）。
verifier
驗證器
替候選答案或步驟打分的模型；用它挑答案或搜尋是第二個旋鈕。
PRM
過程獎勵模型
對解的每一步預測對不對；這篇用 Monte Carlo rollout 的軟標籤訓練，不用人工標註。
ORM
結果獎勵模型
只對整個解打分；在 base 輸出上輸給 PRM，修訂模型則改用前文含修訂歷史的 ORM。
best-of-N
平行抽 N 個挑最好
抽 N 個獨立答案，依驗證器挑一個；這篇的主要基線。
best-of-N weighted
加權 best-of-N
把最後答案相同的解的分數加總，選總分最高的答案（Li 等人）。
majority voting
多數決
取出現最多次的答案，不需要驗證器；修訂時把所有鏈的答案一起投。
beam search
束搜尋
每一步保留 PRM 分數最高的 N/M 個前綴，各再展開 M 個；最多 40 輪。
lookahead search
往前看的搜尋
評一步之前先用溫度 0 往前寫 k 步，取結尾的 PRM 分數；k＝0 就是 beam search。
MCTS
蒙地卡羅樹搜尋
lookahead search 是它拿掉隨機探索的特例。
Monte Carlo rollout
蒙地卡羅推演
從某一步接著寫到底，重複多次估答對的比例；PRM 每一步用 16 次。
reward-to-go
剩餘報酬
從目前這一步往後能得到的報酬；PRM 的逐步預測就是它的估計。
over-optimization
過度最佳化
搜尋利用驗證器的弱點：重複的低資訊步驟、只有一兩步的解；簡單題最明顯。
revision model
修訂模型
看著前幾次的答案再寫一次的模型；前文最多 4 個答案，推論時截斷到最近 4 個。
sequential／parallel
循序與平行
同一個預算：一條鏈一直修訂，或多條獨立的嘗試；兩者的比例是要選的超參數。
compute-optimal scaling
算力最佳分配
對每一題選最好的測試時算力設定（式 1）；實際上是每個難度等級各選一組。
question difficulty
題目難度
某個 base 模型在這題的 pass@1，按五分位分成五級。
oracle／predicted difficulty
oracle 與預測難度
用標準答案算的難度，或用驗證器分數平均估的難度；後者部署時用得到，但要花算力。
pass@1
單次答對率
抽一次就答對的機率；這篇每題用 2048 個樣本估。
MATH
數學競賽資料集
高中競賽題；這篇用 Lightman 等人 12k 訓練、500 測試的切法。
PaLM 2-S*
base 模型
論文用的模型（Codey）；PRM、修訂模型、ORM 都從它微調。
PRM800k
人工標註的 PRM 資料

ReST-EM
簡化的 RL 微調
用模型自己產生、答對的資料反覆微調；拿來最佳化修訂模型反而變差（附錄 K）。
