AGENTIC BENCHMARK CHECKLIST · 圖卡＋教材整合版

代理基準的分數， 先驗過再相信ABC 清單： 任務、評分、回報 各用一組檢查把關

代理基準（agentic benchmark）讓 AI agent 在真實的環境裡做完一整件工作，再用測試或字串比對判斷成敗。這篇 25 位作者的論文指出，評分設計一有漏洞，分數就可能被高估或低估到相對 100%：τ-bench 的航空題什麼都不做就能拿 38%，SWE-Lancer 的測試檔可以被 agent 直接改掉。作者把這些教訓整理成 Agentic Benchmark Checklist（ABC），分任務有效性、結果有效性、回報三部分，拿去檢查十個熱門基準，再用它修正 CVE-Bench。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

先把幾個名詞對齊

  • 代理基準：題目不是選擇題，而是一件要動手做的事，例如修一個 GitHub issue、在網站上訂票、寫一個 GPU kernel。agent 做完之後，基準用程式判斷結果對不對。
  • 標準答案（ground truth）：判斷對錯時的參照。可能是一段文字、一組單元測試，或任務完成後資料庫應該長的樣子。
  • pass@k 與 pass^k：同一題讓 agent 試 k 次，前者是至少成功一次的比例，後者是 k 次都成功的比例。τ-bench 用後者量穩定度。
  • 單元測試與模糊測試：前者是人寫好的一組輸入與預期輸出；後者自動產生大量隨機輸入，拿 agent 的程式和參考實作的輸出互相比對。

論文從 agent 的現況講起。把機器學習模型接上工具、記憶與知識的 agent，已經能處理複雜的問題；為了追蹤進展、幫忙做決定，學界與業界做了一批題目貼近真實的代理基準。引言舉的例子是 τ-bench：一個以 GPT-4o 為核心的 agent，在它的航空子集解出 35% 的題目。這些數字在學術界與產業界的影響越來越大，作者認為得先確定它們值得相信。

代理基準和傳統基準的差別在判對錯的方式。ImageNet、MMLU 這類選擇題資料集，比對的是類別標籤；文字生成的基準用 BLEU 這類自動指標。代理基準的成功，則定義成做完一件端到端的工作：agent 可能要推理、寫程式、執行指令，最後交出一個結果，基準再把它和標準答案的結果比較，比較的方法有程式測試、字串比對等等。判斷的方法是每個基準自己設計的，漏洞也就藏在這裡。

作者的主張是，很多代理基準以結果為準的評分方法有問題，會把 agent 的表現高估或低估，最多到相對 100%。第一個例子是 SWE-bench Verified：agent 要修一個 GitHub issue，產生的 patch 通過人工審過的單元測試就算成功。但後來的研究發現，單元測試可能漏掉重要的邊界情況，通過測試不代表 issue 真的解決了；引言說，因此排行榜前 50 名裡有 24% 的名次是錯的。第二個例子是作者自己發現的：τ-bench 有一些刻意設計成做不到的任務（例如更改一張不能退的機票），一個只回傳空白的 agent 在這些題上被判成功，整體拿到 38%，比那個 GPT-4o 的 agent 還高。

摘要與引言都說誤差最多到相對 100%，但論文沒有指明這個 100% 是哪一個基準、怎麼算出來的。後面第 7、8 章的各個數字，量法也各不相同，有的是一個不解題的 agent 拿到的分數，有的是正確率被高估的百分點。

作者讀了前人對代理基準缺陷的分析，加上 17 個常用的代理基準與自己做基準的經驗，歸納出基準結果成立的兩個條件。結果有效性是指評分的結果（測試或檢查）真的代表任務成功；SWE-bench Verified 在這裡失守，因為錯的 patch 也可能通過測試。任務有效性的定義，引言寫成一句：

"a task should be solvable if and only if the agent possesses the target capability" 「一個任務應該在 agent 具備目標能力時才解得開，而且具備時一定解得開」：引言對任務有效性的定義。τ-bench 讓一個不懂航空票務規則的 agent 通過 38% 的題目，就是在這裡失守。

第 3 節用圖 1 把這兩個條件畫在同一張圖上。上排是評估實際怎麼跑：代理基準在特定的環境裡、給一組工具，讓 agent 去完成任務；來回幾輪動作之後，agent 交出任務結果，基準再依任務的要求，用字串比對、狀態比對、測試或自訂指標判斷成功與否。下排是這個流程想量的東西：目標能力、任務成功、評分通過。作者的說法是，一次代理評估是嚴謹的，若且唯若兩個等價同時成立：目標能力等價於任務成功（任務有效性），任務成功等價於評分通過（結果有效性）。

代理基準比傳統基準更難守住這兩個等價，作者點出兩個特有的難處。第一是任務設定複雜：除了題目描述，還要架一個讓 agent 操作的環境、提供它能用的工具。第二是任務結果沒有固定格式：文字回應、程式、檔案修改都有可能，要判斷對錯並不簡單，得特別設計方法。任務設定不當會破壞任務有效性，τ-bench 就是例子；沒有嚴格判斷非結構化的結果會破壞結果有效性，SWE-bench Verified 就是例子。作者說，任務有效性失守的方式通常是兩種：出現捷徑，或出現做不到的任務。

這篇要做的，是把兩個有效性的標準翻成一份可以照著做的清單，幫研究者找出並減輕特定基準的問題；某一條做不到的時候，清單也告訴你怎麼解讀、怎麼回報得到的分數。

同一個例子，兩種分法

τ-bench 的空回覆，算任務的問題還是評分的問題？

引言與第 3 節拿 τ-bench 當任務有效性的例子；到了第 5.2 節與附錄 D，它違反的是結果有效性的 O.b.3 與 O.g.3（標準答案太簡單），任務有效性的十條它全拿分（第 6 章）。論文沒有說明兩處分法的差別。整理者的讀法是，同一個漏洞兩邊都看得到：題目刻意設計成做不到，是任務設定的事；評分只看資料庫有沒有被改，是評分的事。

作者列的貢獻有四項：點出代理基準評估嚴謹度的兩個威脅（結果有效性與任務有效性）；做出一份可以照做的檢查清單 ABC；用它評估十個常用的代理基準，找到讓表現估計最多錯到相對 100% 的新問題；以及一個在開發途中用 ABC 改進代理基準的案例。

思考題 · 01

你最常看的那個排行榜，守住了哪一個等價？

挑一個你會拿來挑模型或挑 agent 框架的代理基準，想想它的題目與評分怎麼設計。

問兩個問題就好。一個什麼都不做、或把所有可能的答案都列出來的 agent，能拿到幾分？這是在測任務與評分有沒有捷徑。一個真的做對、但寫法和標準答案不同的解，會不會被判錯？這是在測評分會不會誤殺。答不出來的那一題，就是這個排行榜需要附註的地方。

背景

偽陽性與偽陰性

借醫學檢驗的說法：偽陽性是沒病卻驗出陽性，放到基準裡就是 agent 沒完成任務，評分卻說成功；偽陰性反過來，完成了卻被判失敗。一個基準可以同時有兩種錯，彼此抵銷之後的總分看起來正常，逐題看卻錯得不少。這段說明是整理者加的背景。

工具。外部工具能大幅擴充 agent 的能力。現有基準提供兩種工具：自己架的工具（Python、命令列工具）與透過 API 呼叫的工具（網路服務）。自己架的工具，要在 prompt 裡寫明正確的工具或套件版本（T.1）。API 型的工具，要確保服務在評估期間連得上、處理好限流（T.2）；萬一 API 中斷，作者建議偵測到就終止評估，讓使用基準的人知道（T.3）。第 2 節提到的前人研究就發現，WebArena 的網站有限流，擋住了 agent 解題。

環境。代理基準常要一個沙箱環境模擬真實情境，任務越複雜越難實作與維護。第一，為了讓各題互不影響，開始新任務之前要把殘留的資料與狀態清乾淨（T.4）。第 4.1 節的例子是 KernelBench 沒有把標準答案從 GPU 記憶體清掉，agent 可以用越界讀取記憶體拿到正確結果。第二，為了避免偷看標準答案，agent 要和標準答案完全隔開（T.5）。第三，環境的設定要能完整重現，在基準發佈時就凍結（T.6）；作者不建議依賴持續更新的外部網站這類動態資源。

KernelBench 這個例子在附錄 D 的記法不同：第 4.1 節把它放在 T.4 下面，附錄 D 的表 14 卻給 KernelBench 的 T.4 一分，把同一個記憶體問題記在 T.5（標準答案的 kernel 先跑、而且和 agent 的程式在同一個行程裡）。兩處照錄。

實作。工具與環境都架好了，細微的實作漏洞仍然可能造出捷徑或做不到的任務。所以作者建議驗證標準答案的標註與任務設定是否正確（T.7、T.8），並提供一個能自動解題的 oracle 解題器，證明任務的設定沒問題（T.9）。第 4.1 節還說，照 τ-bench 的做法檢查試跑時的離群值，對找出實作錯誤很重要（T.10）：agent 在簡單的題目上一直失敗，可能表示題目做不到；只在困難的題目上成功，可能表示有捷徑。圖 2 對 T.10 的寫法是「實作沒有能讓人不做完任務就通過的漏洞」，正文講的是怎麼找出這種漏洞。

第 4.2 節是全篇最長的一節。它的分法是先看任務要 agent 交出什麼（文字答案、程式、改過的環境、推理後的最終答案），再看基準用什麼方法判斷，每一種方法各配幾條檢查（圖 3）。

資訊取得。要測 agent 搜尋、擷取、整合與摘要資訊的能力，基準會把任務寫成查詢，再用三種方式判斷 agent 的文字回應。整段字串比對直接比較回應與標準答案，標註標準答案時要考慮語意相同的寫法（O.a.1）與多餘的字（O.a.2）；作者在註腳補充，實務上使用者常會指定答案格式，這會縮小替代寫法的範圍，不照格式回答算是真的失敗。子字串比對看回應裡有沒有包含標準答案，除了等價的寫法，還要處理「不是」「陰性」這類否定詞（O.b.1），並把題目設計好，不讓 agent 靠列出所有可能的答案（O.b.2）或亂猜（O.b.3）過關。LLM 評審用 LLM 模擬人類標註者；前人研究顯示 LLM 標註的準確度會隨領域改變，所以作者建議先做試跑實驗，量 LLM 評審的準確度與自我一致性（O.c.1）。圖 3 另有一條 O.c.2：評審要能抵抗對抗性的輸入與獎勵駭客。

附錄 E.5 的例子

63 分鐘的題目，答 53 分鐘也被判對

WebArena 有一題問：從 MIT 走路到哈佛，再開車到波士頓羅根機場，總共要多久？標準答案是 63 分鐘。agent 上網查了之後回答走路 45 分鐘、開車 8 分鐘，加起來 53 分鐘，和標準答案不同，LLM 評審卻判它正確。這是 O.c.1 要先量 LLM 評審準確度的理由。

程式生成。寫程式的代理基準用程式測試判斷 agent 的程式對不對，分成三種。單元測試替個別的函式或類別設計測試案例；測試寫得不好，偽陽性與偽陰性都會發生，所以作者建議人工驗證測試案例的正確性與品質（O.d.1），並用客觀指標保證品質，例如程式碼覆蓋率、循環複雜度（O.d.2）。模糊測試自動產生大量輸入，把 agent 的程式和參考實作的輸出拿來比；輸入產生器要依目標程式調整，涵蓋不同的數值、型別、記憶體排列與邊界情況（O.e.1、O.e.2），而且輸入要真的會影響輸出（O.e.3）。第 4.2 節的例子是 relu(x)：隨機產生的負數輸入，對它什麼也測不出來。端到端測試模擬完整的使用流程，除了測試案例本身的品質，還要涵蓋使用流程所有可能的分支（O.f.1）；它很複雜，需要額外的防護來消除不確定性、讓結果可以重現（O.f.2）。

狀態修改。有些代理基準要 agent 改動環境的狀態，例如訂機票、編輯網站，評分時把 agent 做完的最終狀態和標準的最終狀態比較。作者提出三條。第一，標準答案要包含成功完成任務後所有可能達到的狀態（O.g.1）；例如要 agent 攻擊一個網站，就要把所有可能的攻擊結果都算進去（第 9 章的 CVE-Bench）。第二，檢查的狀態要同時包含相關與無關的部分（O.g.2），例如改過與沒改過的檔案都要看，才抓得到 agent 動了範圍以外的東西。第三，狀態空間要夠複雜（O.g.3），例如牽涉多個變數或相依關係，讓隨機或微不足道的改動不太可能剛好得到正確的結果。

多步推理。這類基準要 agent 觀察、分析、產出結果，作者整理兩種常見的評法。答案比對先解析 agent 的輸出，再和標準答案比；作者發現現有基準的解析器可能對 agent 的輸出有隱含的假設（O.h.1），例如 MATH 資料集假設 agent 的答案以「Answer:」開頭，所以格式要求要明白寫出來。為了讓單一的最終答案反映真正的推理過程，題目也要設計成很難靠亂猜成功（O.h.2）。品質指標用在標準答案不可能取得的情況（例如 ML 工程任務的預測結果），用自訂的指標和基準線比較；指標的選擇很主觀，為了避免不解決任務也能刷高指標，作者建議選的指標要和推理過程強烈相關（O.i.1，圖 3 寫成 O.I.1，要能防止鑽漏洞）。

τ-bench。τ-bench 評的是 agent 和人類使用者互動、遵守領域規則的能力：給一份領域政策，agent 要和使用者對話、回應請求。評分看兩件事：資料庫的最終狀態對不對，以及（有些題目）回應裡有沒有包含要求的文字。第一個問題出在刻意做不到的題目，它們佔航空子集的 38%、零售子集的 6%。附錄 E.2 的例子是一題取消機票並退款的請求：agent 應該查資料庫裡這張票的細節，如果是不能退的票就拒絕。這題沒有要求的輸出，只要資料庫沒變就算成功，所以什麼都不做的 agent 也成功。第二個問題是，航空題的 2% 與零售題的 3.6% 直接拿資料庫的原文當標準答案、用子字串比對，把整個資料庫倒出來的 agent 就能過。

附錄 E.2 量了兩種不解題的 agent。立刻結束的 do-nothing agent，在航空與零售子集的 pass^k 或 pass@k（k 取任何值都一樣）是 38% 與 6.0%；把所有資料都輸出的 spamming agent 是 40% 與 9.6%。整理者核對：38＋2＝40、6.0＋3.6＝9.6，倒出資料的 agent 多過的，剛好是那些拿資料庫原文當答案的題目。

WebArena。WebArena 評 agent 和網站互動的能力，任務是取得指定的資訊或把資料正確填進網頁表單。作者找到兩個問題：子字串比對不管多餘的內容，所以回應裡夾帶無關資訊的 agent 也算成功；標成「N/A」的題目，LLM 評審會把空白回覆判為正確，一個不解題的 agent 就能通過。附錄 E.5 另外指出，整段字串比對處理不了替代寫法與修飾語，子字串比對擋不住把網站內容全部列出來，LLM 評審的結果也不可靠（第 4 章的 63 分鐘例子）。

SWE-bench：測試不夠，錯的 patch 也過。SWE-bench 評 agent 解決真實 GitHub issue 的能力：給 issue 描述與程式庫的摘要，agent 產生一個 patch，再用 repo 裡既有的單元測試判對錯。附錄 E.1 引用前人研究 UTBoost 的發現：測試案例不夠，就會出現很多偽陽性。它的例子來自 Python 套件 seaborn：PolyFit() 在計算多項式擬合時處理不好 x、y 的缺值，但它的單元測試只考慮了 x 與 y 同時缺值的情況。IBM SWE-1.0 產生的一個錯 patch 因此被判為正確。下面是教學用的精簡版：

# 原本的測試：同幾列的 x 與 y 一起設成缺值
df.iloc[5:10] = np.nan
res1 = PolyFit()(df[["x", "y"]], groupby, "x", {})

# 通過測試的錯 patch：x 與 y 各自丟掉缺值
y = data["y"].dropna()

if x.shape[0] != y.shape[0]:

KernelBench：模糊測試只換數值，越界的 kernel 也過。KernelBench 要 agent 寫出正確又更快的 GPU kernel：給任務說明與原本的 PyTorch 程式，agent 寫一段內嵌 kernel 實作的 PyTorch 程式。它用隨機產生的張量測正確性。第 5.2 節說，它的 fuzzer 只改變張量的數值，張量的形狀與記憶體排列都不變，所以在其他設定下會出錯的 kernel 仍然通過。附錄 E.6 列了三個問題：部分題目測的函式對均勻隨機的輸入不敏感，例如 mean(softmax(x)) 與 relu(x−2)；評估時先跑標準答案的 kernel、再跑 agent 的 kernel，前人研究指出 agent 可能寫出讀取標準答案執行結果的程式；fuzzer 沒有涵蓋不同的記憶體排列（例如不連續的張量）、張量形狀與硬體環境。附錄舉了一個 layernorm 的 kernel：平行加總時的索引範圍依執行緒的數量而定，執行緒比要正規化的長度多時，會讀到沒有初始化的記憶體，需要加一道保護，KernelBench 卻判它正確。

要大規模找出這類問題，作者讓 o3-mini 幫忙寫測試：level 1 的每一題抽 3 個生成的 kernel，請 o3-mini 找出可能的缺陷、替每個缺陷寫測試案例；人工驗證這些測試案例之後，再套到 Lange 等人發表的所有生成結果上。結果是 kernel 的正確率被高估了 31%，引言註明這是絕對值。

OSWorld：網站改版，對的操作也不過。作者發現 OSWorld 的 chrome 區有 13/46 題壞掉了，因為基準建立之後，那些網站的版面、網址與功能都變了。很多評分依賴 HTML 元素的選擇器，例如 class 與 XPath，網站改版後就對不上。實驗裡，這個問題讓 OSWorld 上最強的開源 agent UI-TAR（論文的寫法）被低估了 28%，論文註明是絕對值。附錄 D 把它記在 T.6（設定不隨時間改變）。

BIRD：題意有兩種讀法，另一種就被判錯。BIRD 比較標準 SQL 與 agent 的 SQL 的執行結果。附錄 E.3 指出，自然語言的描述有歧義，同一句話可能有好幾個正確的查詢。例子是：「人口最少的國家，它的名稱、獨立年份與面積是多少？」

給初學者

兩種攻擊目標在做什麼

  • 時間型 SQL 注入：攻擊者看不到查詢的結果時，讓資料庫在某個條件成立時故意延遲，再從回應的快慢反推資料庫的內容。論文的說法是在 IF 條件裡執行 SLEEP，量延遲就知道條件是否成立。
  • 對外連線：誘使網頁應用程式把請求送到一台被禁止的外部伺服器。論文說這是嚴重的資安攻擊。
  • one-day 與 zero-day：前者是漏洞已經公開、agent 知道要找什麼；後者是 agent 事先不知道漏洞在哪裡。這段說明是整理者加的背景。

狀態比對太天真。CVE-Bench 原本判斷時間型 SQL 注入成功的方法，是看資料庫的紀錄裡有沒有出現 SLEEP 子句。但紀錄裡有 SLEEP，不代表 SLEEP 真的被執行；論文把這個問題歸在 O.g.1（標準答案要包含成功之後所有可能的狀態）。結果 agent 只要在查詢的任何地方加一個 SLEEP 就能通過，表現被高估 32.5%。圖 6a 是修正這個判定設計前後的比較，論文沒有寫新的判定細節。

外部伺服器沒設門檻。CVE-Bench 判斷對外連線攻擊成功的方法，是看那台外部伺服器有沒有被連上。為了回答 T.9（有沒有能證明題目設定正確的 oracle），作者跑了好幾輪模擬執行，發現 agent 在這個攻擊目標上一直都通過，這很可能表示實作有 bug。查下去果然發現，agent 從同一個 docker 網路連線，本來就連得到那台外部伺服器，形成一條捷徑。讓外部伺服器拒絕外來的請求之後，agent 的成功率降了 10%（圖 6b）。

兩個數字的關係有一處沒有交代。摘要說 ABC 讓 CVE-Bench 的高估少了 33%，引言說是絕對值、並經資安專家確認；第 5.3 節則分別寫時間型注入的 32.5% 與外部伺服器的 10%。33% 怎麼從這兩個數字來，論文沒有說明，v1 就是這樣寫。

Chapter 10 · Related Work

零星的問題報告，還缺一份系統化清單

作者把自己放在三條研究線之間：評估一般 AI 基準的研究、各領域的代理基準，以及個別代理基準的問題報告。前者多半處理選擇題與生成題，後者一次只看一個基準，沒有人給出可以照做的系統化準則。

第一條線是評估 AI 基準本身。基準是量測進展、找出潛在風險的關鍵工具，但維持品質一直是難題。前人研究過基準的許多面向：標籤的品質與數量、標準化的評估流程、建構效度、資料污染、可重現性與實際的使用方式；ImageNet 這樣知名的基準也有資料偏差與標籤雜訊的問題。LLM 興起之後，也有研究提出一般基準或程式基準的最佳做法（Reuel 等人的 BetterBench、Cao 等人）。作者說這些研究提供了重要的參考，但它們聚焦在選擇題或不需要多步推理的生成題，歧義與複雜度都比代理基準少。

第二條線是各領域的代理基準：寫程式、在環境裡完成指定目標、解數學題，以及其他。這些任務通常模擬真實世界的問題，輸出不是類別、執行要好幾步。評估 agent 因此比傳統基準複雜，要處理 agent 和環境的動態互動、判斷非結構化的回應，確保嚴謹就更難。

第三條線是個別代理基準的問題報告。結果有效性方面：Kydlíček 與 Gandenberger 發現對答案格式的隱含假設讓表現被低估 5.3%；Yu 等人發現 SWE-bench Lite 7.7% 的題目、Verified 5.2% 的題目，agent 不產生正確的 patch 也能通過；也有研究發現 BIRD 的標註雜訊明顯影響表現評估的準確度。任務有效性方面：WebArena 的網站限流擋住了 agent 解題（Kapoor 等人）；Lange 等人發現 KernelBench 的評分有漏洞，agent 可以繞過正確性檢查。作者的結論是，這些研究都沒有發展出一份可以照做的系統化準則。

整理者的讀法

放回這一講：評估的四樣東西，各有一組檢查

下面是整理者的連結。這一講把評估拆成請求、環境、何時結束、評分器；ABC 大致可以對上：請求對 T.7、T.8 與 O.h.1，環境對 T.1 到 T.6，評分器對結果有效性的 20 條，可靠度對回報的 R.9 到 R.11。何時結束是 ABC 最少談的一塊，τ-bench 的例子卻說明它很關鍵：一個立刻結束的 agent 也能拿分。設計一個代理基準時，可以先問三件事：一個不解題的 agent 能拿幾分？一個對的解換個寫法會不會被判錯？兩個系統的分數差多少才算真的有差？

ABC 適用於所有代理基準嗎？
作者沒有這樣宣稱。附錄 A 說它只根據 2024 年 1 月到 2025 年 3 月的 17 個代理基準寫成，可能不夠完整；結果有效性的條目也要依基準用的評分方法挑著用。
在 ABC 拿高分，就代表基準嚴謹嗎？
不一定。只用答案比對的基準，結果有效性只看兩條；第 5.1 節的分數是用來找問題的。十個基準的回報沒有一個做到每一條，最高的 MLE-bench 也缺 trivial agent 的結果。
論文找到的問題修好了嗎？
論文沒有追蹤。附錄 A 說發現只反映寫作當時的版本，之後的改版可能不同；作者公開了程式與網站，說會持續更新。

Workshop · Apply it yourself

動手做：拿 ABC 檢查一個代理基準

這一章不在原文裡。它把 43 條檢查（整理者數的）壓成發佈或採用一個代理基準之前可以照做的七步，括號裡是對應的檢查項。

  1. 寫下要量的能力與評的對象講得出能力和任務結果之間的關係，也講清楚評的是模型還是 agent 框架（R.5、R.6）。
  2. 把環境固定下來工具與套件的版本寫進 prompt；每題之間清掉殘留的資料；不依賴會改版的線上網站（T.1、T.4、T.6）。
  3. 把標準答案藏好，把 API 顧好agent 讀不到、改不動測試與答案；API 連不上時，評估要停下並告訴使用者（T.2、T.3、T.5）。
  4. 證明每一題做得到驗證標準答案與題目的可解性，準備一個 oracle 解題器跑過全部題目（T.7 到 T.9）。
  5. 先讓最笨的 agent 跑一輪什麼都不做、把所有可能的答案列出來、隨便猜；分數應該接近 0，否則就有捷徑（R.13、O.b.2、O.b.3、O.g.3、O.h.2）。
  6. 驗證評分器本身LLM 評審先量準確度與一致性；單元測試人工檢查並量覆蓋率；模糊測試換形狀、型別與記憶體排列，輸入要影響輸出（O.c.1、O.d.1、O.d.2、O.e.1 到 O.e.3）。
  7. 公開時附上缺陷的影響抽樣估計評分的錯誤率，給信賴區間與解讀建議，附上人類專家與 trivial agent 的分數（R.8 到 R.13）。

Reference · 名詞速查

關鍵名詞與檢查項目速查

先列兩種有效性與清單本身，再列評分方法與測試，最後是案例裡出現的基準與攻擊。

agentic benchmark
代理基準
任務需要多步推理或執行指令、以做完一整件工作為成功的基準（附錄 B）。
task validity
任務有效性
任務成功若且唯若 agent 具備目標能力；失守時常見捷徑或做不到的任務。
outcome validity
結果有效性
評分通過若且唯若任務真的成功；失守時錯的結果也會通過。
ABC
代理基準檢查清單
Agentic Benchmark Checklist：任務有效性 T.1–T.10、結果有效性 O.a.1–O.i.1、回報 R.1–R.13。
ground truth
標準答案
評分時的參照：文字、測試案例，或任務完成後環境應有的狀態。
trivial agent
不解題的 agent
什麼都不做、倒出全部資料或亂猜的 agent；R.13 要求公開它的分數。
oracle solver
oracle 解題器
能自動解出所有題目的參考解法，用來證明題目做得到（T.9）。
false positive / negative
偽陽性／偽陰性
沒完成卻判成功（高估）、完成了卻判失敗（低估）。
whole string matching
整段字串比對
回應與標準答案整段比較；要收下語意相同的寫法與多餘的字（O.a）。
substring matching
子字串比對
看回應是否包含標準答案；要擋住列舉所有答案與亂猜（O.b）。
LLM-as-a-Judge
LLM 評審
用 LLM 判斷回應對不對；要先量準確度與自我一致（O.c）。
unit testing
單元測試
替函式或類別寫的測試案例；要人工驗證並量覆蓋率（O.d）。
fuzz testing
模糊測試
自動產生輸入，和參考實作比輸出；要涵蓋邊界、型別與記憶體排列（O.e）。
end-to-end testing
端到端測試
模擬完整的使用流程；要走遍分支、消除不確定性（O.f）。
flaky test
不穩定的測試
同樣的程式時過時不過的測試，例如寫死的逾時（O.f.2）。
state matching
狀態比對
比較任務完成後的環境狀態；成功狀態要算全、夠複雜（O.g）。
answer matching
答案比對
解析 agent 的最終答案再比對；格式假設要寫進題目（O.h）。
quality measure
品質指標
沒有標準答案時，用自訂指標和基準線比；要防止刷指標（O.i.1）。
construct validity
建構效度
量到的東西和想評估的能力之間的關係；R.5 要求講清楚。
data contamination
資料污染
題目或答案跑進模型的訓練資料；R.3 建議保留不公開的測試集。
confidence interval
信賴區間
分數可能落在的範圍；附錄 F 把標準答案的錯誤率代進去算（R.10）。
pass@k / pass^k
k 次內成功
試 k 次至少成功一次／k 次都成功的比例；τ-bench 的 do-nothing agent 兩者都是 38%。
SWE-bench Verified
人工審過的 SWE-bench
用 repo 的單元測試判 patch；附錄 E.1 引 UTBoost 說 5.3% 的題不解也過（第 2 節寫 5.2%）。
τ-bench
工具、agent 與使用者的互動基準
航空與零售兩個領域；刻意做不到的題目讓空回覆拿 38%。
CVE-Bench
網頁漏洞攻擊基準
檢查 agent 是否達成預先指定的攻擊目標；第 5.3 節用 ABC 修了兩個漏洞。
time-based SQL injection
時間型 SQL 注入
從資料庫回應的延遲反推內容；紀錄有 SLEEP 不等於真的執行。
