寫程式的 agent，外面那一層怎麼做SWE-agent、OpenHands、Claude Code 文件、Effective Harnesses 與 SWE-bench 在三個問題上的證據

五篇的證據形式不一樣，後面每一章都要記得這件事。SWE-bench 是基準論文，量的是模型，它的基線沒有 agent：先替模型挑檔案，再讓模型一次寫出 patch。SWE-agent 把模型固定住，一次換掉介面的一個元件來比。OpenHands 介紹並評估自家的平台，表上每個對手都附了出處論文。兩份 Anthropic 的文件沒有附實驗：Claude Code 文件是使用指南，本頁把它對自家產品的說法寫成「文件說」；Effective Harnesses 分享內部實驗的經驗，寫成「作者說」。三篇論文用的是 2023 到 2024 年的模型（Claude 2、GPT-4 Turbo、Claude 3 Opus、gpt-4o、claude-3.5-sonnet 等），Effective Harnesses 用的是 Opus 4.5，分數只對當時的組合成立。

日期也先交代。課程書單列的 Claude Code 讀物，是 Anthropic 2025 年的部落格文〈Claude Code: Best Practices for Agentic Coding〉，那個網址現在轉到文件頁〈Best Practices for Claude Code〉；本站依 2026 年 9 月 29 日抓到的版本整理，頁面沒有日期，網站 sitemap 記的最後修改是 9 月 26 日。本頁的時間軸用這個日期，所以五篇從 SWE-bench 的 2023 年 10 月排到 2026 年 9 月，跨 35 個月。五篇的正式篇名與原文連結列在頁尾。

  • 「4-tuple framework」這個詞，五篇原文都沒有出現。本站讀物裡，把一個評估任務寫成四元組（request、environment、stopping criteria、scorer）的是單元 11 Ofir Press 的〈Good LM Benchmarks〉，文中就拿 SWE-bench 舉例；那一頁的序章記錄第 7 週有一講的講題列了這個四元組框架（Good LM Benchmarks 第 7 章）。第 9 週的講題指的是不是同一個，課程頁沒有寫明，本頁不替課程對上。表上這一列只對 SWE-bench 本身。
  • 「端到端怎麼運作」，SWE-bench 的基線沒有 agent：挑檔案、一次寫出 patch、套上去跑測試。其餘四篇都描述了一個會反覆執行、看結果再改的迴圈。
  • 「軟體開發的未來」五篇都是 ○：各篇只在結尾的限制與方向帶到，沒有一篇用專章談。

課程講題沒有列、但四篇都碰到的有兩件事：模型每一步看得到什麼（第 3 章），以及怎麼確認做完了（第 4 章）。前一件事，OpenHands 的論文沒有談。

固定模型，換外面那一層

SWE-agent 的前提寫得很清楚：語言模型固定不變，研究的是介面怎麼設計（SWE-agent 第 2 章）。表 3 用同一個 GPT-4 Turbo 在 Lite 上一次換掉一個元件：預設的介面是 18.0%，拿掉 edit 指令是 10.3%，換成一筆一筆看的搜尋是 12.0%，比完全不給搜尋工具的 15.7% 還低；檢視器改成 30 行是 14.3%、一次顯示整個檔案是 12.7%，保留完整歷史是 15.0%（第 8 章）。表 1 還有同一個模型的另一組對照：只給 Linux shell 是 11.00%，再拿掉示範是 7.33%，用 SWE-agent 的介面是 18.00%（第 7 章）。

SWE-bench 沒有 agent，但它的檢索與輸出格式，也是包在模型外面的選擇。Claude 2 用 BM25 挑檔案，context 上限從 13k 放寬到 27k、50k，解題率從 1.96% 降到 1.87%、1.22%；只給參考解改到的檔案（oracle）是 4.80%，把這些檔案折疊到只剩改動附近的程式，升到 5.93%（SWE-bench 第 8 章）。同樣在 oracle 設定下，要 Claude 2 重寫整個檔案只解出 2.2%，寫 patch 是 4.8%（第 10 章）。

兩份 Anthropic 的文件也只改外層，但沒有附數字。Effective Harnesses 的實驗固定用 Opus 4.5 跑在 Claude Agent SDK 上，改的是第一個 session 的開場提示、初始化 agent 建好的檔案，以及測試用的瀏覽器工具；作者說給了這類測試工具之後，表現大幅提升（Effective Harnesses 第 2、5 章）。Claude Code 文件談的是使用者這一側能設定的部分：CLAUDE.md、權限、hooks、skills、subagents 與 plugins，文件說這些設好一次，之後每個 session 都受益（Claude Code 第 4、5 章）。

固定外層，換模型

OpenHands 的評估方向相反。作者說同一個 CodeAct agent 不改 system prompt，三大類基準都有競爭力（OpenHands 第 7 章）；換的是模型。同一個 CodeActAgent v1.8 在 Lite 上配 gpt-4o-mini 是 7.0%（表 3 寫 6.3%），配 gpt-4o 是 22.0%，配 claude-3.5-sonnet 是 26.0%；每題成本依序是 0.01、1.72、1.10 美元（第 8 章）。同一個 CodeActAgent 換成 gpt-3.5 系列，其他基準的落差也很大：ToolQA 從 47.2 掉到 2.3，HumanEvalFix 從 79.3 掉到 20.1，ML-Bench 從 76.5 掉到 13.2。作者在附錄 A 說，目前的 agent 做複雜任務、編輯長檔案都還很吃力，想從訓練與推論兩邊做出更強的 agent（第 13 章）。

SWE-agent 也換過模型。同一套介面配 Claude 3 Opus，全集是 10.46%、Lite 是 13.00%，配 GPT-4 Turbo 是 12.47% 與 18.00%；作者說介面是替 GPT-4 Turbo 開發的，也能搬到另一個模型上。他們試過 Llama 3、DeepSeek Coder，說它們在 agent 設定下表現不佳，Llama 3 的 context 只有 8k（SWE-agent 第 7 章）。

SWE-bench 在模型這一側做的是微調。現成的 CodeLlama 跟不上「修改整個 repo」這種指示，作者用另外 37 個 repo 的資料微調出 SWE-Llama（SWE-bench 第 5 章）。它的套用率是表 5 最高的（13b 53.62%），但它是看著 oracle 檔案學的，學到「context 裡每個檔案都要改」，換成 BM25 挑進來的檔案只解出 0.70%，oracle 設定下是 3.97%。

一次呼叫：SWE-bench

SWE-bench 的一題，issue 平均 195 字，codebase 平均卻有 438K 行，放不進模型的 context，所以先用 BM25 挑檔案（SWE-bench 第 6 章）。上限放寬，挑中的參考檔案變多：放到 27k 時，約 40% 的題目取回的檔案包含參考解改到的全部檔案。解題率卻反過來降：Claude 2 從 13k 的 1.96% 降到 50k 的 1.22%，兩個 SWE-Llama 都降到 0（第 8 章）。作者的解釋是模型會被多餘的 context 分心，對目標內容在輸入裡的位置也很敏感，引的是〈Lost in the middle〉。反過來把 oracle 檔案折疊到只留改動附近的程式，Claude 2 從 4.80% 升到 5.93%，Claude 3 Opus 是 9.39%，是全篇最高的解題率。

一個 session：SWE-agent

SWE-agent 管的是一個 session 裡的 context。檢視器一次只顯示 100 行；搜尋指令只回摘要，結果超過 50 筆就不列出來，請 agent 換一個更具體的查詢（SWE-agent 第 4 章）。最近 5 個以前的觀察各折成一行，只寫省略了幾行；格式錯的回應，在下一次正確的回應之後從歷史裡刪掉（第 6 章）。表 3 量了兩個方向：保留完整歷史是 15.0%，一次顯示整個檔案是 12.7%，視窗縮到 30 行是 14.3%，預設是 18.0%；作者的結論是內容太少或太多都會拉低表現（第 8 章）。

作者也看到 agent 用不上後面的輪次：最初的做法如果在前 10 到 20 輪沒有成功，之後就很難從錯誤裡換一條路，多半留在原地繼續改；他們歸因於 context 太多，或貪婪的傾向（第 9 章）。

session 之內與之間：兩份 Anthropic 文件

Claude Code 文件把 context window 當成最需要管理的資源：它裝著整段對話、讀過的每個檔案、每次指令的輸出，一次除錯就可能用掉數萬個 token，文件說越滿表現越差（Claude Code 序章）。它的做法是積極清：換到不相關的任務就 /clear；同一件事糾正超過兩次，也 /clear 再寫一個更具體的 prompt；還在同一件事上就 /compact，並寫明要留什麼；順口的問題用 /btw，答案不進歷史；要讀很多檔案的調查交給 subagent，只拿回摘要（第 6 章）。文件最後也寫了例外：深陷一個複雜的問題時，歷史有價值，這時該讓 context 累積（第 10 章）。

Effective Harnesses 處理的是 session 之間。Claude Agent SDK 有 compaction，作者說它不夠：交給下一個 agent 的指示不一定完全清楚，只拿到一句高階 prompt 的 agent 還是會一次做太多，或太早宣布完成（Effective Harnesses 第 1 章）。作者的交接靠檔案：初始化 agent 建好功能清單、進度檔 claude-progress.txt 與 git repo，之後每個 session 開工先讀進度檔、git log 與功能清單（第 2、6 章）。

OpenHands：論文沒有談

OpenHands 的事件流依時間記下每一個動作與觀察，也包括使用者的訊息；圖 3 的最小 agent 每一步把整條歷史轉成訊息交給模型（OpenHands 第 2 章）。歷史變長之後怎麼精簡，論文沒有談：整理者在原文裡搜尋過 condense、truncate、summarize、context window，都沒有出現。

單元 8 Neubig 的部落格寫到 OpenHands 當時的另一個做法：把多個 agent 的 prompt 全部串成一份，缺點之一是模型可能被太多額外的 context 分心（Neubig 第 4 章）。那句話連到的論文（arXiv 2307.03172），就是 SWE-bench 第 8 章引的〈Lost in the middle〉。

其他單元的對照

Claude Code 的壓縮，單元 2 有另一份描述

單元 2 的〈Effective Context Engineering〉說，Claude Code 壓縮時把訊息歷史交給模型摘要，保留架構上的決定、還沒解決的 bug 與實作細節，丟掉重複的工具輸出；CLAUDE.md 一開始就放進 context，glob、grep 讓它需要時再去找檔案（Context Engineering 第 5、7 章）。單元 2 的對照頁第 5 章，已經把 Effective Harnesses 的「compaction 不夠」與 SWE-bench 的 context 量測並排過（單元 2 對照第 5 章）。

整理者的讀法

三種尺度，量的不是同一件事

  • 一次呼叫：SWE-bench 調的是放進 prompt 的檔案多寡，模型只回答一次。
  • 一個 session：SWE-agent 調的是每一輪看到的視窗與保留的歷史，agent 還可以自己再去找。
  • 跨 session：Claude Code 文件與 Effective Harnesses 處理的是清空、壓縮之後怎麼接續，兩篇都沒有附量測。
  • 給少也降：五篇裡只有 SWE-agent 的 30 行視窗這一個數據點。

還沒有答案的地方：SWE-agent 說 agent 用不上後面的輪次，可以從改進模型、改進介面或兩者一起下手（SWE-agent 第 13 章）；Claude Code 文件說什麼時候該清、什麼時候該讓 context 累積，要靠使用者看它做事時養出的直覺（Claude Code 第 10 章）。

測試全過：SWE-bench 的判定

SWE-bench 的規則只有一條：模型的 patch 套得上，FAIL_TO_PASS 與 PASS_TO_PASS 兩份清單裡的測試全部找得到、全部通過，才算解出；這些測試來自那次 PR，模型看不到（SWE-bench 第 3、4 章）。作者說這讓評估很穩健：每題至少有一個 F2P 測試，40% 有兩個以上，P2P 測試的中位數是 51 個（第 1 章）。

作者也寫了這套判定的邊界。討論一節的第三個限制是：只靠執行測試，不足以保證生成的程式可靠，語言模型寫的程式常常比人寫的不完整、沒效率，或比較難讀（第 13 章）。附錄 C.7 的例子裡，Claude 2 給 requests 的 patch 解出了題目，卻把一個條件判斷塞進複雜又被廣泛使用的類別，Cyclomatic 複雜度從 3 升到 5（第 10 章）。沒解出的 patch 多半一個 F2P 測試都沒過，不是什麼都沒改變，就是還弄壞了原本的功能（第 11 章）。

SWE-agent 的 agent 會自己檢查。解出的 286 條軌跡，第一步不是寫重現問題的腳本，就是去搜尋；常見的收尾是改完、跑過、刪掉重現腳本、交卷（SWE-agent 第 9 章）。附錄 D 的案例看得到另外兩種情況：django 那題改了幾次之後，agent 認為環境跑不起伺服器，沒有測試就交卷，結果沒有解出；requests 那題通過了測試，但沒有用 codebase 裡現成的工具函式，作者說在正式環境裡可能比較難維護（第 11 章）。

OpenHands 也有測試，對象是平台自己：整合測試把模型換成錄好的回應，檢查 prompt 的組裝、訊息的傳遞與沙箱的執行；模型的能力有沒有退步，作者說仍要靠完整的評估（OpenHands 第 11 章）。

測試之外：像使用者測，換一個審查者

Effective Harnesses 的作者看到的最後一種失敗，是功能沒測好就標成完成。沒有明確指示時，Claude 會改程式，也會跑單元測試、用 curl 打開發用的伺服器，卻看不出功能沒有端對端跑通；明確要它用瀏覽器自動化工具、像使用者一樣測過之後，作者說它大多能找出並修掉這類 bug（Effective Harnesses 第 5 章）。功能清單也照這個方向設計：coding agent 只准改每一項的 passes 欄位，提示裡寫明刪改測試是不可接受的（第 3 章）。工具也有看不到的地方：透過 Puppeteer MCP，Claude 看不到瀏覽器原生的 alert 對話框。

Claude Code 文件從另一端講。文件說，Claude 覺得做完了就會停；沒有它自己能跑的檢查，「看起來完成」就是唯一的訊號，使用者就成了那個驗證迴圈（Claude Code 第 1 章）。檢查可以是測試、build 的結束碼、linter 或截圖比對，擋住「停下」的做法由輕到重有四種：在同一個 prompt 裡跑、設成 /goal 條件、用 Stop hook 擋住、交給驗證用的 subagent；文件也要使用者看證據，不要只聽聲稱。工作做完，再讓一個新的 subagent 只看 diff 與使用者給的標準來審；文件提醒，被要求找缺口的審查者幾乎總會找到一些，只修影響正確性與需求的就好（第 8 章）。五種常見失敗裡的「先信了才驗」，修法是一定要給驗證，驗證不了就不要上線（第 9 章）。

整理者的讀法

三種判定，查的東西不同

  • SWE-bench 的測試：寫在那次 PR 裡，模型看不到，查的是 issue 要的行為與原本的行為。

判斷題 · 01

你的 coding agent 卡住時，先改外面那一層，還是先換模型？

改外層這一邊：SWE-agent 固定 GPT-4 Turbo，只換介面的一個元件，Lite 上最多差 7.7 個百分點；SWE-bench 同一個 Claude 2，換一種給檔案的方式，分數也跟著變。換模型這一邊：OpenHands 固定 CodeActAgent，換三個模型差 19.0 個百分點，作者也說 agent 本身還要更強（都在第 2 章）。

還缺的證據：同一組題目、同樣的預算下，兩個模型各配兩種外層的並排。單元 10 SWE-smith 的表 3 兩個方向都有，但數字多半取自排行榜。

挑二三十個你自己的任務，準備兩種外層（例如只給 shell，和加上檢視、編輯、搜尋指令的介面）與兩個模型，四種組合各跑一次；記解題率、每題成本與失敗的樣子。

判斷題 · 02

該給模型看多少？跨 session 的交接，靠摘要還是靠檔案？

給多了會降：SWE-bench 的檢索上限放寬，Claude 2 從 1.96% 降到 1.22%；SWE-agent 保留完整歷史、一次看整個檔案，都比預設低。給少也會降：SWE-agent 的視窗縮到 30 行是 14.3%。跨 session：Claude Code 文件靠清空、壓縮與 subagent，Effective Harnesses 說壓縮不夠，改寫進檔案（都在第 3 章）。

還缺的證據：跨 session 的交接，兩份文件都沒有附量測；有數字的兩篇，一篇是一次呼叫，一篇是一個 session。

找一個一次做不完的任務，分兩組：一組每個 session 結束時只留壓縮的摘要，另一組另外寫進度檔、留 git commit。記每個新 session 開工時重做了多少、有沒有接手到壞掉的狀態。

判斷題 · 03

agent 說做完了，要看到什麼才算數？

測試判定：SWE-bench 要 F2P 與 P2P 全過，但它自己說只靠測試不足以保證可靠，單元 11 的 ABC 也引了錯的 patch 照樣通過的研究。測試之外：Effective Harnesses 要 agent 像使用者一樣端對端測；Claude Code 文件要一個只看 diff 與標準的審查者（都在第 4 章）。

可以拿來判斷的問題：你的檢查查的是程式的行為、使用者走得通的路徑，還是需求有沒有做到？要查的東西在不在檢查者手上？

拿二十個已經通過測試的 agent 產出，各做一次端對端的檢查，再交給一個只看 diff 與需求的審查者；分別記三種檢查各抓到幾個問題、重疊了幾個。

為什麼不附答案

證據在別人的任務上量出來

五篇的數字來自不同的任務、模型與年份，兩份文件沒有附數字；放到你自己的任務上會不會成立，要用你的任務量過才知道。這一頁只負責把證據排在一起，判斷留給讀者。

Reference · 用詞對照

同一件事，五篇各用不同的名字

五篇對模型外面那一層、一題、紀錄、context 與檢查各有說法。每一條先寫這件事，再列各篇怎麼稱呼、在本站讀物頁的哪一章；沒有談到的篇就不列。

scaffold
模型外面那一層
SWE-agent：agent-computer interface（ACI），夾在模型與電腦之間（第 1、2 章）。OpenHands：平台的 runtime、工具庫與 agent 庫（第 2 到 6 章）。Effective Harnesses：agent harness，Claude Agent SDK 是通用的 harness（第 1 章）。Claude Code 文件：環境的設定（第 4、5 章）。課程講題用 scaffold；單元 11 的〈Demystifying Evals〉說 agent harness 也叫 scaffold。
ACI
替 agent 設計的介面
SWE-agent 提出這個詞（第 2 章）。OpenHands 說它是 SWE-Agent 的用語，AgentSkills 的編輯工具改編自它（第 5 章）。單元 2 的〈Building Effective Agents〉也用 ACI，原文沒有連到 SWE-agent（整理者搜尋過）。
task instance
一題
SWE-bench：codebase、問題描述、測試、參考解四個部分，表 9 有 14 個欄位（第 3 章）。SWE-agent：沿用 SWE-bench 的題（序章）。Effective Harnesses：功能清單裡的一項，附測試步驟與 passes 欄位（第 3 章）。
trajectory
做事的紀錄
SWE-agent：trajectory，每一輪的想法、指令與回應（第 3 章）。OpenHands：event stream，動作與觀察依時間排列（第 2 章）。Claude Code 文件：session 與 checkpoint，可以倒回、接續（第 6 章）。Effective Harnesses：git log 加上進度檔 claude-progress.txt（第 2 章）。
context management
給模型看多少
SWE-agent：history processor，最近 5 個以前的觀察折成一行（第 6 章）。Claude Code 文件：/clear、/compact、/rewind、/btw 與 subagent（第 6 章）。Effective Harnesses：compaction，作者說不夠（第 1 章）。SWE-bench：context 上限 13k、27k、50k 與 oracle-collapsed（第 6、8 章）。
verification
檢查做對了沒
SWE-bench：FAIL_TO_PASS 與 PASS_TO_PASS 兩組測試（第 4 章）。SWE-agent：重現問題的腳本，以及 edit 之後的 linter 護欄（第 5、9 章）。Effective Harnesses：端對端測試與 passes 欄位（第 3、5 章）。Claude Code 文件：能跑的檢查、/goal、Stop hook、對抗式審查（第 1、8 章）。OpenHands：整合測試，測的是平台的程式（第 11 章）。
done
什麼時候算做完
SWE-agent：agent 下 submit；成本用完時自動交出（第 9 章）。OpenHands：AgentFinishAction（第 2 章）。SWE-bench：% Resolved，兩組測試全過（第 4 章）。Effective Harnesses：測過才把 passes 改成 true，收尾留下乾淨的狀態（第 2、3 章）。Claude Code 文件：不能只靠「看起來完成」（第 1 章）。
sandbox
在哪裡執行
SWE-agent：用完即丟的 Docker 容器，環境改編自 InterCode（第 3 章）。OpenHands：每個 session 一個 Docker 容器，任意 image 都能裝上執行 API（第 3、4 章）。SWE-bench：依 release 版本手工建的 conda 環境（第 2 章）。Claude Code 文件：作業系統層的沙箱與權限模式（第 5 章）。Effective Harnesses：init.sh 啟動的 dev server（第 6 章）。
edit
改檔案的方式
SWE-agent：edit 換掉第 n 到 m 行，套用後跑 flake8（第 5 章）。OpenHands：edit_file，改編自 SWE-Agent 與 Aider（第 5 章）。SWE-bench：patch 檔；要模型重寫整個檔案，解題率較低（第 10 章）。Claude Code 文件：檔案編輯工具，checkpoint 只追蹤它的改動（第 6 章）。
delegation
分給另一個 agent
OpenHands：AgentDelegateAction，把瀏覽交給 BrowsingAgent（第 6、9 章）。Claude Code 文件：subagent、/batch 的 fan-out、寫與審分開的兩個 session（第 5、7 章）。Effective Harnesses：初始化 agent 與 coding agent 只差開場的 user prompt（第 2 章），分工的多 agent 留作開放問題（第 8 章）。
SWE-bench subsets
同一個基準的不同切法
SWE-bench：全集 2,294 題、Lite 300 題、開發集 225 題（第 2 章）。SWE-agent：全集與 Lite（第 7 章）。OpenHands：Lite，不給 hint（第 8 章）。單元 10 的 SWE-smith、單元 11 的 ABC 與〈Demystifying Evals〉用的是 Verified。
budget
成本與上限
SWE-agent：每題上限 4 美元，超過就自動交出（第 7 章）。OpenHands：每題成本；完整跑一次 SWE-bench 估 6.9k 美元（第 8 章）。SWE-bench：context 的 token 上限（第 6 章）。Claude Code 文件：context window 是最需要管理的資源（序章）。
