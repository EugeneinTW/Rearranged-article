CS 329Z UNIT 2 · 單元對照

流程寫死多少，context 給多少Anthropic 相隔九個月的兩篇工程文章並排

CS 329Z 第 2 週「LLMs for Builders」那一講配了兩篇讀物，都是 Anthropic 的工程文章。2024 年 12 月的〈Building Effective Agents〉（本頁簡稱 Agents 篇）把系統分成工作流與 agent，建議先找最簡單的解；2025 年 9 月的〈Effective Context Engineering for AI Agents〉（簡稱 Context 篇）回頭引用它，把重點移到每一步該讓模型看到哪些 token。這一頁把兩篇並排，整理它們在流程、工具、分工、長任務四件事上各怎麼說、後一篇怎麼引前一篇、講題裡哪些兩篇都沒有談；判斷題不附答案。每章開頭先放一張圖解卡講重點，往下是詳細說明；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

兩篇讀物，相隔九個月，出自同一家公司

一篇把 agentic 系統拆成幾個可以組合的模式，一篇把 context 當成有限的資源來管。後一篇回頭引用了前一篇，改用一個更簡單的 agent 定義。這一頁不重述兩篇，而是把它們放在一起讀：哪裡接得上、各自把重點放在哪裡、講題裡哪些兩篇都沒談。

CS 329Z 第 2 週星期一的「LLMs for Builders」屬於「Foundations & Landscape」分區。課程頁列的講題有六個：API 與 SDK、結構化輸出與受限生成、解碼與 test-time compute、context engineering、選模型，以及成本與延遲。這一講配了一篇必讀、一篇選讀，本站都整理過：

  • 兩篇的重心幾乎不重疊。Agents 篇的專章落在架構與取捨：先直接用 API，要用框架就看懂底下的程式（第 1 章），以及 agentic 系統常拿延遲與成本去換表現（第 1、3 章）。Context 篇整篇只談一個講題；它提到的平台功能是 Claude Developer Platform 上的工具結果清除與 memory tool（第 7、8 章），這是作者對自家平台的說法。
  • 結構化輸出只在 Agents 篇的附錄 2 出現一次：同一段程式放在 markdown 或 JSON 裡，對模型的難度不同，放進 JSON 要多跳脫換行與引號（附錄 2）。受限生成兩篇都沒有談。單元 4 的 MCP 規格有一個名字相近的 structuredContent，規格特別註明它是伺服器產生的結果資料，和模型的結構化輸出無關（MCP 第 6 章）。
  • 兩篇都沒有用 test-time compute 這個詞，也沒有談溫度、取樣這類解碼設定。Agents 篇的投票（同一個任務跑很多次，拿多樣的輸出）與評估者-優化者（生成、評估、再生成的迴圈），和單元 9〈Scaling LLM Test-Time Compute Optimally〉比較的平行取樣與循序修訂形狀相近（單元 9 第 9 章）；這個對應是整理者的讀法。
  • 選模型兩篇都只順帶一句。Agents 篇在路由一章舉例：簡單常見的問題分給較小、較省的模型（頁面現在寫 Claude Haiku 4.5），困難少見的分給較強的模型（Claude Sonnet 4.5）（第 4 章）；Context 篇建議先用手上最好的模型測一份最小的 prompt（第 3 章）。單元 9 在同樣的總運算量下，比了小模型加測試時算力與參數約多 14 倍的模型（第 11 章）。

成本與延遲這一列，兩篇說的「花費」不是同一種。Agents 篇的取捨是延遲與成本，全文沒有用 budget 這個詞；Context 篇的注意力預算，是模型讀 context 時的有限注意力，每多一個 token 就用掉一些（Context 篇第 2 章）。Context 篇談到時間的只有一處：跑的時候才探索，比讀預先算好的資料慢（第 5 章）。

Agents 篇：兩種系統，一路往上加

Agents 篇的第一件事是畫線：工作流是模型與工具照預先寫好的程式路徑被安排，agent 是模型動態決定自己的流程與工具用法（Agents 篇第 1 章）。它把兩者放在一條由簡到繁的路上：最底下是單一次呼叫加上檢索與情境內範例，作者說很多應用做到這裡通常就夠；往上是五種工作流，最後才是 agent。作者說 agentic 系統常常是拿延遲與成本去換任務表現，所以建議只在需要時才加複雜度，這可能代表根本不做 agentic 系統。

兩種系統各有適用的地方。工作流給定義明確的任務可預測與一致；agent 適合需要彈性、需要由模型做決定、而且要規模化的情況，例如難以預測要走幾步、沒辦法寫死一條路徑的開放式問題。agent 的代價也寫在同一章：成本更高、錯誤可能累積，要在沙箱裡大量測試、配上護欄（第 7 章）。談到組合這些模式時，作者重複一次：只有在複雜度明顯改善結果時才加上去；總結又說，框架能幫你快速起步，走向生產環境時要願意減少抽象層、用基本元件來建（第 8 章）。

Context 篇：一個定義，自主跟著模型走

Context 篇在談跑的時候取用資料的那一節，開頭回頭引用 Agents 篇：前一篇區分了工作流與 agent，寫完之後他們越來越傾向一個簡單的定義，agent 就是模型在迴圈裡自主地使用工具（這個定義連到 Simon Willison 的整理）。作者說和客戶合作時，看到整個領域正往這個簡單的樣子收斂；底下的模型越強，agent 能承擔的自主程度就越高，能自己在細膩的問題空間裡找路、從錯誤中恢復（Context 篇第 5 章）。

它沒有因此主張全部交給模型。同一章舉了一個混合的例子，作者說 Claude Code 一開始就把 CLAUDE.md 放進 context，其他檔案讓它用 glob、grep 這類工具在跑的時候去找。作者說自主要放多少看任務而定，內容變動較少的法律、金融工作，可能更適合混合策略；長期的方向，是隨著模型變強，放手讓聰明的模型自己判斷，需要人工預先挑選的越來越少。在這個變化速度下，作者給團隊的建議仍是「先做最簡單、能用的那一版」。結論再說一次：越聰明的模型，需要越少規定式的工程（第 10 章）。

整理者的讀法

兩篇都談「寫死」，指的是不同的層

  • Agents 篇的工作流：路徑寫在程式裡，作者把它當成定義明確的任務的正當選項。
  • Context 篇反對的寫死：把複雜、脆弱的 if-else 邏輯寫進 system prompt，想逼出精確的行為（第 3 章）。這是 prompt 的寫法，談的不是系統的架構。
  • Context 篇沒有談的：它沒有逐一回頭評論五種工作流，也沒有說工作流不再適用；全文只在引用 Agents 篇的那一句提到工作流這個詞。
  • 兩篇的證據：「只在明顯改善時才加複雜度」與「模型越強、自主越多」，都來自作者團隊與客戶的經驗，都沒有附量測。

還沒有答案的地方，原文點出了一部分。Context 篇說自主程度該放多少看任務，沒有給判斷的界線；Agents 篇要讀者量測表現、反覆調整，自己沒有公布任何一組工作流對 agent 的比較。模型變強之後，前一篇那條由簡到繁的路還要不要照走，兩篇都沒有回答。

Agents 篇把工具放在附錄 2 整篇談（Agents 篇附錄 2）。它的主張是工具的定義與規格，應該得到和整體 prompt 一樣多的提示工程。同一個動作常有好幾種寫法：改檔案可以寫 diff，也可以整個檔案重寫；程式可以放在 markdown 或 JSON 裡。對軟體來說這些差別只是表面，對模型來說有的格式難寫得多：寫 diff 要先算對區塊標頭裡要改幾行，放進 JSON 要多跳脫換行與引號。作者的建議是給模型足夠的 token 先想、格式貼近網路上自然出現的文字、不要有格式上的額外負擔，再把工具的說明寫成像給團隊初級工程師的 docstring，並把工具做成不容易用錯的樣子（poka-yoke，防呆）。它的例子是做 SWE-bench 的 agent：作者說花在工具上的時間比花在整體 prompt 上的多，把工具改成一律要絕對路徑之後，模型用這個方法就沒再出錯。

整理者的觀察

「邊界情況」在兩篇裡出現在不同的地方

Agents 篇說，好的工具定義常包含用法範例、邊界情況、輸入格式的要求，以及和其他工具的清楚分界。Context 篇說，很多團隊把一長串邊界情況塞進 prompt，想寫明模型該守的每一條規則，作者不建議這樣做，改給一組多樣、典型的範例（第 4 章）。前者講的是工具的說明文件，後者講的是 prompt 裡的規則與範例，兩篇沒有互相回應；工具的描述該寫多長，兩篇都沒有給數字。

兩篇的檢查方法也相近。Agents 篇要人站在模型的角度，看光憑描述和參數能不能明白怎麼用，需要仔細想才懂的，模型多半也是；Context 篇說人類工程師說不出某個情況該用哪個工具，就別期待 agent 做得更好。一個問的是單一工具的說明，一個問的是一整組工具的選擇。工具定義有哪些欄位、執行錯誤該怎麼回給模型，單元 4 的 MCP 規格有逐條的規定（MCP 第 6 章）；兩篇讀物都提到 MCP，都沒有談到規格的內容。

Agents 篇：注意力集中，子任務跑了才知道

Agents 篇有兩種一對多的工作流（Agents 篇第 5 章）。平行化由程式把任務拆成獨立的子任務同時跑（分段），或把同一個任務跑很多次（投票），再由程式彙整。作者說有多個考量的複雜任務，每個考量各自一次呼叫、讓注意力集中在一個面向，通常比一次呼叫全包表現好；例子是一個模型實例回答使用者、另一個同時篩查不當內容，作者說這往往比同一次呼叫兼做護欄與回答表現好。協調者-工作者則由一個中央模型依這次的輸入拆解任務、派給工作者、再合成結果，適合事先無法預測需要哪些子任務的情況，例如每次要改好幾個檔案的程式產品。Agents 篇全文沒有用 multi-agent 或 sub-agent 這兩個詞，整理者在原文裡搜尋過。

Context 篇：乾淨的視窗，只收摘要

Context 篇把子 agent 架構列為長任務的三種技巧之一（Context 篇第 9 章）。作者描述的做法，是不讓一個 agent 撐住整個專案的狀態，改由專門的子 agent 在乾淨的 context window 裡處理聚焦的任務：主 agent 拿著高層的計畫協調，子 agent 做深入的技術工作，或用工具找相關的資訊。每個子 agent 可能用掉數萬個 token 甚至更多，交回的只有一份濃縮的摘要，常見是 1,000 到 2,000 個 token。作者說這帶來清楚的關注點分離：詳細的搜尋脈絡留在子 agent 裡，主 agent 專心綜合與分析結果。

它引用自家另一篇談多代理研究系統的文章，說這個模式在複雜的研究任務上，比單一 agent 的系統有顯著的改善；那篇不在課程讀物裡，Context 篇本身沒有給數字。它也寫了適用的範圍：平行探索划算的複雜研究與分析用子 agent，需要大量來回的任務用壓縮，有清楚里程碑的迭代開發用筆記（第 6 章）。單元 13 的 Claude Code 文件給了同樣的做法：把調查交給 subagent，它在自己的 context window 裡讀檔，只回報摘要（Claude Code 文件第 6 章）。

其他單元：交接時掉東西

單元 8 的 Neubig 談的是同一個動作的另一面。多代理系統要在 agent 之間傳遞資訊，傳遞本身就可能讓資訊流失；他的例子是 CodeR 的 Fault Localizer，如果只把工作的摘要傳給後面的 agent，常常丟掉了對下游有用的脈絡（Neubig 第 2 章）。他也寫明，一個 agent 握有特權資訊、或不同的 agent 代表不同的人時，多代理就是對的做法（第 5 章）。Neubig 的部落格（2024-09）早於 Context 篇，Context 篇沒有提到它，整理者在原文與連結裡搜尋過。

整理者的讀法

同一份摘要，兩種算法

  • Context 篇算省下的：子 agent 探索用掉的數萬個 token 留在外面，主 agent 的視窗只多 1,000 到 2,000 個。
  • Neubig 算丟掉的：摘要沒寫進去的脈絡，下游就拿不到。
  • Agents 篇的理由在別處：每次呼叫專心在一個面向，以及子任務事先不知道；它沒有談交接時資訊的多寡。
  • 沒有量過的：同一個任務裡，摘要漏掉了多少下游需要的東西，三篇都沒有量。

還沒有答案的地方：Context 篇說選哪一種技巧取決於任務的特性，但「平行探索划算」要怎麼判斷，沒有給條件；摘要該寫多長、漏掉什麼算太多，兩篇都沒有談。

Agents 篇：每一步都對一次真實情況

Agents 篇描述 agent 怎麼跑的那一段，重點放在控制（Agents 篇第 7 章）。執行時每一步都要從環境拿到「真實情況」，例如工具呼叫的結果或程式執行的輸出，用來判斷進度；可以在檢查點或遇到阻礙時暫停，等人回饋；任務通常在完成時結束，但常見的做法是加上停止條件，例如最大迭代次數，把控制權留在手上。自主的代價是更高的成本，以及可能累積的錯誤，作者建議在沙箱裡大量測試，配上合適的護欄。寫程式的例子裡，自動化測試驗證的是功能，解法符不符合系統更廣的需求，作者說仍然要人審（附錄 1）。

Context 篇：token 越多，注意力越薄

Context 篇從一個觀察出發：大海撈針式的基準測試揭露了 context rot，context window 裡的 token 越多，模型準確回想其中資訊的能力越差；有的模型退化得比較平緩，但每個模型都有這個特性（Context 篇第 2 章）。作者用注意力預算來比喻，每多一個 token，預算就被用掉一些，原因有三個：n 個 token 之間有 n² 組兩兩關係、訓練資料以短序列居多、位置編碼內插會讓模型對位置的理解有些退化。結果是一道漸層，不是懸崖。這一章連到外部的研究，Context 篇本身沒有給退化的數字。

長任務要連續工作數十分鐘到數小時，token 總數會超過 context window。作者不把希望放在更大的視窗上：在可預見的未來，各種大小的視窗都會有 context 污染與資訊相關性的問題（第 6 章）。三種技巧各自處理一種情況：壓縮在快到上限時摘要對話，帶著摘要與最近存取的五個檔案開新視窗，調壓縮的 prompt 時先把召回拉到最高、再提高精準（第 7 章）；結構化筆記讓 agent 把進度寫到視窗外，重置之後讀回來接著做（第 8 章）；子 agent 把探索留在自己的視窗裡（第 9 章）。

其他單元：後來的文章與一組量測

單元 13 有兩份同一家公司後來寫的文件，都沒有提到這兩篇讀物（整理者在原文裡搜尋過），談的卻是同一件事。〈Effective Harnesses for Long-Running Agents〉（2025-11-26）說 compaction 不夠：即使是 Opus 4.5 在 Agent SDK 上跨好幾個 context window 迴圈地跑，只拿到一句高階的 prompt，也做不出上線品質的 web app；作者再加上功能清單、進度檔、git，以及每個 session 開工前的端對端測試（第 1 章、第 6 章）。Claude Code 的最佳實務文件把 context window 當成最需要管理的資源，說它滿得很快、越滿表現越差（序章）。

單元 13 的 SWE-bench 論文（2023-10）有一組和 context 長度有關的量測：把 BM25 取回的 context 上限從 13k 放寬到 50k，Claude 2 的解題率從 1.96% 降到 1.22%（SWE-bench 第 8 章）。它的條件和 Context 篇談的不同：那是一次呼叫、給進一整段程式碼，不是跑很多輪的 agent。

整理者的讀法

兩種風險，指的不是同一種失敗

  • 錯誤累積：前面某一步的結果錯了，後面的步驟在錯的基礎上繼續；Agents 篇的對策是每一步向環境查一次、設停止的條件。
  • context 腐化：該用的資訊還在 context 裡，模型卻找不回來，或被多餘的 token 分散；Context 篇的對策是少放、放對，重置之前先把重要的寫下來。
  • 兩者會不會一起出現：一段很長的 trace 裡，某一步出錯是因為前面錯了，還是因為前面的資訊被淹沒了，兩篇都沒有提供分辨的方法。

還沒有答案的地方：Context 篇說即使模型持續進步，在長時間的互動裡維持連貫，仍會是做出更有效 agent 的核心挑戰（第 6 章）；Agents 篇沒有談長任務。長任務出錯時該先查哪一種，兩篇都沒有說。

判斷題 · 01

模型變強之後，流程還要先寫成工作流嗎？

先寫的一方：Agents 篇由簡到繁，單次呼叫、工作流、agent 一層一層加，只在評測證明有改善時才往上。放手的一方：Context 篇改用「模型在迴圈裡自主使用工具」的定義，預期模型越強、需要的人工挑選越少，同時仍建議先做最簡單、能用的那一版（都在第 2 章）。

還缺的證據：同一個任務寫成工作流與交給 agent 兩個版本，在不同能力的模型上各跑一次的結果。兩篇都沒有公布這種比較。

挑一個步驟大致固定的任務，做一條帶檢查閘的提示鏈，再做一個拿同一組工具的 agent 迴圈；用一個較小、一個較強的模型各跑二三十題，記成功率、token 數與延遲，看兩個版本的差距會不會跟著模型改變。

判斷題 · 02

把探索交給子 agent、只收摘要，省下的比丟掉的多嗎？

看好的一方：Context 篇說子 agent 讓主 agent 的視窗保持乾淨，只收 1,000 到 2,000 個 token 的摘要；Agents 篇說每個考量各自一次呼叫，注意力更集中。存疑的一方：單元 8 的 Neubig 說只傳摘要，常常丟掉下游用得到的脈絡（都在第 4 章）。

還缺的證據：同一個研究型的任務，單一 agent 加壓縮，對上主 agent 加子 agent 的比較，以及摘要漏掉了多少最後答案用得到的事實。Context 篇提到的改善，來自另一篇不在課程裡的文章。

準備一個要查好幾個來源的問題，先列出正確答案需要的十個事實；讓子 agent 各查一部分、只交回摘要，數一數十個事實有幾個出現在摘要裡、幾個進了最後的答案。

判斷題 · 03

長任務出錯時，先加檢查，還是先整理 context？

加檢查的一方：Agents 篇的每一步向環境查真實情況、檢查點、停止條件、沙箱測試。整理 context 的一方：Context 篇的 context rot 與三種技巧。單元 13 的 harness 文章兩樣都做：進度檔與功能清單，加上每個 session 開工前的端對端測試（都在第 5 章）。

還缺的證據：長任務的失敗裡，錯誤累積與資訊被淹沒各佔多少。兩篇都沒有給數字；單元 13 SWE-bench 的長度量測來自單次呼叫，不是跑很多輪的 agent。

從自己的 agent 挑幾段失敗的長 trace，對每一段問兩件事：出錯的那一步，需要的資訊還在 context 裡嗎？前面有沒有一個早就錯了、卻沒被發現的結果？兩種各記一欄，再決定先試哪一種對策。

為什麼不附答案

證據來自作者自己的經驗

兩篇都是 Anthropic 根據自家與客戶的經驗寫的建議，沒有對照實驗；放到你的任務、你的模型上會不會成立，要量過才知道。這一頁只負責把證據排在一起，判斷留給讀者。

Reference · 用詞對照

同一件事，兩篇各用不同的名字

兩篇對 agent、context、工具、長任務各有說法。每一條先寫這件事，再列各篇怎麼稱呼、在本站讀物頁的哪一章；沒有談到的篇就不列，其他單元只在名字容易混淆時列出。

agent
什麼叫 agent
Agents 篇：模型動態決定自己的流程與工具用法的系統，和工作流合稱 agentic 系統（第 1 章）；實作上通常就是模型依環境的回饋，在迴圈裡使用工具（第 7 章）。Context 篇：模型在迴圈裡自主地使用工具（第 5 章）。
workflow
工作流
Agents 篇：模型與工具照預先定義的程式路徑被安排的系統；五種是提示鏈、路由、平行化、協調者-工作者、評估者-優化者（第 3 到 6 章）。Context 篇只在引用 Agents 篇時提到這個詞（第 5 章）。
context
模型每次看到的東西
Agents 篇：擴增型 LLM，模型接上檢索、工具、記憶三種能力（第 2 章）。Context 篇：取樣時放進模型的整組 token，包括 system 指示、工具、MCP、外部資料、訊息歷史（第 1 章）。
retrieval
取用資料
Agents 篇：檢索，模型自己產生搜尋查詢（第 2 章）；單次呼叫加檢索與情境內範例常常就夠（第 1 章）。Context 篇：推論前的 embedding 檢索，對上跑的時候用識別碼即時載入（just in time），兩者可以混合（第 5 章）。
memory
記憶
Agents 篇：擴增型 LLM 的記憶，模型自己決定要留下什麼（第 2 章）。Context 篇：結構化筆記，也叫 agentic memory，寫在視窗外、之後讀回；平台另有 memory tool（第 8 章）。
tools
工具的介面
Agents 篇：ACI，agent 與電腦之間的介面，工具的定義與文件要像人機介面一樣用心，並做防呆（附錄 2）。Context 篇：工具是 agent 和資訊空間、行動空間之間的契約，要最小可行的一組（第 4 章）。
examples
範例
Agents 篇：情境內範例（第 1 章）；好的工具定義附上用法範例（附錄 2）。Context 篇：few-shot，給一組多樣、典型的範例，不塞一長串邊界情況（第 4 章）。
budget
預算與成本
Agents 篇：延遲與成本，拿來換任務表現（第 1 章）；全文沒有用 budget 這個詞。Context 篇：注意力預算，每多一個 token 就用掉一些（第 2 章）。兩篇量的是不同的東西。
delegation
分工
Agents 篇：平行化（分段、投票）與協調者-工作者（第 5 章），全文沒有用 multi-agent 這個詞。Context 篇：子 agent 架構，也叫多代理架構（第 6、9 章）。
control
跑久了怎麼控制
Agents 篇：每一步從環境拿真實情況（ground truth）、檢查點、停止條件（第 7 章）。Context 篇：長任務（long-horizon）、context 污染，以及壓縮、工具結果清除（第 6、7 章）。
simplicity
簡單
Agents 篇：先找最簡單的解，需要時才加複雜度（第 1、8 章）。Context 篇：最小、訊號最強的一組 token（第 3、10 章），以及「先做最簡單、能用的那一版」（第 5 章）。
prompt
prompt 的位置
Agents 篇：從簡單的 prompt 開始，用完整的評估最佳化（第 8 章）；工具定義值得和整體 prompt 一樣多的提示工程（附錄 2）。Context 篇：context engineering 是 prompt engineering 的自然延伸；system prompt 要寫在剛好的高度（第 1、3 章）。
structured output
結構化輸出
Agents 篇：程式放在 markdown 或 JSON 裡，對模型的難度不同（附錄 2）。單元 4 的 MCP 規格：structuredContent 是工具結果裡的 JSON 物件，規格註明它和模型的結構化輸出無關（MCP 第 6 章）。
