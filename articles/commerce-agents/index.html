Prologue · 整理者的引言

電商 agent 難的不是推薦商品，是守住邊界

現在很多模型都能做商品問答。主題頁作者 Philo 的判斷是：難的是讓 agent 只引用真實價格、不能擅自扣款、改促銷前要有人批准，而且換了模型或改了 prompt 之後，這些規則還在。本頁把這個判斷當主軸，用 Anthropic 的工程文章與藍圖的內容來驗證它。

Anthropic 說，過去一年他們和零售、市集、旅遊、娛樂票務、電信業者一起做的電商 agent 已經在生產環境運作，企業客戶看到更大的購物車與更有效率的賣家營運。公告裡給的數字是購物車最高大 35%、完成購買的機率高 60%；主題入口 AI Post Hub 提醒，公告沒有公開樣本、產業分布與實驗設計，這些數字不是用了藍圖就保證得到的結果。

這些 agent 共用一個簡單的架構：一個模型在 agent loop 裡，配一組 skills、一組 tools，加一套夠強的 eval suite。工程文章分成三部分：架構（決定一次就好）、快與省、上線後的記憶、安全、evals 與多團隊協作。藍圖的安全文件則把規則分成三類：程式強制的、仍靠模型的、部署自己要負責的。這個三分法會貫穿整頁。

給初學者

先把五個名詞對齊

  • Agent loop：模型反覆「推理目標、呼叫工具、觀察結果」直到任務完成的迴圈。
  • Harness：包在模型外面、真正執行工具與規則的程式。這篇的安全全部在這裡。
  • Skill：可按需載入的任務說明書；Tool：模型能呼叫的函式，背後接你的系統。
  • Provenance（出處）：伺服器記得自己交給模型哪些 ID，之後只認這些。
  • Staged change：商家 agent 提出的修改先進暫存，由人或政策套用。

為什麼安全要在程式裡？工程文章講得很直接：商業上的失敗是金錢，而且常常不可逆；prompt 裡的規則距離被跳過，只差一次注入或一個壞樣本。所以 prompt 是安全行為的起點，卻不能是強制執行的地方。

模型負責理解需求與提案；涉及金錢或不可逆的動作，由程式規則、身分與批准流程決定。 整理自安全一節與藍圖的安全文件
為什麼值得工程團隊讀

它把隱性的 PRD 變成可以檢查的程式

價格必須來自商品資料、付款不能由模型執行、商家的修改必須批准、第三方文字不得變成指令。這些要求平常散在需求文件與口頭默契裡；藍圖把它們寫成閘、上限與圍籬，而且每一條都有 evals 盯著。

思考題 · 01

你的系統裡，哪些「只讀」的問題最常被問？

訂單到哪了、這款有沒有貨、上週哪個品項賣最差。這些不寫入任何東西的問題，就是 agent 第一版最該做的範圍。

把最近一週的客服與營運提問分成「只讀」與「會改東西」兩堆，只讀那堆的前三名就是起點。

把一次對話放慢看：使用者說出目標，模型被呼叫一次，決定要做什麼「行動」——呼叫一個工具、載入一個 skill、或用呈現工具畫出一個 UI 元件；環境把結果當「回饋」送回來，模型再被呼叫一次；需要澄清時它回到使用者，目標完成才停。這個迴圈本身沒有電商特有的東西，電商特有的東西全在環境裡。

三種執行方式，同一份定義

閘在工具呼叫裡面跑，所以三條路徑共用

藍圖把兩個 agent 各定義一次：prompt、skills、工具契約、閘。Messages API 是參考迴圈，你自己跑迴圈；Agent SDK 由 SDK 跑；Managed Agents 把執行環境交給 Anthropic。因為出處、上限、批准這些檢查都在工具呼叫裡面執行，換執行方式不用重寫安全規則。

工程文章把這一段稱為「決定一次」，而且在結語再說了一次：這篇大部分講的不是模型。工具呼叫的是你已經在跑的系統，skills 寫下的是你已經在做的程序，evals 是寫成測試的需求文件，harness 強制的是你對任何客戶端都會強制的政策。所以模型換代時，架構直接接上：改一個設定，跑一次 eval sweep。

差別是誰擁有對話：交接換對口，委派留住 orchestrator。
硬規則：安全與法規、品牌限制、過敏這類關鍵使用者事實，永遠在 system prompt，不做成 skill。

面對零售、客服、庫存、行銷這麼多領域，很多團隊的直覺是一個領域一個 subagent。Anthropic 的經驗是這樣不划算：orchestrator 握著購物車或暫存變更、使用者偏好與對話歷史，每次交接都是會遺失狀態的操作，回答品質跟著掉，還要多付幾倍 token 與幾秒延遲。領域也很少切得乾淨，退貨流程同時需要訂單歷史、目前的購物車與商品目錄。而模型每一代都能處理更多脈絡、更多 skills 與工具，今天的切分規則會逐代鬆綁。

Skills 提供同樣的模組化與脈絡控制，卻沒有交接稅，因為 skill 的指令載入的是那個已經握有整段歷史的主 agent。在多個企業部署的比較裡，單一 agent 加 skills 在品質上一致贏過「一個 prompt 包所有事」與 subagent 兩種設計，而且常常更便宜、更快。

兩個例外

什麼時候 subagent 反而對

  • 委派（delegate）：一個範圍窄、可獨立完成、需要自己一個 context window 的任務。典型是 deep research：搜尋、讀文件、寫程式跑、走進死路，全在 subagent 裡發生，只回一個精簡答案。
  • 交接（hand-off）：某個領域已經有自己的專屬 agent 與合規面（例如藥局、金融服務）。這時由那個 agent 接管對話，直接用自己的迴圈把事做完。

兩者的差別是「誰擁有對話」：交接讓領域 agent 成為使用者的對口；委派則保留 orchestrator，只在單一回合內把領域 agent 叫進來再送出去。

那什麼放 system prompt、什麼做成 skill？決定因素是頻率。載入一個 skill 要花一輪模型呼叫，所以大多數回合都會用到的東西放 prompt。起手的經驗法則：三分之一以上的流量會碰到的內容放 system prompt，其餘做成 skills；能從既有訊號預測的 skill（例如使用者從哪個頁面進來），由 harness 在第一次呼叫前直接注入，省掉那一輪；安全與法規、品牌限制、過敏這類關鍵使用者事實，永遠在 prompt。

兩個常見反模式

工具裡開始寫業務邏輯，就是該回後端的訊號

一個「有沒有貨」的工具如果自己去問目錄拿 SKU、逐店問庫存、問物流拿截止時間，再自己套替代規則與取貨資格，它就變成一團難以維護的領域知識。修法是後端提供一個能直接回答問題的端點，工具只呼叫它。另一個反模式是把整個原始回應塞給模型，包括每列的圖片網址。

接著是介面。電商 agent 的回應多半是 UI 元件：商品輪播、行程、座位圖、圖表，所以 agent 要輸出 schema。有些團隊一開始讓模型吐自訂標籤、再由前端解析，介面一長大就撐不住：模型對你的標記不如對 tool call 熟，巢狀元件一多可靠度就掉；標籤定義住在 system prompt 裡，每加一個元件都撐大 context、每改一次都可能弄壞別處；歷史對話存成只有你的解析器看得懂的格式。

撐得住的做法是每個 UI 元件就是一個工具。模型呼叫 present_products、present_itinerary、present_plan_comparison 並帶型別化參數；伺服器驗證、補齊資料、發出事件；前端渲染。因為呈現是 tool call，它本來就在 messages 陣列裡，重新載入舊對話不用再解析。

Fewer turns

更少的輪數

把可能用到的脈絡先載進去（從商品頁進來就先放該頁資料）；用更聰明的模型，它規劃工具呼叫更好，常抵過較慢的 token；讓模型平行呼叫獨立的工具，結果放在同一則使用者訊息裡回去。一個任務常超過五輪時，更快的模型往往就是更聰明的那個。

Faster tools

更快的工具

先優化工具後端本身；把拼湊在工具裡的邏輯還給後端端點；參數一串完就先執行（eager dispatch），多秒的空檔縮到幾百毫秒，Agent SDK 預設就這樣做；提示模型把最慢的呼叫最先發出。

第一輪時，全域段已經在快取裡，會話段這一輪寫進去，斷點放在它後面。第二輪時，上一輪的訊息、回應與工具結果全部變成前綴的一部分，會話段的斷點跟著往後移；只要揮發內容永遠在最後，前面的一切都一字不差，整段從快取讀出來。這就是為什麼順序等於命中率。

最常見的錯

時間戳放在 system prompt 開頭，等於每次請求都讓快取失效

還有兩個實作細節：skill 要以工具結果的形式載入，而不是接在 system prompt 後面，這樣它會落在被快取的前綴裡；斷點數量有限，每一輪都把最新的斷點往後移到使用者訊息的尾端，長長的工具結果才會從快取讀出來。記憶是每個使用者的，所以住在會話段、全域斷點之下。

你的請求裡，哪些內容每一輪都在變？它們現在放在哪裡？

時間、目前頁面、購物車快照、剛剛的搜尋結果。只要有一個放在前面，後面的一切都不會命中快取。

規則三：上限要擋得住重複的請求。票券配額、促銷價、防詐都會限制一個人能買幾個，而 agent 會重試、換句話說、平行呼叫，這是人點按鈕從來不會做的事。所以上限套在「寫入之後那一行會變成什麼」，第二句「再加兩個」疊不過去；同一個 session 的購物車寫入序列化，單一回合裡的平行呼叫不能合起來超額。商家端對價格幅度、折扣深度、補貨量、活動預算做同樣的檢查，另有一份任何變更都不得碰的受保護欄位。原則可以推廣：每個限制都套在結果狀態上而不是請求上，寫入按 session 序列化。

規則四：第三方內容一律消毒。電商的 context 大多是別人寫的：賣家、評論者、競爭者。每一次後端讀取都是不受信任的輸入，商品、評論、政策、賣家訊息、儲存的記憶，都先經過同一個消毒器並包進帶固定標籤的圍籬，模型才看得到。消毒器去掉控制字元與雙向字元、拿掉模仿圍籬標記的東西、拆解偽裝成對話輪次或工具呼叫的文字，並限制長度。prompt 負責另一半的契約：圍籬裡的文字是要回報的材料，永遠不是要執行的指令。

大多數團隊沒有好好測「注入的狀態」。案例要編碼失敗的前置條件，不只是任務本身：如果某個行為只在忙碌的第一輪、好幾次工具呼叫之後，或 session 早先出現矛盾之後才會冒出來，從乾淨狀態開始的案例每種設定都會過，什麼都測不出。多數 suite 都太偏乾淨狀態，要確保一部分案例從又長、又亂、又矛盾的歷史開始。而且每一個正向案例都要有它的負向對照：每個「應該拒絕」配一個「應該服務」，每個「應該先問」配一個「應該直接做」。缺負向案例是最常見的缺口。

案例類型在測什麼要檢查的東西
核心請求占多數流量的簡單查詢、多條件請求、商品與方案問題、多意圖訊息每個價格、庫存、屬性都能回溯到回傳的資料；資料缺時說缺，不編
脈絡相依指著螢幕上的東西、跨輪帶過來的限制、對既有購物車寫入、記憶記憶有被抽出、被取回、而且改變了答案
安全與品牌注入（分使用者自己寫的、與埋在商品名、評論、網頁片段裡的兩種）、讀別人的資料、法規文字法規文字逐位元比對；兩種注入分開寫案例
介面渲染對的元件、數量上限、逾時與空結果使用者看得到的文字裡沒有內部識別碼
跨能力「降價 15% 的話庫存夠嗎」這種同時是定價與庫存的問題兩半都要對：暫存降價並附庫存預測；分能力寫的案例抓不到

案例跟第一線看見失敗的人一起寫：產品、法務、商家營運、客服、品類管理。真實的失敗是最好的 evals，每個使用者流程 50 到 100 個案例是不錯的起點；生產環境的逐字稿是新案例的來源，尤其是刁鑽的那些；coding agent 很會生成額外案例與對抗變體，藍圖的 plugin 就附了一個依這套方法寫 evals 的 skill。

Chapter 12 · Key takeaways

五件事帶走

這篇文章大部分講的不是模型。工具呼叫你已經在跑的系統，skills 寫下你已經在做的程序，evals 是寫成測試的需求文件，harness 強制的是你對任何客戶端都會強制的政策。模型換代，架構用一次設定加一次 eval sweep 就接上。

01

架構決定一次：一個 agent 在迴圈裡，載 skills

環境是你既有的工具、skills、呈現元件與記憶，harness 跑迴圈並強制規則。交接會遺失狀態，三分之一以上流量會用到的放 prompt，其餘做成 skill；只有研究型委派與已有專屬 agent 的交接是例外。

02

模型碰到的一切都是工具，UI 元件也是

搜尋回來就已排序，模型只做判斷；工具結果只回用得到的欄位；商品卡、行程、座位圖用 present_* 工具輸出結構，伺服器補齊、前端渲染，版面自然留在對話裡。

03

延遲三個槓桿，快取靠順序

更少輪、更快的工具、更快的 token，用 sweep 選模型並量每完成任務的成本；邊成形邊串流、把工作秀出來。請求排成全域、會話、揮發三段，斷點每輪往後移，時間戳放最後。

04

安全在 harness：提案、出處、上限、圍籬

模型只能提案；只認伺服器發的 ID；上限套在結果狀態且寫入序列化；第三方文字全部消毒圍籬。記憶在背景寫、在寫入時驗、存在你的資料庫。模型出錯只剩說錯話。

05

Evals 以快照為單位，改動連著案例出貨

建構狀態、接上訊息、評結果不評路徑；正負成對，每個流程 50 到 100 個案例；CI 只跑核心、安全與碰到的部分；先做答錯不花錢的流程，付款永遠不交給模型。

"The model's most dangerous action is to propose." 模型最危險的動作就是提案。工程文章對安全設計的總結：提案之後的每一步，交給程式、身分與批准流程。

eager_input_streaming
參數即時串流
工具定義上的選項：換得 token 級串流，代價是放棄伺服器端的 schema 保證。
Eager dispatch
提前執行
工具參數一串完就先執行，不等整個回應結束；Agent SDK 預設如此。
Prompt caching
提示快取
前綴式快取：讀取約十分之一價、寫入約 1.25 倍。順序決定命中率，設計目標 90 到 99%。
Global / Session / Volatile
全域 / 會話 / 揮發
一個請求依變動頻率排成的三段；斷點放在全域段尾端與會話段尾端，揮發內容放最後。
Effort
推理力度
模型的思考深度設定。與模型大小是同一個取捨，用 eval sweep 決定。
Sweep
全掃描
把整套 evals 跑過每個候選模型與 effort，依真實流量加權後讓數字決定。
Staged change
暫存變更
商家 agent 每個寫入產生的、帶伺服器 ID 的待批准變更；apply_change 只對批准過的 ID 成功。
Host approval / maker-checker
主機批准
由真實介面（後台按鈕、CLI 確認、平台批准提示）設定的記號；對話裡打的「我批准」不算。maker-checker 是「提案的人與核可的人分開」的既有流程。
Provenance
出處
伺服器記錄本 session 交給模型的每個 ID；寫入與渲染只認這些，其他來源的 ID 一律拒絕。
Fence / Sanitizer
圍籬 / 消毒器
第三方文字先去掉控制字元、偽裝的對話輪次與工具呼叫，限制長度，再包進固定標籤的圍籬；prompt 規定圍籬內是材料不是指令。
Guardrail
硬上限
價格幅度、折扣深度、補貨量、預算、每個變更的品項數與受保護欄位；暫存時查一次、套用時再查一次。
Memory extractor
記憶抽取器
回合結束後另開一線讀對話、寫事實的程序；只讀使用者與助理的文字，寫入前過驗證器（鍵 64 字元、值 200 字元、三類、拒絕識別碼）。
Snapshot eval
快照評測
直接建構對話狀態、接上測試訊息、評最終結果的案例；不評路徑，不靠模擬使用者。
Negative case
負向案例
每個「應該拒絕」配一個「應該服務」、每個「應該先問」配一個「應該直接做」；最常缺的那一半。
CI set
持續整合案例集
每個 PR 跑的子集：最高流量核心案例、全部安全案例，加這次改動碰到的部分；全套每晚與發版前跑。
StorefrontBackend / MerchantBackend
後端介面
你要實作的兩個介面，把目錄、購物車、訂單、政策與分析、庫存、定價、活動系統接進 agent；憑證由主機持有，方法在伺服器端呼叫你的服務。
