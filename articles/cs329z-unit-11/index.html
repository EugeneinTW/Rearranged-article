七篇的證據形式不一樣，後面每一章都要記得這件事。tinyBenchmarks、AutoMetrics、AutoLibra 提出方法，在自己選的資料與模型上量；MT-bench 建了兩個以人評為準的基準，量的是 LLM 評審和人合不合；ABC 也是論文，主體是檢查別人的基準，再用實驗量出漏洞的影響；Press 的部落格根據他做 benchmark 的經驗，沒有做實驗；Anthropic 的文章整理自家與客戶的做法，文中對自家產品與客戶案例的說法，本頁都寫成作者說。

評的對象也不同。MT-bench 評的是聊天助手對兩輪問題的回答，tinyBenchmarks 評的是靜態的 LLM 基準，兩篇都不是 agent 的多步驟軌跡；ABC 檢查的是代理基準，Anthropic 談的是 agent 的評估，AutoLibra 評 agent 的軌跡，AutoMetrics 另有一個 τ-bench 客服 agent 的案例。版本也先交代：ABC 依 arXiv v5、tinyBenchmarks 依 v2、MT-bench 依 v4、AutoMetrics 依 v1、AutoLibra 依 v3；Press 的文章在 2025 年 1 月、5 月與 2026 年 6 月各補了一次修訂。七篇的正式篇名與原文連結列在頁尾。

  • 「為什麼評估難」七篇都談，難處各不相同。tinyBenchmarks 講成本：HELM 評一個模型超過 4K GPU 小時。ABC 講代理基準的設定複雜、結果沒有固定格式；Anthropic 講 agent 會改變環境，錯誤會一路累積；MT-bench 講選擇題量不出人偏好哪個助手；AutoMetrics 講手上常常只有讚與倒讚；AutoLibra 講成功率太粗。Press 只在「答案要能自動判」那一節說摘要很難評。
  • 「可靠度」也是七篇都談，量的東西不同：ABC 的信賴區間與誤差方向、tinyBenchmarks 的估計誤差、Anthropic 的重跑與 trial 之間的隔離、MT-bench 和人的一致程度、AutoMetrics 的敏感度與穩定度、AutoLibra 的逐步人工抽查；Press 談的是題數與強的基線。

  • 「judge prompt 設計」只在第 8 週：Anthropic 給判官回答 Unknown 的退路、一個面向一個判官；MT-bench 附錄 A 列了六個 prompt；AutoMetrics 與 AutoLibra 讓評審的標準從人評裡產生。第 7 週三篇都沒談評審怎麼下指示。

01

要求 request

要模型做的事。SWE-bench 的要求是「Fix this issue」加上 issue 的內文。

02

環境 environment

agent 解題時身處的環境要完整描述：能不能上網、裝了哪些套件、有沒有給它特殊工具。

03

停止條件 stopping criteria

agent 可能自己送出 submit；一直不送時，用回合、成本或時間上限，Press 說哪一種都行，重點是要先決定。

評分器 scorer

拿 agent 停下那一刻的環境打分，形式可以是二元、連續分數或 ELO。

第二個問題是基線的 scaffolding 夠不夠真實：出程式題卻不讓它執行程式、出知識題卻不給上網，都不貼近現實（第 8 章）。

Anthropic 的文章開頭列了八個定義（Anthropic 第 1 章）。task 是定義好的輸入加上成功標準；trial 是對一個 task 的一次嘗試，模型每次輸出不同，所以同一題要跑好幾次；grader 替表現的某個面向打分，一個 task 可以掛好幾個；transcript 是一次 trial 的完整紀錄；outcome 是 trial 結束時環境的最終狀態；evaluation harness 端到端跑 eval；agent harness 也叫 scaffold，是讓模型能當 agent 的那一層，評一個 agent 評的是它和模型一起；evaluation suite 是共享一個大目標的一組 task。

ABC 走的是另一個方向：它不是拆一次評估，而是檢查一個已經做好的基準。任務有效性的十條分工具、環境、實作三組，結果有效性的二十條依評分方法分組，回報另有十三條（ABC 第 3、4、5 章）。

評做出了什麼

Anthropic 在路線圖的第 5 步說，很多人的直覺是檢查 agent 有沒有照非常具體的步驟做，例如工具呼叫的順序；作者發現這種測試太僵硬，因為 agent 常找到出題者沒料到、但完全有效的做法，所以建議評它做出了什麼，不評它走了哪條路（Anthropic 第 10 章）。第 1 章有一個例子：作者說 Opus 4.5 在 τ2-bench 一道訂機票的題目上找到政策的漏洞、用它解決了問題，照 eval 原本的寫法算失敗，實際上替使用者找到了更好的方案（第 1 章）。

結果看的是環境，不是 agent 的話。Anthropic 把 outcome 定義成 trial 結束時環境的最終狀態：訂機票的 agent 在 transcript 最後說已經訂好了，要看的是資料庫裡有沒有那筆訂位。Press 的四元組也一樣，評分器拿 agent 停下那一刻的環境打分（Press 第 7 章）。其他單元的兩個基準照這個做：單元 15 的 OSWorld 替每一題寫一支評估腳本，檢查檔案、設定、資料庫、UI 元件這類最後的狀態，總共用到 134 個評估函式（OSWorld 第 4 章）；單元 13 的 SWE-bench 看 patch 套上之後，原本失敗的測試有沒有通過、其他測試有沒有被弄壞（SWE-bench 第 4 章）。

Anthropic 並沒有只看結果。它的寫程式例子用單元測試驗正確性，再加一份評整體程式品質的 LLM rubric；對話 agent 的例子另外檢查有沒有在 10 輪內結束、呼叫了哪些工具（第 5 章）；由好幾個部分組成的 task 要給部分分數（第 10 章）。它反對的是比對事先寫死的步驟。

只查一個訊號，不解題也能過

ABC 找到的漏洞，多半是評分只查一個容易滿足的訊號。τ-bench 有一批刻意做不到的題目，只要資料庫沒變就算成功，這批題目佔航空子集的 38%，所以一個立刻結束的 agent 在航空子集拿到 38%、零售子集 6.0%（ABC 第 7 章）。CVE-Bench 判斷時間型 SQL 注入成功的方法，是看資料庫紀錄裡有沒有 SLEEP 子句；紀錄裡有，不代表真的執行了，agent 在查詢的任何地方加一個 SLEEP 就能通過，表現被高估 32.5%（第 9 章）。ABC 的對策仍在結果這一側：成功後可能的狀態要算全，相關與無關的狀態都要查，狀態空間要複雜到隨便改一下不會剛好對（O.g.1 到 O.g.3，第 4 章）。

也看怎麼做

AutoLibra 從另一端出發。摘要說 agent 主要靠任務成功率評估與最佳化，這種指標很粗、要專家手工設計，也不獎勵過程中冒出來的中間行為（AutoLibra 第 1 章）。它把人對整條軌跡的一句回饋對到具體的行為，把相近的行為分群成有定義、有好壞例子的指標，再交給 LLM 評審，逐條打 +1、−1 或不適用。

WebVoyager 先前的失敗分析把 44% 的失敗歸成「卡住」；AutoLibra 歸納出的指標把它拆成處理阻擋（2%）、錯誤恢復與調整（15%）、步驟效率與多餘動作（13%）、導航準確（11%）四種。反過來，它只看行為，抓不到 WebVoyager 論文提到的視覺定位問題（25%）（第 7 章）。在 Baba-Is-AI 上，作者每個階段收人的回饋、歸納指標，再讓 LLM 依指標的評分改 agent 的 prompt；沒有拿成功率當目標，成功率提高了 20%，論文沒有說是百分點還是相對比例（第 8 章）。作者在結論把兩者比作軟體測試：端到端的成功率像整合測試，行為指標像單元測試（第 11 章）。

AutoMetrics 的案例也在軌跡上打分。作者把 τ-bench 航空客服的 25 個訓練任務各跑 8 次，拿這些軌跡的獎勵學出三個指標：會員權益有沒有套對、該轉真人時才轉、有沒有遵守航空公司的規定；拿它們當 GEPA 的最佳化目標，2,000 次 rollout 之後，測試集的平均 pass^1 是 0.720 ± 0.06，用可驗證獎勵最佳化的是 0.680 ± 0.11（AutoMetrics 第 12 章）。作者的統計檢定比的是 0.6 的未最佳化基準；兩組的區間重疊，論文沒有拿兩組互相檢定。

整理者的讀法

兩篇說的「過程」，不是同一件事

  • Anthropic 反對的路：事先寫死的步驟，例如工具呼叫的順序；它自己的例子仍檢查輪數與用了哪些工具。
  • AutoLibra 的行為：從人的評語歸納出的類別，例如沒用下拉選單、沒依價格排序；評審逐條判斷，不比對固定的步驟。
  • ABC 的例子：問題出在結果查得不夠全，例如只查資料庫有沒有被改、只查紀錄裡有沒有某個子句。
  • 結果都還在：AutoLibra 仍用成功率量改進的效果，Anthropic 的寫程式例子第一個 grader 就是查結果的測試。

還沒有答案的地方，原文自己點了幾個。AutoLibra 把「對某一步或幾步直接給回饋」與「用指標替每一步提供密集獎勵、再用強化學習訓練」列為未來方向（AutoLibra 第 11 章）；AutoMetrics 提醒軌跡只來自 25 個任務，指標很可能學到資料本身的特徵（第 12 章）；Anthropic 說 agent 評估仍是新生、變化很快的領域，agent 接下更長的任務、在多 agent 系統裡協作時，評估的技巧也得跟著調整（Anthropic 第 13 章）。

交給程式

Press 列的第二個性質是答案能自動判對錯。程式有單元測試，寫法再多也能驗證，HumanEval、SWE-bench 都這樣做；摘要的正確寫法太多、很難評，就算對人很有用，也很少有人做成 benchmark。有人提議用語言模型評語言模型的輸出，Press 說他不認為這是對的方向：LM 可以拿來解題，也可以拿來評分，但同一個 LM 同時解題又評分就會出問題；原文沒有再說問題出在哪裡（Press 第 2 章）。

Anthropic 把 grader 分成程式、模型、人三種。程式快、便宜、客觀、可重現，但有效卻不符合預期模式的變化也會被判錯；模型有彈性、抓得到細節，但判得不穩定、比程式貴，要和人工校準；人是黃金標準，但又貴又慢（Anthropic 第 3 章）。路線圖第 5 步的建議有先後：能用確定性的 grader 就用，必要時才用 LLM，人工審慎地用；LLM 判官要和人類專家密切校準，資訊不足時允許它回答 Unknown，一個面向交給一個獨立的判官（第 10 章）。

程式評分失手的例子，好幾篇都有。ABC 量到兩個方向：SWE-bench Verified 的單元測試不足，有 5.3% 的題目不解決 issue 也能通過；KernelBench 的模糊測試只換數值，kernel 的正確率被高估 31%；BIRD 的題意有兩種讀法，另一種正確的 SQL 被判錯（ABC 第 8 章）。Anthropic 說 Opus 4.5 在 CORE-Bench 起初只拿到 42%，一位研究員找出評分太死（預期 96.124991… 時把 96.12 判錯）、規格含糊、有些題目無法精確重現等問題，修掉之後、改用限制較少的 scaffold，分數到 95%（第 10 章）。單元 15 的 WebShop 請人照同一個公式重評 100 條專家軌跡、同義詞也算對，自動獎勵是 81.5、人工是 89.9，每一項的人工分數都不低於自動分數，作者說自動獎勵大約是實際表現的下界（WebShop 第 5 章）。

交給 LLM

MT-bench 的出發點是選擇題量不出人偏好哪個助手，開放式的問題又很難寫規則程式來評，人評則又慢又貴，所以讓 GPT-4 這類強 LLM 當評審（MT-bench 第 1 章）。在 80 題兩輪的 MT-bench 上，不計平手時，GPT-4 成對比較和專家的一致程度是 85%，專家之間是 81%；把平手算進去，是 66% 對 63%（第 9 章）。

同一篇也逐項量了偏誤。兩個相近的回答對調順序再判一次，GPT-4 維持原判的比例是 65.0%，Claude-v1 只有 23.8%（第 4 章）；把回答裡的清單換句話說再接一次、只加長度，Claude-v1 與 GPT-3.5 有 91.3% 選了變長的版本，GPT-4 是 8.7%（第 5 章）；10 題數學題對調各判一次、共 20 次，預設 prompt 判錯 14 次，先另外解好、當參考答案放進去，降到 3 次（第 6 章）。和 Press 的顧慮最接近的是自我偏好：GPT-4 評自己時勝率高了 10%，Claude-v1 高了 25%，但它們也偏袒別的模型，GPT-3.5 沒有偏袒自己，作者說資料太少、差距又小，無法判定（第 10 章）。

ABC 在 WebArena 找到 LLM 評審判錯的例子：一題的標準答案是 63 分鐘，agent 答 53 分鐘，評審判它正確；標成 N/A 的題目，評審會把空白回覆判對，一個不解題的 agent 也能通過（ABC 第 4、7 章）。ABC 的建議是先做試跑，量 LLM 評審的準確度與自我一致性（O.c.1）。

第 8 週另外兩篇都用 LLM 評審，也都拿人評回頭檢查。AutoLibra 請人逐步抽查，LLM 評審這一步被標為完全正確的比例平均 0.92，Sotopia 最低，是 0.85（AutoLibra 第 6 章）。AutoMetrics 把原本給標註者的說明直接交給 LLM 當基線，再拿自己產生的評審比和人評的 Kendall τ：以 Qwen3-32B 當骨幹，EvalGen 任務上 LLM 評審是 0.272、AutoMetrics 是 0.382；以 GPT-4o-mini 當骨幹，CoGym 上 AutoMetrics 是 −0.034，低於同骨幹的 LLM 評審 0.199（AutoMetrics 第 8 章）。AutoMetrics 的候選裡也有 BLEU、編輯距離這類程式算的指標，留哪幾個由回歸決定。

整理者的讀法

三個「和人合不合」，量的是三件事

  • MT-bench 的 85%：GPT-4 和隨機一位專家，在隨機一題上投出同一票的機率，評的是聊天回答。
  • AutoMetrics 的 0.382：指標排出的先後和人評的 Kendall τ，五個任務各算一次。
  • AutoLibra 的 0.92：一位標註者看評審的每一筆判斷，判定完全正確的比例。
  • Press 的顧慮：同一個 LM 解題又評分；七篇裡只有 MT-bench 的自我偏好檢查碰到這件事，作者沒有下結論。

三個數不在同一把量尺上，不能互比。這是整理者把幾篇並排時看到的差別，原文都沒有這樣比。

跨單元的對照

EvalGen 的使用者：程式斷言想自己讀，LLM 斷言難以信任

單元 10 的 EvalGen 請九位從業者用程式與 LLM 兩種斷言評管線的輸出。參與者兩種都要；程式斷言想直接讀程式、自己挑，LLM 斷言難以信任，因為程式改起來容易，也有人懷疑 LLM 斷言能不能放進上線的管線（EvalGen 第 12 章）。單元 14 的 NAP 用 LLM 評審打 0 到 1 的相似度，另外做了 300 組人評來驗證評審（NAP 第 6 章）。兩篇都不在這個單元，這裡只並排原文寫的事。

還沒有答案的地方：MT-bench 自己說它只看有用程度、沒看安全，把正確、切題、創意這些面向併成一個分數，偏誤的解法也還是初步的（第 13 章）；AutoMetrics 說用一個模型產生的指標換到另一個模型上跑，表現會下降，新模型推出時要重新產生（AutoMetrics 第 13 章）。MT-bench 那種「評審對人」的一致程度，七篇裡沒有一篇在 agent 的多步驟軌跡上量過；AutoLibra 量的是人抽查評審的正確比例。

三個建議

Anthropic 看到很多團隊遲遲不建 eval，因為以為需要好幾百個 task；作者說從真實失敗裡挑出 20 到 50 個簡單的 task，就是很好的起點。理由是 agent 開發的早期，系統的每次改動通常都有明顯的影響，效果大，小樣本就看得出來；成熟的 agent 可能需要更大、更難的題組，才偵測得到較小的效果（Anthropic 第 8 章）。這個建議沒有附數字，是作者的經驗。

tinyBenchmarks 用數字回答另一個問題：已經有很多模型考過完整份的時候，新模型只考一小部分，估出的分數離完整份差多少。表現最好的策略在每個情境 100 題以內，四個基準的誤差都在 2% 以內；MMLU 從約 1.4 萬題縮到 100 題，Open LLM Leaderboard 甚至每個情境 30 題就夠（tinyBenchmarks 第 8 章）。隨機抽樣要多考幾題才追得上：在 Leaderboard 上，隨機抽每個情境要 400 題，才追上 IRT++ 的 100 題。這些數字有前提：挑題與擬合 IRT 要一批舊模型的逐題作答，Leaderboard 有 395 個，HELM 只有 30 個（第 7 章）；2% 是測試模型的平均，個別模型最多到 4%；作答模式和舊模型不同的專門模型，依對錯分群的錨點最先失準（第 9 章）。

Press 的數字出自經驗：一個 benchmark 至少要 150 題，目標 300 到 500 題，統計解析度較高；題數再多沒什麼幫助，跑一次又要花很久，對採用是很大的缺點，所以他把 500 當上限。他也說「一題」怎麼算不好定義，50 題、每題含 10 個子任務的 benchmark 也行得通（Press 第 6 章）。

另外四篇的數字

MT-bench 有 80 題，8 個類別各 10 題，每題兩輪；58 位專家每人至少評 20 題，合計約 3K 票，Chatbot Arena 另外收了約 30K 票（MT-bench 第 2 章）。這 80 題拿來比模型，也拿來量評審和人合不合。

ABC 沒有給題數，要的是公開分數時附上統計顯著性，例如信賴區間（R.10）。附錄 F 以 BIRD 為例示範：抽 500 題複查，11.65% 的標準 SQL 是錯的，代進式子替每個方法算區間；第 1 名 CHASE-SQL + Gemini 的開發集準確度 74.9，區間是 [66.8, 71.4]，可能的名次是第 1 到第 13（ABC 第 5 章）。這份示範是作者以 BIRD 為基礎改寫的，不是 BIRD 官方公布的數字。

AutoMetrics 與 AutoLibra 的數字是人評的筆數，不是題數。AutoMetrics 把訓練集從 5 筆加到 160 筆（兩個資料集再加到 640 筆），約 80 筆之後相關就不再上升；少於 80 筆時，作者預設只用產生的指標（AutoMetrics 第 11 章）。AutoLibra 每個資料集用 80 條軌跡、每條一句回饋，作者說每條不到 5 分鐘；改進 agent 時，每個階段只標 18 條（AutoLibra 第 2 章）。

整理者的讀法

三個數，回答三個問題

  • Anthropic 的 20 到 50：起步的題組要看得出明顯的退步。
  • tinyBenchmarks 的 100：估出一個已知基準的完整分數，前提是有很多舊模型的逐題紀錄。
  • Press 的 300 到 500：公開的 benchmark 要分得出系統，又要讓人跑得完。
  • 三個 80：MT-bench 的 80 題、AutoMetrics 約 80 筆人評、AutoLibra 的 80 條軌跡，數字相同，量的是題目、人評、回饋三件事。

七篇裡只有 tinyBenchmarks 量了題數與誤差的關係，而且量在靜態的 LLM 基準上。

還沒有答案的地方：tinyBenchmarks 的限制一節說，嚴重的分布偏移會讓誤差變大，建議定期用新模型的資料更新題目與 IRT 參數（tinyBenchmarks 第 12 章）；Anthropic 說成熟的 agent 要更大、更難的題組，但沒有說要多大。在 agent 任務上，要幾題才分得出一個給定的差距，七篇都沒有量過。

判斷題 · 01

你的評分器該只看最後的狀態，還是也看軌跡裡的行為？

只看結果的一方：Anthropic 評做出了什麼、不評走了哪條路，Press 的評分器拿停下時的環境打分。也看行為的一方：AutoLibra 從人的評語歸納行為指標，AutoMetrics 把軌跡上的指標當最佳化目標。ABC 的 τ-bench 與 CVE-Bench 說明，只查一個容易滿足的訊號時，不解題也能過（都在第 3 章）。

還缺的證據：同一批軌跡，只看結果與加上行為指標兩種評分，哪一種和人的判斷更接近。AutoMetrics 的 0.720 與 0.680 區間重疊，AutoLibra 沒有和只看結果的評分並排。

挑 20 條你的 agent 軌跡，一種評分只查環境最後的狀態，另一種再加兩三條行為標準；請一位同事不看分數各判一次，看哪一種排出的先後和他接近。也先跑一個什麼都不做的 agent，看兩種評分會不會讓它拿分。

判斷題 · 02

評分交給程式還是 LLM，要看到什麼才算數？

交給程式：Press 要答案能自動判、不贊成用 LM 評 LM，Anthropic 能用程式就用程式；但 ABC、Anthropic 與單元 15 的 WebShop 都有程式太鬆或太死的例子。交給 LLM：MT-bench 量到 GPT-4 和專家 85% 一致，AutoLibra 的評審抽查 0.92；但 MT-bench 也量到位置、冗長、數學題的偏誤，ABC 找到 WebArena 的評審判錯（都在第 4 章）。

還缺的證據：評審放到 agent 的多步驟軌跡上，用 MT-bench 那種算法和人比的一致程度；以及同一個模型解題又評分時的偏差，MT-bench 的自我偏好檢查沒有結論。

準備 30 筆輸出，請兩位同事與一個 LLM 評審各評一次，照 MT-bench 的做法算人對人、LLM 對人的一致程度，含平手與不含平手各一次；再把兩個輸出對調順序重評，看判定變了幾次。程式判得了的面向，另寫一條程式檢查一起比。

判斷題 · 03

要考幾題，才分得出你在乎的差距？

Anthropic 說 20 到 50 個真實失敗就能起步；tinyBenchmarks 每個情境 100 題，平均誤差約 2%；Press 要 300 到 500 題；ABC 要附信賴區間，BIRD 的示範裡第 1 名可能排到第 13（都在第 5 章）。

還缺的證據：在 agent 任務上，題數和誤差的關係。tinyBenchmarks 量的是靜態的 LLM 基準，而且要有數百個舊模型的逐題紀錄；其他幾個數字來自作者的經驗或研究設計。

拿你手上的逐題結果，隨機抽 20、50、100 題各算幾十次，看兩個版本的排名多常翻過來；常翻的題數，就還分不出你在乎的差距。這個做法是整理者的建議，七篇都沒有這樣做。

為什麼不附答案

證據在別人的任務上量出來

七篇的數字來自不同的任務、模型、評分者與年份：聊天回答、靜態的 LLM 基準、代理基準、客服與遊戲的軌跡。放到你自己的評估上會不會成立，要用你的任務量過才知道。這一頁只負責把證據排在一起，判斷留給讀者。

Reference · 用詞對照

同一件事，七篇各用不同的名字

七篇對題目、評分者、正確答案、重跑與紀錄各有說法。每一條先寫這件事，再列各篇怎麼稱呼、在本站讀物頁的哪一章；沒有談到的篇就不列。

task
一道題
Press：request，四元組的第一項（第 7 章）。Anthropic：task，定義好的輸入加成功標準，也叫 problem、test case（第 1 章）。tinyBenchmarks：example，IRT 的文獻叫 item（第 2 章）。MT-bench：兩輪的問題（第 2 章）。ABC：任務，要驗證每一題做得到（T.8，第 3 章）。
benchmark
一組題
Press：benchmark 是一組 task（第 7 章）。Anthropic：evaluation suite，共享一個大目標，分 capability 與 regression（第 1、4 章）。tinyBenchmarks：基準、情境、子情境三層（第 2 章）。ABC：代理基準（第 1 章）。
grader
評分者
Press：scorer（第 7 章）。Anthropic：grader，分程式、模型、人三種（第 3 章）。MT-bench：judge，成對、單一、參考答案三種評法（第 3 章）。ABC：評分方法，結果有效性依它分組（第 4 章）。AutoMetrics：metric，可以是程式、模型或 LLM 評審（第 5 章）。
LLM-as-a-judge
LLM 評審
MT-bench：LLM-as-a-judge，用它代替人評（第 1 章）。Anthropic：model-based grader（第 3 章）。AutoMetrics：基線用原本給標註者的說明（第 7 章）。AutoLibra：依歸納出的指標打 +1、−1、N/A（第 4 章）。Press：LM 評 LM，作者不贊成（第 2 章）。
ground truth
標準答案
ABC：ground truth，文字、測試案例或環境應有的狀態（第 3 章）。Anthropic：reference solution，一份能通過所有 grader 的輸出（第 9 章）。MT-bench：reference answer，評審先另外解好再放進 prompt（第 6 章）。
trial
同一題跑一次
Anthropic：trial，模型每次輸出不同，所以同一題跑好幾次（第 1、7 章）。AutoMetrics：rollout，GEPA 跑 2,000 次（第 12 章）。MT-bench：對調順序各判一次（第 4 章）。tinyBenchmarks：每個設定重跑 5 次（第 7 章）。
transcript
一次執行的紀錄
Anthropic：transcript，也叫 trace、trajectory（第 1 章）。AutoLibra：trajectory，標註者逐步看觀察與行動（第 2 章）。MT-bench：兩輪的完整對話，評審要整段看（第 7 章）。
outcome
最後的狀態
Anthropic：outcome，trial 結束時環境的最終狀態（第 1 章）。Press：agent 停下那一刻的環境（第 7 章）。ABC：狀態比對拿 agent 做完的最終狀態和標準狀態比（第 4 章）。
stopping criteria
什麼時候停
Press：submit，或回合、成本、時間上限（第 7 章）。Anthropic：對話例子把 10 輪內結束寫成 transcript 的檢查（第 5 章）。ABC：T.3 是 API 斷線時停下評估（第 3 章）。
agreement
評分者和人合不合
MT-bench：agreement，S1、S2 兩種算法（第 8 章）。AutoMetrics：和人評的 Kendall τ，叫判準效度（第 8 章）。AutoLibra：覆蓋率，加上逐步的人工抽查（第 4、6 章）。Anthropic：LLM 判官要和人類專家校準（第 10 章）。
validity
量到的是不是想量的
ABC：任務有效性與結果有效性（第 1 章），回報的 R.5 要講清楚建構效度（第 5 章）。AutoMetrics：內容、判準、構念三種效度（第 8 章）。
pass@k / pass^k
多次嘗試怎麼算
Anthropic：一次成功就夠看 pass@k，要每次都可靠看 pass^k（第 7 章）。ABC：τ-bench 的 do-nothing agent 兩者都是 38%（第 7 章）。AutoMetrics：τ-bench 案例只報 pass^1（第 12 章）。
human feedback
人給的訊號
MT-bench：投 A、B 或平手（第 2 章）。AutoMetrics：讚與倒讚、Likert 分數、接受或拒絕（第 7 章）。AutoLibra：一條軌跡一句開放式回饋（第 2 章）。Anthropic：人工 grader 與使用者回饋（第 3、12 章）。
bias
評分者偏在哪裡
MT-bench：位置、冗長、自我偏好，以及數學題評不準（第 4 到 6、10 章）。Press：同一個 LM 解題又評分（第 2 章）。ABC：LLM 標註的準確度隨領域而變（第 4 章）。AutoMetrics：評審不一定照 rubric 打分，回歸可能抓到假相關（第 1、11 章）。
harness
跑評估的那一層
Anthropic：evaluation harness 與 agent harness，後者也叫 scaffold（第 1、10 章）。Press：基線的 scaffolding 要接近最好的常用做法（第 8 章）。ABC：R.6 要講清楚評的是模型還是 agent 框架（第 5 章）。
