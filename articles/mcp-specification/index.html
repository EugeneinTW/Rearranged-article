MODEL CONTEXT PROTOCOL SPECIFICATION · 圖卡＋教材整合版

MCP 規格怎麼讀： 先看誰守哪條邊界， 再看訊息怎麼走2025-06-18 修訂版：三種角色、三種訊息、三種伺服器原語、三種客戶端原語、兩種傳輸、一套授權

Model Context Protocol 是讓 LLM 應用接上外部資料與工具的開放協定。它的規格不是教學文件，是一份用 MUST、SHOULD、MAY 寫成的規範，權威定義在一份 TypeScript schema 裡。這一頁把 2025-06-18 修訂版的二十二頁重排成建一個會用工具的系統會需要的順序：先弄清楚主機、客戶端、伺服器各守什麼邊界，再看訊息怎麼握手、工具怎麼被模型呼叫，最後才是傳輸與授權。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

規格不是教學，它寫的是誰有義務做什麼

課程第 3 週「Tool Use & Function Calling」那一講把 MCP 規格排在必讀，講題還有 REPL、function-calling API、怎麼設計好工具、程式沙箱、錯誤處理與重試。規格本身沒有一句話教你怎麼建 agent，但每一條「誰 MUST 做什麼」都是你的系統要守的邊界。

MCP 規格是一份規範性文件。它一開頭就聲明 MUST、MUST NOT、SHOULD、MAY 這些大寫字照 BCP 14 解讀，而且說明文字只是解釋，協定的權威定義在 GitHub 上的 schema.ts。這決定了讀法：每一句先找主詞（主機、客戶端、伺服器、授權伺服器），再找義務的強度；範例 JSON 拿來對照欄位名，不拿來當規則。

規格網站把 2025-06-18 修訂版分成幾區：總覽與變更紀錄、架構、基礎協定（訊息、生命週期、傳輸、授權、安全最佳實務、三個工具程式）、客戶端功能（roots、sampling、elicitation）、伺服器功能（prompts、resources、tools、三個工具程式）、schema 參考。網站的順序是基礎協定在前、伺服器功能在中、客戶端功能在後。這一頁重排成另一個順序：邊界（架構）、訊息與握手、三種伺服器原語與工具細讀、客戶端原語、傳輸、授權與安全、工具程式、版本。理由在最後一章：要建一個會用工具的系統，先需要的是前面那幾塊。

這一頁的處理方式：章節跟「建東西的順序」走，不跟網站目錄走；每一章都標出那條規則是 MUST 還是 SHOULD；數字只用規格寫出的（錯誤碼、HTTP 狀態碼、上限）；圖卡上凡是整理者自己排的形狀，腳註都寫明。名詞先對齊一次：課程與各家 API 說的 function calling、tool use，在規格裡只有一個詞，叫 tools。

給初學者

先把幾個名詞對齊

  • Host（主機）：發起連線的 LLM 應用，例如一個 IDE 或聊天介面；管使用者同意、管模型。
  • Client（客戶端）：主機裡的連接器，一個客戶端對一個伺服器，維持一條有狀態的會話。
  • Server（伺服器）：提供脈絡與能力的服務，可以是本機子程序或遠端服務。
  • JSON-RPC 2.0：MCP 所有訊息的格式，只有請求、回覆、通知三種。
  • capability（能力）：初始化時雙方宣告的功能旗標，沒宣告的功能在這條連線上不存在。
  • primitive（原語）：協定定義的基本功能單位；伺服器有三種，客戶端有三種。
讀規格的第一個動作是找主詞：這一條是主機、客戶端，還是伺服器的義務。 整理者的引言

Chapter 02 · Architecture

主機管人和同意，客戶端一對一連伺服器，伺服器只管能力

MCP 是 client-host-server 架構：一個主機程序裡可以有多個客戶端，每個客戶端和一個伺服器維持一條有狀態的會話。安全邊界畫在主機：同意、授權、跨伺服器的協調都在這裡。

伺服器看不到整段對話
完整的對話史留在主機；伺服器只拿到必要的脈絡，跨伺服器的互動由主機控制，每條連線各自隔離。
設計原則第三條，也是安全那一章的前提。
一個客戶端，一個伺服器
主機要接幾個伺服器就開幾個客戶端；每個客戶端維持一條有狀態的會話，負責協商能力、雙向路由訊息、管訂閱。
規格寫的是 1:1，不是一個客戶端接一堆伺服器。
主機是安全政策的執行者
同意、授權決定、客戶端的連線權限與生命週期都在主機；規格自己說協定層無法強制這些原則，靠實作者做進應用裡。
後面每一張的「人在迴圈裡」都落在這一格。
注意：三個伺服器是規格架構圖的例子，數量不限；主機的六項職責摘成三句是整理者的濃縮，原文列在 Host 一節。

架構頁把三個角色的職責寫成清單。主機是容器與協調者：建立並管理多個客戶端、控制客戶端的連線權限與生命週期、執行安全政策與同意要求、處理使用者的授權決定、協調模型與取樣、彙整各客戶端的脈絡。客戶端由主機建立，每個客戶端只連一個伺服器：建立一條有狀態的會話、處理協定協商與能力交換、雙向路由訊息、管訂閱與通知、維持伺服器之間的安全邊界。伺服器提供專門的脈絡與能力：用原語暴露 resources、tools、prompts、獨立運作、透過客戶端要求取樣、遵守安全限制，可以是本機程序也可以是遠端服務。

角色它守的邊界規格用什麼詞
主機人：同意、授權決定、安全政策；模型：取樣的協調container and coordinator
客戶端連線：一對一的會話、能力協商、訊息路由；伺服器之間彼此隔離isolated server connection、1:1 relationship
伺服器能力：只暴露自己的原語，只拿到必要的脈絡focused responsibilities

四條設計原則解釋了為什麼邊界這樣畫。第一，伺服器要極容易做：複雜的協調責任放在主機，伺服器只做明確的一件事。第二，伺服器要高度可組合：每個伺服器各自提供一塊功能，共用協定讓它們能互通。第三，伺服器不該讀到整段對話，也不該看進其他伺服器：伺服器只收到必要的脈絡，完整的對話史留在主機，跨伺服器的互動由主機控制。第四，功能可以漸進加：核心協定只要求最少的東西，其他能力靠協商，客戶端與伺服器可以各自演進。

"Servers should be extremely easy to build" 「伺服器應該極容易建」：架構頁四條設計原則的第一條；把難的部分留給主機，是整份規格的取捨。

架構頁最後講能力協商：客戶端與伺服器在初始化時明確宣告自己支援的功能，能力決定這個會話能用哪些原語。伺服器宣告的例子是資源訂閱、工具、提示模板；客戶端宣告的例子是取樣與通知處理。雙方 MUST 在整個會話裡遵守宣告過的能力；規格特別舉了幾個對應：要送資源訂閱通知就要宣告訂閱支援、要讓模型呼叫工具就要宣告工具能力、伺服器要取樣就要客戶端宣告 sampling。第 4 章的握手就是這件事的訊息版。

① 版本不合，客戶端 SHOULD 斷線
客戶端送它支援的最新版本；伺服器支援就回同一個，不支援就回自己最新的；客戶端不接受就斷。走 HTTP 時之後每個請求都要帶 MCP-Protocol-Version 標頭。
錯誤例：code -32602，Unsupported protocol version，data 列出支援的版本。
② 每個送出的請求都要有逾時
逾時就送取消通知並停止等待；收到進度通知可以重設時鐘，但一定要有一個最大逾時，防止失控的對方拖住連線。SDK 應允許逐請求設定。
initialize 請求本身不能被客戶端取消。
③ 握手完成前只能 ping
伺服器回覆 initialize 之前，客戶端不該送 ping 以外的請求；收到 initialized 之前，伺服器只能送 ping 與 logging。談好的東西才算數。
這兩條是 SHOULD NOT；「只用談好的能力」在這一版改成 MUST。
注意：把「閘」畫成握手的一格是整理者的排法；規格的三個階段是初始化、操作、關閉，版本與能力協商都在初始化裡。

客戶端 MUST 先送 initialize 請求，內容是它支援的協定版本、它的能力、它的實作資訊（name、title、version）。伺服器 MUST 回自己的能力與資訊，可以附一段 instructions 給客戶端。成功之後客戶端 MUST 送 notifications/initialized，表示準備好進入操作階段。兩條 SHOULD NOT：伺服器回覆 initialize 之前，客戶端不該送 ping 以外的請求；收到 initialized 之前，伺服器不該送 ping 與 logging 以外的請求。

版本協商。客戶端 MUST 送一個它支援的版本，SHOULD 是它支援的最新版。伺服器支援就 MUST 回同一個；不支援就 MUST 回另一個它支援的版本，SHOULD 是它最新的。客戶端不支援伺服器回的版本，SHOULD 斷線。走 HTTP 時，之後每個請求 MUST 帶 MCP-Protocol-Version 標頭。

能力協商。能力決定會話裡哪些選用功能可用。客戶端這邊有 roots、sampling、elicitation、experimental；伺服器這邊有 prompts、resources、tools、logging、completions、experimental。能力物件可以再描述子能力：listChanged（prompts、resources、tools 都有）與 subscribe（只有 resources）。

操作與關閉。操作階段雙方 MUST 遵守談好的版本、MUST 只用成功協商的能力；這一版把這裡的 SHOULD 改成 MUST。關閉由一方（通常是客戶端）乾淨地結束，靠傳輸層：stdio 的客戶端 SHOULD 先關掉子程序的輸入串流，等它退出，不退就送 SIGTERM，再不退就 SIGKILL；伺服器也 MAY 關掉自己的輸出串流然後退出。HTTP 的關閉就是關掉相關的 HTTP 連線。

實作提示

逾時是 SHOULD，最大逾時是一定要有

實作 SHOULD 為每個送出的請求設逾時，逾時就送取消通知並停止等待；SDK SHOULD 允許逐請求設定。收到對應的進度通知時 MAY 重設時鐘，因為那表示工作真的在進行，但 SHOULD 永遠有一個最大逾時，限制失控的客戶端或伺服器造成的影響。要準備處理的錯誤有三種：版本不合、必要能力談不攏、請求逾時；規格的錯誤例子是 code -32602、message「Unsupported protocol version」，data 裡列出支援的版本與被要求的版本。

思考題 · 03

你的伺服器什麼時候該從 stdio 換成 HTTP？

stdio 沒有會話、沒有串流、沒有授權；HTTP 三樣都要處理。

MUST 驗證 token 的對象是自己；無效或過期回 401，範圍不夠回 403，請求格式錯回 400。要呼叫上游 API 時，伺服器自己當 OAuth 客戶端，用另一個 token。
redirect URI 要事先登記、精確比對；state 參數 SHOULD 用並驗證。
注意：stdio 不走這套，SHOULD 從環境拿憑證；動態註冊是 SHOULD，授權伺服器不支援時客戶端要硬編 client id 或讓使用者自己填。

授權頁列了它依據的四份標準：OAuth 2.1 的 IETF 草案（draft 13）、授權伺服器中繼資料（RFC 8414）、動態客戶端註冊（RFC 7591）、受保護資源中繼資料（RFC 9728）；規格只取這些標準的子集。四條總則：授權伺服器 MUST 實作 OAuth 2.1 並對機密與公開客戶端都採取適當的安全措施；授權伺服器與 MCP 客戶端 SHOULD 支援動態註冊；MCP 伺服器 MUST 實作受保護資源中繼資料，MCP 客戶端 MUST 用它來發現授權伺服器；授權伺服器 MUST 提供授權伺服器中繼資料，客戶端 MUST 使用。

1
發現客戶端沒帶 token 發請求，伺服器回 401，MUST 用 WWW-Authenticate 標頭指出資源伺服器中繼資料的網址；客戶端 MUST 能解析它。中繼資料的 authorization_servers MUST 至少列一個授權伺服器；列了多個時由客戶端依 RFC 9728 選。
2
註冊客戶端讀授權伺服器中繼資料取得端點；沒有 client id 就用動態註冊拿，理由是客戶端不可能事先知道所有 MCP 伺服器與它們的授權伺服器。不支援動態註冊的授權伺服器，客戶端只能硬編 client id，或做一個介面讓使用者自己註冊後填進來。
3
授權碼流程客戶端產生 PKCE 參數（MUST），開瀏覽器帶 code_challenge 與 resource 參數；使用者授權後拿到授權碼；用 code_verifier 與 resource 換 token（可能附 refresh token）。
4
使用之後每個 HTTP 請求 MUST 帶 Authorization: Bearer 標頭，即使在同一個邏輯會話裡；token MUST NOT 放在網址的查詢字串。伺服器 MUST 驗證 token 是簽給自己的，無效或過期回 401。

resource 參數。客戶端 MUST 實作 RFC 8707 的 Resource Indicators：resource 參數 MUST 同時出現在授權請求與 token 請求、MUST 指向客戶端要用 token 的那台 MCP 伺服器、MUST 用它的正規 URI。合法的例子有 https://mcp.example.com/mcp、https://mcp.example.com、帶埠號的、帶路徑的；不合法的是缺 scheme 的 mcp.example.com 與帶 fragment 的網址。有沒有結尾斜線兩種都合法，規格建議一律用沒有的那種。不論授權伺服器支不支援，客戶端 MUST 都要送。

token 的處理。伺服器 MUST 照 OAuth 2.1 驗證 token，MUST 驗證它是專門簽給自己的；客戶端 MUST NOT 把不是這台伺服器的授權伺服器發的 token 送過來；授權伺服器 MUST 只接受對自己資源有效的 token；MCP 伺服器 MUST NOT 接受或轉送其他 token。錯誤碼：401 是需要授權或 token 無效，403 是範圍不對或權限不足，400 是授權請求格式錯。

四條原則。使用者同意與控制：使用者必須明確同意並理解所有的資料存取與操作、保有對分享什麼資料與採取什麼行動的控制，實作者應提供清楚的介面來檢視與授權。資料隱私：主機在把使用者資料暴露給伺服器前必須取得明確同意，不得在未經同意下把資源資料傳到別處，資料要有適當的存取控制。工具安全：工具代表任意的程式執行，必須謹慎對待，工具行為的描述（例如註記）除非來自受信任的伺服器否則視為不可信，主機在呼叫任何工具前必須取得明確同意，使用者應理解每個工具做什麼。取樣控制：使用者必須明確核准任何取樣請求，應控制要不要取樣、送出的 prompt、伺服器能看到的結果，協定刻意限制伺服器對 prompt 的可見度。實作指引五條：把穩健的同意與授權流程建進應用、清楚記錄安全影響、實作適當的存取控制與資料保護、在整合裡遵循安全最佳實務、在功能設計時考慮隱私。

token 透傳。最佳實務頁的定義：MCP 伺服器接受客戶端的 token，沒有驗證那些 token 是簽給自己的，就轉給下游 API。授權規格明文禁止，理由有四：繞過安全控制（限速、請求驗證、流量監控往往依 token 的對象設計，客戶端拿著 token 直接打下游就繞過了）；責任與稽核失效（伺服器分不清是哪個客戶端在呼叫，下游的紀錄看起來像來自另一個身分，拿到被偷的 token 的人可以把伺服器當資料外流的代理）；信任邊界被打穿（下游對特定實體的信任被延伸，一個 token 被多個服務接受，攻破一處就通到別處）；未來相容性（今天是純代理，以後要加安全控制會很難）。對策一句話：MCP 伺服器 MUST NOT 接受任何不是明確簽給它的 token。

Chapter 12 · Utilities: Ping, Progress, Cancellation, Logging, Pagination, Completion

六個工具程式：保活、進度、取消、記錄、分頁、補全

基礎協定下有三個雙向的工具程式（ping、progress、cancellation），伺服器功能下有三個（logging、pagination、completion）。每個都很短，但生命週期的逾時、工具的長時間執行、清單的分頁都靠它們。

工具程式訊息硬規則用在哪
Ping任一方送 ping 請求，沒有參數收到的一方 MUST 立即回空的 result；逾時 MAY 視為連線失效、斷線、重連握手期間唯一允許的請求；週期性檢查連線，頻率 SHOULD 可設定，不要過量
Progress請求的 _meta.progressToken；對方送 notifications/progress 帶 token、progress、選用的 total 與 messagetoken MUST 在所有進行中的請求裡唯一；progress MUST 每次遞增，即使 total 未知；完成後 MUST 停止長時間的工具呼叫；第 4 章說收到進度 MAY 重設逾時
Cancellationnotifications/cancelled 帶 requestId 與選用的 reason只能取消同方向、還在進行的請求；initialize MUST NOT 被客戶端取消；收到的一方 SHOULD 停止處理、釋放資源、不回覆；不認識的 id 或已完成的請求 MAY 忽略逾時處理；網路延遲可能讓取消在完成後才到，雙方 MUST 處理這種競態
Logging伺服器宣告 logging；客戶端 MAY 送 logging/setLevel；伺服器送 notifications/message 帶 level、logger、data等級照 RFC 5424 的八級（debug 到 emergency）；訊息 MUST NOT 含憑證、個資、能幫助攻擊的內部細節；SHOULD 限速握手期間伺服器唯一能送的通知；客戶端可以顯示、篩選、保存
Pagination回覆帶 nextCursor；下一個請求帶 cursor游標是不透明字串，客戶端 MUST 不解析、不修改、不跨會話保存；頁大小由伺服器決定，客戶端 MUST NOT 假設固定；沒有 nextCursor 就是結尾；無效游標回 -32602resources/list、resources/templates/list、prompts/list、tools/list
Completion伺服器宣告 completions；客戶端送 completion/complete 帶 ref（ref/prompt 或 ref/resource）、argument（name、value），可帶 context.arguments回 values 依相關性排序，最多 100 個，可帶 total 與 hasMore；MUST 驗證輸入、限速、控制敏感建議提示的參數、資源模板的變數；多參數時把已填好的放進 context，這是這一版加的

三個雙向工具程式的共同點是「射後不理」：取消是通知，不會有回覆；進度是通知，接收方 MAY 完全不送；ping 雖然是請求，但回覆是空的。這讓它們可以在任何時候插進訊息流裡，不干擾正在進行的請求。分頁與補全則是伺服器功能的配件：清單長了才需要分頁，提示與資源模板有參數才需要補全。

  2. 實作 initialize 與 initialized回 protocolVersion 2025-06-18；capabilities 只宣告 tools（可加 listChanged）；收到 initialized 之前只回 ping 與 logging（第 4 章）。
  3. tools/list 回一個工具name、description、inputSchema 是 JSON Schema；描述寫給模型讀（第 6 章）。
  4. tools/call 分兩層錯誤不認識的工具回 -32602 的協定錯誤；業務失敗回 isError: true 並把原因寫進 content；驗輸入、限速、清輸出（第 6 章）。
  5. 客戶端把人放進迴圈把模型選的參數先給人看再送；設逾時；記錄每次呼叫；把工具註記當不可信（第 6 章）。
  6. 要上網路再讀後兩章先做 Origin 驗證、綁 localhost、會話 id 用安全亂數，再照授權章接受保護資源中繼資料與 resource 參數（第 9 到 11 章）。

Reference · 名詞速查

關鍵名詞與它們在規格裡的位置

先列角色與訊息，再列六種原語與傳輸，最後是授權與安全用的詞。

Host
主機
發起連線的 LLM 應用；建立與管理客戶端、執行安全政策與同意、協調模型與取樣、彙整脈絡。架構頁。
Client
客戶端
主機裡的連接器，和一個伺服器維持一條有狀態的會話，負責協商、路由、訂閱與隔離。架構頁。
Server
伺服器
提供脈絡與能力的服務，用原語暴露 resources、tools、prompts；可本機可遠端。架構頁。
JSON-RPC 2.0
訊息格式
所有 MCP 訊息的格式；請求有 id、回覆同 id、通知無 id。基礎協定總覽。
capability negotiation
能力協商
初始化時雙方宣告支援的功能；操作階段 MUST 只用談好的。生命週期頁。
initialize / initialized
初始化請求與通知
客戶端送 initialize（版本、能力、資訊），伺服器回覆，客戶端再送 initialized 通知。生命週期頁。
MCP-Protocol-Version
版本標頭
HTTP 傳輸下，初始化之後每個請求 MUST 帶的標頭；沒帶時伺服器 SHOULD 假設 2025-03-26。傳輸頁。
Tools
工具
模型控制的原語；tools/list 與 tools/call；定義含 inputSchema、選用的 outputSchema 與 annotations。工具頁。
structuredContent
結構化結果
工具結果裡的 JSON 物件，有 outputSchema 時 MUST 符合；SHOULD 同時附序列化的文字版。工具頁。
isError
工具執行錯誤
放在 result 裡的錯誤標記，和 JSON-RPC 的協定錯誤是兩層；模型看得到 content 裡的錯誤文字。工具頁。
Resources
資源
應用控制的原語；用 URI 識別；list、read、templates/list、subscribe。資源頁。
Prompts
提示
使用者控制的原語；帶參數的訊息模板；list、get。提示頁。
annotations
註記
資源與內容的 audience、priority、lastModified；工具的行為註記則 MUST 視為不可信。資源頁、工具頁。
Sampling
取樣
伺服器透過客戶端要一次模型生成；人 SHOULD 審 prompt 與回覆；偏好用 hints 與三個優先權。取樣頁。
Elicitation
引導
這一版新加：伺服器要使用者填扁平的表單；三種回應 accept、decline、cancel；MUST NOT 要敏感資訊。引導頁。
Roots
根目錄
客戶端暴露給伺服器的檔案系統邊界；file:// URI；變了送 list_changed。根目錄頁。
stdio
標準輸入輸出傳輸
客戶端把伺服器當子程序，一行一則訊息；客戶端 SHOULD 盡可能支援。傳輸頁。
Streamable HTTP
可串流的 HTTP 傳輸
單一端點支援 POST 與 GET，回覆可為 JSON 或 SSE；取代 2024-11-05 的 HTTP+SSE。傳輸頁。
Mcp-Session-Id
會話標頭
伺服器 MAY 在初始化時發，之後客戶端 MUST 每個請求都帶；404 就重新初始化。傳輸頁。
Protected Resource Metadata
受保護資源中繼資料
RFC 9728；MCP 伺服器 MUST 提供，用來告訴客戶端授權伺服器在哪。授權頁。
resource parameter
resource 參數
RFC 8707；客戶端 MUST 在授權與 token 請求裡指名 MCP 伺服器的正規 URI，把 token 綁定對象。授權頁。
token passthrough
token 透傳
伺服器不驗對象就把客戶端的 token 轉給下游；規格明文禁止。安全最佳實務頁。
confused deputy
混淆代理人
靜態 client id 加動態註冊加同意 cookie 造成的授權碼被劫；對策是每個客戶端各自同意。安全最佳實務頁。
progressToken / cursor
進度 token 與游標
進度追蹤放在請求的 _meta；分頁游標是不透明字串，客戶端不解析、不保存。工具程式各頁。
