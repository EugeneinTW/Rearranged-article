規格讀的是邊界：
守人、守連線、守能力。

02 / 13三種角色：主機、客戶端、伺服器
主機管人和同意，客戶端一對一連伺服器
架構頁：一個主機程序可以開多個客戶端，每個客戶端只連一個伺服器；伺服器可以是本機的子程序，也可以是網路上的服務
主機（Host）：發起連線的 LLM 應用
建立客戶端、管權限與同意、協調模型、彙整各客戶端的脈絡
客戶端 1
一條有狀態的會話：談能力、雙向傳訊息、管訂閱與通知
客戶端 2
和其他客戶端之間維持安全邊界，彼此看不到對方
客戶端 3
由主機建立與管理；每個客戶端只對一個伺服器
伺服器 1 · 本機：檔案與 Git
用原語暴露 resources、tools、prompts；可以向客戶端要 sampling
伺服器 2 · 本機：資料庫
獨立運作、職責單一；必須遵守安全限制
伺服器 3 · 網路：外部 API
遠端服務，走 HTTP 傳輸，通常要過授權
設計原則
伺服器要極容易做（複雜的協調交給主機）、要能彼此組合、看不到整段對話也看不到其他伺服器、功能靠能力協商漸進加上；核心協定只要求最少的東西。
伺服器看不到整段對話
完整的對話史留在主機；伺服器只拿到必要的脈絡，跨伺服器的互動由主機控制，每條連線各自隔離。
設計原則第三條，也是安全那一章的前提。
一個客戶端，一個伺服器
主機要接幾個伺服器就開幾個客戶端；每個客戶端維持一條有狀態的會話，負責協商能力、雙向路由訊息、管訂閱。
規格寫的是 1:1，不是一個客戶端接一堆伺服器。
主機是安全政策的執行者
同意、授權決定、客戶端的連線權限與生命週期都在主機；規格自己說協定層無法強制這些原則，靠實作者做進應用裡。
後面每一張的「人在迴圈裡」都落在這一格。
注意：三個伺服器是規格架構圖的例子，數量不限；主機的六項職責摘成三句是整理者的濃縮，原文列在 Host 一節。
03 / 13三種訊息：有 id 的要回
三種訊息：有 id 的要回，沒 id 的不回
基礎協定頁：所有訊息都是 JSON-RPC 2.0；MCP 在它之上加了幾條限制，而且這一版拿掉了批次，一次只送一則
訊息
有沒有 id
誰能發
對方要不要回
Request 請求
發起一個操作
有：字串或整數，不能是 null，同一會話裡發送方不能重複用
客戶端或伺服器都可以（例：tools/call、sampling/createMessage）
要，回一則帶同一個 id 的回覆
Response 回覆
請求的結果或錯誤
有：和請求同一個 id
收到請求的那一方；result 與 error 只能設一個，錯誤碼是整數
不回；它本身就是回覆
Notification 通知
單向訊息
沒有，MUST NOT 帶 id
兩邊都可以（例：notifications/initialized、tools/list_changed、progress）
不能回：收到的一方 MUST NOT 回覆
這一版拿掉了批次
2025-03-26 版加進來的 JSON-RPC 批次，在 2025-06-18 移除：走 HTTP 時一個 POST 的本文只能是一則請求、通知或回覆。
變更紀錄的第一條重大變更。
id 不能是 null、不能重複
基礎的 JSON-RPC 允許 null id，MCP 不允許；同一個發送方在同一個會話裡也不能重用 id。回覆靠 id 對帳，這是唯一的依據。
取消與進度通知也都用 id 或 token 指回原請求。
schema.ts 才是真相
規格的文字說明規則，訊息與結構的權威定義是 TypeScript schema；JSON Schema 是從它自動產生的，給工具用。
對欄位有疑問，查 schema，不查範例。
注意：_meta 是保留欄位；前綴含 modelcontextprotocol 或 mcp 的鍵名保留給協定用，實作 MUST NOT 對那些值做假設。規則在正文。
04 / 13握手：先談版本與能力
先談版本與能力，談好才准做事
生命週期頁：初始化 MUST 是第一個互動；操作階段 MUST 只用談好的能力；關閉沒有專用訊息，交給傳輸層
Step 1　initialize 請求
客戶端送：支援的協定版本、
自己的能力、clientInfo
Step 2　initialize 回覆
伺服器回：同一版或它最新的版本、
能力、serverInfo、instructions
Step 3　閘：版本與能力
版本不合就斷線；能力沒談到就不存在
沒談到的不能用
Step 4　initialized 通知
客戶端說「準備好了」
之後才是操作階段
Step 5　操作，然後關閉
只用談好的能力；關閉靠傳輸層：
關 stdin，或關 HTTP 連線
能力表
客戶端宣告：roots（listChanged）、sampling、elicitation、experimental。伺服器宣告：prompts（listChanged）、resources（subscribe、listChanged）、tools（listChanged）、logging、completions、experimental。
三條讓握手不出事的規則
① 版本不合，客戶端 SHOULD 斷線
客戶端送它支援的最新版本；伺服器支援就回同一個，不支援就回自己最新的；客戶端不接受就斷。走 HTTP 時之後每個請求都要帶 MCP-Protocol-Version 標頭。
錯誤例：code -32602，Unsupported protocol version，data 列出支援的版本。
② 每個送出的請求都要有逾時
逾時就送取消通知並停止等待；收到進度通知可以重設時鐘，但一定要有一個最大逾時，防止失控的對方拖住連線。SDK 應允許逐請求設定。
initialize 請求本身不能被客戶端取消。
③ 握手完成前只能 ping
伺服器回覆 initialize 之前，客戶端不該送 ping 以外的請求；收到 initialized 之前，伺服器只能送 ping 與 logging。談好的東西才算數。
這兩條是 SHOULD NOT；「只用談好的能力」在這一版改成 MUST。
注意：把「閘」畫成握手的一格是整理者的排法；規格的三個階段是初始化、操作、關閉，版本與能力協商都在初始化裡。

Resources 資源

Tools 工具

工具頁明說 SHOULD 永遠有人在迴圈裡、能拒絕呼叫：介面要顯示暴露了哪些工具、呼叫時要有明確指示、操作要向人確認。
第 6 卡把這條畫進迴圈。
listChanged 讓清單可以變
三種原語都能宣告 listChanged：清單變了就送 list_changed 通知，客戶端再列一次。只有資源另有針對單一項目的 subscribe。
四個 list 操作都支援游標分頁。
name 給程式，title 給人
這一版加了 title 欄位當顯示名，name 留作程式用的識別字；工具、資源、資源模板、提示都適用。

三條寫在工具頁上的規則
① 工具的註記不可信
工具的 annotations（描述行為的屬性）MUST 視為不可信，除非來自受信任的伺服器；總覽頁把描述文字也算進去。註記能參考，不能拿來決定要不要問人。
這是 MUST，不是建議。
② 伺服器 MUST：驗輸入、限速、清輸出
驗證所有工具輸入、實作存取控制、對呼叫限速、清理輸出。客戶端 SHOULD：送出前把輸入給人看、驗證結果再交給模型、設逾時、記錄呼叫供稽核。
兩邊的清單都在工具頁的安全考量。
③ 一個工具就是一份 JSON Schema
工具定義有 name、title、description、inputSchema，選用 outputSchema 與 annotations。模型看到的只有這份定義，描述要寫給模型讀。
規格的例子：get_weather，參數 location 一個字串。
注意：把「人確認」畫成迴圈裡的一步是整理者的畫法；規格寫的是 SHOULD 永遠有人在迴圈裡並能拒絕，位置由實作決定。
07 / 13一次呼叫的三種去處
一次呼叫三種去處：協定錯、執行錯、結果
工具頁的錯誤處理：協定錯誤是 JSON-RPC 的 error，執行錯誤放在 result 裡用 isError 標；成功的結果可以是內容，也可以再加結構化資料
tools/call 送出
呼叫有發生嗎？
發生了，成功嗎？
沒發生
發生了，但失敗
成功
協定錯誤：JSON-RPC 的 error
不認識的工具、參數不合法、伺服器錯誤。例：code -32602，Unknown tool。工具本身沒有執行
執行錯誤：result 裡 isError: true
API 失敗、輸入資料不合、業務邏輯錯誤。錯誤文字放在 content 裡回去，模型看得到，可以換個做法再試
成功：content，可再加 structuredContent
content 是一串內容：text、image、audio、resource_link、內嵌 resource；有 outputSchema 時，結構化結果 MUST 符合它
內容種類
五種內容都可加 annotations（audience、priority、lastModified）；structuredContent 是伺服器產生的資料，規格特別說它和模型的「結構化輸出」無關
三條讓結果好處理的規則
結構化結果要附文字版
回 structuredContent 的工具 SHOULD 同時在一個 TextContent 裡放序列化的 JSON，舊客戶端才讀得到。
為了向後相容，不是為了模型。
有 outputSchema 就要照它
伺服器 MUST 讓結構化結果符合 schema；客戶端 SHOULD 驗證。好處是型別、嚴格驗證、文件。
這一版的重大變更第二條。
resource_link 不保證在清單裡
工具可以回一個資源連結讓客戶端再抓或訂閱；規格說它不保證出現在 resources/list 的結果裡。
內嵌資源的伺服器 SHOULD 也實作 resources 能力。
注意：「呼叫有發生嗎」的問法與把 content、structuredContent 併成一個出口，是整理者的畫法；兩層錯誤的例子取自工具頁的 Error Handling。

資源頁與提示頁：兩種都是伺服器暴露的內容，差在誰決定放進對話；規格對兩者沒有評價，只規定訊息與欄位

參數可以用 completion/complete 補全；清單變了送 prompts/list_changed。缺必要參數或名稱不對回 -32602。
URI 方案有規矩
https:// 只在客戶端能自己從網路抓到時用，否則 SHOULD 用別的或自訂方案；file:// 表示像檔案系統的資源，不一定是真檔案，目錄可用 inode/directory 標；git:// 是版控；自訂方案要符合 RFC 3986。
找不到資源回 -32002；伺服器 MUST 驗證所有 URI。
提示是給人選的模板，不是給模型的指令
規格的例子是 code_review 帶一個 code 參數，取回的訊息是「請審這段 Python」；訊息裡可以內嵌伺服器端的文件或範例。伺服器 SHOULD 先驗參數再處理；所有輸入輸出 MUST 檢查，防注入。
介面模式不強制，斜線指令只是規格舉的例子。
注意：兩種都是可用的原語，規格沒有偏好，所以這張不用 ✗／✓；左右的流程是整理者照兩頁的 Message Flow 排的。

工作區（roots）
伺服器問它能動哪些目錄；答案是 file:// 的 URI，變了送 roots/list_changed
引導不能要敏感資訊
伺服器 MUST NOT 用 elicitation 要敏感資料；schema 只允許扁平物件與 string、number、boolean、enum；客戶端要讓人看得出是哪個伺服器在問。
這一版新加的功能，規格自己說設計可能再變。
取樣要人審兩次
SHOULD 永遠有人能拒絕：送模型前審 prompt，回伺服器前審回覆。模型用 hints 加成本、速度、智能三個優先權挑；伺服器不需要自己的 API 金鑰。
hints 只是建議，最後由客戶端選模型。
roots 是邊界，不是權限
客戶端 MUST 只暴露有適當權限的根目錄、驗證 URI 防路徑穿越；伺服器 SHOULD 先確認能力、在操作時尊重邊界、處理根目錄消失。
暴露之前 SHOULD 先徵求使用者同意。
注意：把三種客戶端功能畫在同一個客戶端旁是整理者的排法；規格各自一頁，三者互相獨立，各靠一個能力旗標開關。
10 / 13傳輸：stdio 對 Streamable HTTP

HTTP 的三條安全底線
伺服器 MUST 驗證 Origin 標頭防 DNS rebinding；本機執行 SHOULD 只綁 127.0.0.1；所有連線 SHOULD 有認證。會話 id SHOULD 密碼學安全、MUST 只含可見 ASCII，而且不能拿來當認證。

11 / 13授權：token 要指名給伺服器
遠端伺服器是資源伺服器，token 要指名給它
授權頁：只有 HTTP 傳輸走這套；MCP 伺服器是 OAuth 2.1 的資源伺服器，MCP 客戶端是 OAuth 客戶端，授權伺服器可以是同一個實體也可以分開
Step 1　沒帶 token 先問
收到 401，WWW-Authenticate 標頭
指出資源中繼資料在哪
Step 2　找授權伺服器
讀 /.well-known/oauth-protected-
resource，取 authorization_servers
Step 3　讀它的中繼資料
RFC 8414 的端點資訊；沒有 client id
就動態註冊（RFC 7591，SHOULD）
Step 4　授權碼流程
PKCE 必做；resource 參數指名伺服器
RFC 8707，MUST
Step 5　每個請求帶 Bearer
Authorization 標頭；伺服器驗 token
是不是簽給自己的，無效回 401
三個角色
MCP 客戶端＝OAuth 客戶端，替資源擁有者發請求；MCP 伺服器＝資源伺服器，收 token 並驗證；授權伺服器負責和使用者互動、發 token，實作細節不在規格範圍內。
三條 MUST
① token 不進網址，不給別人
存取 token MUST 放在 Authorization 標頭、MUST NOT 放在查詢字串，而且同一個會話的每個請求都要帶。客戶端 MUST NOT 把別的授權伺服器發的 token 送給這個 MCP 伺服器。
授權伺服器 SHOULD 發短效 token；公開客戶端 MUST 輪換 refresh token。
② resource 參數一定要送
授權請求與 token 請求都 MUST 帶 resource，值是這台 MCP 伺服器的正規 URI：有 scheme、沒有 fragment、盡量具體；就算授權伺服器不支援也要送。
合法例：https://mcp.example.com/mcp；不合法：mcp.example.com（缺 scheme）。
③ 伺服器只收簽給自己的 token
MUST 驗證 token 的對象是自己；無效或過期回 401，範圍不夠回 403，請求格式錯回 400。要呼叫上游 API 時，伺服器自己當 OAuth 客戶端，用另一個 token。
redirect URI 要事先登記、精確比對；state 參數 SHOULD 用並驗證。
注意：stdio 不走這套，SHOULD 從環境拿憑證；動態註冊是 SHOULD，授權伺服器不支援時客戶端要硬編 client id 或讓使用者自己填。
12 / 13安全：token 不能透傳
token 不能透傳：每一跳各自驗、各自拿 token
安全最佳實務頁：透傳是規格明文禁止的反模式；MCP 伺服器收到的 token 只能用來驗自己，對下游要用自己申請的另一個
✗ 透傳：收到什麼就轉什麼
✓ 各跳各驗：伺服器自己當客戶端
MCP 客戶端
送來 token A
伺服器不驗對象
原樣轉給下游
繞過限速稽核
分不清是誰
偷到就能借道
下游只看到「MCP 伺服器」這個身分，紀錄對不回真正的客戶端；被偷的 token 可以拿伺服器當資料外流的代理；一個 token 被多個服務接受，攻破一處就通到別處。
MCP 客戶端
帶 resource 參數，token A 只綁這台伺服器
伺服器驗 token A 的對象是自己
自己去拿 token B
上游只認 token B
每一跳各有紀錄
token A 從不離開這一跳；上游拿到的是伺服器自己申請的 token B
伺服器對上游 API 是另一個 OAuth 客戶端，用上游授權伺服器發的 token；限速、稽核、信任邊界在每一跳都成立。
透傳的三種後果
繞過依 token 對象設計的限速與驗證；伺服器與下游都分不清呼叫者，稽核失效；信任邊界被打穿，一個 token 通到多個服務。
規格：伺服器 MUST NOT 接受不是明確簽給自己的 token。
兩條 MUST 就擋掉
伺服器 MUST 只接受簽給自己的 token；客戶端 MUST 帶 resource 參數讓 token 綁定對象。對上游時伺服器自己當 OAuth 客戶端，MUST NOT 把收到的 token 轉出去。
授權頁「存取 token 權限限制」一節；最佳實務頁的 Token Passthrough。
注意：混淆代理人與會話劫持兩種攻擊在正文表格；四條安全原則（同意、隱私、工具安全、取樣控制）規格說協定層無法強制，靠實作。
