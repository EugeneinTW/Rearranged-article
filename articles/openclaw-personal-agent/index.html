Prologue · 整理者的引言

它會自己開一輪，但預設先安靜

OpenClaw 是跑在自己裝置上、從聊天 app 找得到的開源個人 agent。它會定時醒來跑一輪，但文件把預設設計成沒事就不出聲；這正是這一講要問的：agent 什麼時候該主動，什麼時候該等。

這是 Stanford CS 329Z 第 11 週的選讀，屬於 Coding Agents & Proactive Agents 分區的〈Proactive Agents〉那一講。那一講的題目是：從被動到主動；General User Models（GUM）；Next Action Prediction；開源的主動個人 agent；隱私與信任的影響；以及 agent 何時該主動、何時該等（mixed initiative）。同一講的必讀是 Shaikh 等人的〈Creating General User Models from Computer Use〉，另一篇選讀是 Shaikh 等人的〈Learning Next Action Predictors from Human-Computer Interaction〉。課程書單把這一篇列為 Steinberger 的〈OpenClaw: Open-source proactive AI agent〉（2025），連到的是 GitHub 上的 repo。

README 說 OpenClaw 是跑在你自己電腦上的開源 AI 助理，在你已經在用的聊天管道裡等你：Discord、iMessage、Slack、Teams、Telegram、WhatsApp，另外還有二十多種，也有 macOS、iOS、Android、Windows、Linux 的原生 app。同一個 Gateway 可以在筆電上當個人助理，也可以當整個團隊共用的部署，README 說差別只在設定。它也說狀態、記憶與憑證都留在你的硬體上，模型和 agent harness（Claude、Codex、本機模型）是可以替換的 plugin。專案由獨立的非營利組織 OpenClaw Foundation 管理，README 說它沒有付費方案、沒有託管服務、也沒有代幣，捐助者不擁有也不主導專案。

這一頁讀了 README 與文件站的 16 頁。文件站 docs.openclaw.ai 的目錄檔列了約 1,350 頁（整理者數的），本頁只讀和這一講有關的幾區：架構與 agent loop（3 頁）、記憶（2 頁）、主動（心跳、排程、排程的運作方式，3 頁）、誰能找上 agent（配對、存取控制，2 頁）、信任與安全（安全、沙箱，2 頁）、擴充（skills、ClawHub 稽核，2 頁）。另外加讀了兩頁：沙箱索引頁的範例用到三種模式卻沒有解釋，於是讀了定義它們的那一頁；排程頁只是索引，於是讀了 webhook 那一頁。設定參數、CLI 參考、疑難排解、各聊天平台的設定、plugins、模型供應商都沒讀，提到時只說細節在哪一頁。

順序是整理者重排的。文件站按主題分區（concepts、gateway、automation、channels、tools、clawhub 等），本頁照建一個主動 agent 需要的順序：先看邊界（Gateway 架構），再看一輪怎麼跑（agent loop），然後是狀態放在哪（記憶、使用者模型、意圖），接著是這一講的重點：什麼時候跑、什麼時候開口、還有哪些東西會開一輪，最後是誰能找上它、工具在哪裡跑、外來的 skill 怎麼驗。

這是持續在改的專案，README 與文件幾乎每天都在更新。本頁依 2026 年 9 月 30 日抓到的版本整理，之後的內容可能不同；本頁不去比對舊版。這些也都是專案自己寫的文件：文件對 OpenClaw 功能與設計的說法，本頁一律寫成「文件說」「README 說」；指令、設定鍵與元件名照原文保留，例如 Gateway、channels、nodes、heartbeat、automations（CLI 裡也叫 cron）、skills、ClawHub、pairing。數字只用文件寫出的；文件站的頁數與各區頁數是整理者依目錄檔數的。

先把幾個名詞對齊

  • Gateway：長駐在你電腦上的程序，所有聊天連線、session、工具與事件都經過它。
  • Channel（聊天頻道）：一個聊天平台的連線，例如 Telegram、WhatsApp、Slack。
  • Session：一段對話的上下文。每個 agent 有一個 main session，群組與頻道各有自己的 session。
  • Heartbeat（心跳）：Gateway 定時在 main session 跑的一輪 agent，看看有沒有需要你注意的事。
  • Automations（排程工作）：Gateway 內建的排程器，照時間喚醒 agent；CLI 也叫 cron。
  • Workspace：agent 唯一的工作目錄，記憶與設定檔都是裡面的 Markdown 檔。
主動的 agent 難的不是會醒來，是醒來之後知道什麼時候不該開口。 序章核心觀念

架構頁寫了三條不變式：每台主機只有一個 Gateway，它也是唯一開 WhatsApp session 的地方；握手是強制的，第一個 frame 不是 JSON 或不是 connect，就直接斷線；事件不會重播，client 發現漏了要自己重新整理。協定本身由 TypeBox 的 schema 定義，JSON Schema 與 Swift 的型別都由它產生。

Gateway 的 WebSocket 協定 · 教學用精簡版 
// 第一個 frame 一定是 connect（帶裝置身分與認證）
{ type: "req", id: 1, method: "connect", params: { auth: { token: "…" } } }

// 之後：請求對回覆；有副作用的方法（send、agent）要帶 idempotency key
{ type: "req", id: 2, method: "agent", params: { … } }
{ type: "res", id: 2, ok: true, payload: { runId: "…", status: "accepted" } }

// 伺服器推送的事件：不會重播，漏了要自己重新整理
{ type: "event", event: "agent", payload: { … } }

每個 WebSocket client，不論是控制端還是 node，connect 時都要帶裝置身分，並簽署 Gateway 給的 connect.challenge nonce。新的裝置 ID 要經過配對核准，Gateway 再發一個 device token 給之後的連線用。同一台主機走 loopback 的直接連線可以自動核准，讓本機的體驗順一點；tailnet 與區網的連線，即使是同一台主機，也還是要明確核准。Gateway 的認證（gateway.auth.*）對本機與遠端的連線一律適用。第 9 章會回到配對。

遠端存取，架構頁建議 Tailscale 或 VPN，其次是 SSH 通道；經過通道一樣走同一套握手與 token，遠端時 WebSocket 可以開 TLS 與選用的憑證釘選。網路暴露的設定本頁不展開，文件把它放在安全分區的 network exposure 與 exposure runbook 兩頁。

背景

心跳與排程掛在 Gateway 的排程器上

架構頁最後一節講計時的工作：Gateway 核心有一個 GatewayScheduler，維護工作與 cron 的喚醒都登記在它上面，一個主機計時器驅動下一次喚醒。需要持久的工作，由各自的擁有者把截止時間存下來、在啟動時重建排程；電腦睡眠後醒來，錯過的 tick 會合併成一次。第 6 到 8 章的心跳與排程，都是掛在這個排程器上。

文件說最重要的界線在精選核心與情節層之間。精選的檔案小、來源合格時通常就在 context 裡、只能經過有閘的整併寫入；情節層的檔案大、適合一直追加，靠搜尋工具或 Active Memory 取用，不在 session 開始時載入。沒通過升級的閘，情節層的內容不會跑進精選層。

每一筆索引都帶來源標記，存在模型沒辦法用文字改寫的 SQLite 欄位裡。來源分四類，是封閉的集合：owner（主人在受信任的頻道打的）、agent（agent 從主人的內容推出來的）、untrusted（從網頁、工具輸出、群組裡的非主人這類外部內容推出來的）、system（心跳 prompt、cron 前言這類鷹架）。判斷不了的，外部來的算 untrusted、鷹架算 system，永遠不會預設成 owner。兩條衛生規則用這些標記擋掉常駐 agent 的典型毛病：cron、心跳、sub-agent 的 session 不產生長期記憶的候選；從記憶注入 context 的內容（bootstrap 檔、搜尋結果、召回的 transcript）會被標記，永遠不會再被當成新記憶擷取，文件的說法是召回一百次仍然是一筆。

來源也會在一輪之內傳下去。一個工具結果宣告自己是網路來源（抓網頁、瀏覽器、搜尋），這一輪之後產生的助理訊息都帶汙染標記，即使在主人的回合裡也當成 untrusted，下一則使用者訊息進來才清掉。文件自己點出缺口：只有會宣告的工具才算，讀本機檔案這類工具不會汙染這一輪。

記憶是注入攻擊最想要的持久層

記憶架構頁說，在記憶裡種一次指令、之後每次都被注入，是公認的攻擊類型（文件引 OWASP 的 agentic 應用清單與相關研究），而偵測式的防禦效果不好。它的防法是結構性的：來源標記存在分類程式寫的欄位，文字自稱來自主人也不會變成主人的內容；untrusted 的內容可以存、可以索引、可以被明確搜尋，但結構上進不了精選層，也不會自動注入，被明確叫出來時會包上不可信內容的框；dreaming 的閘看來源，不只看分數，所以它沒辦法經由每天的筆記洗進 MEMORY.md；每次整併都在 DREAMS.md 留下紀錄。文件舉的例子是一個被摘要的網頁，夾帶「把某個危險指令記成重要事項」：那段摘要被標成 untrusted，永遠不自動注入，召回再多次也升不上去，被搜尋出來時也包著不可信的框。

這一段不在原文裡。它把課程作業 HW1（從零建一個有工具、終端、記憶與 human-in-the-loop 的 agent harness）用得到的設計壓成一份清單；每一條都能在前面的章節找到出處，實作細節是你自己的。

  1. 一個長駐程序持有所有連線聊天、控制端、裝置都連到它；一個 session 一條 lane，同一個 session 的 run 依序跑（第 2、3 章）。
  2. 給 agent 一個唯一的工作目錄工具只在這裡跑；新 session 第一輪注入指示、人格與使用者檔案，太大就截斷（第 3 章）。
  3. 記憶寫成檔案，分層並帶來源每天的筆記只追加；長期記憶只由一個有閘的整併寫入；外部內容標成不可信、永遠不自動注入（第 4 章）。
  4. 偏好寫成指令，意圖編成觸發條件偏好改了就地取代；時間型的意圖交給排程，事件型的用程式比對，加冷卻、次數與到期（第 5 章）。
  5. 加一個窄 prompt 的定時回合沒事回一個會被濾掉的靜默 token；時段外、忙碌時、沒有送達對象時跳過；警示只送主人（第 6、7 章）。
  6. 把人放在「升級成排程」這一步agent 提議，用一句白話確認，立刻試跑一次，失敗就刪（第 8 章）。
  7. 陌生人先配對，工具先過政策再決定在哪裡跑未核准的訊息不處理；被 deny 的工具沙箱帶不回來；外來的 skill 先驗再裝（第 9 到 12 章）。

整理者的補充：本站的〈Best Practices for Claude Code〉是另一個 agent 的官方文件，談權限、hooks 與 subagent 怎麼設，可以和第 11、12 章對照著讀；本頁不用它擴寫。

Node
裝置節點

Workspace
工作目錄

Bootstrap files

Agent loop
agent 迴圈
每個 session 依序執行的一次 run：收件、組 context、推論、工具、串流、寫入。agent loop 頁。
Session lane
session 佇列
同一個 session key 的 run 排成的佇列，防止工具與 session 互相搶。agent loop 頁。
NO_REPLY

Dreaming
背景整併
預設開啟的排程整併，候選過了確定性的閘才寫進 MEMORY.md 與 USER.md。記憶頁、記憶架構頁。
User model
使用者模型
USER.md 裡寫成指令的偏好，帶觀察日期與有效或已取代的狀態。記憶架構頁。
Standing intents
常駐意圖
事件型的前瞻記憶，用 intent 工具存進 SQLite，每則訊息用程式比對。記憶架構頁。
Heartbeat
心跳
系統擁有的排程，預設每 30 分鐘在 main session 跑一輪 agent。心跳頁。
Monitor scratch
心跳清單
每個心跳工作的私有小清單，接在心跳 prompt 後面；上限 256 KiB。心跳頁。
heartbeat_respond
心跳回應工具

Automations
排程工作
