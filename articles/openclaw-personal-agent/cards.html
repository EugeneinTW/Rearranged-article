03 / 13一則訊息變成一次 run
一則訊息變成一次 run，同一個 session 依序跑
agent loop 頁：run 是每個 session 依序執行的一次處理，收件、組 context、模型推論、執行工具、串流、寫入；每個 agent 有自己的 workspace，是工具唯一的工作目錄
Step 1　收件
agent RPC 驗參數、解析 session，
立刻回 runId，不等跑完
Step 2　排隊
同一個 session 一條 lane；
新訊息預設 steer 進這一輪
Step 3　準備
workspace、skills 快照、
bootstrap 檔都備好
Step 4　組 prompt
基礎 prompt、skills、bootstrap
加上這一輪的覆寫
Step 5　推論與工具
模型呼叫工具、讀結果、再推論
同一個 run 裡來回
Step 6　整形回覆
NO_REPLY 濾掉；重複確認刪掉
要不要回，主機決定
Step 7　寫入
transcript 進 SQLite；寫入權
比對不符的過期 run 寫不進去
一次 run 從收件跑到寫入。runtime 的事件接成三條串流：tool、assistant、lifecycle
（start、finishing、end、error）；agent.wait 等的就是這個 runId 的結果。
心跳、排程、webhook 開的也是這樣的一輪（第 08 卡）。
同一條 lane 的下一則
三條讓它可以預期的規則
同一個 session，一次一個 run
run 依 session key 排進 lane，可再經過全域 lane；
每次寫 transcript 都比對寫入權，被取代的 run
不會把過期內容寫回去。
另一個 Gateway 也不能同時佔用同一個狀態目錄。
該回的，一定要回
直接的請求、被接受的群組請求預設要回答；
模型寫出 NO_REPLY 只是空輸出，
不是可以不回的許可。
跑完工具沒寫答案，可以再跑一次不帶工具的收尾。
逾時：48 小時與 30 秒
整次執行預設 48 小時，到期中止，有進度也不重設；
agent.wait 預設 30 秒，時間到只停止等待，
run 照樣在跑。
模型閒置：雲端 120 秒、自架 300 秒。
注意：七步是整理者依 run sequence 與各節的順序排的；推論與工具的來回發生在同一個 run 裡，虛線回到排隊，表示這條 lane 接著處理下一則。

一致性稽核的三個問題（ClawScan 的風險分析）
1
這份權力，在預期之內嗎？
EXPECTED
名稱、摘要、metadata 和實際內容，是不是使用者會合理預期的樣子
2
有沒有揭露？
DISCLOSED
要的憑證、本機指令、供應商 API、套件安裝，都寫在宣告裡，而且和用途一致
3
權力和用途成比例嗎？
PROPORTIONATE
文件說強大的行為不自動等於壞；問的是它有沒有被宣稱的用途撐起來

安裝前的三條規則（skills 頁）
① 第三方 skill 當成不可信的程式碼：啟用前先讀，不可信的輸入與有風險的工具用沙箱跑。
② openclaw skills verify 向 ClawHub 查這個 skill 的 trust envelope；驗證失敗會以非零結束。
③ security.installPolicy 在每一條安裝路徑之前跑本機的政策指令，拿不到有效的決定就擋下。
注意：文件說稽核是強的訊號，不保證零風險，Pass 也不能取代你的判斷；三個問題取自稽核頁「預期、揭露、成比例」的說法，排成三道是整理者的畫法。
13 / 13讀法：觸發者、寫入者、邊界
先找觸發者，再找寫入者，最後找邊界
整理者的讀法：每一種主動都落在 Gateway 開的一輪；每一份狀態都寫明了誰能寫、何時放進 prompt；每一個動作都分層把關
01 · TRIGGERS
每一次主動，
都是 Gateway 開的一輪
訊息、心跳 tick、排程、webhook、
背景指令跑完，最後都進同一條 lane；
先問它由什麼觸發、跑在哪個 session。
✗ 把「記得要去做」寫進記憶檔
✓ 時間型交給排程，事件型交給 intent
02 · WRITERS
每一份狀態，
先問誰能寫、何時注入
五層記憶、USER.md、常駐意圖、
monitor scratch、DREAMS.md 都寫明了；
長期記憶只有一個有閘的寫入者。
✗ 相信文字自稱來自主人
✓ 來源標記存在模型寫不到的欄位
03 · BOUNDARIES
每一個動作，
分三層把關
誰能觸發：配對與允許清單；
模型看到什麼：context 與不可信的框；
工具在哪裡跑：政策、沙箱、elevated。
✗ 用分開的 DM session 隔開互不信任的人
✓ 每個信任邊界，各自一個 Gateway
