MEMGPT · TOWARDS LLMS AS OPERATING SYSTEMS · 圖卡＋教材整合版

把脈絡視窗當記憶體， 讓 LLM 自己換頁MemGPT：主脈絡在視窗內， 其餘放在視窗外， 由模型用函式呼叫搬進搬出

LLM 的脈絡視窗長度固定：最常用的開源模型只撐得住幾十則訊息，長文件更放不下。這篇論文不去加長視窗，而是借作業系統的虛擬記憶體：視窗是有限的主記憶體，完整的對話紀錄與文件放在視窗外的資料庫，模型用函式呼叫自己決定什麼時候存、什麼時候找；事件觸發推論，一個 heartbeat 參數讓它連續呼叫好幾個函式。作者在多段對話與文件分析兩個領域測試，結論是 MemGPT 都勝過只靠固定視窗的做法，但效果很依賴底層模型會不會呼叫函式。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

用管記憶體的方法管脈絡，這個想法出自 MemGPT

Stanford CS 329Z 第 4 週「Agent Memory Architectures」那一講，談短期與長期記憶、把記憶當成工具動作、用檔案系統當外部記憶、結構化記憶，以及跨 agent 的記憶。這篇 2023 年的論文排在這一講的必讀，它是「用作業系統的虛擬記憶體比喻來管理 LLM 脈絡」的出處。

一個 agent 在某一刻「知道」的東西，全部都在它這一次的 prompt 裡；prompt 以外的一切，都得先被放進來才用得上。所以談 agent 的記憶，繞不開兩個問題：視窗裡放什麼，以及由誰、在什麼時候把東西搬進搬出。MemGPT 用作業系統的語言回答：脈絡視窗是容量有限的主記憶體，視窗外的資料庫是磁碟，模型自己用函式呼叫做換頁。這一講的五個講題，幾乎都能在這個切法上找到位置，結論章會逐一對回來。

論文的作者是 UC Berkeley 的七位研究者，第一作者 Charles Packer，Ion Stoica 與 Joseph E. Gonzalez 也在作者群裡。第一版在 2023 年 10 月貼上 arXiv，2024 年 2 月更新成第二版，這一頁依第二版整理；實驗用的是 GPT-3.5 Turbo、GPT-4、GPT-4 Turbo 這些 2023 年底的 OpenAI 模型，數字只對它們成立。後來的 Letta 公司就是從這個專案出來的；這一句是整理者的補充，論文裡沒有。

這一頁怎麼處理論文，先說清楚。章節跟著論證走，不跟著節號走：第 1、2 章是問題與想法，第 3 到 6 章把系統拆成四個元件（記憶階層、佇列管理器、函式執行器、事件與函式連鎖），第 7 到 11 章是實驗設計與四個任務，第 12 章是相關工作，第 13 章是結論與代價。數字只用正文與表 1 到表 3 寫出來的；圖 5、圖 7 的點沒有標數字，這裡不替它們估。附錄的提示詞改寫成中文說明，函式名照原文保留。哪些歸納是整理者的，每張圖卡的腳註都會說。

先把幾個名詞對齊

  • 脈絡視窗（context window）：模型一次推論能讀進的最大 token 數，prompt 與它的輸出都算在裡面。超過就得刪減或截斷。
  • token：模型處理文字的單位，一個英文單字大約一到兩個 token。表 1 用每則訊息約 50 tokens 來估算。
  • 函式呼叫（function calling）：模型不直接回話，而是輸出「呼叫哪個函式、帶什麼參數」，由外面的程式執行後把結果交回給它。
  • 虛擬記憶體與分頁（virtual memory、paging）：作業系統把暫時用不到的資料寫到磁碟，要用時再讀回主記憶體，讓程式以為記憶體比實際的多。
  • 檢索增強（retrieval augmentation）：先用檢索器找出相關文件，再放進 prompt 讓模型回答，也就是常說的 RAG。

直接把視窗加長呢？作者列了兩個障礙。第一是成本：transformer 的自注意力機制讓運算時間與記憶體用量隨長度平方增加，所以設計新的長脈絡架構本身就是一個迫切的研究題目。第二是效果：就算克服了運算上的難題，近期研究（Liu 等人，2023a）發現，長脈絡模型也很難有效運用多出來的脈絡。再加上訓練頂尖 LLM 要耗費大量資源、加長脈絡的回報又遞減，作者的結論是需要別的技術來支援長脈絡。

文件分析的處境更明顯，論文在第 3.2 節補充：OpenAI 的模型當時最多 128k tokens，但像美國證管會 10-K 年報這類法律或財務文件，很容易超過一百萬 tokens；真實的文件分析還常常要在好幾份這樣的長文件之間找關聯。Liu 等人也觀察到大視窗模型的注意力分布不均，模型比較容易想起視窗開頭與結尾的內容，中間的較差。作者因此認為，一味加大視窗很難當成固定脈絡問題的解法。

作者把問題換了一個問法：不去改模型，能不能繼續用固定視窗的模型，卻給出「脈絡沒有上限」的效果？論文的原話是這樣描述研究目標的：

"the illusion of an infinite context while continuing to use fixed-context models" 「在繼續使用固定脈絡模型的同時，營造出脈絡無限的錯覺」：第 1 節對研究目標的描述。

靈感來自作業系統的虛擬記憶體。它當初是為了讓應用程式處理遠大於可用記憶體的資料而發明的：作業系統把溢出的資料分頁寫到磁碟，程式要用時再透過 page fault 讀回主記憶體，程式因此以為可用的記憶體比實體的多。MemGPT 把同一套想法搬到 LLM：脈絡視窗對應實體的主記憶體，視窗外的儲存對應磁碟，負責管理的系統就是作者說的「LLM OS」，也就是 MemGPT 本身。模型可以把視窗裡缺少的歷史資料找回來，也可以把比較不相關的資料逐出到外部儲存。

能這樣做，靠的是 LLM 代理當時剛成熟的函式呼叫能力（作者引用 Schick 等人與 Liu 等人 2023b 的研究）。透過函式呼叫，模型能讀寫外部資料來源、修改自己的脈絡，並選擇什麼時候回應使用者。同樣的函式呼叫也用來管控制流程，讓模型在管理脈絡、產生回應、和使用者互動之間切換。所以在單一個任務裡，模型可以反覆調整視窗裡放什麼，把有限的脈絡用得更有效。

論文的圖 1 與圖 2 是兩個小例子。圖 1 裡，使用者提到男友 James 烤了生日蛋糕給自己，模型回完話，系統隨即發出一則「記憶壓力」警告；模型接著呼叫兩次 working_context.append，把「生日是 2 月 7 日」與「男友叫 James」寫進常駐的工作脈絡。圖 2 裡，使用者說「我們去了六旗樂園」，模型呼叫 recall_storage.search 搜尋舊對話，找到三筆提過六旗樂園的訊息，其中一筆提到使用者和 James 就是在那裡認識的，於是順著這件事回問。

作者把三樣東西並列為 MemGPT 能處理無界脈絡的原因：記憶體階層、作業系統式的函式，以及事件驅動的控制流程。接下來四章依序拆開：記憶階層（第 3 章）、佇列管理器（第 4 章）、函式執行器（第 5 章）、事件與函式連鎖（第 6 章）。

提醒

類比的邊界

作業系統的分頁對程式是透明的：程式不知道哪一頁在磁碟上，換頁由核心自動完成。MemGPT 裡大部分的搬移，反而是模型自己看情況呼叫函式做的，只有佇列滿了才由系統自動逐出（第 4、5 章）。這個對照是整理者加的，論文沒有這樣比；但它說明了為什麼後面的實驗結果，那麼依賴底層模型的函式呼叫能力。

佇列管理器管兩樣東西：recall storage 與 FIFO 佇列。系統收到新訊息時，它把訊息接到 FIFO 佇列尾端，串起 prompt tokens，觸發一次 LLM 推論，產生輸出（completion tokens）。進來的訊息和模型產生的輸出，它都寫進 recall storage。模型用函式從 recall storage 找回來的訊息，也由它接回佇列尾端，重新放進視窗。

注意：request_heartbeat=true 出自圖 3 的圖說；「帶 heartbeat 嗎」那一格，是整理者把第 2.4 節的兩種情況畫成的分岔。

作業系統靠中斷管理控制流程，MemGPT 對應的是事件：事件是 MemGPT 泛稱的輸入。原文列了四種：聊天應用裡的使用者訊息；系統訊息，例如主脈絡的容量警告；使用者的動作，例如「使用者剛登入」或「使用者剛上傳完一份文件」的通知；以及排程、定時執行的事件，讓 MemGPT 在沒有使用者介入時也能自己運作。MemGPT 用一個解析器把事件轉成純文字訊息，接進主脈絡，最後成為 LLM 處理器的輸入。

很多實際的任務，要依序呼叫好幾個函式才做得完，例如翻閱同一個查詢的多頁結果，或從不同查詢拿到的不同文件裡彙整資料。函式連鎖（function chaining）讓 MemGPT 在把控制權交回使用者之前，連續執行好幾個函式。做法是呼叫函式時加一個特別的旗標。帶了旗標，函式執行完之後，輸出放進主脈絡，控制權立刻回到處理器，不會暫停；沒帶旗標，就是一次 yield，MemGPT 不會再跑 LLM 處理器，直到下一個外部事件發生，例如使用者的新訊息或排定的中斷。

圖 3 的圖說寫出了這個旗標的名字：模型在輸出裡產生關鍵字參數 request_heartbeat=true，就能要求立刻再推論一次。作者說，MemGPT 能做多步檢索來回答使用者的問題，靠的就是函式連鎖。圖 6 的文件問答是一個例子：模型搜尋 archival storage 拿到第 1 頁，再帶著頁碼查第 2 頁，才回答。

圖 6 的連鎖呼叫 · 教學用精簡版（heartbeat 參數與最後的 yield 是依第 2.4 節加上的示意）

# 事件：使用者問「第一座諾貝爾物理獎頒給了誰？」
archival_storage.search("nobel physics", request_heartbeat=true)
#   → 124 筆結果中的 10 筆（第 1 頁，共 13 頁）

# 回答使用者；這一步不帶 heartbeat，等下一個事件

這個設計把「做一步」和「要不要接著做」分開：模型每一輪只輸出一次函式呼叫，要不要緊接著再跑一輪，由它在同一次輸出裡用 heartbeat 表態。所以一個使用者問題，背後可能是好幾輪推論。作者在相關工作一節也提到，Yao 等人（2022）顯示穿插推理能改善互動式代理的規劃，而 MemGPT 裡的模型在執行函式時同樣會「邊想邊說」（plan out loud）。

背景

yield 這個詞

yield 是作業系統與程式語言裡的用語，意思是主動讓出執行權。第 2.4 節用它指「沒有要求立刻再推論」的函式呼叫：處理器停下來，等下一個事件叫醒它。事件可能是使用者的新訊息，也可能是排程的中斷，所以 MemGPT 在沒有人開口的時候，也能被定時事件叫醒。

Chapter 09 · Conversation opener task (engagement)

記在工作脈絡的事實，讓開場白接得上前幾次的對話

開場白任務看代理在新一段對話的開頭，會不會主動提起先前累積的了解。MemGPT 的開場白和人設的相似度，三個模型都高過人寫的開場白；和人寫開場白本身比，落在 0.767 到 0.817 之間。

兩邊用同一個檢索器：以 OpenAI 的 text-embedding-ada-002 嵌入向量做餘弦相似度搜尋，取前 K 篇。MemGPT 用預設的儲存設定，archival storage 是啟用了 pgvector 擴充的 PostgreSQL；嵌入向量預先算好載入資料庫，用 HNSW 索引做近似搜尋，查詢時間在一秒以內。MemGPT 把整批嵌入過的文件都載進 archival storage，檢索器就自然成了 archival storage 的搜尋功能；基線則在 LLM 推論之外獨立取出前 K 篇，和原本的 retriever-reader 設定一樣。資料是 2018 年底的 Wikipedia 傾印檔，照 NaturalQuestions-Open 先前研究的做法；作者抽了 50 題評估，題目與嵌入後的段落都有公開。

評分用 LLM 評審，確認答案真的是從檢索到的文件裡推出來的，也避免字串不完全相同的正確答案被判錯。附錄的提示詞要求兩邊都同時給出答案與出處文件。基線被告知文件裡可能有無關的，找不到答案就回答「資訊不足」（INSUFFICIENT INFORMATION）；MemGPT 被告知答案一定在它的 archival memory 裡，找不到就繼續搜；兩邊都被要求假設現在是 2018 年。評審只在回答同時有正確答案與對應的文件文字時判對，回答資訊不足、或缺了出處文件，都算錯。

結果在圖 5：橫軸是檢索回來的文件數（0 到 200），縱軸是準確率，圖上的點沒有標數字。作者的解讀是，基線的表現大約被檢索器封頂：它們只能用視窗裡被放進來的資訊，只要嵌入式檢索器用這個問題撈不到金牌文章，基線就保證看不到它。MemGPT 則能對檢索器發出多次查詢，主動搜尋 archival storage，還能一頁一頁翻下去，所以它能用的文件總數，不再受限於視窗裡放得下幾篇。

這個任務對所有方法都難，原因在嵌入式相似度搜尋本身：作者觀察到，NaturalQuestions-Open 標註的金牌文件，常常排在前十幾筆之後，甚至更後面。檢索器的表現直接反映在基線的結果：GPT-4 在文件少時準確率偏低，隨著更多文件放進視窗而提高，因為它確實只根據檢索到的文件回答。MemGPT 理論上不受檢索器排序不佳的限制，只要金牌文件在完整的排名裡，翻得夠多頁就找得到；但作者觀察到，MemGPT 常常在翻完檢索結果之前就停下來。

要讓基線和 MemGPT 比到超過預設視窗的長度，作者把檢索器回傳的文件截短，讓同樣數量的文件塞得進視窗。不出所料，文件截得越短，金牌文件裡相關片段被切掉的機會越大，準確率跟著下降。MemGPT 配 GPT-3.5 的表現明顯變差，作者歸因於它有限的函式呼叫能力；配 GPT-4 表現最好，圖 5 的圖說也說配 GPT-4 與配 GPT-4 Turbo 的結果相同。

思考題 · 02

你的 RAG 是一次塞滿，還是讓模型自己翻頁？

多數 RAG 管線取固定的前 K 段，一次放進 prompt；K 太小會漏，K 太大又得截短。

先統計檢索失敗裡，有幾成是「正確段落排在前 K 名之後」。比例高的話，讓模型能帶頁碼再查一次、並在提示詞裡寫清楚什麼時候該繼續找，可能比調大 K 有用；但也要量它會不會太早停，這是第 3.2.1 節自己承認的問題。

關鍵觀念 · 二

資料都在視窗裡，問題就不在視窗大小

140 組鍵值對約 8k tokens，基線的 GPT-4 其實整份都看得到。它失敗的原因不是資料被截掉，而是要在一次推論裡連續追好幾層。MemGPT 把這件事拆成好幾次函式呼叫：每一次只查一層，看了結果再決定要不要繼續。

整理者的讀法：這個實驗量到的，比較像是「把多步查找拆成多次呼叫」的價值，而不只是記憶容量。停止條件也寫得很乾淨：查到只剩一筆、而且它是值，就停。

作者點名的後續方向有三個：把 MemGPT 用到其他有大量或無界脈絡的領域；整合不同的記憶層技術，例如資料庫或快取；以及進一步改進控制流程與記憶管理的策略。

下面是整理者把這一講的五個講題對回論文的讀法，論文沒有這樣講：

第 4 週的講題在 MemGPT 裡對應的東西（整理者的讀法）
短期與長期記憶主脈絡在視窗內，每次推論都看得到；外部脈絡（archival、recall storage）在視窗外，要搜尋才看得到
記憶當成工具動作記憶的存、改、找全是函式呼叫：working_context.append、working_context.replace、recall_storage.search、archival_storage.search
檔案系統當外部記憶論文用的是資料庫（PostgreSQL 加 pgvector），不是檔案系統；共同點是放在視窗外、要用工具讀進來
結構化記憶工作脈絡是一塊固定大小的非結構化文字；記憶要不要結構化，論文沒有討論
跨 agent 的記憶論文只有單一代理，沒有討論
MemGPT 需要重新訓練模型嗎？
不用。它是包在固定視窗 LLM 外面的系統：記憶階層、系統指令裡的函式 schema、佇列管理器與事件處理，都在模型之外（第 2 節）；實驗直接用 GPT-3.5 Turbo、GPT-4、GPT-4 Turbo 的 API 端點。
它和一般的 RAG 差在哪？
多文件問答裡兩邊用同一個檢索器，差別在誰決定查、查幾次、翻到第幾頁：基線一次拿前 K 篇，MemGPT 讓模型自己搜尋 archival storage、一頁頁翻（第 3.2.1 節）。作者也說外部記憶的設計建立在檢索增強的研究上（第 4 節）。
視窗越來越長，還需要這套嗎？
作者的看法是兩者相輔：更長的視窗讓 MemGPT 的主記憶體變大（第 4 節）；但長文件、多份文件與跨數週的對話仍會超過視窗（第 3.1、3.2 節），長脈絡模型也不一定用得好多出來的脈絡（第 1 節）。
思考題 · 03

把記憶管理交給模型之後，你怎麼知道它「搜夠了」？

MemGPT 的兩個失敗都和查得不夠有關：文件問答太早停、巢狀鍵值少查一層。

把每次任務的函式呼叫都記下來，數它搜了幾次、翻了幾頁，和答案的對錯放在一起看。第 11 章的鍵值任務有一個乾淨的停止條件（查到只剩一筆、而且是值就停）；想想你的任務有沒有類似、能寫進提示詞的停止條件。

視窗有多大是模型的事；什麼時候把什麼搬進視窗，才是記憶架構要設計的事。 整理自第 1、2、5 節

Reference · 名詞速查

關鍵名詞與它們在論文裡的位置

先列系統的記憶階層與元件，再列控制流程，最後是實驗的資料集、任務與指標。

MemGPT
MemoryGPT
讓固定視窗的 LLM 自己管理多層記憶的系統；作者也稱它為 LLM OS（第 1、2 節）。
virtual context management
虛擬脈絡管理
借虛擬記憶體的想法，在視窗與外部儲存之間搬資料，營造脈絡沒有上限的效果（第 1 節）。
main context
主脈絡
LLM 的 prompt tokens，推論時看得到的全部內容；對應主記憶體（第 2 節）。
external context
外部脈絡
視窗外的資訊，一定要搬進主脈絡才用得上；對應磁碟（第 2 節）。
system instructions
系統指令
主脈絡的第一段，唯讀；寫控制流程、各層記憶的用途與函式用法（第 2.1 節）。
working context
工作脈絡
主脈絡的第二段，固定大小的非結構化文字，只能用函式寫；附錄的提示詞稱它 core memory（第 2.1 節）。
FIFO queue
先進先出佇列
主脈絡的第三段，滾動的訊息與函式呼叫紀錄；第一格是遞迴摘要（第 2.1 節）。
recursive summary
遞迴摘要
用舊摘要加上這次被逐出的訊息寫成的新摘要，放在佇列第一格（第 2.2 節）。
queue manager
佇列管理器
把訊息放進佇列並寫進 recall storage，依警告門檻與清空門檻處理溢出（第 2.2 節）。
memory pressure warning
記憶壓力警告
prompt 超過警告門檻（例如視窗的 70%）時插入的系統訊息，讓模型趁逐出前先存重點（第 2.2 節）。
recall storage
回憶儲存
存所有訊息原文的資料庫；佇列管理器寫入，模型用函式分頁搜尋（圖 3）。
archival storage
封存儲存
讀寫都靠函式的資料庫，存任意長度的文字；文件實驗把整批文件放在這裡（圖 3）。
function executor
函式執行器
把模型的輸出解析成函式呼叫、驗證參數、執行，再把結果與錯誤回饋給模型（第 2.3 節）。
pagination
分頁
檢索結果一次只回一頁，避免撐爆視窗；模型可以帶頁碼再查下一頁（第 2.3 節、圖 6）。
event
事件
觸發推論的輸入：使用者訊息、系統訊息、使用者的動作、定時事件（第 2.4 節）。
function chaining
函式連鎖
帶 request_heartbeat=true 的呼叫做完後立刻再推論；沒帶就是 yield，等下一個事件（第 2.4 節）。
MSC
Multi-Session Chat
人類標註者扮演固定人設的多段對話資料集；每組五段，每段約十幾則訊息（第 3.1 節）。
DMR
深度記憶檢索
在第 6 段問一個只有前五段對話才答得出的問題，測一致性（第 3.1.1 節）。
ROUGE-L recall
ROUGE-L 召回率
依最長共同子序列算的召回率；DMR 用它抵銷回答比標準答案囉嗦的影響（第 3.1.1 節）。
LLM judge
LLM 評審
用 LLM 判斷回答對不對；DMR 的評審只要主題相同就算對，文件問答還要附上出處（附錄 6.1.2、6.1.5）。
SIM-1、SIM-3、SIM-H
開場白相似度
開場白和人設標籤（SIM-1、SIM-3）或人寫開場白（SIM-H）的相似度；原文稱 CSIM（表 3）。
nested KV retrieval
巢狀鍵值檢索
值可能也是鍵的鍵值查詢，要一層層查；140 組 UUID，約 8k tokens，層數 0 到 4（第 3.2.2 節）。
