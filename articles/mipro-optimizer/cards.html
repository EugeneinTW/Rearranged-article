每個 LM 模組各一段指令、K 個示範（這個程式 2 個模組、3 次 LM 呼叫）。看得到的訊號只有第 5 格的分數：前面寫出什麼查詢，沒有標準答案可以對。

最佳化後 · 圖上印的品質 40%
各有一條新指令加示範，例如「依脈絡與問題，寫一個簡潔的搜尋查詢」
既有的做法，為什麼用不上
單一呼叫的最佳化器
APE、OPRO、EvoPrompt 在字串上搜尋表現好的 prompt，但大多假設每次 LM 呼叫都有金標或評估指標；多階段程式裡，中間的呼叫兩樣都沒有。
第 1 節：這類工作大多不能直接用在多階段程式上。
DSPy 原本的最佳化器
能替多階段管線 bootstrap 示範，拿來最佳化 prompt、權重或兩者；但調不了多個 prompt 的指令。這篇補上的就是指令。
第 7 節：DSPy 只探索 bootstrap 強示範的最佳化器。
這篇只假設文字進出
不碰權重、不用 log 機率、中間步驟沒有標籤；
只要程式、指標與訓練輸入。Sordoni 等人的
變分推論要 token 的 log 機率，商用 API 給不了。
依指標的需要，再加上最終輸出的標籤。

13 / 13結論：先示範再指令
示範撐起大部分提升，指令補上規則
結論：MIPRO 同時調指令與示範，在七個設定裡的五個最有效；few-shot 示範很有力，有多條條件規則的任務少不了指令。下面三條原則是整理者從全文歸納的
原則 01
先把示範調好
多數任務裡，只調示範勝過只調指令；作者推論 bootstrap 的示範帶的是成功推理的資訊，不只是格式（第 09 卡）。
✗ 只寫指令、不放例子
✓ 先 bootstrap 示範，再挑組合
原則 02
規則藏在條件裡，
才輪到指令
HotPotQA Conditional 只調指令贏過只調示範；
但要從寫明規則的種子開始，
最佳化器還推不出完整規則（第 10、12 卡）。
✗ 期待最佳化器自己發明規則
✓ 把規則寫進種子指令
原則 03
提案與分功勞，
分開來做
提案 LM 讀過資料、程式與示範才寫候選；
代理模型在小批次上挑組合（第 04、07 卡）；
該給提案 LM 看什麼，因任務而異（第 11 卡）。
