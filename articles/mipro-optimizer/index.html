MIPRO · OPTIMIZING MULTI-STAGE LM PROGRAMS · 圖卡＋教材整合版

只有最後一個分數， 也能調每個模組的 指令與示範MIPRO：提案之前先讀資料與程式， 挑組合交給貝氏代理模型

多階段的 LM 程式把好幾次 LM 呼叫接成管線，每一步的 prompt 都要一起有效，平常靠人工反覆試錯。這篇論文研究怎麼交給演算法：沒有各模組的標籤，也拿不到梯度，只有最後一個評估分數。作者把問題拆成兩個難處，一是提出少數好的候選，二是把整體分數的功勞分回各個模組，各提出三種策略，組成 MIPRO 等最佳化器，在七個任務上用 Llama-3-8B 比較，歸納出何時該調示範、何時該調指令。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

這一講比三種調法，這篇只調 prompt

Stanford CS 329Z 第 5 週「Optimization」那一講，從 prompt 一路講到微調：prompt 最佳化（GEPA、MIPROv2、OPRO、TextGrad）、test-time compute、LoRA／QLoRA、蒸餾、RLHF／DPO，最後問什麼時候該調 prompt、調權重，還是調推論算力。這篇 2024 年的論文是同一講的選讀，只處理第一種。

這一講的必讀是 GEPA 與 test-time compute 各一篇，另一篇選讀是 BetterTogether。講題列的名字是 MIPROv2，這篇論文提出的最佳化器叫 MIPRO；論文全文沒有出現 MIPROv2 這個名字，所以這一頁不談兩者的關係，只記下講題列了 MIPROv2。講題裡的其他方法，論文提到的只有 OPRO：作者把它推廣到多個模組，當成對照組（第 5 章）。GEPA、TextGrad，以及後面幾種調權重、調推論算力的方法，論文都沒有談到。

放在這一講裡看，這篇的條件很清楚：只動 prompt，不動權重。作者假設拿不到 LM 的權重與 log 機率，中間步驟也沒有標籤，手上只有程式本身、一個要最佳化的指標與一批訓練輸入。要調的是每個模組 prompt 裡的兩樣東西：一段自由格式的指令，以及幾個 few-shot 示範。引言提到 DSPy 的最佳化器能最佳化 prompt、權重，甚至兩者一起，那裡引用的是 Soylu、Potts、Khattab（2024）的〈Fine-tuning and prompt optimization: Two great steps that work better together〉（整理者的補充：從標題看，應是同一講另一篇選讀 BetterTogether 談的那篇）。

這篇和本站整理過的 DSPy 論文（arXiv 2023、ICLR 2024，這篇論文引作 Khattab 等人 2024）有三位共同作者：Omar Khattab、Matei Zaharia、Christopher Potts（整理者依兩篇的作者名單對照）。論文也把自己放在 DSPy 的延長線上：它沿用 DSPy 的程式模型，第 5 章的基線 Bootstrap Random Search 就是 DSPy 原本的最佳化器，附錄 F 說它推廣自 DSPy 的 BootstrapFewShotWithRandomSearch；新的最佳化器與基準也釋出在 DSPy 裡。依相關工作一節的說法，DSPy 的最佳化器只 bootstrap 示範，這篇補上的是多個模組的指令。

Krista Opsahl-Ong 與 Michael J Ryan 是同等貢獻的第一作者，七位作者來自 Stanford、Basis、KTH 皇家理工學院與 UC Berkeley。arXiv 的 v1 在 2024 年 6 月 17 日貼出，這一頁依的是 2024 年 10 月 6 日的 v2；abs 頁的註記寫 EMNLP 2024。實驗的任務模型是 Llama-3-8B，寫指令的提案模型多半是 GPT-3.5，數字只對那時的設定成立。

先把幾個名詞對齊

  • 多階段程式：把一個任務拆成幾次 LM 呼叫，前一步的輸出接到後一步，中間可以穿插檢索之類的工具。圖 1 的兩跳檢索就是一例。

  • 指標（metric）：判斷一次輸出好不好的函式，例如答案是否完全相符。這篇的指標只看程式最後的輸出。

  • 小批次（minibatch）：每次只拿訓練集裡隨機的一小批來打分，而不是跑完整個訓練集。

引言從現況講起。用 LM 解複雜任務，常要套用 Chain of Thought 這類 prompting 技巧，再把它們串成多階段的管線；作者把這種東西叫作 LM 程式（Language Model Program）。它們靠系統性的組合與工具使用持續推進 NLP 任務，但今天多半還是靠「prompt engineering」做出來：人工反覆試錯，寫出能逼某個特定 LM 在某條特定管線裡做好每一步的 prompt。

自動化的 prompt 最佳化器已經有了，例如 APE、OPRO、EvoPrompt，它們在字串上搜尋表現好的 prompt。問題是這些方法大多用不到多階段的 LM 程式，因為個別的 LM 呼叫沒有金標，也沒有評估指標。DSPy（Khattab 等人，2024）把每次 LM 呼叫的指令、示範與權重都當成可以對任何指標最佳化的參數，它的最佳化器能替多階段管線產生示範，拿來最佳化 prompt、權重或兩者，但調不了多個 prompt 的指令。摘要用一句話描述這篇的設定：

"without access to module-level labels or gradients" 「拿不到模組層級的標籤，也拿不到梯度」：摘要對問題設定的描述。

作者刻意把假設放得很弱，和 DSPy 程式模型的抽象一致：不碰 LM 的權重，不用 log 機率，中間步驟也沒有手寫的指標或標籤。需要的只有三樣：LM 程式本身、一個要最佳化的指標，以及一批訓練輸入；依指標的需要，再加上最終輸出的標籤。圖 1 是一個兩跳檢索程式：寫搜尋查詢的模組跑兩次，每次檢索一批段落接進脈絡，最後由另一個模組寫答案；訓練集是問答對，指標是答案完全相符。最佳化器替每一步提出新指令、bootstrap 新示範，圖上印出的品質從 21% 變成 40%。

第 7 節把這個位置講得更完整。調字串 prompt 的研究有好幾路：梯度引導的搜尋、重排序的暴力搜尋、演化演算法、請另一個 LM 提 prompt，以及強化學習；其中 RL 的先前工作只改幾個字、改片語，或用在文生圖。DSPy 只探索 bootstrap 示範的最佳化器。Sordoni 等人（2023）處理疊起來的 LLM 呼叫，把聯合 prompt 最佳化當成變分推論，試了兩個簡單的層；但它要取得傳給 LM 的 token 的 log 機率，作者認為這個假設在只允許文字進、文字出的商用 API 上越來越難成立。相對地，這篇的最佳化器可以直接用在任意數量模組的任何 LM 程式上。

引言最後預告了發現與貢獻。發現有三個：最佳化 bootstrap 出來的 few-shot 例子，常是拿到最大提升的關鍵；帶條件規則的任務，最佳化指令變得更重要；指令與示範一起最佳化，通常最好。貢獻也有三個：把問題形式化，並列出提案與分功勞各三種策略的設計空間；釋出一個七個任務的基準；做出並評估一組最佳化器，其中 MIPRO 在基準的七個任務裡有五個勝過基線，最多高出 13% 的準確率。

背景

什麼叫「模組層級的標籤」

以圖 1 的程式為例（整理者的例子），模組層級的標籤是「第一跳該寫出什麼查詢」「第二跳該寫出什麼查詢」的標準答案。資料集通常不會標這些，只給問題與最終答案。所以每個模組的指令與示範，都只能透過最後的分數間接評估；第 2 章把這件事寫成「每個變數都是潛在的」，第 4 章講怎麼把分數推回各個模組。

形式上，LM 程式 Φ 由 m 個模組組成，每個模組用某個 LM，並由一個 prompt 模板定義；模板裡有幾個變數，也就是留給字串填的空格。例如 few-shot 問答的模板，可能有指令、示範、目標問題三種變數。把程式用到的所有變數集合記成 V，一個「全指派」就是把 V 裡每個變數都對應到一個字串，在這個指派下執行的程式記成 Φ 加上這個指派。

目標是找到一個全指派，讓程式在訓練集 D 上對指標 μ 的平均分數最高；訓練集有輸入，也可以附上標籤之類的 metadata。作者說這就是設計 LM 程式的人面對的問題，而它不可行，理由有五個：

1
字串沒有邊界每個變數可以是任何字串。
2
每個變數都是潛在的指標只在整個任務的層級給監督，V 裡沒有一個變數有自己的標籤。
3
沒有梯度拿不到 LM 的梯度或 embedding，排除了許多 RL 與 prompt tuning 演算法。
4
資料少設計系統的人手上的資料集通常很小。
5
預算少能拿來評估程式的 LM 呼叫次數也少。

所以作者只最佳化變數的一個子集：每個 prompt 有一個自由格式指令的變數，加上 K 個示範的變數，其餘變數固定成常數。求近似解的做法寫成 Algorithm 1：最佳化器先用訓練資料初始化，然後重複 I 次，每次提出一組指派、從訓練集抽 B 筆組成小批次、在小批次上執行程式並算平均分數、把分數交回最佳化器更新；迴圈結束後，由最佳化器取出它認為最好的一組指派，回傳套用這組指派的程式。

for k in range(I):
    assignment = M.propose(theta)            # 每個模組的指令與示範
    batch = sample(trainset, B)              # 抽 B 筆組成小批次
    score = mean(metric(program(assignment, x), meta) for x, meta in batch)
    M.update(assignment, score)              # 用觀察到的分數更新內部狀態
best = M.extract_optimized_sets()            # 取出最好的指派

作者說這個框架把 OPRO 與 APE 這類既有做法推廣到了 LM 程式上。每個最佳化器只要實作 Initialize、Propose、Update、ExtractOptimizedSets 四個方法，並維護一個會影響提案、在 Update 時更新的內部狀態。第 3 節的目標也從這裡來：盡量少呼叫程式（演算法的第 10 行），連帶也少抽提案（第 8 行）。後面幾章的每個最佳化器，都是這四個方法的一種實作。

第 3.2 節的出發點是：提出的指派可以組合成許多設定，要搜尋這個空間，就得辨認出特定選擇對 LM 程式表現的貢獻。作者提出並探索三種解法：貪婪（greedy）、代理模型（surrogate）與歷史（history-based）。

貪婪法一次只提出並評估單一階段的改動。它比較不會把錯誤歸給錯的階段，但沒有效率：改動只能一次套一個；有些階段的改動，要等其他階段先變好，才會反映在整體分數上。初步實驗裡，它沒有比其他做法有效，時間複雜度卻差很多。第 4.5 節的 CA-OPRO（coordinate ascent）走的就是這條路：逐一走過每個模組，用 Module-Level OPRO 的提案函式提出 N 條指令，固定其他參數各自評估，換上目前最好的一條再做下一個模組，整個過程重複 D 次。作者從初步實驗判斷，它的表現抵不過它的沒效率，所以沒放進主要實驗。

代理模型法用貝氏學習，作者說它以能有效率地最佳化帶有多個潛在變數的函式著稱：代理模型從過去的評估學著預測不同參數組合的品質，讓之後的探索集中在搜尋空間裡有希望的區域。實作上用 Optuna 的 Tree-structured Parzen Estimator（TPE），它的多變量版本會模型化參數選擇之間的聯合貢獻，所以能一起最佳化程式的所有變數。缺點是它只能在一組固定的提案裡最佳化，過去評估學到的東西，不能拿來改進提案本身。

歷史法假設：給一個夠強的 LM 看過去評估的歷史，它就能自己分功勞，不需要明確的代理模型；提案 LM 理論上可以同時分功勞、同時提出改進的指令。做法照 OPRO：把評估過的指令與分數放進脈絡，讓提案 LM 輸出新指令。第 4.5 節分成兩種寫法。Module-Level OPRO 讓每個模組各看自己的歷史，隱含的假設是指派之間沒有相依、各模組的功勞相等；Program-Level OPRO 讓提案 LM 看完整的多階段軌跡，自己把任務分數分到各階段，假設 LM 讀了長歷史就能完成分功勞。作者直說這些都是很強的假設，而且歷史越長，裡面的資訊越可能遺失。實驗用的是 Module-Level OPRO，因為 Program-Level OPRO 比較複雜，也看不出額外的效益。

Module-Level OPRO 從 OPRO（Yang 等人）出發。OPRO 讓提案 LM 看提過的指令與它們的分數，隨時間學著提出更好的指令。要推廣到有 m 個模組的程式，作者先假設程式分數夠好地代表每一條指令的品質：程式雖然由 m 條指令參數化，仍假設這個分數足以反映每一條。四個方法是：

1
Initialize用一條種子指令參數化每個模組，評估一次。
2
Propose把得到的分數與第 i 個模組的指令交給提案 LM，替模組 i 寫一條新指令；m 個模組都做一次，用這 m 條新指令參數化程式，再評估。
3
Update每條指令連同這次的分數，加進各自模組的歷史；再用更新後的歷史跑一次 OPRO 子程序，產生下一組指令。
4
ExtractOptimizedSets迭代到上限後，回傳分數最高的那組參數化。

作者特別註明，每個階段的最佳化器只看得到模組層級的軌跡與代理分數，也就是整個程式的分數。附錄 F.2 還交代了一個簡化：OPRO 原論文每一步產生並評分一組候選指令，這裡每一步只產生一條。附錄 F 也說明了演算法的來歷：Bootstrap Demonstrations 推廣自 DSPy 的最佳化器，單模組 OPRO 推廣自 OPRO 論文對單一階段指令的做法，其餘的演算法都是這篇新提出的。

第 9 章的表 2 裡，Module-Level OPRO 還有一個去掉 grounding 的版本 −G：它的提案 prompt 只用原本 OPRO 論文裡的元件，也就是 few-shot 例子，加上之前提過的指令與分數。拿它和有 grounding 的版本比，就能看出第 3 章那些脈絡的用處（第 11 章）。

MIPRO 的全名是 Multi-prompt Instruction PRoposal Optimizer。作者提出用一個貝氏代理模型，在最佳化過程中明確學到任務層級的分數對模組層級參數（指令與示範）有多敏感。把分功勞和提案分開，提案 LM 就能只專心提案；分功勞與最後的選擇，事後由代理模型來做。

第二個設計是小批次。作者說貝氏最佳化以對雜訊穩健著稱，因為它把不確定性納入最佳化過程；所以每次迭代只在訓練資料的一個小批次上評估，不跑整個訓練集，能更有效率地探索與利用參數設定。四個方法是：

1
Initialize用第 3 章的 bootstrap 與 grounding，替每個模組各準備 N 組 few-shot 例子與 N 條指令。代表「每個模組選哪組示範、哪條指令」的潛在類別變數，一開始是均勻的先驗。
2
Propose用 TPE 的取樣規則，選出這一次要用的指令與 few-shot 例子，參數化程式。
3
Update在隨機抽的 B 筆小批次上替這個程式打分，用分數更新估計器對參數品質的先驗。
4
ExtractOptimizedSets每 S 步，把各次試驗平均分數最高的候選參數化，拿到完整的訓練集上評估；最後回傳完整評估分數最高的那一組。

附錄 F.5 用另一套記號寫同一個演算法：一開始替每個模組提出 T 條指令、bootstrap K 組示範，全部事先做好；Update 讓好候選的權重上升、壞候選的權重下降；ExtractOptimizedSets 則寫成替每個潛在變數選出機率最高的候選，在驗證集上評估後回傳。正文第 4.3 節說最後的評估用完整的訓練集，附錄說驗證集，這一頁兩種都記下，不替作者選。

背景

小批次為什麼行得通

整理者的讀法：一次小批次的分數雜訊很大，單看一次會誤判；但代理模型把許多次試驗的分數一起累積在它對每個候選的估計裡，同一條指令被抽到很多次，雜訊就被平均掉。第 4.3 節只說貝氏最佳化對雜訊穩健；第 5.2 節補充，同樣的預算換成小批次，實際的試驗次數會多很多，附錄 B.2 的例子是 50 次完整評估約等於 300 次小批次試驗。

一種成對資料的無母數檢定：看兩個方法在同一批題目上的分數差，是不是一致地偏向其中一邊。表 2 的粗體就是依它決定的，第 9 章會說明。

思考題 · 02

你手上的預算，夠跑幾次完整評估？

一次完整評估要把訓練集的每一筆都跑過程式，每一筆又可能呼叫好幾次 LM。

先算一次完整評估要呼叫幾次 LM（訓練筆數乘上每筆的 LM 呼叫數），再乘上試驗次數。預算很緊時，小批次的方法能用同樣的呼叫數試更多組合；第 12 章的教訓 5 也猜測，預算很低時 0-Shot MIPRO 可能最好。

HoVer 要替未查證的宣稱做三跳檢索：程式在寫查詢、檢索維基百科、用結果寫下一個查詢之間交替三次（附錄 E.3 的程式每跳取 7 篇），用金標文件算召回率；表 1 寫 Recall@21，正文寫 Retrieval@21。作者只留下需要 3 個支持事實的例子，但不同的事實可能出自同一篇文件，所以有些題目不到三跳就能找齊：訓練集約 67%、測試集約 83% 是三跳，其餘是兩跳。他們建議後續研究只留下真正需要三跳的題目。

關鍵觀念 · 一

示範教的不只是格式

教訓 1 最後有一句推論：好的 bootstrap 例子提供的，是關於「成功的推理行為」的資訊，不只是教會任務的格式。證據是不同的 few-shot 組合之間表現差很多；如果示範只是在示範格式，哪一組應該都差不多。

整理者的讀法：bootstrap 留下的是整條程式一起答對的那幾次執行，示範裡帶著那次的推理過程與中間步驟。這也說明了為什麼 MIPRO 要替每個模組準備好幾組示範、再讓代理模型挑，而不是隨便放幾個例子。

提醒

「五／七」和 13% 怎麼對

摘要、引言與結論都說 MIPRO 在七個任務（或設定）裡的五個勝過基線，最多高出 13% 的準確率。整理者對表 2 的測試欄核對：按平均分數，MIPRO 在 ScoNe、HotPotQA、HoVer、HotPotQA Conditional、Iris-Typo 五個任務最高，其中 HotPotQA 的 46.4 和 Bayesian Bootstrap 的 46.2、Bootstrap RS 的 45.8 差距不顯著；照教訓 2 的統計檢定算，則是扣掉三個例外剩下的四個。13% 論文沒有交代是和哪個最佳化器、在哪個任務上比；測試欄裡 MIPRO 比 Bootstrap RS 高最多的是 HotPotQA Conditional，23.3 對 10.4，差 12.9 個百分點（整理者算的），但論文沒有說 13% 指的就是這一格。

1

2
模型固定提案 LM 與任務 LM 都固定，換成別的模型時方法是否一樣有效，要再驗證。
3
推不出規則沒有手寫的種子 prompt，推斷複雜任務規則的能力有限；grounding 給的資料細節與任務例子，可能不足以外推出一整套規則。作者鼓勵研究不靠手寫輸入學到任務的動態。
4
基準還不夠已盡量涵蓋多樣的任務與程式，但更複雜的任務與程式還有很多要學，改進基準本身就是方向。

作者的收尾很短：他們形式化了 LM 程式裡最佳化 prompt 的問題，指出兩個關鍵的難處，一是提出一小組高品質的 prompt，二是最佳化過程中的分功勞；用三種提案策略與三種分功勞策略處理它們，並在一個新的、任務多樣的基準上，探索了一組有代表性的最佳化器。發現是：最佳化 few-shot 示範非常有力，但對有多條條件規則的複雜任務規格，指令最佳化可能不可或缺；最後，用 MIPRO 同時最佳化指令與示範，在七個設定裡的五個是最有效的做法。

整理者的讀法

放回這一講：什麼時候調 prompt

下面是整理者的連結，論文沒有這樣講。這一講問的是何時調 prompt、調權重、調推論算力；這篇只回答第一個問題裡面的細節：同樣是調 prompt，先調示範通常收穫最大，規則藏在條件裡時要調指令，而且從寫明規則的種子開始，兩者一起調時把提案和分功勞分開。權重與推論算力這篇沒有碰；引言提到 prompt 與權重可以一起最佳化時，引用的是 Soylu 等人（2024），序章提過它的標題。

一定要有中間步驟的標籤嗎？
不用。第 1 節說只需要 LM 程式、一個要最佳化的指標與一批訓練輸入；依指標的需要，再加上最終輸出的標籤。
預算大概要多少？
第 5.2 節與附錄 B.2：依任務 20 到 50 次在訓練集上完整評估的試驗；HotPotQA 與 ScoNe 的 50 次約等於 300 次小批次試驗。每個方法在每個任務上跑 5 次。
只調指令夠嗎？
多數任務不夠。教訓 1 說連 Bootstrap RS 都在「除了一個以外」的任務上勝過最好的只調指令最佳化器；例外是 HotPotQA Conditional 這種有條件規則的任務（第 10 章）。

LM program
LM 程式

module
模組

指令

demonstration
示範
prompt 裡的輸入輸出例子；這篇的示範都由 bootstrap 產生。
proposer LM
提案 LM
負責寫候選指令的 LM；實驗多半用 GPT-3.5。
task LM
任務 LM

Algorithm 1
最佳化框架
Initialize、Propose、Update、ExtractOptimizedSets 四個方法組成的迴圈，每次在 B 筆小批次上打分（第 2 節）。
proposal
提案
提出少數高品質候選的難處；作者的三種策略是 bootstrap 示範、grounding、學著提案（第 3.1 節）。
credit assignment
分功勞

bootstrap 示範

grounding
替提案補脈絡

tip
寫 prompt 的建議

learning to propose
學著提案

代理模型
從過去的評估學預測參數組合品質的貝氏模型；只能在固定的候選裡挑。
