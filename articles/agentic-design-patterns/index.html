AGENTIC DESIGN PATTERNS · 圖卡＋教材整合版

進步來自工作流， 不只來自下一代模型Andrew Ng 的四種 agent 設計模式，五封信併成一頁

2024 年 3 月，Andrew Ng 在 The Batch 寫下一個判斷：這一年 AI 的進步會來自 agent 工作流，可能比下一代基礎模型帶來的還多。他用 HumanEval 的數字撐這個判斷，把當時百花齊放的 agent 做法歸成四種設計模式，接著用四封信逐一展開。這一頁把五封信合併整理：先講為什麼，再講四種模式各自的機制與成熟度。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

先讀這五封信，後面的框架才有座標

Part 1 是 CS 329Z 第一週的選讀。它只有六百字，四種模式各一句；機制都在後面四封信裡，所以這一頁把五封一起整理。

2024 年初，agent 這個詞正在從研究圈擴散到所有做 AI 應用的人身上。開源工具、論文、demo 每週都在增加，Ng 自己說這令人興奮也令人困惑。他的回應是一張很粗、但很好記的分類：Reflection、Tool Use、Planning、Multi-agent collaboration。這四個名字後來變成很多人談 agent 時的預設座標，也是這門課第一週把它排進讀物的原因。

讀的時候要記得兩件事。第一，Ng 是用實務者的口吻在寫：「在我的應用裡可靠」是經驗，不是 benchmark；哪一種模式成熟、哪一種難預測，都是他 2024 年春天的觀察。第二，這五封信之後，function calling、MCP、各種 agent 框架都變了很多，但四種模式描述的是做法的形狀，形狀沒有變。課程第四週會用更細的分類（workflows 對 agents、ReAct、plan-and-execute）重講一次；先有 Ng 這一版，後面那些才有對照。

給初學者

先把四個名詞對齊

  • zero-shot（零樣本）：直接叫模型一次生成最終答案，途中不修改。這裡指的是「一口氣寫完」的用法，不是指有沒有給範例。
  • agentic workflow（agent 工作流）：對模型呼叫很多次，每一次做一小步，讓它有機會修改、查資料、用工具。
  • HumanEval：一組寫程式的測驗題，看模型能不能把函式寫對；Ng 用它比較零樣本與 agent 工作流。
  • design pattern（設計模式）：一種反覆出現、可以命名的做法；四種模式可以各自單獨用，也可以疊起來。
四種模式不是四個步驟，是四種可以各自單獨用、也可以疊起來用的做法。 整理者的引言

Chapter 01 · Zero-shot vs. iterative workflows

零樣本是一口氣寫完，工作流是反覆修改

今天多數用法是叫模型一次生成最終答案、途中不回頭。Ng 的比喻是寫作文不准按退格鍵；agent 工作流則讓模型像人一樣多繞幾次。

圖卡 02 / 09零樣本一口氣寫完，工作流反覆修改
零樣本是一口氣寫完，工作流是反覆修改
Ng 的比喻：叫人從頭到尾打完一篇作文、不准按退格鍵，還要求高品質。模型在這種條件下已經做得很好，但讓它多繞幾輪會好很多

每一輪都在改上一輪的產物；人寫好文章也是這樣。原文的五步後面寫著「and so on」：這只是例子，工作流可以更長。
一次生成：品質全押在第一次輸出
沒有機會發現自己站不住的論點、砍掉多餘的內容；想再提升，只能等更強的模型。
原文的評價仍是正面的：即使如此，模型的表現已經令人驚豔。
反覆修改：每一輪都把弱點修掉一些
大綱、查資料、初稿、審、改，各是一次呼叫；和人寫作一樣，迭代把品質往上推，結果比單次生成好很多。
後面四種設計模式，都是把這個「多繞幾輪」系統化。
注意：五個步驟是原文舉的例子；左邊「交出唯一的一版」是整理者對零樣本的畫法，原文只說它逐 token 生成、不修改。

Ng 先描述現況：我們大多用零樣本的方式用模型，叫它逐個 token 生成最終輸出，中間不修改。他的比喻是要求一個人從頭到尾打完一篇作文、不准按退格鍵，還要求高品質。模型在這種條件下的表現已經令人驚豔，這一點他特別強調，因為後面的主張不是「零樣本很糟」，而是「還有很多可以拿」。

agent 工作流的做法是讓模型對同一份文件反覆處理。他舉的順序是這樣的：

1
排大綱先決定要講什麼、什麼順序。
2
決定要不要查資料需要哪些網頁搜尋來補資訊。
3
寫初稿照大綱寫出第一版。
4
讀初稿找弱點挑出站不住的論點、多餘的內容。
5
依弱點修改然後視情況再來一輪。

這個流程對人類作者是理所當然的：好文章都是改出來的。Ng 的主張是同一件事對模型也成立，而且差距很大，迭代的結果比一次生成好很多。這句話在下一章有數字。

提醒

零樣本不是錯誤用法

原文對零樣本的評價是正面的：在不准修改的條件下，模型的表現已經超出預期。工作流要換的不是模型，是給模型的工作條件；很多任務一次生成就夠，反覆修改是為了品質要求高、或一次做不對的任務。

思考題 · 01

你現在哪一個用法是「一口氣寫完」？

想一個你天天在用的 prompt。如果讓模型多跑兩輪，先排大綱、後審稿，最可能改善的是哪一步的輸出？

先找輸出裡最常出錯的那一段，只針對它加一輪檢查，再決定要不要把整個流程拆開。

為什麼要分類
2024 年初，開源 agent 工具與論文同時暴增，Ng 說這令人興奮也令人困惑；四種模式是為了把這些工作放進同一個座標。
他的團隊 AI Fund 在很多應用裡用這四種。
注意：四種模式與定義來自 Part 1；「機制一句話」與成熟度評語是整理者從 Part 2 到 5 摘的，綠底兩列是 Ng 說可靠的兩種。

為什麼需要分類？Ng 的理由是實務的：開源 agent 工具和學術論文同時在暴增，做應用的人很難知道哪些是同一件事、哪些真的不同。他的團隊 AI Fund 在很多應用裡用這四種模式，所以他把它們寫成一個框架，希望讀者拿來當座標。四種模式在 Part 1 裡各只有一句定義：

Reflection

模型檢查自己的輸出

看自己剛才做的東西，找出可以改進的地方，然後改。

Tool Use

模型呼叫外部函式

網頁搜尋、執行程式、任何函式，用來蒐集資訊、採取行動、處理資料。

Planning

模型自己排步驟

想出一個多步驟的計畫並執行它：先大綱、再查資料、再寫初稿。

Multi-agent

多個 agent 分工

拆任務、討論、辯論，得到比單一 agent 更好的答案。

後面四封信各展開一種，也各自帶了 Ng 對成熟度的評語。Reflection 與 Tool Use 兩種，他說在自己的應用裡可以相對可靠地運作；Planning 與 Multi-agent 能讓 agent 做更多事，但比較不成熟、比較難預測。這個判斷貫穿後四封信，值得先記住再往下讀。

背景

和課程後面的分類怎麼對

CS 329Z 第四週用的是「workflows 對 agents」的分類：步驟固定的叫 workflow，由模型自己決定流程的叫 agent。對到 Ng 的四種：固定次數的 Reflection 迴圈和 Tool Use 多半是 workflow；Planning 是讓模型決定流程，就是 agent 那一側；Multi-agent 兩邊都有。

Chapter 04 · Reflection（Part 2）

Reflection 是把「你再檢查一次」自動化

你在聊天視窗裡對模型說「這裡不對，改一下」會得到更好的答案。Reflection 就是把這句話交給模型自己說，然後帶著批評重寫。

圖卡 05 / 09Reflection：自動化的「再檢查一次」
Reflection 是把「你再檢查一次」自動化
你在聊天裡對模型說「這裡不對，改一下」會拿到更好的答案；Reflection 把這句批評交給模型自己說，然後帶著批評重寫

夠好就輸出；
不夠好就回到批評

批評的 prompt
「這是為任務 X 寫的程式：[上一輪的程式]。請仔細檢查正確性、風格、效率，提出具體的改進建議。」第三次呼叫再把程式與建議一起給它，要求依建議重寫。三次呼叫，就是最小的 Reflection。
三種實作，從最簡單開始
① 自我批評：最快能上的版本
兩次額外呼叫：批評、重寫。Ng 說這是相對基本的模式，卻在他幾個應用裡帶來意外大的改善。
先固定跑一輪批評加一輪重寫，看輸出有沒有變好。
② 加工具評估：讓批評有依據
程式跑幾個單元測試看結果對不對；文字上網查證；再把找到的錯誤交給模型反思、提出改法。
批評從「感覺」變成「證據」。
③ 兩個 agent：一個生成、一個批評
用多 agent 框架實作：一個 prompt 負責產出好結果，另一個負責建設性批評，兩者的對話把回應推高。
這也是 Multi-agent 模式最小的用法。
注意：Step 4 是原文說的可選加強；迴圈的畫法是整理者的。原文推薦 Self-Refine、Reflexion、CRITIC 三篇進一步閱讀。

Ng 從一個大家都有的經驗講起：問模型、得到不滿意的回答、給它批評、拿到更好的第二版。既然人給批評有用，就把「給批評」這一步也交給模型。以寫程式為例，流程是這樣：

1
生成叫模型為任務 X 寫程式。
2
批評把程式丟回去，請它檢查正確性、風格、效率，提出具體的改進建議。
3

這個做法對寫程式、寫文字、回答問題都適用。Ng 接著給了兩個加強版。第一個是給模型工具來評估自己的輸出：程式就跑幾個單元測試看結果對不對，文字就上網查證，然後把找到的錯誤交給模型反思、提出改法。第二個是用多 agent 的框架實作：一個 agent 的 prompt 負責產出好結果，另一個負責建設性批評，兩者的對話把回應推高。

實作提示

從哪裡開始

Ng 的評價是：這是相對基本的模式，實作很快，卻在他幾個應用裡帶來意外大的改善，所以他鼓勵讀者在自己的工作裡試。最小的版本只要兩次額外呼叫；先固定跑一輪批評加一輪重寫，看輸出有沒有變好，再決定要不要加測試工具或第二個 agent。

模型是被微調、或用少量範例的 prompt 教會輸出這種字串的；字串的格式依實作而定，重點在有一段程式負責掃描、呼叫、回填。這也是為什麼「工具」可以是任何函式：搜尋網頁、Wikipedia、arXiv，寄信、讀寫行事曆，生成或解讀影像。做法是把每個函式的說明寫進脈絡，包括它做什麼、需要哪些參數，然後期待模型自己挑對的函式來用。

當工具多到數百個，脈絡放不下所有說明。Ng 說這時可以用啟發式規則挑出這一步最相關的子集放進脈絡，Gorilla 論文描述了這種做法；他把它比作 RAG 系統在文字太多時挑一部分放進脈絡的規則。

背景

工具使用是從電腦視覺長出來的

在 LLaVa、GPT-4V、Gemini 這類多模態模型普及之前，模型看不了圖，唯一的辦法是呼叫函式，例如叫一個物件辨識模型處理影像；所以早期很多 Tool Use 的工作是電腦視覺社群做的。GPT-4 在 2023 年中推出的 function calling 是通用實作的一大步，之後越來越多模型原生支援工具。

推薦閱讀三篇：Patil 等人的 Gorilla（2023）、Yang 等人的 MM-REACT（2023）、Gao 等人的 Chain-of-Abstraction（2024）。Ng 在這封信結尾說，Tool Use 和 Reflection 是他能相對可靠地在應用裡跑起來的兩種模式，值得先學。

思考題 · 02

你的系統裡，哪個問題模型現在是用猜的？

算術、查最新資料、讀一個檔案的內容：這些都是 transformer 猜不準、但一個函式可以確定回答的事。

先接一個工具就好。把它的說明寫清楚（做什麼、參數是什麼），然後觀察模型會不會在該用的時候選它。

Chapter 06 · Planning（Part 4）

拆不出固定步驟的任務，才讓模型自己排步驟

Planning 是讓模型自己決定要做哪幾步、什麼順序。很多工作流不需要它；需要它的，是那些你事先寫不出拆解方式的任務。

關鍵觀念 · 一

Ng 的「AI agentic moment」

他在一場現場 demo 展示一個有多種線上搜尋工具的研究 agent。私下測試時它一直用網頁搜尋，那天網頁搜尋的 API 卻回了限流錯誤。他以為 demo 要當場失敗，結果 agent 自己改用 Wikipedia 搜尋工具完成任務，那個工具是他給了卻忘記的。

他說很多人在 ChatGPT 剛出來時有過「原來 AI 能做到這樣」的時刻；看到 agent 用你沒預期的方式自主完成任務，是另一個這樣的時刻，而且很多人很快就會遇到。

Ng 也明說，很多 agent 工作流不需要規劃。例如讓模型反思並改進固定的次數，步驟順序是固定而確定的。規劃是給那些複雜到你無法事先寫出拆解方式的任務用的，這時讓 agent 動態決定要做什麼。代價是可預測性：他自己說 Planning 很強，但在他的經驗裡比 Reflection 與 Tool Use 不成熟，很難事先預測它會做什麼；他也相信這一塊會很快進步。

提醒

不要為了「像 agent」而加規劃

原文的順序很清楚：能用固定流程就用固定流程，拆不出固定步驟才讓模型排。固定流程可以測、可以重現；讓模型排步驟之後，同一個輸入兩次跑的路徑可能不同，測試與除錯的方法都要跟著換。

推薦閱讀：Wei 等人的 Chain-of-Thought（2022）、Shen 等人的 HuggingGPT（2023）、Huang 等人關於 LLM agent 規劃的綜述（2024）。

以寫軟體這種複雜任務為例，多 agent 的做法是把任務拆成不同角色的子任務：軟體工程師、產品經理、設計師、QA 工程師，各由一個 agent 負責。而每個 agent 可能只是對同一個模型下不同的 prompt，例如工程師 agent 的 prompt 是「你擅長寫清楚、有效率的程式，請寫程式完成……」。既然是同一個模型，為什麼要用多個 agent 這個抽象？Ng 給三個理由：

1

它有效

很多團隊用這個方法拿到好結果；AutoGen 論文的消融實驗顯示多個 agent 的表現優於單一 agent。

2

一次只顧一件事

有些模型能吃一百萬 token 的輸入，但真正理解長而複雜輸入的能力參差。角色 prompt 告訴模型現在該在乎什麼，例如「清楚有效率」而不是「可擴展又安全」，子任務才好各自最佳化。

3

給開發者的拆解框架

寫單機程式時我們把它拆成行程與執行緒；想多 agent 的角色是同一種抽象。Ng 說這一點可能最重要。

他用管理來類比：主管決定要請哪些角色，再把大專案拆成小任務分給不同專長的人。每個 agent 有自己的工作流、自己的記憶（記憶本身是另一個快速演變的題目：agent 要記住多少過去的互動，才能把下一次做好），可以向其他 agent 求助，也可以規劃、可以用工具。結果是大量的模型呼叫和 agent 之間的訊息傳遞，工作流可以變得非常複雜。他補了一句：管錯一個 AI agent 的代價，比管錯人低得多。

可以動手玩的東西

框架與一個範例專案

Ng 點名 AutoGen、Crew AI、LangGraph 這些框架提供了建多 agent 系統的方法。想玩一個完整的例子，他推薦 ChatDev：一個開源的「虛擬軟體公司」，一組 agent 各司其職把軟體做出來。他建議直接把 repo 拉下來跑，結果不一定是你要的，但常常會讓人驚訝它做得多好。

成熟度的評語和 Planning 一樣：多 agent 的輸出品質難以預測，尤其是讓 agent 自由互動、又給很多工具的時候；Reflection 與 Tool Use 仍是更可靠的兩種。推薦閱讀：Qian 等人的 ChatDev 論文（2023）、Wu 等人的 AutoGen（2023）、Hong 等人的 MetaGPT（2023）。AutoGen 也是 CS 329Z 第五週的必讀。

Reflection 可以用工具評估、也可以用兩個 agent 實作；多 agent 裡的每個角色又能規劃、能用工具。導入不是四選一，是決定先後；順序只是風險由低到高。
注意：三條原則來自五封信；五步順序是整理者依 Ng 對成熟度的評語排的，不是原文的建議清單。

把五封信壓成三句話。第一，進步先從工作流找：同一個模型換一種用法，HumanEval 上的差距比換模型還大。第二，Reflection 與 Tool Use 先上：一個只要多兩次呼叫，一個只要一段字串加後處理，兩種都能相對可靠地跑。第三，Planning 與 Multi-agent 要有心理準備：任務拆不出固定步驟才用規劃，需要多角色分工才用多 agent，兩者都強，但 Ng 自己也說結果難預測。

"perhaps even more than the next generation of foundation models" 「或許比下一代基礎模型帶來的還多」：Part 1 對 agent 工作流的判斷。

四種模式可以疊加。Reflection 可以用工具評估、也可以用兩個 agent 實作；多 agent 裡的每個角色又能規劃、能用工具。所以導入時不是選一種，而是決定先後。下面這個順序是整理者依 Ng 對成熟度的評語排的，原文沒有這份清單：先量零樣本的品質當基準；加 Reflection；接第一個工具並把說明寫清楚；任務拆不出固定步驟時再讓模型規劃；需要多角色時再拆成多個 agent。每一步都保留前一步，順序只是風險由低到高。

思考題 · 03

只能加一種模式進你現在的系統，你選哪一種？

用「風險最低、收益最明顯」來挑。哪一種不改變系統的結構、又最可能立刻看到差別？

Ng 的答案是 Reflection：實作最快，而且他自己被它的效果嚇到。第二個才是接一個工具。

Reference · 名詞速查

關鍵名詞與它們在五封信裡的位置

先列四種模式與基本用語，再列 Ng 推薦閱讀裡出現的方法名，方便對照第二章的圖。

zero-shot
零樣本
這五封信裡指「一次生成最終輸出、途中不修改」的用法；Ng 拿它當比較的基準。
agentic workflow
agent 工作流
對模型呼叫多次、每次做一小步的做法，讓模型有機會修改、查資料、用工具。
HumanEval
程式測驗集
一組要模型把函式寫對的測驗題；原文用它比較零樣本與 agent 工作流的正確率。
design pattern
設計模式
反覆出現、可以命名的做法。Ng 的四種：Reflection、Tool Use、Planning、Multi-agent collaboration。
Reflection
反思
模型檢查自己的輸出、提出批評、再依批評重寫；可加工具評估，也可用兩個 agent 實作。
Tool Use
工具使用
模型輸出特殊字串請求呼叫函式，程式呼叫後把結果塞回脈絡。
function calling
函式呼叫
模型原生支援輸出結構化的函式呼叫；Ng 提到 GPT-4 在 2023 年中推出的版本是通用實作的一大步。
Planning
規劃
模型自主決定要執行哪些步驟、什麼順序；給拆不出固定步驟的任務用。
Multi-agent collaboration
多 agent 協作
把任務拆給不同角色的 agent，角色可以是同一個模型的不同 prompt。
Self-Refine
自我修正
Madaan 等人 2023 年的論文，Reflection 的推薦閱讀之一：用自己的回饋反覆修正輸出。
Reflexion
語言式強化
Shinn 等人 2023 年的論文；第二章圖上 GPT-4 那一列的 Reflection 類方法。
CRITIC
工具互動式批評
Gou 等人 2024 年的論文，讓模型用工具驗證後自我修正。
Gorilla
大量 API 的模型
Patil 等人 2023 年的論文；工具太多時挑相關子集放進脈絡的做法出自這裡。
HuggingGPT
用 ChatGPT 調度模型
Shen 等人 2023 年的論文；原文借它的例子說明模型輸出計畫、軟體依序呼叫工具。
Chain-of-Thought
思維鏈
Wei 等人 2022 年的論文，Planning 的推薦閱讀：讓模型先寫出推理步驟。
AutoGen
多 agent 對話框架
Wu 等人 2023 年的論文與框架；Ng 引用它的消融實驗說明多 agent 勝過單 agent。
ChatDev
虛擬軟體公司
Qian 等人的開源專案：一組角色 agent 合作把軟體做出來，Ng 建議直接跑跑看。
MetaGPT
多 agent 元編程
Hong 等人 2023 年的論文；第二章圖上 GPT-4 那一列的 Multi-agent 類方法之一。
RAG
檢索增強生成
文字太多放不進脈絡時挑一部分放進去的做法；Ng 用它類比工具太多時挑工具子集。
LATS
Language Agent Tree Search
第二章圖上 Planning 類的方法，GPT-3.5 與 GPT-4 兩列都有它的點。
