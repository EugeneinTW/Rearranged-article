02 / 09零樣本一口氣寫完，工作流反覆修改
零樣本是一口氣寫完，工作流是反覆修改
Ng 的比喻：叫人從頭到尾打完一篇作文、不准按退格鍵，還要求高品質。模型在這種條件下已經做得很好，但讓它多繞幾輪會好很多
✗ 零樣本：一次生成
✓ 工作流：多次呼叫、反覆修改
拿到任務：寫一篇文章
從頭生成到尾，逐 token 輸出
途中不看、不改、不查
交出唯一的一版
像沒有退格鍵的打字：想到什麼寫什麼，錯了也只能往下走。原文說模型在這種條件下已經表現驚人，只是還有很多可以拿的。
① 排大綱
② 決定要查什麼資料
③ 寫初稿
④ 讀初稿，找弱點
站不住的論點、多餘的內容
⑤ 依弱點修改
再來一輪，直到夠好
每一輪都在改上一輪的產物；人寫好文章也是這樣。原文的五步後面寫著「and so on」：這只是例子，工作流可以更長。
一次生成：品質全押在第一次輸出
沒有機會發現自己站不住的論點、砍掉多餘的內容；想再提升，只能等更強的模型。
原文的評價仍是正面的：即使如此，模型的表現已經令人驚豔。
反覆修改：每一輪都把弱點修掉一些
大綱、查資料、初稿、審、改，各是一次呼叫；和人寫作一樣，迭代把品質往上推，結果比單次生成好很多。
後面四種設計模式，都是把這個「多繞幾輪」系統化。
注意：五個步驟是原文舉的例子；左邊「交出唯一的一版」是整理者對零樣本的畫法，原文只說它逐 token 生成、不修改。

換模型：多 18.9 個百分點
GPT-3.5 到 GPT-4，零樣本從 48.1% 到 67.0%。這是大家最熟悉的進步方式：等下一代模型，然後換上去。

換工作流：多 47 個百分點
同一個 GPT-3.5 包進 agent 迴圈，最高 95.1%，比自己的零樣本多 47 個百分點，也超過零樣本的 GPT-4。
模型沒換，換的是給它的工作條件。
所以 Ng 押注在工作流
他判斷這一年 agent 工作流帶來的進步，可能比下一代基礎模型還多；圖上每個點的顏色，就是後面四種設計模式。

04 / 09四種模式的地圖與成熟度
四種模式是一張地圖，不是四個步驟
每一種都可以單獨用、也可以疊在一起用；成熟度是 Ng 在後四封信裡對自己應用的觀察，不是 benchmark
模式
模型多做了什麼（Part 1 的定義）
機制一句話（Part 2 到 5）
Ng 的成熟度評語
Reflection
反思
檢查自己的輸出，找出可以改進的地方
生成 → 批評 → 帶回饋重寫，可重複；可加工具評估或兩個 agent
可靠；實作最快，效果意外地好
Tool Use
工具使用
呼叫外部函式：搜尋、執行程式、任何 API，用來蒐集資訊、行動、處理資料
輸出特殊字串 → 後處理呼叫函式 → 結果塞回脈絡
可靠；和 Reflection 一樣值得先學
Planning
規劃
自己想出並執行一個多步驟的計畫
輸出計畫字串 → 軟體依序執行工具；拆不出固定步驟的任務才需要
很強，但事前難預測它會做什麼
Multi-agent
多 agent 協作
多個 agent 拆任務、討論、辯論，得到比單一 agent 更好的答案
同一個模型用不同角色 prompt 拆任務；角色各有工作流與記憶，互相請求
輸出品質難預測，自由互動加多工具時尤其
四種是積木，可以疊加
Reflection 可以用工具評估、也可以用兩個 agent 實作；多 agent 裡的每個角色又能規劃、能用工具。
所以導入時是決定先後，不是四選一。
成熟度是經驗，不是數字
「在我的應用裡可靠」是 Ng 2024 年春天的觀察；Planning 與 Multi-agent 的效果，他自己也說難以事先預測。
他同時預期這兩種會快速成熟。
為什麼要分類
2024 年初，開源 agent 工具與論文同時暴增，Ng 說這令人興奮也令人困惑；四種模式是為了把這些工作放進同一個座標。
他的團隊 AI Fund 在很多應用裡用這四種。
注意：四種模式與定義來自 Part 1；「機制一句話」與成熟度評語是整理者從 Part 2 到 5 摘的，綠底兩列是 Ng 說可靠的兩種。
05 / 09Reflection：自動化的「再檢查一次」
Reflection 是把「你再檢查一次」自動化
你在聊天裡對模型說「這裡不對，改一下」會拿到更好的答案；Reflection 把這句批評交給模型自己說，然後帶著批評重寫
Step 1　生成
叫模型為任務 X 寫程式
（或寫文字、回答問題）
Step 2　批評
要它檢查正確性、風格、效率
模型批評自己
Step 3　重寫
把原輸出＋批評一起給它，
要求依批評重寫
Step 4　檢查（可選）
跑測試、查證，把錯誤交給模型
用工具評估
Step 5　更好的一版
夠好就輸出；
不夠好就回到批評
再來一輪：重複批評與重寫，可能再改善
批評的 prompt
「這是為任務 X 寫的程式：[上一輪的程式]。請仔細檢查正確性、風格、效率，提出具體的改進建議。」第三次呼叫再把程式與建議一起給它，要求依建議重寫。三次呼叫，就是最小的 Reflection。
三種實作，從最簡單開始
① 自我批評：最快能上的版本
兩次額外呼叫：批評、重寫。Ng 說這是相對基本的模式，卻在他幾個應用裡帶來意外大的改善。
先固定跑一輪批評加一輪重寫，看輸出有沒有變好。
② 加工具評估：讓批評有依據
程式跑幾個單元測試看結果對不對；文字上網查證；再把找到的錯誤交給模型反思、提出改法。
批評從「感覺」變成「證據」。
③ 兩個 agent：一個生成、一個批評
用多 agent 框架實作：一個 prompt 負責產出好結果，另一個負責建設性批評，兩者的對話把回應推高。
這也是 Multi-agent 模式最小的用法。
注意：Step 4 是原文說的可選加強；迴圈的畫法是整理者的。原文推薦 Self-Refine、Reflexion、CRITIC 三篇進一步閱讀。
06 / 09Tool Use：特殊字串加後處理
工具呼叫是一段特殊字串加一個後處理
模型不會自己上網或算數；它被微調或用少量範例教會輸出像 {tool: …} 的字串，程式掃到就呼叫函式，把結果當新的脈絡再給模型
網頁搜尋
「評論者最推薦哪台咖啡機」→ {tool: web-search, query: …}，下載網頁當脈絡
程式執行
「100 元 7% 複利 12 年」→ 交給 Python 算 100 * (1+0.07)**12，不用 transformer 猜

更多函式
查 Wikipedia、arXiv；寄信、讀寫行事曆；生成或解讀影像。每個函式的說明與參數都寫進脈絡
工具太多時，脈絡放不下
有系統接上數百個工具，說明全放進脈絡放不下；用啟發式規則挑出這一步最相關的子集（Gorilla 論文的做法）。
Ng 說這和 RAG 挑文字子集是同一個道理。
格式不重要，後處理才重要
字串長什麼樣依實作而定；重點是有一段程式負責掃描、呼叫、回填。GPT-4 在 2023 年中推出的 function calling 是通用實作的一大步。
之後越來越多模型原生支援工具。
早期的工具是給模型「眼睛」
在 LLaVa、GPT-4V、Gemini 之前模型看不了圖，電腦視覺社群靠呼叫物件辨識這類函式讓模型處理影像；工具使用從那裡長出來。
今天的用法已經遠超過搜尋與執行程式。

07 / 09Planning：模型自己排步驟
拆不出固定步驟的任務，才讓模型排步驟
Planning 是讓模型自己決定要做哪幾步、什麼順序；原文借 HuggingGPT 的例子：看一張男孩的照片，畫一個同樣姿勢的女孩
目標
畫一個和照片裡男孩
同樣姿勢的女孩
模型產生計畫
拆成兩步，輸出結構化字串
模型決定步驟
步驟 1：偵測姿勢
呼叫 pose-detection
image.jpg → temp1
步驟 2：依姿勢畫圖
呼叫 pose-to-image
temp1 → final.jpg
結果
final.jpg
軟體照計畫執行
計畫字串
{tool: pose-detection, input: image.jpg, output: temp1} {tool: pose-to-image, input: temp1, output: final.jpg}。這段字串觸發軟體依序呼叫兩個工具；模型是被微調或用少量範例教會輸出它的。原文說這是簡化的示意，HuggingGPT 實際的格式不同。
什麼時候不需要、什麼時候需要、代價是什麼
① 不需要：步驟固定的流程
例如讓模型反思並改進固定的三次；步驟順序是確定的，不用模型決定。原文說很多 agent 工作流根本不需要規劃。
能用固定流程就用固定流程，它可以測、可以重現。
② 需要：事先寫不出拆解方式
研究一個題目：拆子題、查資料、整合、寫報告，哪幾步、什麼順序看題目而定；這時讓模型動態決定要做什麼。
Ng 的研究 agent 就是這一種。
③ 代價：難預測，也會給你驚喜
Ng 的 demo 現場搜尋 API 被限流，agent 自己改用他忘了給的 Wikipedia 工具完成任務。他說 Planning 很強，但事前很難預測它會做什麼。
成熟度低於 Reflection 與 Tool Use；他預期會快速進步。
注意：五格裡的例子與計畫字串是原文的簡化示意；原文推薦 Chain-of-Thought、HuggingGPT、Huang 等人的規劃綜述三篇。
08 / 09Multi-agent：給開發者的拆解框架
多個 agent 是給開發者的拆解框架，不是多個模型
寫一個軟體，拆成工程師、產品經理、設計師、QA 幾個角色，各自負責子任務；角色可以都是同一個 LLM，只是 prompt 不同
任務：寫一個軟體
拆成幾個角色的子任務；角色是設計時就定好的
軟體工程師
prompt：你擅長寫清楚、有效率的程式
產品經理
同一個模型、另一段角色 prompt；有自己的工作流
設計師
有自己的記憶；可以向其他角色求助
QA 工程師
角色本身也能規劃、也能用工具
整合成交付物
角色之間互相請求、傳訊息，大量的模型呼叫
為什麼要這個抽象
同一個 LLM 也值得拆成多個 agent。Ng 的三個理由：一、有效；二、一次只顧一件事表現較好；三、給開發者一個像行程與執行緒那樣的拆解框架。實線框表示角色是設計時定的，不是跑的時候才決定。
一、它有效
許多團隊用這個方法拿到好結果；AutoGen 論文的消融實驗顯示，多個 agent 的表現優於單一 agent。
AutoGen 也是 CS 329Z 第五週的必讀。
二、一次只顧一件事
長脈絡能吃一百萬 token，但真正理解長而複雜輸入的能力參差；角色 prompt 告訴模型現在該在乎什麼，子任務才好各自最佳化。
「清楚有效率」和「可擴展又安全」是不同的要求。
三、開發者的拆解框架
像把程式拆成行程與執行緒，也像主管決定要請哪些角色、怎麼分工。Ng 說這一點可能最重要；管錯一個 AI agent 的代價比管錯人低得多。
框架：AutoGen、Crew AI、LangGraph；範例：ChatDev。
注意：四個角色是原文的例子，「整合」那一格是整理者補的，原文只說各角色各做子任務並互相請求；原文推薦 ChatDev、AutoGen、MetaGPT 三篇。
09 / 09先用成熟的兩種，再試難預測的兩種
先用成熟的兩種，再試難預測的兩種
五封信讀完，Ng 的建議其實很保守：Reflection 與 Tool Use 在他的應用裡可靠；Planning 與 Multi-agent 能做更多，但事前難預測
原則 01
進步先從工作流找，
不是等下一代模型
同一個 GPT-3.5，零樣本 48.1%，進 agent 迴圈最高 95.1%；換成 GPT-4 只到 67.0%。Ng 據此押注這一年的進步來自工作流。
數字是 HumanEval，來自多個研究團隊的結果。
原則 02
Reflection 與 Tool Use 先上
兩種都能相對可靠地在應用裡運作：Reflection 只要多兩次呼叫，Tool Use 只要一段字串加後處理。Ng 說這兩種值得先學。
Reflection 實作最快，效果意外地好。
原則 03
Planning 與 Multi-agent
要有心理準備
任務拆不出固定步驟才用 Planning；需要多角色分工才用 Multi-agent。兩者都很強，但 Ng 自己也說結果難預測。
他預期這兩種會快速成熟。
一條導入順序：風險由低到高，每一步都保留前一步
1　量零樣本基準
先知道一次生成現在有多好
2　加 Reflection
批評一次、重寫一次
3　接第一個工具
把函式的說明與參數寫清楚
4　需要時才 Planning
拆不出固定步驟再讓模型排
5　需要時才 Multi-agent
多角色分工，接受不可預測
四種是積木
Reflection 可以用工具評估、也可以用兩個 agent 實作；多 agent 裡的每個角色又能規劃、能用工具。導入不是四選一，是決定先後；順序只是風險由低到高。
注意：三條原則來自五封信；五步順序是整理者依 Ng 對成熟度的評語排的，不是原文的建議清單。
