EVALGEN · VALIDATING VALIDATORS · 圖卡＋教材整合版

評分的 LLM， 誰來驗證？EvalGen：用少量人工評分挑出評估器， 並發現標準會隨評分漂移

用 LLM 評估 LLM 的輸出已經很普遍，但評分用的 LLM 和被評的一樣會出錯。這篇 2024 年的論文做了 EvalGen：LLM 建議評估標準、替每條標準寫出幾個候選斷言，使用者在等待時替一部分輸出按好或壞，系統依和人評的一致程度挑斷言。作者先離線和全自動的 SPADE 比較，再請九位業界從業者試用，發現人要有標準才能評分，標準卻是在評分中才定下來。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

少量的人工評分，決定評估器可不可信

Stanford CS 329Z 第 7 週「Data Selection & Quality」那一講（Data for Agentic Systems 分區），談怎麼找出資訊量最大的資料、怎麼篩選與挑選、怎麼做小而精準的 benchmark、怎麼標註、怎麼評估品質，以及怎麼從 agent 的執行軌跡建資料集。這篇論文是這一講的必讀，它把同一組問題搬到評估器身上。

同一講的另一篇必讀是 SWE-smith，選讀是 LIMA。這篇的對象是評估器：拿來判斷 LLM 輸出好壞的那些檢查。評估器越來越常是另一個 LLM，寫一段評分 prompt，請它判斷某個輸出夠不夠簡潔、有沒有編造。作者的問題是，評分用的 LLM 和被評的 LLM 一樣會出錯，誰來驗證它？他們的做法是讓人評一小部分輸出，用這些評分去挑評估器；做出來的工具叫 EvalGen。

Chapter 01 · Introduction

評分用的 LLM，和被評的一樣會出錯

評估 LLM 輸出的指標越來越常交給另一個 LLM 判斷，但評分 prompt 和任何 prompt 一樣，措辭稍微一動結果就變，很多工具卻只請使用者相信分數。作者把這個缺口叫作「誰來驗證驗證者」。

引言從 LLM 會出錯講起：它會幻覺、會不照指令，輸出需要驗證。研究者與業界因此做了一批 prompt engineering 與稽核工具，讓人能更有系統地測試輸出。這些工具都需要指標，也就是一組自動替輸出打分的函式，通常每個都是回 true 或 false 的斷言。能用程式寫的就用程式寫；程式很難描述的品質，例如一段回應「夠不夠簡潔」，越來越常交給一個當裁判的評估用 LLM。

作者指出的問題是：評分的 LLM 和它評的 LLM 一樣不能盡信。評分 prompt 會對看起來微不足道的措辭或結構改動很敏感（作者引 Sclar 等人的研究），而很多現有系統沒有提供驗證評分品質的功能，等於請使用者直接相信。作者想回答的是：使用者怎麼一邊享受 LLM 協助評估的效率，一邊把評估器和自己要的東西之間的落差降到最低？

他們的回答是一個人機協作的做法 EvalGen，放在 prompt engineering 的情境裡，並把使用者的心力與等待時間當成實際的限制。流程有四步：LLM 依使用者的情境（例如正在測的 prompt）用自然語言建議評估標準，使用者可以修改；LLM 替每條標準產生一池候選斷言，可以是程式，也可以是輸出 true 或 false 的評分 prompt；候選產生的時候，系統請使用者替輸出按好（讚）或壞（倒讚）；這些評分用來自動挑出最貼近使用者偏好的斷言，最後的報告卡顯示選中的斷言和使用者的評分一致到什麼程度。

圖 1 把兩種管線並排（第 02 卡）。典型的管線是輸入進受測的 prompt 與 LLM，產生輸出，再交給程式或評估用 LLM 寫成的指標，得到測試結果，不滿意就回頭改。EvalGen 的管線在指標那一段多了一圈：候選標準、候選斷言與使用者的評分互相牽動，篩出選中的斷言，同時產生一份一致程度的報告卡。圖說特別說明，管線的輸入與輸出由更大的系統提供，不在這篇論文的範圍內。

作者說這個做法不綁在他們的介面細節上，可以延伸，例如用人的偏好回頭更新指標的實作，或改成針對每一條標準各問一次評分。EvalGen 的演算法改自 SPADE：一個從 prompt 的修改歷史全自動產生 Python 斷言的演算法。論文有兩個評估：以 SPADE 為基線的離線驗證（第 6 章），以及九位在正式環境用 LLM 的業界從業者參加的質性研究（第 7 到 12 章）。參與者可能受保密協議限制，所以研究用的任務改自一個真實的 LLM 管線；參與者可以自己決定先讓工具建議標準、自己手寫標準，或先評幾筆輸出再定標準。

引言也先預告了最重要的發現：人為了評分，需要先把標準說出來；評分的過程，又幫人把標準說出來。作者叫它標準漂移（第 10 章）。先評分的參與者，評下去之後還是會修改標準，甚至回頭改先前的分數。作者據此主張，評估助手要讓標準與實作能同時快速迭代；而且因為標準依附在輸出上，這件事得和模型更換、prompt 修改、串接管線的上游改動一起考慮。

Chapter 02 · Motivation and Related Work

工具幫人寫評估，卻很少幫人驗證

作者從三個方向說明缺口：現有的 prompt 工具大多支援 LLM 評估器，卻幾乎不幫人檢查它準不準；人本來就容易過度信任 AI，也容易從少數輸出過度概括；機器學習領域的對齊方法多半假設已有標籤與指標。

第 2 節先交代背景。ChatGPT 這類黑箱模型流行之後，prompt engineering 成了新的實務與研究領域；和它並行的是對模型行為的稽核，例如在發布前找出有害輸出的紅隊測試。這些工作帶出一批「LLM 維運」（LLMOps）工具，也帶出 prompt 模板、chain of thought、chain 這類新名詞。

自動化評估。評估 LLM 的行為時，使用者往往一次送出幾百到幾千個查詢，人工看不完，就用程式或另一個 LLM 建自動評估管線。作者把後者叫作 LLM 評估器，別的研究叫 LLM-as-a-judge 或 co-audit。軟體工程裡有同樣的問題：開發者寫一組斷言，通常是單元測試或回歸測試，用來確認程式正確、修改沒有把舊的 bug 帶回來。公開的工具 promptfoo 與 ChainForge 都讓使用者自己寫評估指標，程式與 LLM 評估器都支援；在 promptfoo 裡，使用者可以在設定檔寫一段 rubric，指定 LLM 怎麼評，例如「回應不帶歉意」。EvalLM 與 PromptsRoyale 這類原型也支援 LLM 評估器，常常只支援它，主要用來比較兩個 prompt。

作者說，這些 prompt 工具裡只有 EvalLM 提供計算 LLM 評估器和使用者期待之間一致度的方法，但這個功能只出現在它論文的設計一節，使用者研究裡沒有，EvalLM 在這篇寫作時也還沒公開。其他工具最好的情況是使用者自己回頭檢查評估器的輸出，最差的是把個別分數整個藏起來。就算不談對齊，光是替自訂的任務決定要評哪些指標，對從業者都很難（作者引 Parnin 等人的研究）。很多評估工具要使用者自己宣告關心的指標；SPADE 與 EvalGen 則用 LLM 依使用者管線裡的 prompt 提議自訂指標。

過度信任。工具幾乎不幫人驗證評估器的品質，作者認為這很危險，因為已有研究顯示人容易過度依賴、過度信任 AI 系統。一個例子是 MIT 的研究者在 arXiv 貼出預印本，宣稱 GPT-4 能拿下 MIT EECS 的考試；幾小時內就被 Chowdhuri 等人拆穿，問題之一是過度依賴 GPT-4 替自己評分。其他研究也發現，請 LLM 從一組回應中挑最好的，結果會一致地受排列順序影響；看起來無害的格式改動，也可能讓 LLM 的表現差很多。

過度概括。Zamfirescu-Pereira 等人發現，不熟 prompt engineering 的使用者會從單一失敗過度概括，把可能不錯的 prompt 丟掉，而不是看它整體的表現，即使介面支援有系統的測試。Arawjo 等人發現，就算是熟悉 LLM 的開發者與機器學習研究者，也很難把評估規模做大，架好自動評估管線之後仍然從少數輸出過度概括；他們歸納的三種 prompt engineering 模式裡，第二種「有限評估」的特徵就是使用者在「做評估的原型」，並建議未來的工作支援這件事。傳統機器學習也有類似的現象：Kocielnik 等人發現，準確率一樣的 AI 系統，展示不同的錯誤子集（例如偽陽性或偽陰性），人對準確率的觀感會差很多。

對齊的做法。HCI 領域研究互動式機器學習（iML）很久：使用者反覆挑訓練例子、標註資料、評估模型，介面讓這幾件事之間轉換得順，錯誤就少，結果也更符合期待；有些介面還用機器學習幫人擴大標註。作者提醒，套到 LLM 管線上有個關鍵差別：LLM 常常沒有特定的訓練資料，使用者只是拿自己想像中的輸入做原型，希望 prompt 能推廣。機器學習與自然語言處理領域對齊 LLM 與它的評估，多半靠訓練或微調，所有策略都重度依賴人找出好與不好的輸出範例：Liu 等人用依一致性、相關性這類標準標註過的輸出當 few-shot 例子，來校準 LLM 評估器；Khattab 等人的 DSPy 在給定指標後，自動試不同的 few-shot 例子與 LLM 改寫過的 prompt。也有研究鼓勵使用者用程式與自然語言寫斷言來引導輸出，但斷言要開發者自己寫，費時又容易出錯。作者更廣的觀察是：這些最佳化工具多半來自機器學習與自然語言處理，在有預先定義指標的 benchmark 上驗證，放到使用者自己特殊的任務上表現如何，還不清楚（例如 EvoPrompt、PromptBreeder、AutoCalibrate）。

為什麼這樣設計

人無法完全驗證 LLM 評估器

作者直說這個設計是在開發者的心力與驗證的嚴謹之間取捨。用 LLM 當評估器，本來就是為了省下人工評分；要完全確認它和人一致，唯一的辦法是請人評完全部輸出，那就失去意義了。所以關鍵想法是：請開發者評一部分輸出，用的是他們反正要等的時間。

第 4.1 節先交代拆法。和先前的評估助手一樣，EvalGen 把評估拆成標準與斷言：斷言是實作某條標準、對輸出回 true 或 false 的布林函式。標準由 LLM 依 prompt 產生，每條標準的多種候選實作也由 LLM 產生；使用者評分時，系統依候選和人評的一致程度排序。一致程度的大意是兩件事的組合：覆蓋率，也就是讓人覺得壞的輸出不通過的能力；誤判失敗率，也就是讓人覺得好的輸出不通過的程度，越低越好。正式定義在第 5 章。

和先前的做法相比，EvalGen 有兩處不同。第一，它要向使用者收評分，所以需要一套挑哪幾筆給人評的取樣政策。第二，SPADE 是離線的，一次解一個整數線性規劃，求出最佳的斷言集合；EvalGen 是線上（串流）的，逐步逼近最一致的集合。新候選一產生就立刻在所有 LLM 輸出上執行，明顯不行的直接淘汰，例如執行時出錯的 Python 函式。系統持續估計每個候選的選擇性（通過率），這個估計又回頭影響要挑哪幾筆給人評。架構分成三個元件：

1

標準建議

GPT-4 用自然語言提出各種二元的評估標準，例如回應長度或語氣。開發者從建議裡挑，也能自己加；每條標準都選要用純程式的函式，還是會呼叫另一個 LLM 的函式。

2

候選斷言的產生與執行

每條標準呼叫 GPT-4 一次，在標記之間串流寫出多個候選，可能是程式，也可能是交給 LLM 評的評分 prompt。每偵測到一個標記結尾，就解析出一個候選，交給執行器在管線輸出上跑。

3

評分取樣器

挑管線輸出給使用者按讚或倒讚。每收到一個評分，就更新每個候選的一致程度，再挑下一筆。

為什麼一次產生多個候選？作者說，候選多一點，至少有一個實作符合開發者期待的機率就高一點；而且 LLM 寫程式斷言偶爾會出錯，例如幻想出 Python 函式庫裡不存在的函式，得多準備幾個。使用者不想再評、或全部評完時，系統替每條標準挑出和評分一致程度最高的候選；使用者也可以設一個誤判失敗率的門檻，只挑不超過門檻的斷言。

第 4.2 節列出執行時持續更新的三個估計。候選斷言的選擇性，是它判一筆輸出通過的機率，每處理完「某個候選在某筆輸出上的執行結果」就調整一次。可能差的輸出的信心分數，估計一筆還沒被人評過的輸出品質差的可能性，依選擇性計算，執行新斷言或人評了一筆時都會更新。斷言的一致程度，每次人評一筆就重算。第 4.2 節把一致程度簡稱為「覆蓋率與誤判失敗率的調和平均」，附錄 A.3 的式子用的是覆蓋率與 1 − 誤判失敗率（第 5 章）。

附錄 A.1 說明信心分數的想法。選擇性就是通過率：常常判不通過的斷言（選擇性低）說明不了多少事，一條把每筆都判不通過的斷言，選擇性是 0，完全沒有鑑別力。反過來，一筆輸出如果被平常很少判不通過的斷言判不通過，它就更可能有問題。附錄 A.1 的式子把每條斷言的選擇性乘上它對這筆輸出的結果（通過記 1、不通過記 0），全部加總，當成信心分數 σ。

原文前後不一致

信心分數的式子和文字，方向對不上

附錄 A.1 的文字說：σ 一定不小於 0；σ 為 0 代表沒有任何斷言判這筆不通過，品質比較可能是好的；分數若來自低選擇性斷言的不通過，代表不確定或可能有問題。附錄 A.2 也把 σ 最高的輸出當成「可能有問題」的那一端。照式子的字面，卻是通過的斷言才會把自己的選擇性加進來。論文沒有說明這個差別，這裡兩種都照錄，本頁只轉述它的用意：被平常很少判不通過的斷言判不通過，這筆輸出就更可能是壞的。

整理者的讀法

只按好壞，單一標準的覆蓋率容易偏低

一筆輸出被按倒讚，只說它至少違反了一條標準，沒說是哪一條。對某一條標準的斷言來說，人評為壞的輸出裡，有些其實壞在別的標準上，它本來就不該判不通過，所以拿整體的好壞去算單一標準的覆蓋率，數字會偏低。讚的訊號就清楚得多：第 3 章說過，按讚代表通過所有標準。第 9 章會看到，好幾位參與者想要逐條評分。這一段是整理者的讀法，論文沒有這樣分析。

思考題 · 01

你會怎麼替自己的斷言設誤判失敗率的門檻？

想一條你手上的 LLM 管線：一條斷言放在回應送給使用者之前擋東西，另一條只是每天出報表。

第 13 章會看到作者的提醒：放在關鍵路徑上的斷言誤判失敗太多，就會觸發不必要的重跑、拉長延遲；只出報表的可以寬一點。也可以參考第 11 章 P3 的建議，每條標準各設一個門檻，而不是整組共用一個。論文的實驗用過 10%、20%、40% 三種門檻，但沒有給建議值，怎麼訂是整理者留給你的練習。

分析。研究者在參與者放聲思考時記下他們的想法與看得到的情緒，例如 EvalGen 建議了一條他們自己說不出來的標準時的驚喜，或找不到好斷言時的挫折，也錄下每場通話的逐字稿。分析用開放編碼與主軸編碼：先逐句替每位參與者值得記的句子編碼，第二輪在每個人之內歸成較大的主題，最後把所有人的主題合併、重新整理。

關鍵觀念 · 一

標準依附在輸出上

作者在摘要裡把這一點說得更重：有些標準看起來依附在實際看到的 LLM 輸出上，不是能事先獨立定好的東西；這對「評估可以和觀察模型輸出分開」的做法，提出嚴肅的問題。

用 hashtag 的例子說：在看到輸出之前，每個人都以為自己知道「不要 hashtag」是什麼意思；是輸出的各種樣子，逼人決定邊界畫在哪裡。這一段是整理者的讀法。

第 8.1 節把這個發現放回評估的大脈絡。機器學習與自然語言處理的 benchmark，預設標準已經定義清楚、資料已經標好；例如 AutoCalibrate 校準 LLM 評估器，需要大量專家標註、而且事先定好標準的資料。作者在研究裡看到的卻是開發者快速迭代標準，而且實際接觸 LLM 的輸出，幫他們細化了標準。所以在互動的情境裡，修訂標準和評分應該同時進行；這也對那些假設「專家標籤已經定案」的對齊方法提出挑戰。標準依附在特定的 prompt 與它的輸出上，代表管線的任何變動都可能引發標準漂移，例如 LLM API 換成新模型，造成 prompt 漂移（作者引 Chen 等人的研究）。

作者替未來的評估助手提了幾個方向：在使用者評分、給回饋時動態調整標準；在保留讚與倒讚這種簡單性的前提下改成逐條標準評分，讓助手能更精準地調整標準本身與它的實作；在 LLM 評估器的 prompt 裡放好與壞的輸出例子；以及每當輸出改變，可能要請使用者重評、或重想標準。

作者說這個發現呼應教育領域的研究：老師改的作業越多，越常依常見的錯誤更新評分標準（作者引 Singh 等人的研究）。就像老師看了更多學生作業後調整標準、重新改分，讓使用者在更新標準後重新評估輸出，也可能讓評分更準、更一致。考慮到參與者的評分並不一致，評估助手也可以借用群眾外包的方法，例如多數決、自評或他評，來決定一筆輸出的評分。另一個挑戰是把改過的標準延伸到沒評過、以及未來還沒看到的輸出：評估助手要怎麼取樣，才能讓評過的輸出反映整條管線成功與失敗的整體分布？

讀者可能會問，標準什麼時候會定下來？也許研究的時間太短，如果參與者評上一兩個小時，標準就會穩定，漂移也就消失。作者認為有理由相信不會：參與者細化的標準，是在適應被評的輸出的行為，這是依附的評估，而不是獨立的評估。現實裡也有標準永遠不會完全定下來的情境，例如法庭，案件一直進來。一位參與者說，人看到壞的輸出就知道它壞；作者指出這句話呼應 1964 年一件猥褻內容案裡，一位美國最高法院大法官的名言。法學者 Gewirtz 分析那句話時主張，主觀不必然代表不理性；接受法官的不完美也有好的理由，承認這是目前能做到的最好，不能解決所有問題，但是一個開始，而且會繼續想下去。作者借此提出更深的問題：對評估助手來說，「對齊」是可以達成的目標嗎？我們慣用的說法與假設，例如「有一組真實的標籤，只等著被引出來」，會不會在這裡失靈？驗證驗證者，會不會永遠是一件進行中的工作？

作者的結論是：對齊不只是效能的問題，也就是不只是「換一個更好的 LLM 就會更好」。他們看到的不一致，有時來自參與者心中沒有用自然語言說明的隱性標準；和先前比較不同 LLM 的研究一樣，這種隱性的理解可能非常主觀，在參與者之間甚至互相矛盾。

提醒

評得多，不一定救得回來

第 5 章的挑選機制有個前提：候選池裡至少有一條斷言的讀法和人一樣。如果 GPT-4 對一條標準只想得到一種讀法，所有候選都會一樣不一致，多給的評分只會讓報告卡更清楚地顯示沒有一條對得上。這時要改的是標準的文字，多評幾筆幫不上忙。這是整理者依第 7.3.3 節整理的提醒。

什麼時候用哪一種，參與者心裡有數。格式檢查（例如輸出是不是 Markdown）、計數，以及要不要包含特定字詞，他們偏好程式斷言。P6、P8 說自己的管線會想用 LLM 斷言，因為他們大多數的標準都很模糊。P2 的做法是：一時想不出能實作的 Python 函式，就交給 LLM。P8 偏好 LLM 斷言還有一個理由：遇到品質或格式出乎預期的輸出，LLM 比較寬容，程式檢查的則是精確的限制。

程式斷言，參與者想直接驗證。不論哪一種斷言，EvalGen 都用同一套流程：每條標準探索多個候選，挑出和評分最一致的。參與者對 LLM 斷言大致喜歡這套做法，對程式斷言卻不喜歡；作者說這可能只適用於擅長寫程式的使用者，而研究的參與者全都是。P2、P5、P7 想看每個候選的程式碼，自己挑每條標準最好的 Python 函式。P5 的理由是：能用 Python 解的事，他心裡已經有一個想好的實作，而且很容易驗證，直接給他看程式碼比較快。P7 想用回饋調整程式斷言的「花俏」程度，例如依看過的輸出，要求檢查某個樣式的正規表示式更複雜或更簡單；但他也承認，能不能改要看程式的長短：十行左右以內他會讀程式，更長的函式大概就只看結果，這時界線就模糊了。整體來說，參與者覺得 EvalGen 替程式斷言開了好頭，想改也容易；P4、P6 甚至要求能把程式斷言匯出成單元測試或 Python 檔。

參與者希望自己的評分也幫忙產生候選。他們喜歡 EvalGen 替每條標準試多個候選，但希望它請 LLM 產生候選時，用上自己的評分，以及倒讚時寫的自然語言回饋（P3、P4、P5、P7）；例如每給一個評分，就請 LLM 產生一個把新評分放進 prompt 的新候選，讓它更貼近使用者的評分，程式斷言也能這樣產生。P3、P5 還想把標好的輸出直接放進 LLM 斷言的 prompt；P3 在看結果表格時興奮地想到，可以把這些好與壞的例子當成 LLM 評估器 prompt 裡的 few-shot 範例。作者說這指向一個類似 ConstitutionMaker 與 DSPy 的最佳化迴圈，只是用在產生與驗證斷言，而不是最佳化 prompt。

LLM 斷言比較難信任。參與者覺得 EvalGen 建議的程式斷言，不一致的時候比 LLM 斷言明顯（第 11 章）；但他們也承認 LLM 斷言比較難信任，因為程式斷言改起來比 LLM 斷言容易（P2、P5、P6、P8、P9）。有些參與者懷疑 LLM 斷言能不能搬到上線管線裡監控輸出（P3、P6、P8）：P8 說他完全想不出 LLM 當驗證器上線要怎麼運作，非常懷疑；P9 問，評估要怎麼長期維護，是不是得把整個流程重跑一次。作者的一個建議是：做一個向其他人收評分的介面，對象甚至可以是這條管線的終端使用者，持續讓 LLM 斷言重新對齊。

參與者想把斷言部署到正式環境。有人想放在 LLM 管線的關鍵路徑上，在壞輸出送到終端使用者之前擋下；也有人想要被動的部署，一位參與者希望每天收到一封報告，列出斷言集合在當天抽樣的輸出上的結果。兩種部署的要求不同：斷言放在關鍵路徑上，誤判失敗就不能多，否則 LLM 會被不必要地重新提示、重跑一次，整條管線的延遲跟著增加。標準會隨時間改變，所以評估助手應該請使用者評上線後看到的新輸出，並自動調整斷言集合。

研究確認參與者兩種斷言都需要，也顯示兩種在挑實作與感受一致程度上要分開對待。程式斷言常用來做輸出結構這類基本檢查，可以放在關鍵路徑上，也已經有不少 LLMOps 工具讓人寫這種程式護欄（作者舉 NeMo Guardrails、Guardrails、Instructor）。但找到對的實作並不簡單，它可能細緻地取決於 LLM 輸出的特性：例如可接受的回應長度，會隨實際輸出的分布差很多。P3 說，對輸出長度這條標準，他會看一批輸出的字數直方圖，找出字數異常的區間，看它們是不是也有別的失敗，例如 LLM 寫得又長又囉嗦。

有些參與者想讓產品經理這類協作者也在 EvalGen 裡評分。多人一起評時，評估助手要考慮評分者之間的信度，並處理分歧；作者建議再次借用群眾外包的技術，例如替每位評分者的準確度建模，必要時修正（作者引 Zhuang 等人的研究）。協作者的程式經驗也不同，經驗少的人可能對其實適合用程式評的標準選 LLM 斷言；EvalGen 雖然會建議每條標準該用程式還是 LLM，評估助手可能還要確保同一個團隊對實作有共識。作者想像的介面，像是替一條新斷言開一個 pull request、請隊友審查，再用類似持續整合與持續部署（CI/CD）的流程把新斷言推上線。

第 8.3 節點名的未來方向，有三個超出 EvalGen 目前的範圍。第一，不只是是非題：以字數為例，與其設死的門檻，監控不同輸出之間字數的變化可能更有用，就像傳統機器學習的監控；但字數多少算壞仍然說不準，AI 助手對壞的定義也不一定和使用者一樣；追蹤比 true 或 false 更細的資訊，能在知道輸出壞了之後幫忙除錯。第二，很多人的 LLM 管線是多次 LLM 呼叫串成的鏈，評估助手可以協助端到端的對齊；這不只在鏈上複雜，在使用檢索增強生成這類其他元件的複合 AI 系統裡也一樣。第三，使用者越來越希望 prompt 能依斷言的結果自動改進，例如某條斷言在一群輸出上失敗，就在 prompt 裡加一條指令處理這種失敗；已有框架試著用斷言或評分的回饋改 prompt，但放進評估助手並不直接，可能形成一個循環：評估助手依 prompt 的表現調整斷言，也用這些洞見建議修改 prompt，讓 prompt、斷言與評估機制本身在同一個介面裡一起演化。

限制有兩個。第一，離線評估只看了兩條管線，不同的應用可能需要不同的取樣與對齊方法。第二，質性研究的樣本小，參與者全是部署 LLM 經驗豐富的開發者；他們在 EvalGen 裡也沒有足夠的時間反覆迭代，研究的設定沒有涵蓋 LLM 工作流程的部署階段。作者建議未來研究整個 LLMOps 生命週期裡評估的最佳做法與陷阱。

第 9 節的結論很短：EvalGen 是讓 LLM 產生的評估函式對齊人的偏好的人機協作做法，幫使用者訂出可接受輸出的標準、寫出檢查這些標準的函式，讓評估反映使用者自己的評分標準。在 9 位專家使用者的質性研究裡，作者觀察到標準漂移：使用者評的輸出越多，越會細化自己的評估標準。作者說，認清標準依附在 LLM 輸出上，為未來評估助手的設計指出新的方向。

整理者的讀法

放回這一講：把資料品質的問題搬到評估上

下面是整理者的連結。這一講談資料的挑選與品質，這篇把同一組問題搬到評估器上：挑哪幾筆給人評，是資料挑選；16 筆人評能不能代表全體，是小而精準的 benchmark 會碰到的問題；只按好或壞、邊評邊改標準，是標註做法；覆蓋率、誤判失敗率與一致程度，是品質評估的尺。論文沒有處理從 agent 執行軌跡建資料集，但它在未來工作點名的端到端對齊，就是把同樣的問題延伸到多步驟的管線。

EvalGen 能保證選出的斷言和人一致嗎？
不能。作者說人無法完全驗證 LLM 評估器，唯一的辦法是評完全部輸出；EvalGen 用一部分評分挑斷言，再用報告卡讓人看到一致到什麼程度。使用者研究裡，對「斷言和我的評分一致」的評價從 1 到 6 都有（表 2）。
評分評得夠久，標準就會定下來嗎？
作者認為不一定。參與者細化的標準是在適應被評的輸出，是依附的評估，不是獨立的評估；作者用法庭作類比：案件一直進來，標準就不會完全定下來。
程式斷言和 LLM 斷言該用哪一種？
參與者兩種都要：格式、計數、特定字詞偏好程式；模糊的標準用 LLM。程式斷言他們想自己讀、自己挑；LLM 斷言比較難信任，也比較難放心搬上線（第 7.4 節）。

EvalGen
評估助手
這篇的系統：LLM 建議標準、產生候選斷言，使用者評一部分輸出，依一致程度挑斷言（第 3、4 節）。
ChainForge
prompt 工具
開源的 prompt engineering 工具，用節點拼出資料流；EvalGen 做在它裡面。
Multi-Eval node
多重評估節點
作者新增的節點，一個節點放多個評估器，對前一個節點的所有輸出一起跑。
SPADE
全自動斷言產生
Shankar 等人較早的演算法，從 prompt 的修改歷史產生 Python 斷言，離線解整數線性規劃挑最小集合；第 5 節的基線。
criteria
評估標準
用自然語言寫的二元標準，例如「不要把 hashtag 當成實體」；由 LLM 建議、使用者增刪改。
assertion
斷言
實作某條標準的布林函式，對輸出回 true（通過）或 false（不通過）。
code-based assertion
程式斷言
用 Python 寫的斷言；參與者偏好拿它檢查格式、計數與特定字詞，也想自己讀程式、自己挑。
LLM-based assertion
LLM 斷言、評分 prompt
交給另一個 LLM 判斷的斷言，別處也叫 LLM-as-a-judge；適合模糊的標準，但參與者覺得比較難信任。
grade
評分
使用者對一筆輸出按讚（好）或倒讚（壞）；讚代表通過所有標準，候選若讓讚的輸出不通過就往後排。
coverage
覆蓋率
人評為壞的輸出裡，被斷言集合判不通過的比例；作者說它是集合的真陰性率（附錄 A.3）。
false failure rate（FFR）
誤判失敗率
人評為好的輸出裡，被斷言集合判不通過的比例；可以設門檻，只挑不超過門檻的斷言（附錄 A.3）。
alignment
一致程度
覆蓋率與 1 − 誤判失敗率的調和平均；像 F1，但算的是「不通過」，而且以整組斷言為單位。
selectivity
選擇性
一條斷言判通過的比例，也就是通過率；把每筆都判不通過的斷言，選擇性是 0（附錄 A.1）。
confidence score σ
信心分數
估計一筆沒評過的輸出品質差的可能性，依選擇性計算，取樣器靠它挑輸出（附錄 A.1、A.2）。
sampling policy
取樣策略
挑哪幾筆給人評：隨機、最高、最低、交替；使用者研究用交替（附錄 A.2、A.4）。
report card
報告卡
評分結束後的畫面：每條標準的一致程度與混淆矩陣，整組的覆蓋率與誤判失敗率（圖 2(e)）。
Table View
表格檢視
列是輸出、欄是斷言的結果表（圖 3），讓人看斷言在沒評過的輸出上怎麼判。
criteria drift
標準漂移
評分的過程改變了標準：看到新的壞法而加新標準，或重新詮釋既有的標準（第 7.3.1 節）。
mixed-initiative
人機協作
人與系統輪流主導的互動方式；EvalGen 讓 LLM 起頭，人修正標準、提供評分。
think-aloud
放聲思考
受試者邊操作邊說出想法；這場使用者研究的主要資料來源（第 6 節）。
open and axial coding
開放與主軸編碼
先替逐字稿的句子編碼，再歸成主題、跨參與者整合的質性分析方法（第 6 節）。
over-reliance、over-generalization
過度依賴與過度概括
