Don't Sleep on Single-agent Systems · 圖卡＋教材整合版

Single-agent Systems別急著拆成多個 agent 一個夠強的可能就夠

2024 年，「多代理系統」是 AI 圈最熱門的詞之一。打造 OpenHands 的 Graham Neubig 寫了這篇反方意見：把工作拆給一組專門的 agent 很直覺，卻要在結構、脈絡與維護上付代價；而一個 agent 的三個元件裡，模型與工具已經能合成一個，真正難的是 prompt。本頁分七章重述。每章開頭先放一張圖解卡講重點，往下是詳細說明；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

多代理正熱，這篇替單一代理說話

原文寫於 2024 年 9 月。作者用打造 OpenHands 的經驗主張：在大家忙著把系統拆成多個 agent 的時候，先看看一個夠強的單一 agent 能走多遠。

這篇是 Stanford CS 329Z 第 5 週的選讀。那一講叫 Multi-Agent Systems，屬於 Memory & Multi-Agent Systems 分區，談單一 agent 對多個 agent、編排的模式、handoff 與狀態轉移、委派與協作，以及協調與錯誤傳播帶來的挑戰。同一講的必讀是 AutoGen 論文，一個多代理框架。這篇站在另一面：它不否定多代理，但要讀者先想清楚，把工作拆給多個 agent 換到什麼、又付出什麼。

原文的開頭先描述當時的潮流。「多代理系統」是 AI 圈最熱門的流行詞之一：MetaGPT、AutoGen 這些受歡迎的開源框架以它為重心，黑客松與許多研究論文也圍著它轉。作者想檢視這股潮流，並主張單一代理系統有幾個很有力的理由。他的依據是團隊打造 OpenHands 的經驗，那是一個做軟體開發 agent 的框架。整理者補一句：原文點名的 AutoGen，正是本週必讀論文的主角。

原文的順序是：先拆解一個 agent 由哪些元件組成，再拿一個多代理系統當例子，列出它的幾個麻煩，最後談怎麼從多個專門的 agent 走到一個夠強的 agent，以及還沒解決的問題。本頁照這個順序走，前兩段併成一章。

給初學者

先把六個名詞對齊

  • LLM-based agent：以大型語言模型為核心、會用工具在環境裡做事的系統。
  • 多代理系統（multi-agent system）：由多個 agent 分工的系統。原文的定義是，各個 agent 之間至少有一個元件不同。
  • 單一代理系統（single-agent system）：一個 agent 從頭做到尾，用同一個模型、同一組工具、同一套 prompt。
  • Prompt：給模型的指示。原文的用法也包含從環境拉進來的資訊。
  • 動作空間（action space）：提供給 agent 的工具，決定它能對外面的世界做哪些事。
  • Context window：模型一次讀得進的 token 上限；prompt 越長，佔掉的越多。
閱讀提醒

這是公司部落格，也是 2024 年的文章

原文發表在 OpenHands 的部落格，作者是打造它的團隊成員。文中提到 OpenHands 與它的 CodeActAgent 的地方，本頁都寫成「作者說」，產品名照原文保留。原文寫於 2024 年 9 月，提到的模型（GPT-4o、llama-3.1、Qwen-2.5）與 context 長度都是當時的狀況；本頁照原文轉述，沒有換成現在的數字。

注意：兩個例子（Verifier、只傳摘要）是原文的；Reproducer 與 Fault Localizer 上下並列，是因為原文沒說兩者的先後；三種團隊毛病一對一對上三個麻煩，是整理者排的。

作者說，做多代理系統會碰到好幾個困難，他列了三個，每一個都拿上一章的 CodeR 當例子。

結構要剛好對上題目。多代理系統靠加上結構來解決問題：題目剛好符合事先定好的結構時，效果很好；不符合時怎麼辦？原文的例子是 Verifier。它想自己做檔案定位，確定自己真的把答案驗證好了；但這些 agent 彼此完全分開，Verifier 手上沒有做這件事需要的工具。

脈絡要保得住。多代理系統通常要在幾個 agent 之間傳遞資訊，而傳遞本身就可能讓資訊流失。例如 Fault Localizer 如果只把工作的摘要傳給後面的 agent，常常就丟掉了重要的脈絡，而那些脈絡本來對下游 agent 的工作有用。

維護。每個 agent 通常是一個獨立的 code base，至少也是一份獨立的 prompt。所以多代理系統的程式碼往往更大、更複雜。

關鍵觀念 · 一

這三個麻煩，人類的團隊也有

作者覺得有意思的是，這些挑戰很多都能對應到人類的組織。大部分人都待過這樣的團隊：組織得很鬆散、彼此溝通不良，或是某個成員離開之後，團隊需要的技能就接不上。

三種團隊的毛病，排列的順序剛好對上三個麻煩：組織鬆散對應結構對不上題目，溝通不良對應脈絡流失，技能接不上對應維護。這個一對一的對照是整理者排的。

整理者的讀法

三個麻煩都出在 agent 之間的邊界

Verifier 缺的工具在另一個 agent 手上；流失的脈絡發生在兩個 agent 交接的地方；多出來的程式碼，是每個 agent 各自的一份。三者的共同點是 agent 之間那道邊界。這是整理者的歸納，原文沒有這樣說。

整理者的思考題 · 01

你的多代理流程裡，哪一道交接最常掉東西？

挑一個你做過或用過的多代理流程，把 agent 之間的每一次交接列出來：傳過去的是完整的紀錄，還是一段摘要？下游的 agent 有沒有「需要上游的工具或資料，卻拿不到」的時候？

整理者的建議：先找出最常失敗的那一道交接，比較只傳摘要與傳完整紀錄的結果；差得多，那道邊界就值得重新考慮。

作者先承認多代理系統有它的道理：只要能給每個 agent 做好工作所需的結構與工具，專門的 agent 在特定任務上確實做得好。那麼一個 agent 能跟它們競爭嗎？作者認為這可能比想像的容易，而且 OpenHands 裡實作的 CodeActAgent 已經是一個好的原型。他把問題拆成三件事：一個 LLM、一個動作空間、一套 prompt 的技術，並自己評了每一件的難易。

單一 LLM：相對容易的部分。現在已經有很好的通用 LLM，閉源的有 Claude、GPT-4o，開源的有 llama-3.1、Qwen-2.5。作者說這些模型不是什麼都會，但能做的事範圍很廣；如果缺少某種能力，可以用持續訓練把它加上，其他能力也不會因此大幅下降。

單一動作空間：也不太難。如果有好幾個 agent，各自手上有不同的工具，作者提了兩個做法：一是給模型相對通用、能解決問題的工具；二是不同 agent 的工具箱不同時，直接把它們串在一起。OpenHands 提供的工具讓 agent 能寫程式、跑程式、瀏覽網頁。作者說這種通用的做法，讓 agent 能用上已經為人類開發者做好的軟體工具，因此非常多用途，涵蓋了其他多代理系統能做的大部分事。

實作提示

想合併之前，先把工具列在一起

要評估一個多代理系統能不能合成一個 agent，可以先把每個 agent 的工具列成一張清單：哪些重複、哪些能用「寫程式、跑程式」這類通用工具取代。剩下的工具箱，就是原文第二個做法要直接串起來的部分。這個檢查順序是整理者依原文排的。

作者說 prompt 是最棘手的地方：要確定 agent 拿到怎麼完成任務的適當指示，也拿到環境裡的適當資訊。他列了兩個選項。

把所有 prompt 串在一起。如果一個多代理系統有 10 份不同的 prompt，何不全部串起來？當時已經有長 context 的模型，能處理幾十萬到上百萬個 token，原文寫的是 Claude 200k、Llama 128k（2024 年 9 月的數字）。作者說這是 OpenHands 目前採用的做法。它有兩個缺點。第一是成本：prompt 越長，花的錢與時間越多，不過 Anthropic 的 prompt caching 這類功能，已經讓它比以前便宜很多。第二是模型可能被太多額外的 context 分心，不過越強的語言模型，越來越會從長 context 裡找出重要的資訊。

檢索式 prompting（retrieval-augmented prompting）。另一個選項是改用檢索。檢索增強生成（RAG）系統會為了效率或準確度，把很長的 context 砍短；同樣的道理，也可以對 prompt 做檢索。作者說，挑選放進 prompt 的範例已經有一些研究，但就他所知，放在 agent 情境裡的研究比較少。

示意 · 兩條路（教學用假想程式碼，非原文，也不是 OpenHands 的實作） 
prompts = load_role_prompts()        # 例如原本 10 個 agent 的 10 份 prompt

# 路一：全部串接。每一輪都帶著全部的指示，靠長 context 撐住
system = "\n\n".join(prompts)

# 路二：檢索式 prompting。先挑出和這一步有關的幾段，再組成 prompt
picked = retrieve(prompts, query=current_step, k=2)
system = "\n\n".join(picked)

哪一條路最好，作者說仍是進行中的研究問題，但他相信能夠克服；他也邀請有興趣的人到 OpenHands 的 Slack 一起討論。

整理者的讀法

串接的兩個缺點，正好是檢索想處理的兩件事

串接的缺點一個是錢與時間，一個是注意力。原文說 RAG 砍短 context 是為了效率或準確度，對到的正是這兩件事；代價是要先挑對段落。這是整理者依原文的 RAG 類比做的推論，原文沒有比較兩條路的優劣。

整理者的思考題 · 02

把你所有 agent 的 prompt 串成一份，會發生什麼事？

把系統裡每個 agent 的 system prompt 接在一起，看看總長度，也看看有沒有互相打架的指示，例如一份要它只輸出是或否，另一份要它修改檔案。

整理者的建議：互相打架的段落，最容易讓模型分心；先把它們改寫成「什麼情況下做什麼」，再決定要全部串接，還是改成按需檢索。

整理者的讀法

同一道邊界，換個情況就是目的

第 2 章的三個麻煩，都出在 agent 之間的邊界：工具拿不到、脈絡傳不過去。原文舉的兩個例子，要的正是這道邊界：特權資訊不該被其他 agent 看到，代表不同的人的 agent 也各有各的立場。這是整理者把結論和第 2 章接起來的讀法。

原文的最後一段是產品推薦：想試試以單一的通用 agent 為基礎的開源軟體開發 agent，可以用 OpenHands 的開源版或線上版，也歡迎加入社群貢獻。本頁照原文保留產品名，沒有另外評估它。

下面這份清單不在原文裡，是整理者把全文的論點壓成的檢查順序，讓你下一次想「再加一個 agent」之前先走一遍。

  1. 把每個 agent 的三個元件列成一張表模型、prompt、動作空間各一欄；只差在 prompt 與工具的 agent，就是可以考慮合併的候選。
  2. 標出每一道交接傳了什麼傳的是完整紀錄還是摘要？下游有沒有需要上游的工具或脈絡，卻拿不到？
  3. 問兩個問題：有特權資訊嗎？代表不同的人嗎？任一題答「是」，那道邊界就是必要的，保留多代理；這是原文舉的兩個例子。
  4. 其餘的先合成一個 agent 當基準工具用通用的或直接串起來，prompt 先全部串接，和原本的多代理版本比結果。
  5. 串接的 prompt 太長、模型開始分心，再試按需檢索作者說這一步還沒有定論，要用自己的任務量過才知道。
整理者的思考題 · 03

你的系統裡，有沒有真的需要隔開的資訊？

想一個你正在做或打算做的多 agent 系統：有沒有哪一份資料，只能讓其中一個 agent 看到？有沒有 agent 是代表不同的人或單位在行事？

整理者的建議：兩個問題都答「沒有」時，先用一個 agent 加上完整的工具與 prompt 當基準，確定它做不到，再把工作拆出去。

十八個名詞，看懂單一與多代理

Multi-agent system
多代理系統

Single-agent system
單一代理系統
一個 agent 用一個模型、一個動作空間、一套 prompt 技術完成全部工作。
Prompt
提示
給模型的指示；原文的用法包含 system prompt，也包含從環境拉進來的資訊。
System prompt
系統提示
規定模型整體行為的那段指示。
Action space
動作空間

可維護性

作者團隊的框架

OpenHands 裡實作的 agent；作者說它是單一代理的好原型。
Continual training
持續訓練

Long-context model
長 context 模型
一次能讀幾十萬到上百萬 token 的模型；原文寫 Claude 200k、Llama 128k（2024 年 9 月）。
Prompt caching
prompt 快取
重複使用同一段 prompt 時降低成本的功能；作者說它讓串接的長 prompt 便宜很多。
RAG
檢索增強生成

檢索式 prompting
像 RAG 一樣，先檢索出這一步用得到的 prompt 內容，再組成 prompt；原文說 agent 情境的研究還少。
Privileged information
特權資訊
只有某個 agent 能接觸的資訊；原文說這是多代理當然該用的情況之一。
