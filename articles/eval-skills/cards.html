02 / 10三種悄悄溜進來的 regression
「變好了」靠的不是感覺，是三個能答是／否的問題
迭代 skill 時最難分辨的是「改善了」還是「只是改變了行為」—— 某版感覺快、某版感覺穩，regression 就從這個縫隙溜進來

✓ 靠 eval 迭代

v3：感覺穩了

三個版本都「感覺」還行。regression 從感覺的縫隙溜進來：跳過必要步驟、留下多餘檔案、或某天根本不觸發 —— 直到有人踩到才知道。

每一版都再跑一輪
跑一輪 eval：10–20 條 prompt
有呼叫 skill？

遵守了慣例？
每題答「是／否」—— 答「否」的那題，就是 regression 的位置
改動先過檢查再算數。同一組 prompt、同一套檢查，分數可以跟上一版比；哪一題從是變否，一眼看到。
三種 regression，都是事後才發現
不觸發、跳過必要步驟、留下多餘檔案 —— 沒有量測時，只有使用者踩到才知道。
「感覺快」「感覺穩」都不是可以放進時間軸比較的東西。
三個問題，各自一個是／否
有沒有呼叫 skill、有沒有跑預期的指令、輸出有沒有遵守慣例。答案能記錄、能跨版本比較。
evals 就是輕量的 end-to-end 測試：跑、錄、打分。
注意：skill 本質是一組給 LLM 的 prompt 與指令 —— 所以評估它的方法，就是評估任何 LLM prompt 的方法。
03 / 10一條 eval 的四步鏈
eval 不是一次考試，是「每改一版就再跑一輪」
一輪 = 一版 skill 跑完整組 prompt：prompt → 錄下的執行（trace ＋ artifacts）→ 一小組檢查 → 可以放進時間軸比較的分數

Step 3　Artifacts

一輪 = 一個版本的 skill 跑完整組 prompt。每條 prompt 各留一份 JSONL 與那次執行的產出 —— 分數才有東西可對帳，檢查失敗時打開檔案就知道發生了什麼。
下一版
三個讓分數可以比較的前提
① 不只看最終輸出，看過程
只看 app 能不能跑，會漏掉過程的 regression：指令順序錯、跳過 npm install，結果可能還是「能跑」。
--json 讓 stdout 變成事件流，過程才進得了帳。
② 檢查清單要小，只放 must-pass
目的不是一開始編進所有偏好，而是抓住最在乎的行為；其他的等真實失敗出現再補。
快速、針對性的訊號，勝過最後一個 pass／fail 總判決。
③ 同一組 prompt、同一套檢查
分數要能跨版本比，輸入與量尺就不能一起變。改一版 skill，就能 diff 出哪一題從是變否。
這就是「感覺」變成「證據」的那一步。
共同前提：一輪只改一個東西 —— 同時改 skill 又改 prompt 集，分數變動就說不清是誰造成的。

front matter 的 name 與 description 是主要訊號；後面的 eval 會用隱含呼叫與負向對照專門測它。

06 / 10手動跑，逼出三種隱藏假設
第一輪手動跑，找的不是正確性，是「隱藏假設」
觸發與否高度依賴 name 與 description —— 先用 /skills 或 $ 前綴明確啟用，在真實 repo 或 scratch 目錄跑，看它在哪裡壞掉
01　觸發假設 · TRIGGERING
該觸發的沒觸發，不該的反而觸發
「set up a quick React demo」應該喚起 setup-demo-app 卻沒有；「add Tailwind styling」更泛用，卻意外觸發、直接建了新專案。
✗ 只用 $ 前綴明確呼叫來測
✓ 用不提 skill 名字的 prompt 去試
02　環境假設 · ENVIRONMENT
以為目錄是空的、以為 npm 一定在
skill 假設自己在空目錄執行；假設 npm 可用、而且優先於其他套件管理器。換一個 repo 就露餡。
✗ 只在自己的 scratch 目錄跑
✓ 換一個真實 repo 再跑一次
03　執行假設 · EXECUTION
跳過 npm install、順序反了
agent 以為依賴已經裝好，所以跳過安裝；或在 Vite 專案還不存在時，就先去設定 Tailwind。
✗ 只看最後 app 能不能跑
✓ 看 trace 裡的指令與順序

這一輪不追求速度與精緻。補上的 npm install、修正的 Tailwind 順序、收緊的 description，每一個都是未來 eval 的候選 —— 記下來，等下就變成 CSV 的一列。codex exec 為自動化設計：進度走 stderr，最終結果才走 stdout。
硬規則：codex exec 預設在受限 sandbox；要寫檔才加 --full-auto —— 自動化時尤其只給完成任務所需的最小權限。

08 / 10兩層評分
「輸出看起來對」不是證據，trace 和 rubric 才是
第一層用 codex exec --json 的事件流做確定性檢查，第二層用 --output-schema 的結構化 rubric 評質性 —— 先快後慢，兩層都要
最終回覆（看起來很完整）
demo-app 已建立完成
已安裝依賴
Tailwind 已設定好
元件結構符合要求
exit 0 · 1 turn · 6 files
↑ 三句都是自述，不是痕跡
兩層對帳（只驗痕跡，不採信自述）
1
跑了 npm install 嗎？
第一層 · 確定性
item.completed · command_execution · "npm install" → 出現在第 3 個指令　✓
2
package.json 建出來了嗎？
第一層 · 確定性
existsSync("demo-app/package.json") → true　✓
3
元件只用 Tailwind class 嗎？
第二層 · RUBRIC
--output-schema style-rubric.schema.json → checks[style].pass = false：Card.tsx 用了 CSS module　✗
判定：基本功通過，風格不通過
兩個確定性檢查都過，rubric 的 style 項 fail。這一版不算改善 —— 修 Card.tsx 後再跑一輪，分數才會動。
為什麼要兩層，不是一層
確定性檢查回答「有沒有做到基本功」：快、免費、失敗直接對到某個事件。rubric 回答「有沒有照你要的方式做」—— 元件寫法、樣式慣例這類規則抓不到的東西。
直接可以拿去用的三條
① 用 codex exec --json，讓 stdout 變成 JSONL；每一次指令執行都是一個依序的 item.* 事件。
② 評分那次 codex exec 不給寫檔權限、加 --output-schema：固定欄位（overall_pass、score、checks[id, pass, notes]）才能 diff。
③ 檢查失敗時打開 JSONL 檔 —— 可解釋，是確定性檢查最大的價值。
適用範圍：rubric 可信的前提是「唯讀 ＋ 逐項可判定」—— 一個總分很難追，四個布林值（vite、tailwind、structure、style）很好 diff。

快的三種：直接從 trace 算

慢的兩種：只在降風險時加

權限 regression：自動化後最重要

注意：門檻要自己訂 —— 指令次數、token 用量都是「比上一版」的相對值，不是絕對數字。
10 / 10五個結論與一個習慣
從「感覺變好」到「證明」，差的不是工具，是一個迴圈
跑 agent、記錄發生的事、用一小組檢查打分 —— 迴圈一旦存在，每個微調都容易確認，每個 regression 都會清楚
01　量測真正重要的東西
好的 eval 讓失敗可解釋，
不是讓報表好看
清單小而準：結果、過程、風格、效率各挑最在乎的。regression 清楚、失敗能對到某個事件，才算量到了。
✗ 一個最後的 pass／fail 總判決
✓ 快速、有針對性的訊號
02　把 evals 建立在行為上
證據是 trace 和 rubric，
不是最終輸出
codex exec --json 擷取 JSONL，對 command_execution 寫確定性檢查；規則到不了的風格與慣例，用 --output-schema 的結構化 rubric。
✗ 只看 app 能不能跑
✓ 先確定性、再 rubric，兩層都要
03　讓真實失敗驅動覆蓋率
每一次手動修補，都是一條測試
從可檢查的 definition of done 出發，用 $skill-creator 起手、收緊指令；之後每個 miss、每個修補都加成 CSV 的一列。
覆蓋率不是設計出來的，是累積出來的。
下週就能開始的五步
01
寫 3–5 條 must-pass
02
CSV 放 4 種 prompt
03
--json 跑一輪，存 trace
04
兩個檢查 ＋ 一份 rubric
05
