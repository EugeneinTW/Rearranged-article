Testing Agent Skills with Evals · 圖卡＋教材整合版

用 Evals 系統化測試 Agent Skills從「感覺變好了」到「拿得出證據」

一份 skill 本質上就是一組給 LLM 的提示詞與指令。要讓它越改越好，最可靠的方法是像評估任何 prompt 一樣去評估它：跑一次、錄下發生的事、用一小組規則打分。本教材把原文 8 個步驟重新整理成可逐章閱讀的版本，並加上一章「搬到你自己的 skill 上」的實作清單。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · Why vibes don't count

為什麼「感覺變好了」不算數

迭代一個 skill 時，最難的是分辨你到底是「改善了它」，還是「只是改變了它的行為」。

注意：skill 本質是一組給 LLM 的 prompt 與指令 —— 所以評估它的方法，就是評估任何 LLM prompt 的方法。

如果你替 Codex 這類 agent 寫過 skill，這個場景應該不陌生：某個版本感覺跑得比較快，另一個版本似乎比較穩，然後某一天，一個 regression 悄悄溜了進來：skill 不再觸發、跳過了一個必要步驟、或是在專案裡留下多餘的檔案。沒有量測，這些全都只能靠印象察覺，而印象是不可靠的。

原文給了一個很乾脆的定位：skill 的本質是一組有組織的 prompts 與 instructions。既然它是 prompt，那麼讓它長期進步最可靠的方法，就是用你評估任何 LLM 應用 prompt 的方式去評估它。

Evals（evaluations 的簡稱）檢查兩件事：模型的輸出、以及它產生輸出的過程，是否符合你的意圖。它把「這樣有比較好嗎？」這種靠 vibes 的問題，換成三個可以回答「是」或「否」的具體問題：

  • agent 有沒有呼叫這個 skill？
  • 它有沒有執行預期的指令？
  • 它產出的東西有沒有遵守你在意的慣例？
給初學者

先把三個名詞對齊

  • Skill：一個目錄，核心是 SKILL.md，告訴 agent「什麼時候該用我、該怎麼做」。Codex 與 Claude Code 的 skill 格式概念相同。
  • Eval：一條 prompt、一次被錄下來的執行、一小組檢查、一個分數。分數可以跨版本比較。
  • Trace：那次執行到底做了什麼的逐筆紀錄。本文用的是 codex exec --json 輸出的 JSONL 事件流。

一條 eval 長什麼樣

原文把 eval 的定義壓成一條鏈：prompt、一次被完整擷取的執行（trace 加上 artifacts）、一小組檢查、最後是一個可以放進時間軸比較的分數。

eval 不是一次考試，是「每改一版就再跑一輪」
一輪 = 一版 skill 跑完整組 prompt：prompt → 錄下的執行（trace ＋ artifacts）→ 一小組檢查 → 可以放進時間軸比較的分數

一輪 = 一個版本的 skill 跑完整組 prompt。每條 prompt 各留一份 JSONL 與那次執行的產出 —— 分數才有東西可對帳，檢查失敗時打開檔案就知道發生了什麼。
下一版
三個讓分數可以比較的前提
① 不只看最終輸出，看過程
只看 app 能不能跑，會漏掉過程的 regression：指令順序錯、跳過 npm install，結果可能還是「能跑」。
--json 讓 stdout 變成事件流，過程才進得了帳。
② 檢查清單要小，只放 must-pass
目的不是一開始編進所有偏好，而是抓住最在乎的行為；其他的等真實失敗出現再補。
快速、針對性的訊號，勝過最後一個 pass／fail 總判決。
③ 同一組 prompt、同一套檢查
分數要能跨版本比，輸入與量尺就不能一起變。改一版 skill，就能 diff 出哪一題從是變否。
這就是「感覺」變成「證據」的那一步。
共同前提：一輪只改一個東西 —— 同時改 skill 又改 prompt 集，分數變動就說不清是誰造成的。

換句話說，agent skill 的 eval 其實很像輕量的 end-to-end 測試：跑 agent、記錄發生的事、對照一小組規則打分。接下來的 8 個步驟，就是用 Codex 把這個迴圈實際建起來，從定義成功開始，加上確定性檢查與 rubric 評分，讓改善與 regression 都變得清楚可見。

不要問「這樣感覺有比較好嗎」。要問「它有沒有做到我說的那三件事」。 序章核心觀念

以原文的範例來說，被評估的是一個「建立 demo app」的 skill。有些檢查非常具體：有沒有跑 npm install？有沒有產生 package.json？原文把這類具體檢查，跟一份結構化的風格 rubric 搭在一起，用來評估慣例與版面。

這個混搭是刻意的。你要的是快速、有針對性的訊號，能及早浮現特定的 regression，而不是跑到最後只得到一個 pass 或 fail 的總判決。總判決告訴你「壞了」，針對性訊號告訴你「哪裡壞了」。

實作提示

must-pass 清單怎麼寫才檢查得了

每一條都要能被「程式」或「一條 rubric 條目」判定。寫法可以套這個範本：

  • 結果：npm run dev 能啟動、指定檔案存在。
  • 過程：trace 裡出現 npm install，而且出現在建立專案之後。
  • 風格：只用 functional component、只用 Tailwind class、沒有多裝 UI 函式庫。
  • 效率：指令次數不超過某個上限、token 用量不比上一版多出一個門檻。
思考題 · 01

挑一個你最常用的 skill。它的「成功」能不能用四類指標，寫成五條以內的 must-pass？

如果寫不出來，通常不是 eval 的問題，而是 skill 的 definition of done 本身還太模糊。

先寫結果與過程各一條，這兩類最容易變成確定性檢查；風格與效率各留一條給後面的 rubric 與 trace 統計。

front matter 裡的 name 與 description 是 Codex 決定「要不要呼叫這個 skill」以及「什麼時候把 SKILL.md 其餘內容注入 agent context」的主要訊號。如果這兩個欄位寫得模糊，或是塞了太多東西，skill 就不會穩定觸發。這也是為什麼後面的 eval 會特別花力氣測「觸發」這件事。

最快的起手式是用 Codex 內建的 skill creator（它本身也是一個 skill）：在對話裡輸入 $skill-creator。它會問你三件事：這個 skill 做什麼、什麼時候該觸發、它是 instruction-only 還是 script-backed。預設建議是 instruction-only。

範例 skill：setup-demo-app

原文刻意選了一個極簡的例子：一個用可預測、可重複的方式建立小型 React demo app 的 skill。它要做四件事：

  1. 用 Vite 的 React + TypeScript 樣板建立專案。
  2. 用官方 Vite plugin 的方式設定 Tailwind CSS。
  3. 強制一套最小、一致的檔案結構。
  4. 定義清楚的 definition of done，讓「成功」變得直接可評估。

檔案可以放在 repo 層級的 .codex/skills/setup-demo-app/SKILL.md，或使用者層級的 ~/.codex/skills/setup-demo-app/SKILL.md。下面是它的骨架（教學用精簡版，指令保留、說明改成中文）：

.codex/skills/setup-demo-app/SKILL.md 
---
name: setup-demo-app
description: Scaffold a Vite + React + Tailwind demo app with a small, consistent project structure.
---

## When to use this
需要一個全新的 demo app 做 UI 實驗或重現問題時。

## What to build
Vite + React + TypeScript，設定 Tailwind，保持最小。
樣式要求：TypeScript 元件、只用 functional component、
只用 Tailwind class（不用 CSS modules）、不多裝 UI 函式庫。

## Steps
1. npm create vite@latest demo-app -- --template react-ts
2. cd demo-app 然後 npm install
3. npm install tailwindcss @tailwindcss/vite
   - 在 vite.config.ts 加入 tailwind plugin
   - 把 src/index.css 內容換成 @import "tailwindcss";
4. 實作最小 UI：Header（標題 + 副標）、Card（可重用容器）、
   App（Header + 兩張放假文字的 Card）

## Definition of done
- npm run dev 能成功啟動
- package.json 存在
- src/components/Header.tsx 與 src/components/Card.tsx 存在

設定完成後，專案結構應該長這樣：

demo-app/ 目錄結構 
demo-app/
├─ index.html
├─ package.json
└─ src/
   ├─ main.tsx          入口
   ├─ App.tsx           根 UI：Header + 2 張 Card
   ├─ index.css         只有 @import "tailwindcss";
   └─ components/
      ├─ Header.tsx     標題 + 副標
      └─ Card.tsx       可重用卡片容器
為什麼要這麼有主見

沒有限制，就沒有可評估的東西

這個範例 skill 故意採取很強的立場：指定樣板、指定 Tailwind 的設定方式、指定檔案結構、禁止 CSS modules 與額外 UI 函式庫。原因很簡單：如果 skill 說「做一個 React app」，那什麼結果都算對，也就沒有任何東西可以檢查。限制寫得越具體，eval 才寫得出來。

沒有清楚的限制，就沒有具體可評估的東西。definition of done 是 eval 的前置條件，不是附錄。 整理自第 2 節

Chapter 03 · Manually trigger the skill to expose hidden assumptions

手動觸發，逼出隱藏的假設

因為觸發與否高度依賴 SKILL.md 的 name 與 description，第一件要檢查的事就是：它會在你預期的時候觸發嗎？

圖卡 06 / 10手動跑，逼出三種隱藏假設
第一輪手動跑，找的不是正確性，是「隱藏假設」
觸發與否高度依賴 name 與 description —— 先用 /skills 或 $ 前綴明確啟用，在真實 repo 或 scratch 目錄跑，看它在哪裡壞掉
01　觸發假設 · TRIGGERING
該觸發的沒觸發，不該的反而觸發
「set up a quick React demo」應該喚起 setup-demo-app 卻沒有；「add Tailwind styling」更泛用，卻意外觸發、直接建了新專案。
✗ 只用 $ 前綴明確呼叫來測
✓ 用不提 skill 名字的 prompt 去試
02　環境假設 · ENVIRONMENT
以為目錄是空的、以為 npm 一定在
skill 假設自己在空目錄執行；假設 npm 可用、而且優先於其他套件管理器。換一個 repo 就露餡。
✗ 只在自己的 scratch 目錄跑
✓ 換一個真實 repo 再跑一次
03　執行假設 · EXECUTION
跳過 npm install、順序反了
agent 以為依賴已經裝好，所以跳過安裝；或在 Vite 專案還不存在時，就先去設定 Tailwind。
✗ 只看最後 app 能不能跑
✓ 看 trace 裡的指令與順序

01

硬規則：codex exec 預設在受限 sandbox；要寫檔才加 --full-auto —— 自動化時尤其只給完成任務所需的最小權限。

一開始，先明確地啟用它：用 /skills 指令，或用 $ 前綴直接點名，在一個真實的 repo 或 scratch 目錄裡跑，然後看它在哪裡壞掉。這個階段要找的是「misses」：完全不觸發、觸發得太積極、或是跑了但偏離你設計的步驟。

此時你不是在追求速度或精緻度，而是在找 skill 悄悄做出的隱藏假設。原文把它們分成三種：

Triggering

觸發假設

像「set up a quick React demo」這種應該觸發 setup-demo-app 的 prompt 卻沒觸發；或是「add Tailwind styling」這種更泛用的請求，反而意外觸發了它。

Environment

環境假設

skill 假設自己在空目錄裡執行；假設 npm 可用，而且比其他套件管理器優先。

Execution

執行假設

agent 以為依賴已經裝好，所以跳過 npm install；或是在 Vite 專案還不存在時就先設定 Tailwind。

準備好要重複執行時，改用 codex exec

當你想讓這些執行變得可重複，就切換到 codex exec。它是為自動化與 CI 設計的：進度串流到 stderr，只把最終結果寫到 stdout。這個分工讓執行結果很容易被腳本擷取、存檔、事後檢視。

codex exec 預設在受限的 sandbox 裡執行。如果任務需要寫檔，就加上 --full-auto。原文的通則是：尤其在自動化時，只給完成任務所需的最小權限。

terminal · 一次基本的手動執行 
codex exec --full-auto \
  'Use the $setup-demo-app skill to create the project in this directory.'
為什麼 stderr / stdout 分開很重要

自動化的前提是「輸出可以被機器讀」

互動模式下，進度訊息和結果混在一起沒關係，反正是人在看。但一旦要寫 harness，你需要 stdout 只有結果（下一章會讓它變成 JSONL），進度另外走 stderr。這樣 res.stdout 直接存檔就是 trace，不用再去清雜訊。

關鍵觀念 · 一

每一個手動修補，都是未來的 eval 候選

這第一輪手動跑，重點不在驗證正確性，而在發現邊界案例。你在這裡做的每一次修補：補上漏掉的 npm install、修正 Tailwind 的設定順序、把 trigger description 收緊一點，都是一個訊號，告訴你「這個行為值得被鎖住」。

把它們記下來。等到要大規模評估時，這份清單就是你的第一批測試案例。這樣你鎖定的是「曾經真的壞過的地方」，而不是憑空想像的情境。

Chapter 05 · Get started with lightweight deterministic graders

從輕量的確定性評分器開始

這是評估步驟的核心：用 codex exec --json，讓你的 eval harness 針對「實際發生了什麼」打分，而不只是最終輸出看起來對不對。

為什麼要兩層，不是一層
確定性檢查回答「有沒有做到基本功」：快、免費、失敗直接對到某個事件。rubric 回答「有沒有照你要的方式做」—— 元件寫法、樣式慣例這類規則抓不到的東西。
直接可以拿去用的三條
① 用 codex exec --json，讓 stdout 變成 JSONL；每一次指令執行都是一個依序的 item.* 事件。
② 評分那次 codex exec 不給寫檔權限、加 --output-schema：固定欄位（overall_pass、score、checks[id, pass, notes]）才能 diff。
③ 檢查失敗時打開 JSONL 檔 —— 可解釋，是確定性檢查最大的價值。
適用範圍：rubric 可信的前提是「唯讀 ＋ 逐項可判定」—— 一個總分很難追，四個布林值（vite、tailwind、structure、style）很好 diff。

開啟 --json 之後，stdout 會變成結構化事件的 JSONL 串流。這讓你可以直接寫出綁在具體行為上的確定性檢查，例如：

  • 它有沒有跑 npm install？
  • 它有沒有建立 package.json？
  • 它有沒有按預期順序呼叫預期的指令？

這些檢查刻意保持輕量。在加入任何模型評分之前，它們先給你快速、可解釋的訊號。

看懂事件

JSONL trace 裡有什麼

  • 每一行是一個 JSON 事件。指令執行會以 item.started 與 item.completed 出現，item.type 是 command_execution，item.command 是實際指令字串。
  • 事件依時間順序排列，所以「順序」也能檢查。
  • turn.completed 事件帶有 token 用量（usage.input_tokens、usage.output_tokens），第 7 章會用到。

一個「夠用就好」的 Node.js runner

原文的最小 harness 只做三件事：

1
對每條 prompt 執行codex exec --json --full-auto "<prompt>"
2
把 JSONL trace 存到磁碟stdout 就是 trace，直接寫檔，之後可以重看。
3
解析 trace，對事件跑確定性檢查每個檢查就是一個回傳 true / false 的小函式。
evals/run-setup-demo-app-evals.mjs（教學用精簡版） 
import { spawnSync } from "node:child_process";
import { existsSync, mkdirSync, readFileSync, writeFileSync } from "node:fs";
import path from "node:path";

// 1. 跑一條 prompt，把 JSONL trace 存到磁碟
function runCodex(prompt, tracePath) {
  const res = spawnSync("codex", ["exec", "--json", "--full-auto", prompt], { encoding: "utf8" });
  mkdirSync(path.dirname(tracePath), { recursive: true });
  writeFileSync(tracePath, res.stdout, "utf8");   // --json 時 stdout 就是 JSONL
  return { exitCode: res.status ?? 1, stderr: res.stderr };
}

// 2. 每行一個 JSON 事件
const parseJsonl = (text) => text.split("\n").filter(Boolean).map((line) => JSON.parse(line));

// 3a. 過程目標：有沒有跑 npm install？
const ranNpmInstall = (events) => events.some((e) =>
  (e.type === "item.started" || e.type === "item.completed") &&
  e.item?.type === "command_execution" &&
  String(e.item.command ?? "").includes("npm install"));

// 3b. 結果目標：package.json 有沒有被建立？
const hasPackageJson = (dir) => existsSync(path.join(dir, "package.json"));

// 單一案例示範
const trace = "evals/artifacts/test-01.jsonl";
runCodex("Create a demo app named demo-app using the $setup-demo-app skill", trace);
const events = parseJsonl(readFileSync(trace, "utf8"));

console.log({
  ranNpmInstall: ranNpmInstall(events),
  hasPackageJson: hasPackageJson("demo-app"),
});

這裡的價值在於：一切都是確定性的、可除錯的。某個檢查失敗時，你可以打開那份 JSONL 檔，逐行看到底發生了什麼。每一次指令執行都以 item.* 事件依序出現，所以 regression 很容易解釋、也很容易修。這正是這個階段你要的東西。

Chapter 06 · Conduct qualitative checks with Codex and rubric-based grading

規則到不了的地方，用 Codex 做 rubric 評分

確定性檢查回答的是「它有沒有做到基本功」，但回答不了「它有沒有照你想要的方式做」。

對 setup-demo-app 這種 skill，很多要求是質性的：元件結構對不對、樣式慣例有沒有遵守、Tailwind 是不是照預期的方式設定。這些用檔案存在檢查或指令計數很難抓到。

務實的解法，是在 eval pipeline 加上第二個「模型輔助」的步驟：

1
跑 setup skill這一步會把程式碼寫到磁碟。
2
對產出的 repo 跑一個唯讀的風格檢查第二次 codex exec，只看、不改。
3
要求結構化的回應讓 harness 能用一致的方式打分。

Codex 直接支援這件事：--output-schema 會把最終回應限制在你定義的 JSON Schema 裡。

一份小小的 rubric schema

先定義一個只包含你在意的檢查的 schema：

evals/style-rubric.schema.json 
{
  "type": "object",
  "properties": {
    "overall_pass": { "type": "boolean" },
    "score": { "type": "integer", "minimum": 0, "maximum": 100 },
    "checks": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "id":    { "type": "string" },
          "pass":  { "type": "boolean" },
          "notes": { "type": "string" }
        },
        "required": ["id", "pass", "notes"],
        "additionalProperties": false
      }
    }
  },
  "required": ["overall_pass", "score", "checks"],
  "additionalProperties": false
}

這個 schema 給你穩定的欄位：overall_pass、score、逐項的 check 結果。穩定的欄位才能被合併、diff、長期追蹤。

風格檢查的 prompt

接著跑第二次 codex exec，它只檢視 repo，並輸出符合 rubric 的 JSON：

terminal · 唯讀的風格檢查 
codex exec \
  "Evaluate the demo-app repository against these requirements:
   - Vite + React + TypeScript project exists
   - Tailwind is configured via @tailwindcss/vite and CSS imports tailwindcss
   - src/components contains Header.tsx and Card.tsx
   - Components are functional and styled with Tailwind utility classes (no CSS modules)
   Return a rubric result as JSON with check ids: vite, tailwind, structure, style." \
  --output-schema ./evals/style-rubric.schema.json \
  -o ./evals/artifacts/test-01.style.json

這就是 --output-schema 派上用場的地方。你拿到的不是難以解析、難以比較的自由文字，而是一個可預測的 JSON 物件，harness 可以跨很多次執行一致地打分。如果之後把這套 eval 搬進 CI，Codex GitHub Action 明確支援透過 codex-args 傳入 --output-schema，自動化流程也能強制同樣的結構化輸出。

護欄

讓模型評分可信的兩道限制

  • 唯讀：評分的那次 codex exec 不加 --full-auto，只看不改，評分者不會順手「修好」被評的東西。
  • 逐項可判定：rubric 拆成固定的 check ids（vite、tailwind、structure、style），每項各自 pass / fail 加 notes。一個總分很難追，四個布林值很好 diff。

確認 skill 不靠額外權限提升也能完成。最小權限預設一旦被悄悄放寬，自動化會把它放大。
跟 --full-auto 一樣：只給任務需要的。
注意：門檻要自己訂 —— 指令次數、token 用量都是「比上一版」的相對值，不是絕對數字。

快

計算 trace 裡 command_execution 的數量，抓住 agent 開始迴圈或重跑指令的 regression。

count(item.type === "command_execution")

快

turn.completed → usage.input_tokens / usage.output_tokens

Repo 乾淨度

快

確保執行沒有留下不想要的檔案。git 狀態應該是空的，或符合一份明確的 allow list。

git status --porcelain → 空 或 符合 allow list

Build 檢查

中

skill 完成後跑一次 build。這是更強的 end-to-end 訊號，能抓到壞掉的 import 或設錯的工具鏈。

npm run build → exit code 0

中

確認 skill 在不超出你預期的權限下仍能運作。一旦自動化，最小權限的預設最重要。

不靠額外權限提升也能完成

Runtime smoke 檢查

慢

啟動 dev server 用 curl 打一下，或跑一個現成的輕量 Playwright 檢查。選擇性使用：它增加信心，但花時間。

npm run dev → curl localhost → 200

六種擴充背後的模式是一致的：先用能解釋行為的快速檢查，只有當它們能真正降低風險時，才加入慢而重的檢查。快的檢查每次 commit 都跑，慢的檢查留給合併前或每日排程。

先加快的、能解釋行為的檢查；慢而重的檢查，只在它真的能降低風險時才加。 整理自第 7 節
思考題 · 03

上面六種檢查，哪些該進 CI 每次都跑，哪些只在本機或合併前跑？

決定的依據不是「哪個比較嚴謹」，而是成本乘以它能防住的風險。

把每種檢查標上「秒數」與「上次抓到 regression 的時間」。跑得快又常抓到問題的進 CI；慢又很少抓到問題的，降頻或拿掉。

Workshop · Apply it to your own skill

動手做：把這套流程搬到你自己的 skill 上

這一章不在原文裡。它把前面 8 節壓成一份下週就能執行的清單，並附上 Codex 與 Claude Code 的概念對照。

  1. 挑一個你最常用、也最常「怪怪的」skill寫下 3 到 5 條 must-pass，結果、過程、風格、效率四類至少各有一條候選。
  2. 建立 evals/<skill>.prompts.csv先放 4 條：明確呼叫、隱含呼叫、情境呼叫、負向對照。id、should_trigger、prompt 三欄。
  3. 用結構化輸出模式跑一輪，把 trace 存檔每條 prompt 一個 JSONL。先不寫檢查，先確定 trace 拿得到、看得懂。
  4. 寫兩個確定性檢查一個過程目標（某指令有出現）、一個結果目標（某檔案存在）。跑起來全綠再往下。
  5. 寫一份 rubric schema，加一次唯讀的風格檢查check ids 固定、每項 pass / fail 加 notes。評分那次不給寫檔權限。
  6. 從此以後，每次手動修補都加一列 CSV這是整套方法的引擎：真實失敗驅動覆蓋率，而不是憑空想像情境。

Reference · 名詞速查

關鍵名詞與旗標

讀原文或動手實作時會反覆遇到的 21 個詞。依「skill、eval、Codex 指令、範例工具」四群排列。

Skill
技能
一組有組織的 prompts 與指令，以目錄加 SKILL.md 的形式存在，讓 agent 在特定情境下用既定方式工作。
SKILL.md
技能主檔
YAML front matter（name、description）加上 Markdown 指令；可附資源與腳本。name 與 description 決定會不會被觸發。
Front matter
前言區塊
檔案開頭以三個連字號包住的 YAML 區塊。Codex 用其中的 name 與 description 判斷是否呼叫 skill、何時注入其餘內容。
$skill-creator
技能產生器
Codex 內建、本身也是 skill 的建立工具。會問 skill 做什麼、何時觸發、instruction-only 或 script-backed。
Definition of done
完成定義
可檢查的成功條件清單，例如 dev server 能啟動、指定檔案存在。沒有它就沒有可評估的東西。
Eval
評估
檢查模型輸出與產出過程是否符合意圖：一條 prompt、一次被擷取的執行、一小組檢查、一個可比較的分數。
Trace
執行軌跡
一次執行中所有事件的紀錄。本文中是 codex exec --json 輸出的 JSONL，含每次指令執行與 token 用量。
Artifacts
產出物
執行後留在磁碟上的東西：專案檔案、trace 檔、rubric 結果 JSON。確定性檢查與 rubric 都以它們為依據。
Deterministic grader
確定性評分器
用程式規則（檔案存在、指令出現、順序正確）給出可重現、可解釋的 pass / fail。快、免費、先跑。
Rubric grading
評分量表評分
由模型依明確條目（check ids）評質性要求，輸出結構化結果。用來評元件寫法、樣式慣例這類規則抓不到的東西。
Regression
退化
原本做對的行為在改動後變壞：不觸發、跳步驟、順序錯、留下多餘檔案。evals 的首要任務就是讓它清楚可見。
Negative control
負向對照
should_trigger=false 的 prompt，用來抓 false positive：skill 被過於積極地選中，使用者只想小改卻被建了新專案。
Thrashing
空轉
agent 迴圈、重複跑指令、浪費 token。用 command_execution 計數與 turn.completed 的 usage 抓。
codex exec
非互動執行模式
為自動化與 CI 設計：進度串流到 stderr，只把最終結果寫到 stdout，方便腳本擷取。
--full-auto
允許寫檔
解除預設 sandbox 的寫入限制。原則是最小權限：只在任務真的需要寫檔時才加。
--json
結構化事件輸出
讓 stdout 變成 JSONL 事件流。item.started / item.completed 記錄指令執行，turn.completed 記錄 token 用量。
--output-schema
輸出結構限制
用 JSON Schema 約束最終回應的形狀，讓 rubric 結果變成可 diff、可追蹤的固定欄位。
command_execution
指令執行事件
JSONL 中代表一次指令執行的 item 類型，帶有 command 字串。確定性檢查與空轉計數的主要對象。
JSONL
逐行 JSON
每一行是一個獨立 JSON 物件的串流格式。逐行解析即可，適合存檔與事後重看。
Codex GitHub Action
CI 整合
在 GitHub Actions 中執行 Codex 的 action；可透過 codex-args 傳入 --output-schema，讓 CI 也強制結構化輸出。
Vite · Tailwind
範例工具鏈
範例 skill 用的前端工具：Vite 提供 React + TypeScript 樣板與建置，Tailwind 以 @tailwindcss/vite plugin 設定並在 CSS 內 import。
