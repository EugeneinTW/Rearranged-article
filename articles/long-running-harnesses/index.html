Effective Harnesses for Long-Running Agents每個新的工作階段都從零開始 交接要寫在檔案裡

一個大專案，agent 要跨好幾個 context window 才做得完，每個新的 session 卻都不記得前一個做了什麼。Anthropic 這篇工程文章分享他們讓 Claude 長時間寫程式的做法：第一個 session 的初始化 agent 搭好功能清單、進度檔、init.sh 與 git，之後每個 session 的 coding agent 一次只做一個功能，像使用者一樣測過，收尾留下 commit 與進度。本頁分十一章重述。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

長任務的難處，在 session 之間的交接

一個 context window 裝不下整個專案，agent 只能分好幾個 session 做，而每個新的 session 都不記得上一個。這篇講的是怎麼把交接做好，讓工作接得下去。

這篇是 Stanford CS 329Z 第 9 週的選讀，屬於 Coding Agents & Proactive Agents 分區的〈Coding & Software Agents〉那一講。那一講的題目有：coding agent 從頭到尾怎麼運作；SWE-agent、Claude Code、OpenHands 的架構；scaffold 是一種設計決策；SWE-bench 與「4-tuple framework」的實戰；以及 agent 時代軟體開發的未來。同一講的必讀是 Yang 等人的〈SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering〉與 Wang 等人的〈OpenHands: An Open Platform for AI Software Developers as Generalist Agents〉；另兩篇選讀是 Anthropic 的〈Claude Code: Best Practices for Agentic Coding〉，以及 Jimenez 等人的〈SWE-bench: Can Language Models Resolve Real-World GitHub Issues?〉。

整理者把講題和原文對了一下。「scaffold 是設計決策」這一題，這篇給了一個具體的例子：它沒有談換模型，改的是模型外面那一層，也就是兩份不同的開場提示、初始化 agent 建好的檔案，以及測試用的瀏覽器工具（本頁第 2 到 6 章）。原文把這一層叫 harness，只在一處把初始化 agent 搭好的環境稱作 scaffolding。「coding agent 從頭到尾怎麼運作」對應第 6 章每個 session 的開場與第 4 章的收尾；「軟體開發的未來」對應第 8 章作者留下的開放問題。SWE-agent、OpenHands、Claude Code 的架構，以及 SWE-bench 與 4-tuple framework，這篇都沒有談；4-tuple framework 是課程的用語，原文沒有出現，要看同一講的其他讀物。

原文是 Anthropic 工程部落格 2025 年 11 月 26 日的文章，文末寫明由 Justin Young 執筆。它分享的是 Anthropic 內部的實驗，文中關於 Claude、Claude Agent SDK、Opus 4.5 這些自家產品與模型的說法，以及實驗裡的觀察，本頁都寫成「作者說」；產品名照原文，Opus 4.5 是寫作當時的模型。原文附的程式範例放在另一個 quickstart 專案，本頁沒有引用；頁面上的程式片段都是依正文改寫的教學用精簡版。

原文分四大段：先講長時程 agent 的問題與兩段式的解法，再細講環境裡的三樣東西（功能清單、漸進推進、測試），接著講每個 session 怎麼快速進入狀況，最後是一張四種失敗的整理表與未來方向。本頁照這個順序走，把第一大段拆成「失敗」與「解法」兩章，表格獨立成第 7 章。

整理者的補充：本站的〈Effective context engineering for AI agents〉談 compaction 與結構化筆記這類長時程任務的做法，〈Building effective agents〉談 agent 的基本模式，〈Demystifying evals for AI agents〉談怎麼評估 agent，Letta 的〈Agent Memory: How to Build Agents That Learn and Remember〉談 agent 的記憶；本頁不用它們的內容擴寫。

給初學者

先把六個名詞對齊

  • Context window：模型一次看得到的內容上限。原文說大部分複雜的專案，沒辦法在一個視窗裡做完。
  • Session：agent 的一段工作，從一個新的 context window 開始；新的 session 不記得前一個發生過什麼。
  • Compaction（壓縮）：一種 context 管理的能力，讓 agent 做一件事時不會把 context window 用完。第 1 章會講它為什麼不夠。
  • Agent harness：包在模型外面、讓它能當 agent 運作的那一層系統。原文說 Claude Agent SDK 是一個通用的 agent harness。
  • 初始化 agent 與 coding agent：原文的兩種 agent。前者只在第一個 session 搭環境，後者在之後每個 session 寫程式。
  • git commit：把程式碼目前的樣子存成一個版本，附一段訊息說明改了什麼；之後可以退回任何一個存過的版本。
新的 session 不記得過去，所以過去要寫在它讀得到的地方。 序章核心觀念

開發者越來越常把要做好幾個小時、甚至好幾天的複雜任務交給 agent，但讓 agent 在好幾個 context window 之間穩定地往前推，至今仍是還沒解決的問題。難處在於 agent 只能一段一段地工作：每個 session 是分開的，新的 session 開始時，不記得前一個發生過什麼。context window 有上限，大部分複雜的專案又沒辦法在一個視窗裡做完，所以 agent 需要一個方法，跨過兩個 session 之間的缺口。

關鍵觀念 · 一

每一班都不記得上一班的工程師

作者的比喻：想像一個軟體專案由輪班的工程師負責，每個新來的工程師，都完全不記得上一班發生了什麼。長時程的 agent 就是這個處境，每個 session 是一班。

這個比喻也預告了解法的方向。作者在第一大段的結尾說，他們的做法取自優秀的軟體工程師每天在做的事（第 2 章）。

實驗用的是 Claude Agent SDK。作者說它是一個強大、通用的 agent harness，擅長寫程式，也能做其他需要用工具蒐集脈絡、規劃、執行的任務；它有 compaction 這類 context 管理的能力，讓 agent 做一件事時不會把 context window 用完。照理說，有了這些，agent 應該能一直做有用的事，做多久都行。

實驗的結果不是這樣。作者說 compaction 不夠：直接拿來用，即使是 Opus 4.5 這樣的前沿模型，在 Agent SDK 上跨好幾個 context window 迴圈地跑，如果只拿到一句高階的 prompt，例如「做一個 claude.ai 的複製品」，也做不出上線品質的 web app。作者看到的失敗有兩種：

失敗什麼時候發生什麼
一次做太多專案一開始想一口氣把整個 app 做出來，常在實作到一半時用完 context；下一個 session 接到一個做了一半、沒有紀錄的功能，只能猜上一輪做了什麼，還要花不少時間讓基本的 app 重新能跑
太早宣布完成專案後期已經做好一些功能之後，後來的 agent 看了看四周，發現已經有進度，就宣布工作完成

第一種失敗，有 compaction 也會發生。作者說，compaction 交給下一個 agent 的指示，不一定完全清楚；上一個 session 停在一個做了一半的功能上，下一個 session 看到的是沒有說明的程式碼。第 02 卡把兩種失敗排在一條 session 的時間線上。

補充說明

實驗的條件

這兩種失敗出現在同一組條件下：模型是 Opus 4.5，跑在 Claude Agent SDK 上，跨好幾個 context window 迴圈執行，而使用者只給了一句高階的 prompt。後面幾章的做法，都加在模型外面這一層：換開場的提示、先建好檔案、給測試工具；原文沒有談換模型。

更新版的 Claude 4 prompting guide 分享過跨多個 context window 工作的做法，其中一種 harness 結構，是第一個 context window 用一份不同的 prompt。作者說，這份不同的 prompt 要初始化 agent 把之後的 coding agent 需要的脈絡全部備好；原文這一大段挑了這種環境裡的幾個重要元件細講，第一個是功能清單。

功能清單針對的是第 1 章的兩種失敗：一口氣做完整個 app，以及太早認定專案完成。作者要初始化 agent 寫一份完整的功能需求檔，把使用者最初的 prompt 展開。以 claude.ai 的複製品為例，清單超過 200 項，例如「使用者可以開一段新對話、輸入問題、按 Enter，看到 AI 的回應」。每一項一開始都標成 failing，後來的 coding agent 就有一份清楚的大綱，知道完整的功能長什麼樣。原文列了清單裡的一項，下面是精簡改寫的版本：

示意 · 功能清單的一項（依原文 JSON 精簡改寫，內容與註解是整理者的中文） 
{
  "category": "functional",
  "description": "按下 New Chat 會開一段新對話",
  "steps": [
    "打開主畫面，點 New Chat",
    "確認出現新對話，聊天區是歡迎畫面",
    "確認側欄列出這段對話"
  ],
  "passes": false    // coding agent 唯一能改的欄位
}

作者要 coding agent 編輯這份檔案時，只能改 passes 這個欄位的狀態；提示裡還用了很強硬的措辭，說刪掉或改寫測試是不可接受的，理由是那可能讓功能漏掉或出 bug。

"It is unacceptable to remove or edit tests" 「刪掉或改寫測試，是不可接受的。」這是作者給 coding agent 的指示裡的一句，後面接的理由是可能漏掉功能或留下 bug。

檔案格式也是試出來的。作者說，做了一些實驗之後，他們選了 JSON：和 Markdown 比起來，模型比較不會不當地改動或覆寫 JSON 檔。原文沒有再解釋原因。

整理者的讀法

清單同時管住兩件事

「全部先標 failing」讓每個 session 都看得到還剩多少沒做；「只准改 passes」讓這份進度表不會被 agent 自己改寫。兩者合起來，「做完了沒」由清單回答，不由某一個 session 的 agent 看一看就決定。第 7 章的表格裡，功能清單也同時對上兩種失敗。

Chapter 08 · Future work · Acknowledgements

這只是一種解法，還有兩題沒答案

作者說這是讓模型跨很多個 context window 漸進推進的一組可能的解法。還沒答案的有兩題：一個通用的 coding agent 好，還是分工的多 agent 好；以及這些經驗能不能用到 web app 以外。

作者在結尾說，這份研究示範的是長時程 agent harness 裡的一組可能的解法，讓模型能在很多個 context window 之間漸進地推進；還有一些問題沒有答案。

最主要的一題，是單一、通用的 coding agent 是否在各種情境下都表現最好，還是多 agent 的架構能做得更好。作者認為，專門的 agent，例如負責測試、品質保證（QA）或清理程式碼的 agent，在軟體開發生命週期的各種子任務上，可能做得更好。這是作者的推測，原文沒有實驗結果。

第二題是範圍。這個 demo 是針對全端 web app 的開發調整的；作者說，未來的方向是把這些發現推廣到其他領域。他認為部分或全部的經驗，很可能適用於科學研究或財務建模這類需要長時間運作的 agent 任務。

文末的致謝寫明這篇由 Justin Young 執筆，並列出多位參與的同事；作者說這份成果來自 Anthropic 好幾個團隊的共同努力，特別是 code RL 與 Claude Code 團隊，讓 Claude 能安全地做長時程、自主的軟體工程。

初始化 agent 和 coding agent 是兩套不同的系統嗎？
不是。原文的註腳說，它們只差在一開始的 user prompt；system prompt、工具、整個 agent harness 都一樣（第 2 章）。
有 compaction 了，為什麼還要這些檔案？
作者說 compaction 不夠：它交給下一個 agent 的指示不一定完全清楚；只給一句高階 prompt 時，agent 還是會一次做太多，或太早宣布完成（第 1 章）。
功能清單為什麼用 JSON，不用 Markdown？
作者說試過之後選了 JSON，因為模型比較不會不當地改動或覆寫 JSON 檔；原文沒有進一步解釋（第 3 章）。
這套做法只適用於 web app 嗎？
原文的 demo 針對全端 web app。作者認為部分或全部的經驗可能適用於科學研究、財務建模這類長時間的任務，但這是未來的方向，還沒有驗證（本章）。
整理者的思考題 · 03

如果把開發流程交給一組專門的 agent，你會怎麼分工？

原文提了測試、品質保證、清理程式碼三種專門的 agent。對照你團隊現在的分工，哪一種最值得先拆出去？它開場要讀什麼，收尾要留下什麼？

整理者的建議：沿用本頁的交接方式來想，每個專門的 agent 都讀寫同一份功能清單與進度檔，分工才接得起來。這是整理者的延伸，原文沒有談多 agent 之間怎麼交接。

Workshop · Apply it yourself

動手做：替長任務搭一套交接

這一章不在原文裡。它把前面的內容壓成一份可以馬上執行的清單，讓一個一次做不完的大任務，改成一個個 session 接力。

  1. 把一句話的需求，展開成 JSON 功能清單每一項寫描述與測試步驟，全部先標 "passes": false。
  2. 第一個 session 用另一份提示，只搭環境寫 init.sh、開一個進度檔、做第一次 git commit，先不急著寫功能。
  3. 在 coding agent 的提示裡寫死開場pwd、讀進度檔與 git log、讀清單挑優先順序最高的一項。
  4. 開工前先跑一次基本的端對端測試用 init.sh 啟動 dev server；壞了先修既有的 bug，再做新功能。
  5. 一次只做一項這一項測過、存好，才碰下一項。
  6. 像使用者一樣測過，才把 passes 改成 true給它瀏覽器自動化工具；提示裡寫明不准刪改測試。工具看不到的功能，另外安排人工檢查。
  7. 收尾：寫清楚的 commit，加一段進度摘要commit 訊息說明做了什麼；進度檔記下這個 session 的結果，留給下一個 session 讀。

Reference · 名詞速查

二十個名詞，看懂長任務的 harness

依「問題、兩種 agent、環境裡的檔案、做法、未來」的順序排，解釋是整理者依原文的用法寫的。

Long-running agent
長時程 agent
要花好幾個小時、甚至好幾天，跨很多個 context window 才做得完任務的 agent。
Context window
脈絡視窗
模型一次看得到的內容上限；原文說大部分複雜的專案，一個視窗做不完。
Session
工作階段
agent 的一段工作，從一個新的 context window 開始；新的 session 不記得前一個。
Compaction
壓縮
讓 agent 做一件事時不會用完 context window 的 context 管理能力；原文說它交給下一個 agent 的指示不一定完全清楚。
Agent harness
agent 的外層系統
包在模型外面、讓它能當 agent 運作的那一層；這篇的做法都加在這一層。
Claude Agent SDK
Claude 的 agent 開發套件
原文說它是通用的 agent harness，擅長寫程式，也能做其他用工具蒐集脈絡、規劃、執行的任務。
Initializer agent
初始化 agent
第一個 session 的 agent，用專門的提示搭好環境：init.sh、進度檔、第一次 commit、功能清單。
Coding agent
寫程式的 agent
之後每個 session 的 agent，一次推進一個功能，收尾留下 commit 與進度摘要；和初始化 agent 只差開場的 user prompt。
Feature list
功能清單
把使用者的 prompt 展開成的功能需求檔，用 JSON 寫；claude.ai 複製品有 200 多項，一開始都標 failing。
passes
通過欄位
功能清單每一項的狀態；coding agent 只准改它，仔細測過才改成 true。
claude-progress.txt
進度檔
記錄 agent 做過什麼的文字檔；和 git 歷史一起，讓新的 session 很快看懂狀況。
init.sh
啟動腳本
初始化 agent 寫的腳本，用來啟動 dev server；coding agent 開場先讀它、跑它。
Dev server
開發用伺服器
在本機跑 app 的伺服器；每個 session 的基本測試就在它上面跑。
Clean state
乾淨的狀態
可以合併進 main branch 的程式碼：沒有大 bug、整齊、有文件，下一位開發者不用先收拾別的爛攤子。
One-shot
一次做完
想在一個 session 裡把整個 app 做出來；原文說的第一種失敗。
Incremental progress
漸進推進
一次只做一個功能，每一步都用清楚的訊息 commit、寫進度摘要。
End-to-end testing
端對端測試
照使用者的路徑把整個功能走一遍；原文要 agent 用瀏覽器自動化工具做。
Browser automation
瀏覽器自動化
讓程式操作瀏覽器、點按鈕、讀畫面；原文說給 Claude 這類工具，表現大幅提升。
Puppeteer MCP
瀏覽器操作伺服器
原文讓 Claude 操作瀏覽器、拍下截圖的 MCP 伺服器；透過它看不到瀏覽器原生的 alert 對話框。
Multi-agent architecture
多 agent 架構
把工作分給幾個專門的 agent，例如測試、品質保證、清理程式碼；原文列為還沒有答案的問題。
