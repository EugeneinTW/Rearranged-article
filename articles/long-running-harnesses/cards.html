02 / 08兩種失敗：做太多、太早收工
壓縮留不住工作狀態：一次做太多，或太早收工
Opus 4.5 在 Claude Agent SDK 上跨好幾個 context window 迴圈地跑，只拿到一句高階 prompt（做一個 claude.ai 的複製品），做不出上線品質的 web app；作者看到兩種失敗

失敗一跨過兩個 session：context 用完的地方，就是下一個 session 接手的地方；compaction 交給下一個 agent 的指示，不一定完全清楚。
失敗一：一次做太多
想一口氣把 app 做完，context 常在實作中途用完；
下一個 session 接到做一半、沒紀錄的功能。
它得先猜發生了什麼，再花時間讓 app 重新能跑。
失敗二：太早宣布完成
已經做好一些功能之後，後來的 agent
看了看四周、發現有進度，就宣布工作完成。
原文說這種失敗常出現在專案後期。
compaction 不夠
它讓 agent 做事時不會用完 context window，
但交給下一個 agent 的指示不一定完全清楚。
所以失敗一在有 compaction 時也會發生。
共同前提：Opus 4.5 在 Claude Agent SDK 上迴圈執行，只給一句高階 prompt；把兩種失敗排在 session 的時間線上是整理者的畫法，事件都出自原文。

05 / 08一次一個功能，壞了就退回
一次只做一個功能，壞了就用 git 退回
有了功能清單，coding agent 一次只做一項；作者說這是對付「一次做太多」的關鍵，commit 加進度摘要則讓下一個 session 不必再猜
✗ 一次做很多
✓ 一次一個功能
Session：想一口氣做出整個 app
context 在實作中途用完
留下一個做一半的功能
沒有留下紀錄
下一個 session：先猜、先修
Session：從清單挑一項功能
只做這一項，做完、測過
git commit
訊息寫清楚做了什麼
進度摘要
寫進進度檔
下一個 session：讀紀錄就接上
有 compaction 也一樣：它交給下一個 agent 的指示，不一定完全清楚。
改壞了也退得回去：git 能退回改壞的程式，恢復到能動的版本。
乾淨的狀態
原文的定義：可以合併進 main branch 的程式碼，沒有大 bug、整齊、有文件；下一位開發者不必先收拾爛攤子，就能開始做新功能
時間花在猜與修
下一個 session 接到做一半、沒紀錄的功能，
只能先猜發生了什麼，再花時間讓 app 重新能跑。
失敗一的代價，落在下一個 session 身上。
每一步都退得回去
作者說最有效的是用描述清楚的訊息 commit、
把進度摘要寫進進度檔：壞了能退，下一輪也不必猜。
作者說，這也提高了效率。
注意：左右兩條流程是整理者依原文的描述畫的；作者說一次只做一項是對付「做太多」的關鍵，commit 加進度摘要是他們找到最有效的收尾方式。
06 / 08像使用者一樣測過才算
只跑單元測試不夠，要像使用者一樣點過一遍
最後一種失敗：沒測好就把功能標成完成。沒有明說時，Claude 會跑單元測試、用 curl 打 dev server，卻看不出功能沒有端對端跑通
✗ 只從程式這一側測
✓ 從瀏覽器，像使用者一樣測
改完一個功能的程式
跑單元測試
用 curl 打 dev server
把功能標成完成
其實沒有端對端跑通
沒有明說時，Claude 也會測；只是看不出這個功能沒有端對端地運作。
改完一個功能的程式
明說：用瀏覽器自動化工具測
像真人使用者一樣走一遍
例如開新對話、送出訊息、看到回應，邊測邊截圖
找到只看程式看不出的 bug
原文附了 Claude 透過 Puppeteer MCP 測 claude.ai 複製品時拍下的截圖。
單元測試與 curl 不夠
Claude 會改程式、也會測，
卻看不出功能沒有端對端跑通，就標成完成。
這是作者看到的最後一種重大失敗。
表現大幅提升
明說要用瀏覽器自動化、像真人一樣測之後，
Claude 大多能找出並修掉只看程式看不出的 bug。
以 web app 來說，作者說大多做得好。
看不到的，就測不到
Claude 的視覺與瀏覽器自動化都有極限；
透過 Puppeteer MCP 看不到瀏覽器原生的 alert。
依賴這種對話框的功能，bug 比較多。

07 / 08開工前先確認 app 還能動
開工前先確認 app 還能動，壞了先修
每個 coding agent 開場先跑一串步驟，有些很基本但仍然有用；claude.ai 複製品一律先啟動 dev server，開一段新對話、送訊息、等回應
Step 1　pwd
確認工作目錄；
只能改這裡面的檔
Step 2　git log 與進度檔
看最近的 commit 與進度，
知道最近在做什麼
Step 3　讀功能清單
挑優先順序最高、
還沒完成的一項
Step 4　init.sh
啟動 dev server，
不必再摸索怎麼跑
壞了就先修
Step 5　基本的端對端測試
開新對話、送訊息、
等到回應
前三步
回答三個問題：我在哪、最近做了什麼、這一輪做哪一項
壞了：先修既有的 bug
直接做新功能，問題很可能更糟
沒壞：開始做新功能
一次只做一項（第 05 卡）
典型的開場
原文 log 的順序：先說要弄清楚專案狀態 → pwd → 讀進度檔 → 讀功能清單 → git log → 用 init.sh 重啟 server → 驗證基本功能 → 開始做新功能
三個理由
前三步：在哪、做到哪、做哪項
pwd 確認只能改哪個目錄；git log 與進度檔
交代最近的工作；功能清單決定這一輪做哪一項。
作者說有些步驟很基本，但仍然有用。
init.sh 省下摸索的 token
初始化 agent 先寫好啟動 dev server 的腳本，
每個 session 不必再想辦法弄清楚怎麼測。
表格的第四種失敗，就是花時間摸索怎麼跑 app。
先測再做
先開 server、開新對話、送訊息、等回應；
app 若被留在壞掉的狀態，馬上發現、先修。
直接做新功能，作者說問題很可能更糟。
注意：五格依原文的條列與 claude.ai 複製品的做法排；log 裡是先讀進度檔與功能清單、再看 git log，兩種順序原文都有。
