軟體工程 agent 訓練資料， 先建環境 再造 bugSWE-smith：每個 repo 建一次 執行環境， 在裡面合成 五萬個任務

SWE-bench 這類基準讓 agent 在真實的 repo 裡修 bug、用單元測試判對錯；拿同一套方法收訓練資料時，每個任務都要有自己的執行環境，篩到最後只剩幾千個。這篇 Stanford、Princeton 團隊的論文把順序倒過來：每個 repo 先建一次環境，再在裡面合成會弄壞測試的 bug，從 128 個 Python repo 造出約五萬個任務。作者用它產生專家軌跡、微調出 SWE-agent-LM-32B，在 SWE-bench Verified 拿到 40.2%，也用消融檢查哪些資料性質真的影響訓練。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Prologue · 整理者的引言

從執行結果大量造資料，再用執行結果篩

Stanford CS 329Z 第 7 週「Data Selection & Quality」那一講（Data for Agentic Systems 分區），談怎麼找出資訊量最大的資料、篩選與挑選的策略、小而精準的 benchmark、標註做法、品質評估，以及從 agent 的執行軌跡建資料集。這篇 SWE-smith 是這一講的必讀。

同一講另一篇必讀是 Shankar 等人的〈Who Validates the Validators?〉，選讀是 LIMA。下面這段是整理者的連結，SWE-smith 本身沒有引用這兩篇：SWE-smith 把資料品質的把關幾乎都交給「跑測試」這種確定的檢查，bug 要弄壞測試才留、軌跡要真的解出來才留；〈Who Validates the Validators?〉處理的是檢查本身要靠 LLM 時，怎麼確認它和人的判斷一致；LIMA 走另一個方向，用少量精挑的例子做微調。三篇放在一起，剛好是這一講的三種取向：大量合成再用確定的檢查篩、先驗證評估者、少而精。

先把幾個名詞對齊

  • SWE-bench：從 12 個 Python repo 的真實 PR 與 issue 做成的基準，共 2,294 題。模型拿到 repo 與 issue，改完之後跑單元測試判對錯。Lite 是 300 題的較易子集，Verified 是人工挑過、描述較清楚的 500 題。
  • SWE-agent：讓 LM 在 repo 裡工作的 agent 系統，提供看檔、改檔、執行指令的介面（Agent Computer Interface，ACI），每一輪產生一組想法與動作。
  • Docker 映像：把作業系統、套件與 repo 打包好的環境快照，任何機器拉下來都能跑出同樣的測試結果。
  • 拒絕取樣微調（rejection sampling fine-tuning，RFT）：讓強模型去解題，只拿解出來的那些紀錄去微調較弱的模型。
  • pass@1：每題只試一次的解題率；pass@k 是試 k 次、只要有一次解出就算。
要教模型修 bug，先要有一個跑得起測試的地方；SWE-smith 把這件事從每題做一次，改成每個 repo 做一次。 整理者的引言

論文先交代處境。SWE-agent、OpenHands 這類 LM agent 在 SWE-bench 上進步很快，但效果最好的系統仍然靠閉源模型。作者認為開源模型卡在缺少大量、高品質的訓練資料；要讓開放的研究在這個領域跟得上，就得有能大量收集軟體工程訓練資料的基礎設施。

現有的資料來源有兩種。第一種是直接爬 GitHub 的 PR 與 issue：量可以很大，但沒有執行環境、也沒有測試，模型產生的解法無從驗證，只能學程式碼的表面形式，或拿字串相似度當獎勵。第二種延續 SWE-bench 的收集法，把它套到另一批 repo 上做訓練資料，例如 SWE-gym。每個任務都能跑單元測試，可以產生 agent 軌跡、再用測試結果篩選，拿來訓練與蒸餾 agent 很有彈性。問題出在規模：SWE-bench 的篩選只留下同時解決了一個 issue、又對單元測試做了有意義修改的 PR，剩下的不多；替每個任務建執行環境，也要大量人工介入。

摘要把結果說得很直接：既有的資料集最多幾千個實例、來自 11 個以下的 repo，整理的流程常要上百小時人工，配套的環境要好幾 TB。整理者拿表 2 核對：這句話對得上有執行環境、實例數在幾千個的 R2E-gym 子集（4.6k 個、10 個 repo）與 SWE-gym（2.4k 個、11 個 repo）；R2E 有 137 個 repo 但只有 250 個任務，沒有環境的 SWE-fixer 則有 115k 個任務。所以「最多幾千個、11 個以下 repo」說的是能用執行結果驗證的那一類資料集。

SWE-smith 的核心原則寫在第 2 節的第一句：

"define an execution environment first, and then synthesize task instances within the environment" 「先定義執行環境，再在環境裡合成任務實例」：第 2 節開頭的一句。作者說這只是把 SWE-bench 的做法簡單地倒過來。

SWE-bench 先找任務，再試著替每一個任務建環境；SWE-smith 先替一個 repo 建好環境，再在裡面製造任務。作者說關鍵的洞見是：拿執行結果做驗證，不只能檢查解法對不對，也能反過來挑出真的造成軟體退化、會弄壞測試的 bug 候選。這樣一來，任務不必等真實世界裡剛好有人提 issue、又剛好改了測試；只要 repo 有一套會通過的測試，就能在裡面造出上百到上千個任務。

附錄 C.2 用同一個 repo 做了正面對照。pallets/flask 是 SWE-bench 的 12 個測試 repo 之一。SWE-bench 從它的 2,434 個 PR 裡，篩出 107 個連到 issue、又新增了測試的，最後建得起執行環境的只有 11 個，佔 2,434 個的 0.45%。收這 11 個任務要爬 PR、判斷每個任務對應的 repo 版本、替每個版本寫安裝與測試規格、反覆跑驗證，作者估計花了約 38 小時人工。SWE-smith 則替最新的 commit 寫一次安裝與測試規格（10 分鐘），用 LM 改寫函式造 bug（23 分鐘，花 2.47 美元），得到 402 個候選，驗證 14 分鐘後留下 267 個。換算成每個任務，SWE-bench 的做法約 207.27 分鐘，SWE-smith 約 0.176 分鐘（約 10.6 秒）加 0.00613 美元的 API 費用。三段時間相加約 47 分鐘，是整理者算的。

程序化修改完全不花 API 費用：把函式或類別轉成 AST，套一個固定的變換，再轉回原始碼。表 8 列了 13 種，分成四類：類別（刪方法、刪父類別、打亂方法的順序）、控制流程（對調 if 與 else 的內容、打亂函式的各行）、運算式（常數加減一、刪掉連續運算的一段、交換運算元、換運算子）、刪除（刪迴圈、條件、賦值、try 或 with 包裝）。每種變換先用表 7 的條件過濾候選，例如要刪條件就只挑有條件判斷的函式；也用一個「複雜度」分數（條件區塊、迴圈、布林運算、例外處理與比較運算的數量加總）濾掉 getter、setter 這類太簡單的函式。最後用 likelihood 控制套用的頻率，例如 0.5 表示函式裡每個條件各有一半的機會被刪，避免一次改得太難。

合併策略把已經驗證過的 bug 疊起來，做出要改好幾個地方的任務。同一個檔案裡有兩個以上的函式級 bug 時，把它們的 patch 合成一個（演算法 1）；也可以把同一個模組裡改到不同檔案的 bug 合併，只留改到兩個以上檔案的組合（演算法 2）。模組指原始碼裡的子目錄，例如 sklearn/feature_extraction，實際合併時設 depth＝2，也就是主程式資料夾底下的第一層；作者的理由是，SWE-bench 裡改到兩個以上檔案的任務，有 75% 改的檔案在同一個子模組。每組 bug 依序套上，全部都套得上才存下合併後的 patch，再當成一個 bug 重新驗證；為了不讓同一個 bug 被重複用，用過的 bug 會從剩下的組合裡剔除。同檔合併常用的參數是每組 2 到 4 個 bug、每個檔案最多 3 組、最多嘗試 40 組。

PR 反轉以真實的 PR 為原料。作者照 SWE-bench 的方式爬 2023 年 1 月 1 日之後的 PR（少數 repo 也爬更早的），對 PR 改到的每個檔案，把這個檔案在 PR 裡的變更與它目前的原始碼交給 LM，要它改寫整個檔案、把 PR 的變更反轉回去，再把各檔案的改動合成一個 patch。為什麼要用 LM？他們一開始直接跑 git apply --reverse，結果多數 patch 都失敗；檢查 sqlfluff 的 100 個 PR 後發現，PR 的變更多半還在，只是相關程式碼的位置被後來的改動移動了。推理模型（例如 o3-mini）特別擅長這件事。改到超過 8 個檔案的 PR 不做，因為 SWE-bench 裡改超過 6 個檔案的任務從來沒有被解出過，專家模型沒有機會。拿 django 的 100 個 SWE-bench 任務試做，重建出 92 個，其中 84 個弄壞的測試完全相同，另外 8 個弄壞的是其中一部分，因為有些測試後來被刪了。

第 2.2 節解釋成本與產率的差別。三種用 LM 的做法裡，PR 反轉最貴，因為要改寫整個檔案，另外兩種只改一個函式。產率受兩件事限制：改到的地方沒有測試覆蓋，或候選根本沒有造成相關的問題。LM 重寫被要求的是重新實作、不是造 bug，產率 35.0%；直接要 bug 的 LM 改寫是 56.0%。

附錄 C.1 的表 10 把程序化修改拆開來看：打亂類別方法的產率只有 1.88%，對調 if 與 else 是 49.44%，刪賦值 48.65%。同一節的正文寫的是 1.93% 與 47.04%，還說 PR 反轉的產率最低、是 13.18%；表 10 與表 1 的 PR 反轉都是 33.8%，全表最低的是打亂類別方法。正文與表對不上，這裡兩邊都寫；比對 v1 的 PDF，這三個數字在 v1 的正文就已經是這樣。表 11 則依 repo 分：產率 0 到 25% 的 repo 有 10 個、25 到 50% 的 31 個、50 到 75% 的 60 個、75 到 100% 的 27 個，作者觀察到測試覆蓋率低的 repo，產率也低。

  - 模仿示範的風格與結構，連排版凌亂、閒聊都照學
  - 不要解釋修法或 bug 的成因，只寫怎麼重現
  - 不要提 pytest，也不要說是哪個測試失敗
  - 盡量附重現程式：印出錯誤，或並列實際值與預期值

第 4.1 節的消融：隨機抽 600 個 PR 反轉的任務，各配上四種 issue，讓專家（SWE-agent 加 Claude 3.7 Sonnet）產生軌跡，再各用成功的軌跡微調 Qwen 2.5 Coder 7B Instruct，比較它們在 SWE-bench Verified 上的解題率。為了公平，每組的訓練量都截到最少那組的 259 條。訓練怎麼做見第 8 章。

思考題 · 01

你的訓練資料裡，題目有沒有把答案的線索寫進去？

想想你要拿來微調 agent 的任務：描述裡有沒有直接寫出評分用的測試、預期的輸出，或該改哪個檔案？

照這一章的結果，可以同時看兩件事：專家在兩種寫法下的成功率，以及學生學到的行為（例如會不會先重現問題）。專家的成功率變高，不代表資料變好。看行為的這一步是整理者的建議，不是論文的做法。

和 SWE-bench 的任務比，有四個差別。第一，沒有 version 與 environment_setup_commit：SWE-bench 需要這兩個欄位，才能替同一個 repo 在不同時間的版本找到對的安裝指令；SWE-smith 的安裝規格是每個 (repo, commit) 一份。第二，沒有 hints_text，SWE-bench 用它放 PR 第一個 commit 之後的 issue 與 PR 討論。第三，created_at 的意思變了：原本是 PR 建立的時間，這裡是 bug 驗證成功的時間。第四，也是最關鍵的，沒有 test_patch：SWE-smith 的流程不產生、也不合成任何隱藏的測試，所有 F2P 測試在推論時都在 repo 裡，看得到、也跑得動。

少了版本欄位，換來儲存上的簡化。附錄 C.1 解釋：SWE-bench 的每個任務對應一個不同的 base commit，repo 與它的相依套件一路演變，正確的安裝方式變化很大，社群只好替每個任務建一個映像，2,294 個任務就是 2,294 個映像，每個好幾 GB（約 5 到 6 GB）。SWE-smith 的 bug 都從同一個 (repo, commit) 產生，全部可以在同一個映像裡重現與測試；替一個 repo 造 100 個 bug，只需要 1 個映像，不是 100 個。第 6 章看這件事換來多少空間。

少了隱藏測試，決定了這批任務的用途。附錄 C.2 的最後一點說得直接：SWE-smith 目前的流程不產生隱藏測試，這是 SWE-bench 比較適合拿來評估的關鍵差別；產生專家軌跡時，F2P 測試就在 repo 裡。issue 的產生也沒有檢查描述不清或洩漏解法這些已知的問題。作者提的修正很簡單：刪掉 F2P 測試所在的函式或檔案，再加一道檢查 issue 是否模糊、是否洩漏的程序。他們也說，要說服大家拿合成 bug 做評估，還需要徹底分析 SWE-smith 的任務有多貼近真實的 issue 與 PR。

整理者的整理

同一份任務，訓練與評估的標準不同

拿來訓練時，F2P 測試看得到沒有關係，agent 甚至可以先跑它確認問題；拿來評估時，看得到測試就等於看得到評分標準。第 4 章的 F2P issue 是另一種洩漏：測試寫進了題目，學生就少了先重現 bug 的習慣。

Chapter 12 · Related Work · Appendix G

任務合成到整個 repo，還附上環境

作者把自己放在兩條研究線上：軌跡要替 agent 系統產生，而不是固定的工作流；訓練資料要大量、又要能執行。前人的訓練集多半沿用真實 PR 或 SWE-bench 的流程，SWE-smith 讓 LM 直接弄壞整個 repo。

第一條線是做軟體工程的 LM。傳統的程式生成任務已經被現在的 LM 做到飽和，SWE-bench 這類軟體工程基準因為題目多樣、複雜又貼近真實，成了事實上的新標準。開源的進展主要來自兩種系統：由人把任務拆成固定子步驟的工作流（例如 Agentless、AutoCodeRover、Moatless tools），以及 LM agent（例如 SWE-agent、OpenHands）。作者引用 SWE-bench Multimodal 的結果說，工作流可能難以推廣到非 Python 的 repo、需要人重新調整，所以選擇替 agent 系統產生軌跡：沒有強加的流程，agent 更依賴 LM 自己規劃與修正，重點落在 LM 的能力，而不是推論用的腳手架。

第二條線是程式的訓練資料。過去的工作集中在程式補全的指令遵循與偏好學習；最近才有針對 SWE-bench 的訓練集，分別給檢索增強生成（SWE-bench-train、SWE-fixer）、工作流（SWE-RL）與 agent（SWE-bench-extra、Lingma、SWE-gym、R2E-Gym）。作者說他們是把 Haluptzok 等人（2023）的做法搬到 repo 的層級：讓 LM 弄壞一個 codebase，大幅減少定義任務與建環境所需的人力。

兩篇同期的工作被特別拿出來比。RePOST 也替 repo 裡的函式建執行環境，但做法差很多：它把一個函式和它的相依抽到另一支腳本裡，再用 LM 產生測試，原本的 codebase 就不再是 context；任務的來源在 repo 層級，環境與任務本身卻不是，評估也只看 HumanEval 這類程式生成。R2E-Gym 用推論時擴充與 verifier 提升開源 LM 在 SWE-bench 上的表現，它的 4.6k 個訓練任務用 SWE-bench 的流程收集，再用 LM 合成 issue 與測試。作者說就他們所知，自己是第一個處理前人做法放不大這個問題的。

附錄 G 補了兩條。網頁 agent 的軌跡合成常靠隨機遊走再補標指令、拿線上教學當間接監督，或蒐集人類示範；作者說這些在軟體工程不管用，隨機下的命令列指令通常對 codebase 沒有意義的影響。他們也粗略試過從 GitHub 的 commit 歷史重播出軌跡，但 commit 只記下檔案層級的改動，看不到背後的技能、決策與開發脈絡，沒有成功。自動安裝 repo 這一步則受兩條研究影響：用 LM 自動建執行環境，以及用 LM 產生單元測試；作者說他們在研究怎麼把環境建置做到端到端全自動。

第 6 節的結論：SWE-smith 是從 128 個真實 GitHub repo 收來的 5 萬個軟體工程任務；它的收集流程能以前人一小部分的成本放大任務、環境與軌跡，又不犧牲對開源軟體開發實務的忠實；用它訓練的 SWE-agent-LM-32B 在 SWE-bench Verified 拿到 40.2%。作者也說，這些實驗示範了怎麼用 SWE-smith 找出開發軟體工程 agent 的基本趨勢，他們相信它提供了以真正能放大的方式訓練這類 agent 所需的資料與基礎設施。

限制與缺口散在正文與附錄，整理如下：

1

2
只示範了微調受限於算力與預算，也因為這篇定位成資料集的貢獻，沒有試強化學習這類其他訓練方法（第 6 節）。
3
還不能直接評估沒有隱藏測試、F2P 測試看得到，issue 也沒檢查描述不清與洩漏（附錄 C.2，第 5 章）。
4
跨語言幾乎沒有進步SWE-bench Multilingual 上 8.4%，未微調的基礎模型 6.5%，Claude 3.7 Sonnet 43%（附錄 F.4，第 9 章）。
5
重複動作與定位一半以上的失敗被上限打斷，壓掉重複動作也沒有提升解題率（第 4.2 節、附錄 F.5，第 11 章）。

作者對跨語言的負面結果反而樂觀。他們認為，能推廣到多種 repo 與語言的開放模型，要靠更多資料與更好的訓練方法，兩者 SWE-smith 都幫得上：資料方面，雖然 SWE-smith 寫成以 Python 為中心，收集方法與造 bug 的技巧（尤其是用 LM 的那幾種）應該能直接用在其他 repo；訓練方面，這個結果提供了明確的動機，去找只在一種語言上訓練、卻能推廣到多種語言的方法。

整理者的讀法

放回這一講：品質是跑出來的

下面是整理者的連結。這一講談資料的篩選與品質，SWE-smith 的每一道篩子都是執行出來的：bug 要弄壞測試、軌跡要真的解出來、每題最多三條。它也示範了兩件「看起來合理卻不成立」的事：越難的任務不一定是越好的教材（第 10 章），讓專家解得更多的 issue 寫法反而教壞學生（第 4 章）。在 SWE-smith 裡把關的是單元測試，測試沒覆蓋到的改動，bug 就不會被留下，產率因此受限（第 3 章）；和〈Who Validates the Validators?〉對照，可以想想自己的篩子本身可不可信。

SWE-smith 的任務可以拿來評估模型嗎？
作者說目前不適合。它沒有隱藏測試，F2P 測試在推論時就看得到，issue 也沒檢查描述不清與洩漏；刪掉 F2P 測試並加一道 issue 的檢查，才可能改成評估集（附錄 C.2）。
只能用在 Python 嗎？
目前的流程靠 Python 的 ast 找函式與做變換，所以只收 Python repo；作者說收集策略可以移植到其他語言，用 LM 造 bug 的方法尤其容易搬（第 6 節、附錄 F.4）。
資料和模型都公開了嗎？
是。作者公開了收集流程、任務實例、軌跡與模型，摘要說所有資產都放在 swesmith.com。

Reference · 名詞速查

關鍵名詞，和它們在論文裡的位置

先列資料集與流程，再列五種造 bug 的做法與 issue，最後是訓練、評估與 agent 行為的用語。

SWE-smith
資料生成流程與資料集
先替 repo 建執行環境、再合成會弄壞測試的 bug 的工具，也指用它造出的 50,137 個任務（第 2 節、表 1）。
task instance
任務實例
一個要修的 bug：repo、造成 bug 的 patch、issue、F2P 與 P2P 測試；格式沿用 SWE-bench（附錄 A.1）。
execution environment
執行環境
裝好 repo 與相依套件、能跑測試的 Docker 映像；SWE-smith 每個 (repo, commit) 一個，共 125 個（附錄 C.1）。
Fail-to-Pass（F2P）
被弄壞的測試
套上 bug 後失敗、修好後應該通過的測試；至少要有一個，候選才算有效的任務。
Pass-to-Pass（P2P）
沒壞的測試
套上 bug 前後都通過的測試，也就是全部測試扣掉 F2P。
yield rate
產率
候選裡至少弄壞一個測試的比例；合併 96.9%、PR 反轉 33.8%（表 1）。
LM Modify
LM 改寫
把函式交給 LM，要它引入細微的邏輯錯誤；產率 56.0%，難度分數 3.304 最低。
LM Rewrite
LM 重寫
只給函式標頭與 docstring，要 LM 從頭實作，不提 bug；產率 35.0%，難度 5.272。
procedural modification
程序化修改
對 AST 套 13 種固定變換之一，例如刪條件、換運算子；不花 API 費用（附錄 B.2、表 8）。
Combine（patch combination）
合併
把同一個檔案或同一個模組裡已驗證的 bug 疊成一個任務；難度 5.720 最高（附錄 B.3）。
PR Mirror
PR 反轉
讓 LM 把目前的檔案改回某個真實 PR 之前的樣子；django 試做重建 100 個裡的 92 個（附錄 B.4）。
problem statement
問題描述、issue
交給模型的 issue；SWE-smith 預設由 LM 仿 SWE-bench Verified 的風格撰寫（附錄 D）。
difficulty score
難度分數
評分員把任務標成 easy、medium、hard，換成 1、5、9 分後取平均；評分員準確率 75.3%（附錄 E）。
bug coverage
bug 覆蓋率
至少被一個任務弄壞的測試佔全部測試的比例；flask 上 SWE-bench 7.25%、SWE-smith 89.03%（附錄 C.2）。
rejection sampling fine-tuning（RFT）
拒絕取樣微調
讓專家模型解題，只拿解出來的軌跡微調學生；比不篩選的隨機取樣好（第 3 節、圖 23）。
expert、student
專家、學生
產生軌跡的 Claude 3.7 Sonnet 等模型；被微調的 Qwen 2.5 Coder Instruct 7B 與 32B。
SWE-agent
agent 系統
給 LM 看檔、改檔、執行指令的介面（ACI），工具是 bash、str_replace_editor、submit（附錄 F.1）。
SWE-agent-LM-32B
微調出的模型
用 5,016 條軌跡微調的 Qwen 2.5 Coder 32B；Verified 40.2%、Lite 30.7%（表 3）。
SWE-bench Verified
人工挑過的評估集
SWE-bench 裡 500 題描述較清楚、評估較可靠的子集；主結果與消融都在上面測。
SWE-bench Multilingual
多語言評估集
作者新做的 300 題、42 個 repo、9 種語言；32B 只有 8.4%（附錄 F.2、F.4）。
pass@k
試 k 次的解題率
試 k 次只要有一次解出就算；32B 的 pass@1 是 40.2%，pass@6 是 54.8%（圖 22）。
repetitive actions
重複動作
連續下同一個基本指令；長度 10 的重複對應 89% 的失敗機率（第 4.2 節）。
localization
定位
找出該改哪些檔案與程式的步驟；32B 被上限打斷的失敗裡，42 題卡在這裡（圖 8）。
