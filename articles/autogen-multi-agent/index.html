AUTOGEN · MULTI-AGENT CONVERSATION · 圖卡＋教材整合版

讓代理彼此對話， 組出 LLM 應用AutoGen：可對話的代理加上對話程式設計， 用同一套介面組出各種多代理流程

用 LLM 做應用，常常需要幾個角色分工：一個寫程式、一個執行、一個檢查，必要時再請人插手。這篇 Microsoft Research 與幾所大學的論文提出開源框架 AutoGen：每個代理都能接上 LLM、人或工具，收到訊息就自動回覆；開發者用自然語言與程式一起寫出代理之間怎麼對話，兩代理對話、巢狀的專家諮詢、由管理者挑發言者的群組聊天，都用同一套介面。作者用六個應用示範它，從數學解題、檢索問答到下棋。這是作者評自家框架的論文，這一頁會交代每個比較怎麼跑、數字要怎麼讀。每章開頭先放一張圖解卡講重點，往下是詳細作法；想速讀就切到「只看圖卡」。

Chapter 01 · Introduction

作者把多代理協作，統一成代理之間的對話

多個代理合作被認為能幫 LLM 發散思考、提高事實性、互相驗證。作者的問題是怎麼讓各種領域與複雜度的應用，都能用多代理的方式開發；他們的答案是對話，並拆成兩個要先回答的設計問題。

引言從 agent 講起：LLM 已經是做 agent 的基本元件，能推理、用工具、依新的觀察調整。任務越來越多、越來越複雜，一個直覺的擴充方式是讓幾個代理合作。作者引用的先前研究說，多個代理能鼓勵發散思考（Liang 等人 2023）、改善事實性與推理（Du 等人 2023），也能互相驗證（Wu 等人 2023）。問題是怎麼把這些好處變成一般開發者用得上的東西，讓不同領域、不同複雜度的 LLM 應用都能用多代理的方式開發。

作者的洞見是用多代理之間的對話來做。引言介紹對話程式設計時，把 AutoGen 的核心想法寫成這句：

"simplify and unify complex LLM application workflows as multi-agent conversations" 「把複雜的 LLM 應用流程，簡化並統一成多代理之間的對話」：第 1 節對 AutoGen 核心想法的說法。

為什麼對話行得通？作者列了三個理由，都和當時 LLM 的進步有關：

01

聊天型 LLM 會吸收回饋

GPT-4 這類為聊天最佳化的模型，能把回饋納入下一次回答；代理之間就能透過對話互相提供推理、觀察、批評與驗證。

02

同一個 LLM，設定不同就是不同能力

一個 LLM 配上合適的 prompt 與推論設定，就能展現某種能力；設定不同的代理彼此對話，等於把這些能力模組化地組起來。

03

大任務可以拆小

任務拆成比較簡單的子任務時，LLM 比較解得了；多代理對話能直覺地拆解任務，再把結果整合回來。

接著作者提出兩個關鍵問題。第一，怎麼設計單一的代理，讓它有能力、可重用、可客製，而且在多代理合作裡有效？第二，怎麼做出一個簡單、統一的介面，容納各式各樣的對話模式？應用的複雜度不同，需要的代理組合與對話模式也不同：單輪或多輪、人參與的方式不同、流程固定或動態；開發者也可能想用自然語言或程式來寫代理之間的互動。作者說，這兩個問題沒回答好，框架能用的範圍就會受限。

AutoGen 對兩個問題各給一個概念，也就是接下來三章的主題。第一個是可客製、可對話的代理：代理可以接 LLM、人的輸入、工具或它們的組合，開發者挑一組內建能力，就能做出寫程式、執行程式、接人的回饋、驗證輸出等不同角色；每個代理都能收訊息、反應、回覆，可以自主地和別的代理對話好幾輪，也可以在某些輪次請人輸入（第 2 章）。第二個是對話程式設計：開發一個應用分兩步，先定義一組有能力與角色的可對話代理，再用以對話為中心的計算與控制，寫出代理之間怎麼互動；兩步都能混用自然語言與程式語言（第 3、4 章）。

論文第一頁的圖 1 把這些概念畫在一起：左邊是一個可對話的代理，背後接著 LLM、工具與人；中間是代理之間的對話，以及兩種常見的模式，大家一起聊的 joint chat 與一層管一層的 hierarchical chat；右邊是一段例子，使用者要畫 META 與 TESLA 今年以來的股價變化，助理寫程式，執行時發現沒裝 yfinance，裝好再跑，畫出圖之後人又要求改成百分比變化。

引言最後預告了應用與評估。作者說，AutoGen 在許多任務上表現出色，讓 LLM 有新的用法，也減少了開發的工夫（第 3 節與附錄 D）。這些是作者的主張，第 5 到 11 章逐一看它們是怎麼測的。

背景

人也是一種後端

第 2.1 節說，很多 LLM 應用需要人參與，有時非人不可。AutoGen 讓人成為某個代理的後端：被問到時，人的回答就是那個代理的回覆。整理者的讀法：這讓「人要不要參與、什麼時候參與」變成代理的一個設定值。第 5 章的情境 2 就是這樣，只把 UserProxyAgent 的 human_input_mode 改成 ALWAYS，同一個系統就變成人在迴圈裡解題。

思考題 · 01

你的流程裡有哪些角色，各該接什麼後端？

挑一個手上的 LLM 應用，列出它的步驟：誰寫、誰執行、誰檢查、哪裡需要人拍板。

把每個步驟對到一種後端：要判斷與生成的交給 LLM，要真的跑起來的交給工具，要負責任的交給人。能用 AssistantAgent 加 UserProxyAgent 解決的，先不要多開代理，這是附錄 B.1 的第一條建議。

第 2.2 節把對話程式設計拆成兩個概念。一是計算：代理在多代理對話裡，為了產生回應所做的動作；二是控制流程：這些計算在什麼順序、什麼條件下發生。在 AutoGen 裡，計算以對話為中心，代理做的是和它所在的對話有關的動作，動作的結果是傳給後續對話的訊息，除非已經滿足終止條件；控制流程由對話驅動，參與的代理要把訊息送給誰、要怎麼計算，都取決於代理之間的對話。作者說，這讓人能把一個複雜的流程，直覺地想成代理採取行動、代理之間互傳訊息。

第一個設計模式是統一的介面加上自動回覆。每個代理都有 send／receive 函式來收發訊息，以及一個 generate_reply 函式，依收到的訊息採取行動並產生回應。AutoGen 預設採用代理自動回覆：一個代理收到另一個代理的訊息，就自動呼叫 generate_reply，把回覆送回給發訊者，除非終止條件成立。內建的回覆函式有三種：LLM 推論、執行程式或函式、人的輸入；開發者也可以註冊自訂的回覆函式，例如先和另一個代理聊過，再回覆原本的發訊者。

ALFWorld 是合成的文字互動環境，模擬真實的家務場景。代理拿到一個高層的目標（例如把一顆熱的蘋果放進冰箱）與環境描述，透過文字介面探索並互動。一個典型的任務有各種地點，可能要超過 40 步才做得完，所以代理得把目標拆成子任務、一個一個處理，同時有效率地探索環境。

作者先做了一個簡單的兩代理系統：助理代理產生計畫、決定每一步的行動；executor 代理專為 ALFWorld 打造，執行助理提議的行動，並把執行結果回報給助理。因為環境對行動的格式要求很嚴，executor 用 BLEU 比較助理的輸出和所有合法行動的相似度，選最像的那一個當這一輪的行動。這個系統整合了 ReAct 的 prompting：作者把 prompt 改寫成對話的形式，照 ReAct 用兩個示範，示範取自 ReAct 的程式庫。它的表現和 ReAct 差不多。

兩者有同一個問題：偶爾用不上關於物理世界的基本常識，於是一再重複同樣的錯誤，陷入迴圈。作者檢查失敗的嘗試、歸納失敗的原因，整理出助理缺少的常識，交給新加的 grounding 代理。它在任務開始時，以及助理連續三次輸出同一個動作時發言，例如「你必須先找到並拿起物品，才能檢查它」「你必須走到目標物品所在的地方，才能使用它」。作者說，grounding 代理在對的時機提供背景常識，明顯減少了系統堅持錯誤計畫、陷入錯誤迴圈的情況。

附錄 D 說明了實作。玩家代理以 LLM 與人為後端：開了人類輸入時，它先請人輸入要走的棋步與想說的話；人略過或關掉輸入，就由 LLM 產生訊息。棋盤代理用一個自訂的回覆函式實作：用 LLM 把自然語言解析成結構化格式（例如 UCI）的合法棋步，再推到棋盤上；棋步不合法就回錯誤訊息，玩家代理得一直重送，直到走出合法的一步；推上棋盤之後，玩家代理才把訊息傳給對手。LLM 產生訊息時會用到棋盤狀態與棋盤代理的錯誤訊息，作者說這能降低幻覺出不合法棋步的機會。玩家和棋盤代理之間的對話，另一位玩家看不到，這讓送去做聊天補全的訊息保持整齊。

消融實驗拿掉棋盤代理，改成在兩位玩家的 system message 裡加一句提醒：要確定你和對手走的都是合法的棋步。結果是不合法的棋步打斷了棋局。附錄 D 的圖 16 並排了兩種設計：沒有棋盤代理時，白方說要把騎士從 b8 走到 c6，實際上把 a8 的城堡換成騎士移了過去，棋局照樣往下走；有棋盤代理時，它回覆「你的棋步不合法：你把 a8 的城堡換成騎士移到 c6，請檢查後重下」，白方道歉並改走合法的一步。這個消融只有對話的示範，論文沒有報告不合法棋步的次數或比例。

作者列了兩個用 AutoGen 做這個遊戲的好處。一是代理的設計讓遊戲裡需要的物件與互動很自然地建出來，例如聊天訊息互相隔開，讓每次呼叫 LLM 做補全都比較單純。二是用組合來實作代理的行為：玩家代理與棋盤代理都用 register_reply 掛上自訂的回覆函式，擴充的工作集中在回覆函式這一個地方，推理、開發與維護都比較簡單。規則改了、或換成別的西洋棋變體，也只要調整棋盤代理。

原生的人類參與與監督機制，人可以選擇性地加入，也能在過程中給指示。

合作與對抗

代理分享知識、互補能力；有些情境要代理互相對抗，資訊在不同對話之間受控地分享，避免分心與幻覺。

附錄 B.1 給了五條使用指南，順序是作者排的：

1
先用內建代理AssistantAgent 預設由 GPT-4 驅動、帶一份用寫程式解題的 system message；UserProxyAgent 請人輸入並執行工具。客製時先調建構時的設定（人類輸入模式、終止條件、程式執行、LLM 設定），或在第一則使用者訊息加指示。
2
從簡單的拓樸開始先用兩代理對話或群組聊天，通常只要最少的程式就能擴充；兩代理對話也能透過 LLM 可呼叫的函式，動態地拉進更多代理。
3
先重用內建的回覆方法以 LLM、工具或人為基礎的內建回覆方法，常常就能簡單達成目標；GroupChatManager 選發言者時，重用的就是內建的 LLM 回覆函式。
4
先讓人一直在迴圈裡開發新應用時先設 human_input_mode='ALWAYS'，用來評估助理、調 prompt、找邊界案例與除錯；小規模成功之後，再考慮改成 'NEVER'。
5
知道什麼時候用別的工具不需要來回除錯或多代理互動的單向 pipeline，可以用 LangChain、LlamaIndex、Guidance、Semantic Kernel、Gorilla 或低階的推論 API；LangChain 的工具可以當 AutoGen 代理的後端，別的程式庫做的代理也能包成可對話的代理；LLM 推論設定這類參數，可以交給 flaml.tune 這類黑箱最佳化自動調。

附錄 B.2 列了三個未來方向，也是作者自己點出的限制。第一，怎麼設計最好的多代理流程：要幾個代理、怎麼分配角色與能力、代理怎麼互動、哪一段要自動化，可能沒有一體適用的答案；哪類任務最適合多代理、多個代理在不同應用裡怎麼幫上忙、給定任務時最划算的流程是什麼，都還是開放問題。第二，打造能力夠強的代理：作者觀察到 CAMEL 多半解不了問題，主因是不能執行工具或程式，所以需要針對應用的代理設計指南、一個開源的代理知識庫，以及能發現並升級自己技能的代理。第三，規模、安全與人的主導：流程變大變複雜之後，會變得難以記錄與調整，需要清楚的機制與工具來追蹤與除錯，否則代理之間可能變成難以理解的閒聊；完全自主的對話要小心使用，要建立防止連鎖失敗與被利用的保險、處理 reward hacking 與失控的行為，並維持有效的人類監督。

倫理聲明列了五項考量：隱私與資料保護，人參與代理之間的對話時，使用者的資料與對話要保護好；偏誤與公平，LLM 會把訓練資料裡的偏誤帶進代理的對話；問責與透明，多個代理一起做決定時，使用者要能理解並追溯決策的過程；信任與依賴，要清楚說明系統的能力與限制；非預期的後果，讓 LLM 代理透過執行程式或函式呼叫改變外部環境，例如安裝套件，可能有風險，開發者要設好保護措施。

整理者的讀法

放回這一講：協調與錯誤傳播

下面是整理者的連結。這一講最後一個講題是協調與錯誤傳播。AutoGen 在論文裡遇到的錯誤，多半就發生在代理之間的來回：錯誤動作被一再重複、道歉被一再回應、對話停不下來。它給的解法也多半是多一個角色：grounding 代理補常識、critic 審程式、Safeguard 擋危險程式、棋盤代理檢查棋步。同一講的選讀〈Why Do Multi-Agent LLM Systems Fail?〉與〈Don't Sleep on Single-agent Systems〉，可以拿來檢查這個方向的代價：每多一個代理，也多一個會出錯、要追蹤的地方。

AutoGen 需要訓練模型嗎？
不需要。代理的能力來自接上的 LLM、人與工具，行為用 system message、設定與回覆函式來寫；論文的實驗都用現成的 GPT-4 或 GPT-3.5-turbo。
一定要用很多個代理嗎？
不一定。附錄 B.1 建議先用內建的兩個代理與簡單的拓樸；不需要來回修正的單向流程，用其他程式庫做成 pipeline 就好。A5 的表 5 裡，兩代理系統在 12 題裡也解出 8 題（GPT-3.5-turbo）與 9 題（GPT-4）。
對話怎麼結束？
靠終止條件：LLM 依 system message 在全部完成時回覆 TERMINATE，或用 Python 設條件，例如自動回覆的次數上限。設得不好，對話就可能像圖 13 那樣一直重複，直到碰上次數上限。
AutoGen 讓加一個代理變得很容易；每多一個代理，也多一段要追蹤、要能喊停的對話。 整理自第 4 節與附錄 B.2

Reference · 名詞速查

關鍵名詞與它們在論文裡的位置

先列框架本身的概念與介面，再列各應用裡的角色，最後是資料集與基準。

AutoGen
多代理對話框架
Microsoft 的開源框架，用可對話的代理與對話程式設計組 LLM 應用；程式在 github.com/microsoft/autogen。
conversable agent
可對話的代理
能收發訊息、依收發的訊息維持 context、收到就回覆的代理（第 2.1 節）。
ConversableAgent
最上層的代理類別
預設 LLM、人、工具三種後端都能用；其他內建代理是它的子類別。
AssistantAgent
助理代理
LLM 驅動的內建代理，預設 GPT-4 與一份用寫程式解題的 system message。
UserProxyAgent
使用者代理
替人傳話的內建代理：請人輸入，或執行程式碼與函式呼叫。
GroupChatManager
群組聊天管理者
每一輪選發言者、收回覆、廣播的內建代理（A5）。
conversation programming
對話程式設計
先定義代理，再用以對話為中心的計算與控制寫出互動；可混用自然語言與程式。
auto-reply
自動回覆
收到訊息就呼叫 generate_reply、把回覆送回，直到終止條件成立。
generate_reply
產生回覆
依收到的訊息採取行動並產生回應的統一介面；和 send、receive 一起組成代理的介面。
register_reply
註冊回覆函式
替代理掛上自訂的回覆函式，用程式決定它收到訊息時怎麼回。
initiate_chat
開啟對話
一個代理把第一則訊息送給另一個代理，之後靠自動回覆推進。
human_input_mode
人類輸入模式
什麼時候請人輸入；圖 2 裡有 NEVER 與 ALWAYS，附錄 B.1 建議從 ALWAYS 開始。
TERMINATE
終止訊號
預設 system message 要求 LLM 在全部完成時回覆的字串。
control plane
控制平面
專門控制對話流程的模組；作者說自動回覆讓 AutoGen 不需要它。
function call
函式呼叫
LLM 提議呼叫某個函式，由程式執行；A1 的 ask_for_expert 用它開一段內層對話。
dynamic conversation
動態對話
流程不事先定死；做法有自訂 generate_reply、函式呼叫、GroupChatManager。
interactive retrieval
互動式檢索
助理找不到答案時回 UPDATE CONTEXT，換下一批片段再試（A2）。
grounding agent
補常識的代理
A3 裡在任務開頭與助理重複同一動作三次時，提供常識的第三個代理。
executor
執行者代理
A3、A7 裡在環境中執行行動並回報結果的代理。
Commander／Writer／Safeguard
OptiGuide 的三個代理
A4 裡分別負責協調與執行、寫程式與解讀、檢查程式安全。
board agent
棋盤代理
A6 裡把自然語言解析成棋步、檢查合法性的第三方代理。
MATH
競賽數學資料集
A1 用的資料集；level-5 是最難的一級，測試集共 5,000 題。
ALFWorld
文字版家務遊戲
A3 用的互動決策基準，評估用 134 個沒看過的任務。
Natural Questions
開放問答資料集
A2 用 5,332 份文件與 6,775 個問題評估。
MiniWoB++
網頁操作基準
A7 用的瀏覽器互動任務，比較對象是 RCI。
